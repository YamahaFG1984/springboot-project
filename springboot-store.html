这份教程和原书的差别

先说清楚哪些照搬、哪些换掉、哪些是原书没有而这里补上的。

原书的教学设计很好：一个贯穿始终的在线商店（首页 / 商品 / 购物车 / 登录注册 / 我的订单 / 管理后台），每章只推进一小步，先写"不太对"的代码再回头重构。这一套我完整保留。

换掉的是技术栈的每一层，以及讲解的颗粒度。Nest 和 Spring 表面上很像——Nest 的设计本来就抄了 Angular，而 Angular 的依赖注入又抄了 Spring——但相似只在语法层面。真正学 Spring，绕不开 Servlet 容器、Bean 容器、JPA 持久化上下文、Security 过滤器链这几套机制。原书对应的位置全部是"照着敲就能跑"，这里都会展开。

原书没有、这里补上的

下面每一条都对应一个真实会把人绊倒的地方。它们不是"进阶话题"，是写第一个 Spring 应用时就该知道的事：

  • 事务。 原书第 27 章的下单方法，创建订单、扣余额分成两次数据库写入，中间任何一步失败都会留下脏数据。作者自己也承认"没有校验余额够不够"。第 10 部分整章讲这个。
  • 并发。 两个请求同时下单，余额会被覆盖。乐观锁 @Version 是最小代价的正确解。
  • N+1 查询。 订单页遍历订单再遍历明细，TypeORM 和 JPA 都会默默发出 1+N 条 SQL。第 9 部分给出诊断方法和三种修法。
  • 持久化上下文的边界。 LazyInitializationException 和 open-in-view 默认值，是 Spring 新手最高频的两个坑。
  • CSRF。 原书原文写"实现超出本书范围"。Spring Security 默认就开着，所以这里讲的是它怎么工作，以及你的表单需要配合什么。
  • 测试。 原书第 3 章直接删掉了 app.controller.spec.ts，理由是"超出范围"。第 11 部分补一整章。
  • 数据库迁移。 从 ddl-auto 讲到 Flyway，讲清楚为什么前者只能用于本地。

00

环境、脚手架与项目结构

对应原书第 1–3 章。原书用 12 行讲完项目结构，这里花的篇幅多得多，因为 Spring 的"自动"背后有一整套可解释的机制。

装什么

  • JDK 21 或 25（都是 LTS）。Spring Boot 4 的最低要求是 Java 17，但虚拟线程、模式匹配、ScopedValue 这些真正好用的东西都在 21 之后。推荐用 SDKMAN! 或 jabba 管理多版本。
  • Maven 3.9+。项目里会带 Maven Wrapper（./mvnw），所以其实不装也行。
  • Docker。用来跑数据库，替代原书的 XAMPP。
  • IntelliJ IDEA（社区版够用）或 VS Code + Java 扩展包。

Spring Boot 4 是什么，不是什么

原书写"Nest 是构建 Node.js 服务端应用的框架"，一句带过。Spring 这边有个必须先厘清的层次关系，否则后面看文档会一直迷路：

  • Spring Framework 7——真正的核心。IoC 容器、AOP、事务抽象、Spring MVC 都在这里。它不负责启动，也不替你选默认值。
  • Spring Boot 4——在 Framework 之上加了三样东西：依赖版本仲裁（BOM）、自动配置（auto-configuration）、可执行 jar + 内嵌服务器。Boot 不是新框架，是一层意见明确的默认值。
  • Spring Data / Security / Modulith …——独立项目，各有自己的版本号，由 Boot 的 BOM 统一钉住兼容组合。

Spring Boot 4 相比 3.x 的几个会影响到本教程的变化：基于 Jakarta EE 11（Servlet 6.1）、默认 Jackson 3、空安全注解换成社区标准 JSpecify、Spring Security 7 彻底移除了老式链式 DSL、模块拆得更细（很多能力从 spring-boot-autoconfigure 拆成了独立 jar，但 starter 名字基本没变）。

陷阱 · 版本号

不要手写依赖版本号。spring-boot-starter-parent 里的 BOM 已经把几百个库的兼容版本锁死了，你手动指定一个 Hibernate 版本，很可能就和 Spring Data 对不上。本教程所有 <dependency> 都不带 <version>，这是特意的。

项目结构

对照 · 两个目录的关键区别

static/ ≈ Nest 的 public/，里面的文件按原样映射到 URL：static/css/app.css → /css/app.css。
templates/ ≈ Nest 的 views/，但有个重要差别：它不在静态资源路径上，外界无法直接访问模板文件本身。只有控制器返回视图名时才会被渲染。这挡掉了一整类"模板源码泄露"的问题，而 Nest 里的 views/ 是否安全取决于你有没有把它放进 useStaticAssets。

入口类：@SpringBootApplication 到底做了什么

原书对 main.ts 的解释是"它用 NestFactory 创建应用实例"。Spring 这边一行注解背后是三件事，值得拆开看，因为后面每次"为什么我的 Bean 没被注入"都能追溯到这里。

@SpringBootApplication 是三个注解的组合：

  1. @ComponentScan —— 扫描本类所在包及其所有子包，把标了 @Component / @Service / @Repository / @Controller 的类注册成 Bean。这就是为什么 Spring 里不需要像 Nest 那样在 @Module({controllers: [...]}) 里手工登记。也是为什么入口类必须放在包结构的最顶层——放错地方，你的控制器会被静默忽略，没有任何报错。
  2. @EnableAutoConfiguration —— 读取所有 jar 里的 META-INF/spring/…AutoConfiguration.imports 文件，拿到几百个候选配置类，然后逐个跑条件注解决定要不要生效。
  3. @SpringBootConfiguration —— 标记这个类本身也是一个配置类，可以在里面写 @Bean 方法。

本地数据库：compose.yaml

原书第 11 章让你装 XAMPP、启动 Apache、点开 phpMyAdmin、手工建库。这些步骤现在可以全部压缩成一个文件。Spring Boot 的 docker-compose 模块会在应用启动时自动 docker compose up，并把连接信息注入到数据源里——你不需要在 application.yml 里写任何 url、用户名、密码。

为什么把原书的 MySQL 换成 PostgreSQL：两者都能用，Spring 对它们的支持没有差别。选 Postgres 是因为它对 SERIAL/序列、事务隔离级别、SELECT … FOR UPDATE 的行为更符合标准，而这些恰好是第 10 部分要讲的东西。想用 MySQL 就把 image 换成 mysql:8.4、依赖换成 mysql-connector-j，其余不变。

动手与思考 · 第 00 部分

先自己想，再展开思路。

Q1把 OnlineStoreApplication.java 从 com.example.store 挪到 com.example.store.boot，其它类不动。应用还能启动吗？访问任何页面会发生什么？

思路提示

能启动，但所有控制器都会 404。@ComponentScan 的默认扫描根是入口类所在的包，挪到子包后 com.example.store.catalog 就不在扫描范围内了。而且不会有任何报错——Spring 不知道你"本来应该有"那些 Bean。

补救办法有 @SpringBootApplication(scanBasePackages = "com.example.store")，但更好的做法是遵守约定：入口类放最顶层包。这个约定看似随意，实际上决定了整个应用的"可见范围"。

Q2用 --debug 跑一次，在 Negative matches 里找到 RedisAutoConfiguration（或任何一个没生效的）。它给出的失败原因是什么？如果你想让它生效，最小改动是什么？

思路提示

原因通常是 @ConditionalOnClass 没过：Did not match: did not find required class 'org.springframework.data.redis.core.RedisOperations'。最小改动是加上 spring-boot-starter-data-redis 依赖——注意，只是加依赖，不写任何配置代码，Boot 就会给你一个 RedisTemplate。

这正是 Spring Boot 的核心交互模型：依赖即配置。理解了这一点，就能理解为什么"删掉一个依赖"有时会造成看似无关的功能消失。

Q3Nest 需要在 @Module 里显式列出每个 controller 和 provider，Spring 靠包扫描自动发现。显式登记有什么是自动扫描给不了的？

思路提示

显式登记给出了边界：看一眼 module 文件就知道这个模块暴露什么、依赖什么，越界会在编译期或启动期报错。Spring 的包扫描把所有 Bean 放进一个扁平容器，com.example.store.cart 里的类可以毫无阻碍地注入 com.example.store.admin 的 Bean，没有任何机制阻止。

代价是耦合会悄悄长出来。这是真实存在的取舍，不是 Spring 单方面更好。第 6 部分会讲怎么用 Spring Modulith 把边界补回来——它的做法很有意思：不改变运行时，而是把边界变成一个可以被测试断言的规则。

01

一次请求的完整旅程

对应原书第 5 章。原书用三句话讲完 MVC（"Model 装业务逻辑，View 装界面，Controller 在中间"），然后就开始写代码。这一部分是整份教程的地基：把 GET /products 从网卡到 HTML 的每一跳都摆出来。

MVC 这个词被用得太滥，以至于它几乎不再传递信息。真正需要在脑子里建立的模型不是三个词，而是一条有方向的处理链：请求进来时依次经过哪些组件，每个组件能改什么，出错时在哪一层被拦下，响应又是怎么一路拼回去的。

逐跳解读

1 · Servlet 过滤器链（在框架之外）

Tomcat 收到请求后，先走一遍 Filter 链。这里最重要的成员是 SecurityFilterChain——它由十几个过滤器组成，负责解析会话 cookie、还原当前用户、校验 CSRF token、做授权判断。它在 DispatcherServlet 之前执行，所以一个未授权请求根本不会走到你的控制器。

原书的做法是在 main.ts 里手写 app.use('/admin*', ...) 中间件检查 req.session.user.role == 'admin'。功能上等价，但你要自己保证：路径匹配没有绕过（/admin/../x？大小写？尾斜杠？）、中间件注册顺序正确、每个新加的敏感路径都记得配上。Spring Security 把这件事变成声明式的，并且默认拒绝。

2 · DispatcherServlet：前端控制器

整个应用只有一个 Servlet，映射在 /。它自己不处理任何业务，只做调度：

  • HandlerMapping 拿 URL + HTTP 方法去匹配某个 @RequestMapping 方法。Spring 6.0 起默认用 PathPatternParser，比老的 AntPathMatcher 更快也更严格。
  • HandlerAdapter 负责真正调用它。
  • ArgumentResolver 把 HTTP 请求"翻译"成方法参数——这就是为什么你能直接写 list(@PathVariable Long id, @Valid ProductForm form, Model model) 而不用碰 HttpServletRequest。每种参数类型背后都有一个解析器。
对照 · 装饰器 vs 注解

Nest 的 @Param()、@Body()、@Req() 和 Spring 的 @PathVariable、@ModelAttribute、HttpServletRequest 是同一个思路：用元数据声明"这个参数从请求的哪里来"。差别在于 Spring 的解析器列表是可扩展的——你可以注册自己的 HandlerMethodArgumentResolver，让 @CurrentUser User user 这样的自定义参数直接可用。第 8 部分会用到。

3 · 控制器 → 服务 → 仓库

这三层是你唯一需要写的部分，职责边界建议这样划：

层负责不负责
@Controller解析请求参数、调服务、挑视图、处理重定向业务规则、事务、SQL
@Service业务规则、事务边界、跨仓库的编排HTTP 概念（不该出现 HttpServletRequest）
@Repository数据访问，一个聚合根一个仓库业务判断

这条规则的实际检验方法很简单：如果明天要把这个功能改成一个定时任务（没有 HTTP），Service 里的代码需要改吗？ 需要改，说明有 HTTP 的东西漏进 Service 了。

4 · 回程：视图名不是文件名

控制器返回字符串 "products/list"。这不是路径，是一个逻辑视图名。ViewResolver 按配置的前缀后缀把它解析成 classpath:/templates/products/list.html。这层间接性的意义在于：换模板引擎（Thymeleaf → FreeMarker）、加主题、按设备返回不同模板，控制器代码都不用动。

陷阱 · 返回字符串的两种含义

@Controller 里返回 "products/list" = 视图名；@RestController（或方法上有 @ResponseBody）里返回同样的字符串 = 响应体本身，浏览器会看到纯文本 "products/list"。这是新手最常见的困惑之一。本教程做的是服务端渲染，全程用 @Controller。

动手与思考 · 第 01 部分

这几道题的答案都能靠打开日志亲眼看到，别只在脑子里推。

Q1图 1 里安全检查画在 DispatcherServlet 之前。假如把它挪到之后（比如实现成一个 HandlerInterceptor），会多出哪些风险？

思路提示

关键在于"之前"意味着请求还没有被解释。放到之后，安全判断依赖的是 DispatcherServlet 已经做过的路径解析和参数绑定——如果两者对 URL 的理解有一丁点差异（编码、矩阵参数、后缀、大小写），就出现拦截器认为是路径 A、控制器实际执行路径 B 的错配，这类漏洞历史上非常多。

其次，异常处理器、参数解析器、消息转换器都在拦截器之前跑过了，未授权的请求已经消耗了这些资源，甚至可能已经触发了反序列化。Filter 层拦截是"更早失败"，这在安全设计里几乎总是更好的位置。

顺带说：HandlerInterceptor 本身没问题，它适合做日志、耗时统计、给 Model 塞公共数据这些事——只是不该承担认证授权。

Q2为什么 Spring 要在控制器和模板文件之间插一个 ViewResolver？直接返回文件路径不是更直接吗？

思路提示

直接返回路径确实更少一层。代价是把"控制器"和"模板技术 + 目录结构"绑死了。想一想这些需求：给移动端返回另一套模板、支持多主题、把 Thymeleaf 换成 FreeMarker、同一个方法既能返回 HTML 也能返回 JSON（内容协商）。有了逻辑视图名这层间接，这些都是配置层面的变化。

更一般的原则：凡是"名字 → 实现"的映射被抽出来单独一层，通常是为了让映射规则可以独立于两端变化。 Spring 里这个模式反复出现（Bean 名字 → 实例、profile → 配置、视图名 → 视图）。认出这个模式，很多设计就不用死记了。

Q3原书把商品列表的假数据放成了 ProductsController 的一个静态字段。除了"以后要换成数据库"之外，静态字段本身还有什么具体问题？

思路提示

静态字段是全应用共享的可变状态。控制器是单例且被多线程并发调用，任何一个请求线程改动它，其它线程立刻看到，且没有内存可见性保证（Java 里还需要 volatile 或同步）。测试之间也会互相污染——测试 A 加了一个商品，测试 B 看到 5 条而不是 4 条，而且顺序取决于执行次序。

更值得记住的一般规则：Spring 的 Bean 默认是单例，所以 Bean 的字段必须要么是不可变的依赖（构造器注入的 service），要么根本不存在。 任何"每个请求不一样"的状态都应该活在方法局部变量、方法参数或显式的 request/session 作用域里。这条规则会在第 6 和第 9 部分反复出现。

视图层：Thymeleaf

对应原书第 4、6、7 章。原书用 Handlebars + hbs-utils 拼出布局；Thymeleaf 不需要额外依赖就能做到同样的事，而且方式更清晰。

Thymeleaf 的设计取向和 Handlebars 完全不同。Handlebars 模板是"文本里挖了洞"，{{name}} 在纯 HTML 里是非法字符。Thymeleaf 模板是合法的 HTML 文档——所有指令都写成 th: 属性，浏览器会忽略它们。这意味着设计师可以直接双击打开模板文件看到带假数据的静态页面，前后端不需要为"我看不到效果"扯皮。

深入 · @{...} 不只是拼字符串

链接表达式 @{/products/{id}(id=${p.id})} 做了三件手写字符串做不到的事：自动加上应用的 context path（部署到 /store 子路径时不会全站链接失效）、对路径变量做 URL 编码、以及在有必要时附加会话 ID。模板里所有指向本应用的 URL 都应该用 @{}，不要写死。

布局：装饰而不是包含

原书用 hbs.registerPartials() 注册局部模板，再用 {{#> app}}…{{#*inline "content"}} 这套相当拗口的语法把内容塞进布局。Thymeleaf 的做法是参数化片段：布局是一个接受"内容"作为参数的函数。

动手与思考 · 第 02 部分

Q1商品描述允许管理员填写。如果模板里用 th:utext="${p.description()}" 而不是 th:text，会发生什么？管理员是可信的，这样做可以吗？

思路提示

th:utext 不转义，描述里的 <script> 会被浏览器当代码执行——存储型 XSS。"管理员是可信的"这个前提在三种情况下会塌：管理员账号被盗、有低权限的运营也能编辑商品、以及数据从别处导入（供应商 feed、爬虫、迁移脚本）。

真要支持富文本，正确路线是：存储原始 Markdown/HTML → 在服务端用白名单库（如 OWASP Java HTML Sanitizer）清洗 → 再 th:utext。关键是清洗必须在服务端、在写入或输出时，不能靠前端编辑器。

顺带一提：Thymeleaf 默认转义（th:text）是个好默认值。凡是框架把"安全"设成默认、把"不安全"设成需要多打几个字母，都值得留意——这类设计能挡掉大量事故。

Q2把布局改成"每个页面自己 include header 和 footer"（th:replace="~{fragments/header :: bar}"），功能一样。为什么图 2 那种参数化装饰更好？

思路提示

include 式布局把"页面的整体结构"这个知识复制到了每一个页面里。要在所有页面的 nav 和 content 之间加一条面包屑，你得改 N 个文件；漏改一个就不一致。装饰式布局里，页面只声明"我是内容"，结构知识只有布局一份。

另一个角度：include 是页面调用片段（页面是主动方），装饰是布局调用页面（布局是主动方）。这是控制反转在模板层的同一个体现——和 Spring 容器管理你的对象是同一个思想。看出这种同构，比记住语法有用。

Q3开发时 spring.thymeleaf.cache: false 让改模板立即生效。上线时必须改回 true。除了性能，还有别的理由吗？

思路提示

性能是主因：关缓存意味着每次请求都要读文件、词法解析、构建模板 AST。在有并发的生产环境里，这既是 CPU 开销也是文件系统压力，而且模板解析结果本来是完全确定的。

但还有个更实际的理由：打包成 jar 之后，模板在压缩包里，"改文件立即生效"这件事本来就不成立——你以为的热更新在生产上不存在，只是白白付出了解析成本。所以更好的做法不是"记得改回来"，而是把它放进 profile：application-dev.yml 里设 false，主配置里不写（用默认的 true）。凡是"上线前记得改"的配置，都应该改成"环境决定"，人是靠不住的。

03

控制器与视图模型

对应原书第 7、8、10、15 章。原书这四章讲了一个很好的道理（统一数据传递方式、用 getter 收口属性访问），但给出的解法在 Java 里有更好的版本。

原书的 viewData 约定

原书第 8 章立了一条架构规则：控制器只能往视图传一个叫 viewData 的关联数组。理由是一致性——不管传 1 个还是 20 个变量，形状都一样。这个直觉是对的，但实现是一个无类型的字符串键值袋：拼错键名不报错，视图里 viewData.titel 只会渲染成空白。

Spring 的 Model 本质上是同一个东西（Map<String, Object>），有同样的问题。差别在于 Java 让我们有更好的选择：为每个视图定义一个 record 作为视图模型。

对照 · 原书第 15 章的 getter 那一课

原书让你给实体的每个字段写 getter/setter，然后演示"老板要求所有商品名大写"时只需改 getName()。这一课的结论是对的：属性访问要有唯一入口。但它把展示逻辑（大写、货币格式化）塞进了持久化实体，而实体的字段是要落库的。展示格式属于视图模型，不属于实体。

更关键的是：Java 的 record 自带的访问器（name()）已经天然是"唯一入口"，你根本不需要为了这一课手写 60 行样板。而 JPA 实体确实需要可变的 getter/setter——但那是 Hibernate 的要求，不是设计原则。两件事在原书里被混成了一件。

为什么不要把实体直接扔给视图

把实体直接交给模板，代价有三个，全都不是理论问题：

  1. 懒加载在模板里触发。 模板遍历 order.items 时，事务和持久化上下文可能早已关闭 → LazyInitializationException；或者你为了不报错而开着 open-in-view，于是变成第 9 部分要讲的 N+1。
  2. 字段泄露。 User 实体上有 password（哪怕是哈希）、role、balance。模板里手滑一个 ${user} 就可能把它们打进 HTML。DTO 是一道物理隔离。
  3. 耦合方向反了。 视图想多显示一个"已售件数"，你得改实体、改表；实体想重命名一个字段，全站模板跟着挂。DTO 让两边可以各自演化。
深入 · 但也别教条

DTO 不是免费的：多一层映射代码、多一次对象分配。判断标准是这个类会不会跨越一个"变化速率不同"的边界。管理后台一个只有你自己用的调试页面，直接用实体也没什么大不了。面向用户的页面、任何对外的 JSON、任何含敏感字段的实体，就该有 DTO。

控制器该有多薄

原书第 27 章的 purchase 方法有 30 多行：查用户、查商品、循环建 Item、算总价、存订单、改余额、清会话、组装 viewData。它是控制器里唯一一个真正做业务的方法，也是全书最容易出错的地方（没事务、没并发控制、没余额校验）。

判断控制器是否过厚的一个操作性标准：方法体里出现 if、循环、或算术运算，通常就该往下沉了。 控制器合理的形状是"取参数 → 调一个服务方法 → 根据结果选视图"，三步。

动手与思考 · 第 03 部分

Q1上面 show() 方法在商品不存在时重定向回列表页。原书的做法一样。但从 HTTP 语义看，这个行为对吗？换成什么更好？

思路提示

不对。商品不存在应该返回 404，而不是 302 跳转 + 200。区别是实打实的：搜索引擎会把不存在的商品页当成有效重定向而不是死链；监控里看不到任何异常；curl 拿到 200 会以为成功；浏览器缓存行为也不同。

Spring 里的做法是抛一个带 @ResponseStatus(NOT_FOUND) 的异常，再用 @ControllerAdvice + @ExceptionHandler 渲染一个友好的 404 页面（放在 templates/error/404.html，Boot 会自动用）。这样既有正确的状态码，又有好看的页面。

更一般的原则：用户体验和协议语义不冲突，别用重定向掩盖错误。

Q2把 ProductView 写成 record 而不是普通类，除了少写代码，还带来了什么？想一想并发和缓存。

思路提示

record 的字段是 final 的，实例天然不可变。这意味着：可以安全地在多线程间共享（不需要同步）、可以放进缓存而不担心被调用方改坏、equals/hashCode 基于全部字段自动生成因此能直接当 Map 键用、也不可能出现"某个中间层顺手改了一下再传下去"这种极难追查的 bug。

反过来看 JPA 实体：它必须可变（Hibernate 要通过 setter 或字段反射填充、要做脏检查），所以它不能是 record。这不是 Java 的缺陷，是两种对象的职责本来就不同——一个代表"数据库里的一行，会变"，一个代表"某个时刻的一份快照，不变"。把它们分开，很多问题会自己消失。

代码规范与质量门禁

对应原书第 9 章。原书讲 ESLint，结论是"总是用一个规范工具"。Java 生态里这件事被拆成了三件，值得分清。

ESLint 一个工具同时做了格式化、风格检查和一部分静态分析。Java 这边这三件事由不同工具承担，各自解决不同类型的问题——把它们混为一谈，就会出现"我装了 Checkstyle，为什么它没发现我的空指针"这类困惑。

关心什么工具典型能抓到的问题
格式：缩进、换行、import 顺序Spotless + google-java-format不是"问题"，是消除 diff 噪音和风格争论
风格约定：命名、可见性、类长度Checkstyle包私有该用而用了 public、类名不符合约定
语义 bug：编译期能证明的错误Error Proneequals 比较不同类型、格式串参数不匹配、被忽略的返回值

深入 · Spring Boot 4 的空安全：JSpecify

Spring Boot 4 把内部的空安全注解统一换成了社区标准 JSpecify。做法是给包加 @NullMarked，声明"这个包里所有引用类型默认非空"，需要可空时显式标 @Nullable。这本身只是文档；配合 NullAway 才会在编译期强制。

为什么值得做：Spring 应用里 Optional 和 null 混用是常态（findById 返回 Optional，但 Model.getAttribute 返回可能为 null 的 Object）。JSpecify + NullAway 把"这里可能是 null 吗"从一个需要读文档的问题变成了编译器能回答的问题。

数据层：JPA 与迁移

对应原书第 11–14 章。原书这几章有一个必须纠正的做法：synchronize: true。它在本教程里对应 ddl-auto: update，而这条配置是很多线上事故的起点。

三层抽象，别混淆

  • JPA（Jakarta Persistence API）—— 规范。定义 @Entity、EntityManager、JPQL 这些概念，本身没有实现。
  • Hibernate —— JPA 的实现，也是 Spring Boot 的默认选择。真正生成 SQL、管理持久化上下文的是它。
  • Spring Data JPA —— 在 JPA 之上的便利层。它最大的贡献是你只写接口，实现在启动时动态生成。

TypeORM 大致等于 Hibernate + 一层薄薄的 Repository。Spring Data 的抽象层次更高一级：findByNameContainingIgnoreCase 这种方法名解析在 TypeORM 里没有对应物。

实体

陷阱 · 三个新手必踩的点

1. 金额用 BigDecimal，不用 double。 原书的 price 是 number。0.1 + 0.2 != 0.3 在钱上会变成对不上账。数据库列用 numeric(12,2)。

2. 不要给实体加 Lombok 的 @Data。 它会生成基于全部字段的 equals/hashCode/toString：equals 会触发所有懒加载关联；toString 打日志时可能拉整棵对象图甚至无限递归；hashCode 会在对象存进数据库拿到 id 后发生变化，导致它在 HashSet 里"丢失"。

3. 不要给实体写 setId()。 id 由数据库或 Hibernate 分配，任何手工设置都是在制造麻烦。

深入 · 为什么 hashCode 返回常量

看着很反直觉，但这是 JPA 实体的标准做法。考虑这个序列：new Product()（id 为 null）→ 放进一个 Set → save()（Hibernate 回填 id）→ 再去 set.contains(product)。如果 hashCode 依赖 id，对象入库后哈希值变了，它会落到另一个桶里，contains 返回 false——对象"消失"在自己所在的集合里。

返回类的常量哈希，牺牲的是同类对象全部落在一个桶（集合退化成线性查找），换来的是哈希值在实体的整个生命周期内不变。实体集合通常只有几十个元素，这个代价可以接受。

Q1你要把 products.name 从 varchar(120) 改成 varchar(200)。用 ddl-auto: update 会发生什么？用 Flyway 呢？如果反过来，要从 200 缩到 120 呢？

思路提示

加长：ddl-auto: update 通常能处理（Hibernate 会发 ALTER … TYPE varchar(200)），但不保证——它的行为取决于方言实现，换个数据库可能就不动了。Flyway 里你自己写一行 alter table，行为百分之百确定。

缩短才是真正的分水岭。ddl-auto 什么都不会做——它只做"安全的增量"，不会执行任何可能丢数据的操作，而且不会告诉你。于是你的实体说 120、数据库还是 200，两边悄悄不一致，直到某天一条 190 字符的记录读进来把校验搞崩。

Flyway 里你必须先决定超长数据怎么办（截断？报错？先清洗？），把这个决定写进脚本。这才是重点：迁移工具的价值不在于自动，恰恰在于逼你显式做决定。 而 ddl-auto: validate 会在启动时发现这种不一致并拒绝启动——这是它唯一该用的模式。

Q2一个已经上线两周的迁移脚本 V3__add_index.sql，你发现里面索引建错了列。直接改这个文件会怎样？正确做法是什么？

思路提示

直接改会导致校验和不匹配：Flyway 记录了每个已执行脚本的 checksum，启动时发现文件变了会直接失败，报 Migration checksum mismatch。这是个特性不是 bug——它防止了"开发库和生产库执行的是不同版本的同一个脚本"。

正确做法是新增 V4__fix_index.sql，在里面 drop index 再重建。迁移脚本一旦被任何环境执行过，就是不可变的历史记录。 这和 Git 提交历史、和账本是同一个道理：修正靠追加，不靠篡改。

唯一的例外是这个脚本只在你本地跑过（还没推）——那可以改，然后 flyway:clean 重建本地库。判断标准是"别人有没有可能已经执行过它"。

Q3为什么 Product 不提供 setStock(int)，而是提供 reserve(int quantity)？这个差别在什么场景下才显现出来？

思路提示

setStock 把"怎么改库存"的知识散到每个调用方：下单要 setStock(getStock() - n)、退货要 setStock(getStock() + n)、每个地方都得自己记得判断"够不够"。只要有一处忘了判断，库存就能变负数。

reserve(n) 把规则收进实体：不够就抛异常，调用方绕不过去。这就是"充血模型"——数据和操作数据的规则放在一起。原书全篇是清一色的裸 getter/setter（贫血模型），业务规则散落在控制器里。

差别在什么时候显现？当第二个调用点出现的时候。只有一个地方扣库存时两种写法没区别；当运营后台、批量导入、退款流程都要动库存时，贫血模型开始出现"这里判断了、那里忘了"的不一致。所以不必一上来就过度设计，但要能识别出"这个规则开始出现第二个调用方了"这个信号。

依赖注入与模块边界

对应原书第 10、14、17 章。原书在第 17 章遇到了一个真实的设计困境，然后用 @Global 把它绕过去了。这一部分把那个困境拆开讲，因为 Spring 在这里的默认行为更宽松，问题也更隐蔽。

注入，三行代码就够

对照 · 三种注入方式，只用一种

Spring 支持构造器注入、setter 注入、字段注入（@Autowired 直接标在字段上）。只用构造器注入。 理由：字段可以是 final（线程安全、不会被中途替换）；依赖在编译期就写在构造器签名上（一眼看出这个类依赖了什么，太多就说明职责过重）；写单元测试时可以直接 new ProductService(mockRepo)，完全不需要启动 Spring。

字段注入的类没法用 new 构造出可用实例，逼着每个测试都得起容器，这是很多项目测试慢的根因。

陷阱 · 把 session 作用域的 Bean 注入单例

直觉写法 SingletonService(SessionCart cart) 会在启动时就固定注入某一个购物车实例，之后所有用户共用它——这是个能上新闻的 bug。解法是让 Spring 注入一个作用域代理：@SessionScope 默认已启用 proxyMode = TARGET_CLASS，注入的是代理，每次方法调用时才去当前会话找真实对象。理解这一点比记住注解重要：被注入的东西和你以为的那个对象不一定是同一个。

原书第 17 章的困境

原书在 AdminModule 里注入 ProductsService 时报错："Nest can't resolve dependencies of the AdminProductsController"。原因是 ProductsService 只注册在 AppModule 里。作者给了两个选项，选了第二个：给 AppModule 加 @Global()，让它的 provider 全局可见。

这个选择等于把刚建立的模块边界一次性拆掉。而 Spring 的默认状态就是拆掉之后的样子：所有 Bean 在一个扁平容器里，任何类都能注入任何类，没有报错，没有提示。

深入 · 为什么"测试守边界"是个好交易

Nest 的运行时边界给的反馈最强（启动就崩），但每加一个跨模块调用都要改两个 module 文件，摩擦大到作者自己都放弃了。Java 的模块系统（JPMS）能做到编译期强制，但配置复杂、和 Spring 的类路径扫描配合别扭。

Modulith 选的是第三条路：零运行时开销，反馈在 CI（几秒内），违规信息精确到"哪个类引用了哪个类"。 而且因为它只是一个测试，你可以随时用 @ApplicationModule(allowedDependencies = …) 显式放开某条依赖——边界成了可以商量、但必须写下来的东西。这比"能不能编译"更贴近实际的团队协作方式。

动手与思考 · 第 06 部分

Q1两个类互相构造器注入（A 需要 B，B 需要 A），Spring 启动会怎样？如果改成字段注入呢？哪种"更好"？

思路提示

构造器注入会启动失败，报 Circular reference（Spring Boot 2.6 起默认禁止循环依赖）。字段注入或 setter 注入能启动——Spring 先创建半成品对象再回填字段。

但"能启动"不等于更好，恰恰相反。循环依赖是设计问题，字段注入只是把它藏起来了。 藏起来的代价是：Bean 初始化顺序变得微妙，某个 @PostConstruct 里访问对方可能拿到未完全初始化的对象，出问题时极难排查。

真正的修法有三种：抽出双方共同依赖的第三个类；把其中一个方向改成事件（ApplicationEventPublisher，Modulith 特别推荐这个）；或者干脆承认这两个类应该合并。构造器注入的价值就在于它让设计问题在启动的第一秒暴露，而不是在生产的第三个月。

Q2原书用 @Global() 解决了跨模块注入。假设你是当时的作者，另一个选项是"在 AdminModule 里重新 import 一遍"。这两个选项各自的长期代价是什么？

思路提示

@Global() 的代价是一次性、不可逆、且看不见：从此任何模块都能注入任何 provider，没有任何地方记录"谁依赖了谁"。三个月后想拆微服务、想搞清楚改一个 service 会影响谁，都无从下手。

重复 import 的代价是持续的、小额的、可见的：每加一个跨模块依赖，你都要动手写一行，这行代码本身就是依赖关系的文档。

这是一个很典型的权衡形状：一次性消除摩擦 vs 保留摩擦作为信号。摩擦有时候是功能不是 bug——它让"增加一条依赖"这件事需要被意识到。判断标准是：这个摩擦每次的成本，和它防止的问题的成本，哪个大？跨模块依赖这件事，通常是后者大得多。

Q3如果容器里有两个 PaymentGateway 的实现（支付宝和微信），构造器注入 PaymentGateway 会怎样？有几种消歧方式，各适合什么场景？

思路提示

启动失败：NoUniqueBeanDefinitionException，因为 Spring 按类型注入，找到两个不知道选哪个。

四种解法，适用场景不同：@Primary 标一个默认（适合"通常用这个，偶尔用别的"）；@Qualifier("alipay") 在注入点指名（适合调用方明确知道要哪个）；@ConditionalOnProperty 按配置决定只注册一个（适合不同环境用不同实现）；或者注入 List<PaymentGateway> / Map<String, PaymentGateway>，拿到全部然后自己路由——这是策略模式在 Spring 里最自然的落地方式，也是支付这个场景真正该用的。

值得记住："注入一个集合"这个能力，把"多实现"从一个麻烦变成了一个特性。 事件监听器、校验器链、审计钩子都能这么组织，新增实现完全不用改调用方。

安全 · 为什么"检查 mimetype"不算检查

HTTP multipart 里的 Content-Type 是客户端自己填的一个字符串。攻击者用 curl 上传一个 .jsp、.html 或带 EXIF 恶意载荷的文件，同时把 Content-Type 写成 image/png，原书的 imageWhiteList.includes(file.mimetype) 会一路放行。文件随后落进 public/uploads，可以被直接访问。

Q1图 6 里，闪存数据存在哪？如果应用部署了三个实例、负载均衡不做会话粘滞，重定向后的 GET 落到另一个实例上会怎样？

思路提示

存在 HttpSession 里（SessionFlashMapManager）。默认的会话是每个 JVM 的内存对象，所以另一个实例上根本没有这条闪存——用户创建商品成功，但看不到任何提示。更糟的是登录状态也一样，用户会被随机登出。

三条出路：负载均衡开会话粘滞（最简单，但实例重启就丢、扩缩容不友好）；用 Spring Session 把会话外置到 Redis 或数据库（加一个依赖 + 几行配置，会话在实例间共享）；或者完全无会话（JWT 之类），但那样闪存机制就没了，得改用别的方式传消息。

顺带一提：原书用 express-session 的默认 MemoryStore，并且书里自己引用了官方警告"MemoryStore 不适合生产环境，会泄漏内存，无法跨进程扩展"——然后第 30 章照样这么部署上了 Heroku。这类"知道有问题但没改"的地方，是读技术书时特别值得留意的信号。

Q2校验失败时返回视图而不是重定向，保住了用户填的内容。但如果用户此时刷新页面，浏览器会弹出"要重新提交表单吗"。这算 bug 吗？怎么权衡？

思路提示

严格说是 PRG 模式的一个已知缺口：失败路径上我们放弃了 PRG，换取表单回显。刷新会触发重新提交——但因为校验还是会失败，实际后果只是又看到一次同样的错误，没有副作用。

想两头都要，有两条路：把表单对象也放进闪存后重定向（flash.addFlashAttribute(BindingResult.MODEL_KEY_PREFIX + "form", binding) 加上表单对象本身），这样既 PRG 又保留了错误和输入；或者前端做即时校验，把绝大多数失败挡在提交之前，让失败路径变成罕见情况。

要注意的判断方式：先问"重复提交的实际后果是什么"。校验失败的重复提交没有副作用，优先级低；下单接口的重复提交会多扣一次钱，那就必须彻底解决（第 10 部分的幂等键）。同一个技术缺口在不同业务上的严重程度可以差好几个量级。

Q3校验规则写在表单对象上（@NotBlank），但第 5 部分又说实体里要有 reserve() 这样的规则，数据库里还要有 check 约束。同一条"价格不能为负"要写三遍？

思路提示

看起来重复，但三者的目的和触发时机不同，缺一不可：

  • 表单注解：面向用户，目的是给出友好的、字段级的、本地化的错误提示。
  • 实体/领域方法：面向程序员，保证任何代码路径（后台、批处理、别的服务）都无法制造非法状态。
  • 数据库约束：面向数据，是最后一道防线，防的是绕过应用的写入。

判断是否"有害重复"的标准不是"字面上像不像"，而是"改一处时，另外几处是不是必须跟着改，且忘了改会静默出错"。这里不会：把价格下限从 0 改成 0.01，你只需要改表单提示和数据库约束，实体的"不能为负"依然成立。它们是嵌套的而不是重复的。

真正该消除的重复，是同一份规则在同一层被复制多次——比如三个控制器里各写一遍 if (price < 0)。

认证与授权

对应原书第 21、22、24 章。原书用 bcrypt + express-session + 两段手写中间件搭了一套；它能跑，但每一块都有缺口。这里换成 Spring Security，重点是讲清楚它怎么工作，因为它是全书最容易"配了但不知道为什么生效"的部分。

原书第 24 章有一句很坦诚的话：Nest 的 Guards 是为 API 设计的，用在 MVC 上会返回 JSON 错误，"所以我们改用 express 中间件"。于是授权变成了 app.use('/admin*', ...) 里的一个 if。Spring Security 没有这个割裂——同一套机制既能返回 JSON 也能重定向到登录页，因为"认证成功/失败之后做什么"本来就是可配置的。

配置

深入 · 为什么密码哈希要带算法前缀

原书直接存 bcrypt.hash(password, 10) 的结果。这在今天没问题，问题出在三年后：bcrypt 的成本因子需要提高，或者你想换成 Argon2id。因为数据库里的哈希没有任何元信息，你没法区分"这是旧算法编的"和"这是新算法编的"，最终只能让所有用户重置密码。

DelegatingPasswordEncoder 存的是 {bcrypt}$2a$10$…，前缀说明了算法。换算法时只需改默认编码器，老哈希照样能验证通过，而且可以在用户下次登录成功时顺手用新算法重新编码一遍，实现无感迁移。

一般化的教训：任何要长期存储的、且算法可能演进的数据，都应该自带版本标识。 这条同样适用于序列化格式、加密数据、缓存键。

用户从哪来

只要容器里有一个 UserDetailsService 和一个 PasswordEncoder，表单登录就能工作了。登录接口不需要你写控制器——UsernamePasswordAuthenticationFilter 已经处理了 POST /auth/connect。你只需要写登录页的 GET：

安全 · 原书的三个缺口

1. 退出用 GET。 原书是 @Get('/logout')。任何人往论坛贴一张 <img src="https://shop/auth/logout">，你的用户就被登出了。更严重的是，GET 应该是幂等且无副作用的，搜索引擎爬虫和浏览器预取都会触发它。Spring Security 默认要求退出用 POST，正是这个原因。

2. 会话里存了 role。 原书登录时把 {id, name, role} 写进会话，之后所有授权判断读的都是这个副本。管理员被降权后，只要他不退出登录，会话里的 role: 'admin' 就一直有效。Spring 的 SecurityContext 同样存在会话里，但你可以配置每次请求重新加载权限，而且有 SessionRegistry 能主动踢掉指定用户的所有会话。

3. 登录后没有换会话 ID。 攻击者先访问网站拿到一个会话 ID，诱导受害者用这个 ID 登录，登录成功后攻击者手上的 ID 就变成了已认证会话——会话固定攻击。防法只有一个：认证成功的瞬间换发新的会话 ID。Spring Security 默认就做，原书完全没有。

方法级授权

URL 级规则挡不住一类问题：已登录用户 A 访问 /account/orders/42，而订单 42 属于用户 B。URL 匹配 /account/** 只要求"已登录"，是通过的。这叫越权访问（IDOR），是 Web 应用最常见的高危漏洞之一。

深入 · 优先"查不出来"，而不是"查出来再拒绝"

@PostAuthorize 是先执行方法、拿到结果再判断，所以数据已经从数据库读出来了——如果方法里有别的副作用（记日志、更新计数），副作用已经发生。而且它容易漏（新加一个查询方法忘了标注解）。

把归属条件下推到查询里（where buyer_email = ?）是更稳的模式：越权数据根本不进入应用内存，不存在"忘了检查"的可能。@PostAuthorize 更适合当作第二道保险，或用在无法下推的场景。

Q1CSRF 保护对 GET 请求不生效。那如果我把"删除商品"做成 GET /admin/products/5/delete，会怎样？

思路提示

直接被 CSRF 打穿。攻击者只要让管理员的浏览器发出这个 GET（一张 <img>、一个 <iframe>、甚至聊天软件的链接预览抓取），商品就没了——管理员的 cookie 会自动带上，服务端看不出任何异常。

Spring 不对 GET 校验 CSRF 不是疏忽，而是因为按 HTTP 规范，GET 必须是安全的（无副作用）。CSRF 保护建立在这个假设之上。你把有副作用的操作做成 GET，等于自己拆掉了这个前提。

可以记住的一般规则：只要一个请求会改变服务端状态，它就不能是 GET。 这一条同时解决了 CSRF、浏览器预取误触发、爬虫误删数据、以及"用户按后退键重复执行"四类问题。原书的删除商品是 POST（正确），但退出登录是 GET（不正确）。

Q2配置里最后一行是 .anyRequest().denyAll()。很多教程写的是 .anyRequest().permitAll() 或干脆不写。这三种兜底的实际差别是什么？

思路提示

permitAll() 兜底意味着任何你忘了配规则的路径都是公开的。新同事加了个 /internal/debug/dump-users，忘了配安全规则，它就直接对外了。这类"默认开放"的配置是数据泄露事故的经典成因。

denyAll() 兜底则相反：忘配规则的路径直接 403，问题在开发阶段就暴露（你自己第一个撞上），而不是在被人扫描到之后。代价是每加一个页面都要显式开一条规则——这个摩擦是值得的。

安全设计里这叫 fail-safe defaults / default deny：出错时应该倒向"更安全"的那一侧。同样的思路你会在防火墙规则、S3 桶策略、数据库权限里反复见到。问"如果我忘了配，会发生什么"，是评估任何权限系统的第一个问题。

Q3原书登录成功后把用户信息塞进会话，模板里用 {{#if session.user}} 决定显示"登录"还是"退出"。本教程用 sec:authorize="isAuthenticated()"。除了写法，本质区别在哪？

思路提示

本质区别是真相来源只有一个还是两个。原书的会话里有一份用户信息副本，而真正的用户数据在数据库里——两份数据从登录那一刻起就开始漂移（改名、改角色、被禁用，会话里都不知道）。更糟的是授权判断读的是那份副本，所以"漂移"直接变成了安全问题。

SecurityContext 也存在会话里，看起来是同样的结构。差别在于它是框架统一管理的单一入口：过滤器链、方法安全注解、模板方言、审计日志读的都是它；要让它失效有标准手段（SessionRegistry.expireNow()、改密码后使会话失效）。手写的 session.user 则是散落在各处的裸读取，没有任何统一控制点。

可迁移的判断：当同一份信息在系统里有两个存放处时，要立刻问"它们什么时候会不一致，不一致时谁说了算"。 这个问题在缓存、读写分离、事件驱动架构里是同一个形状。

领域模型

N+1：写起来很自然，跑起来很慢

原书第 28 章的"我的订单"页面遍历每个订单，再遍历每个订单的明细，再取每个明细的商品名。作者用 TypeORM 的 relations: ['items', 'items.product'] 解决了它——这其实是个正确做法，但书里的解释是"这是 TypeORM 关联的威力"，没有说清楚不写这一行会发生什么。

还有方案三，适合"多个集合关联"的情况：在 application.yml 里设 spring.jpa.properties.hibernate.default_batch_fetch_size: 32。它不消除额外查询，但把 N 次单条查询合并成 where id in (…) 的批量查询，N 从 12 降到 1–2。当你需要同时 fetch 两个集合时（join fetch 两个集合会产生笛卡尔积），这是更好的选择。

陷阱 · open-in-view 让 N+1 隐身

Spring Boot 默认 spring.jpa.open-in-view=true，意思是数据库连接和持久化上下文一直保持到视图渲染结束。好处是模板里访问懒加载属性不会报 LazyInitializationException；坏处是 N+1 变得完全无声——查询散落在模板渲染过程中，性能问题只在压测或线上才浮现，而且数据库连接被占用的时间被拉长到包含渲染耗时，高并发下连接池会先耗尽。

所以第 0 部分就把它设成了 false。代价是你必须在服务层就把视图需要的数据全部取好——这恰恰是你想要的纪律：让"数据什么时候被加载"成为一个显式决定，而不是副作用。

Q1怎么在开发阶段就自动发现 N+1，而不是等上线后看监控？

思路提示

三个手段，从轻到重：

  • 开 hibernate.SQL: debug 日志，打开页面数一数发了几条 SQL。最简单，但靠人工看。
  • 接入 datasource-proxy 或 Hypersistence Utils 的 SQLStatementCountValidator，在集成测试里断言"这个接口最多允许 2 条 SQL"。这是最有价值的做法——把性能约束变成会失败的测试。
  • 接 Micrometer + 分布式追踪，在预发环境看每个请求的 SQL 数量分布。

值得推广的思路：凡是"上线才会暴露"的问题，都值得想办法把它变成一条本地就能跑红的断言。 N+1、内存泄漏、慢查询、接口响应体积，都有对应的做法。这比"记得注意"可靠得多。

Q2把 @ManyToOne 改成 fetch = EAGER，是不是就永远不会 N+1 了？为什么 JPA 规范里 @ManyToOne 的默认值偏偏是 EAGER？

思路提示

不是，而且往往更糟。EAGER 意味着每次加载这个实体都会连带加载关联对象，无论你需不需要。查订单列表只想显示总价？照样把每个订单的 buyer 和所有 item 拉出来。更麻烦的是 EAGER 无法在查询时关掉——它是映射级别的决定，而"这次查询要不要连带"本该是查询级别的决定。

规范把 @ManyToOne/@OneToOne 默认设成 EAGER，是个被广泛认为设计失误的历史包袱（@OneToMany/@ManyToMany 默认是 LAZY，倒是对的）。实践共识：所有关联一律显式写 fetch = LAZY，需要连带时用 join fetch 或 EntityGraph 在查询处指定。

背后的原则很通用：把"要不要"的决定权放在知道答案的那一层。 映射层不知道每个查询的需求，查询层知道。同样的思路适用于日志级别、缓存策略、超时时间——尽量做成调用点可覆盖的，而不是全局写死的。

Q3购物车用会话存储，用户换台设备就没了；存数据库则跨设备保留但要处理未登录用户。原书选了会话。你会怎么选？

思路提示

这题没有标准答案，重点是把权衡说清楚：

  • 会话： 实现简单，未登录也能用，天然隔离。代价是换设备/清 cookie 就丢，且会话外置（Redis）之前无法多实例部署。
  • 数据库： 跨设备、可分析（"有多少人加了购物车没下单"是重要的商业指标）、可做"降价提醒"。代价是未登录用户需要一个匿名标识（cookie 里的 UUID），登录时还要处理合并——匿名车和账号车里有同一个商品该取哪个数量？
  • 混合： 未登录用会话，登录时合并进数据库。大多数真实电商的做法，也是复杂度最高的。

可迁移的判断方法：先问"这份数据丢了，用户和业务分别损失什么"。 购物车丢了，用户损失几分钟，业务损失一次转化——对小站可以接受，对大站是能用钱衡量的损失。答案取决于规模，所以正确的做法是先做简单的，但把接口设计成能替换的（比如让 CartService 面向一个 CartStore 接口）。

下单：事务与并发

对应原书第 27 章。作者说这是"全书最复杂的方法"，并在末尾留了一句"我们还没有校验用户余额是否足够，你可以试着加上"。缺的其实不止余额校验——这一整段代码在并发下是不安全的。

原书的 purchase 做了这些事：查用户 → 查商品 → 循环建 Item → 算总价 → 存订单 → 算新余额 → 更新余额 → 清空会话。八步，没有事务，没有加锁，没有校验。第五步之后任何一步失败，订单已经存进去了但钱没扣；两个请求同时进来，扣款会互相覆盖。这三个问题各有各的解法。

问题一：原子性

"创建订单"和"扣余额"必须同时成功或同时失败。这就是事务的定义。

陷阱 · @Transactional 的三个失效条件

它是基于代理实现的，所以在这三种情况下会静默失效（不报错，只是不开事务）：

1. 自调用。 同一个类里 this.otherMethod() 调用另一个标了 @Transactional 的方法——调用没经过代理，注解等于不存在。解法是把方法挪到另一个 Bean，或注入自己（不推荐）。

2. 非 public 方法。 默认代理只拦截 public 方法。

3. 受检异常。 默认只有 RuntimeException 触发回滚。抛 IOException 事务照样提交。需要的话写 @Transactional(rollbackFor = Exception.class)。

第一条是最高频的。判断方法：在方法里打印 TransactionSynchronizationManager.isActualTransactionActive()，一测便知。

问题二：并发

深入 · 乐观还是悲观，怎么选

乐观锁（@Version）：假设冲突罕见。不加任何数据库锁，冲突时才付出重试代价。适合绝大多数业务——两个人同时改同一个用户余额本来就少见。

悲观锁（SELECT … FOR UPDATE，JPA 里是 @Lock(PESSIMISTIC_WRITE)）：假设冲突频繁。读的时候就把行锁住，别人等。适合"秒杀同一件商品"这种热点，因为乐观锁在高冲突下会变成大量无效重试。

判断方法很实在：先上乐观锁，然后监控重试率。 重试率长期低于百分之几就不用管；某个接口重试率飙到 30%，那里才需要悲观锁或别的设计（比如把热点行拆成多行、用队列串行化）。先测量再优化在并发问题上尤其成立，因为直觉几乎总是错的。

问题三：幂等

用户在支付页反复点"提交"，或者网络超时后客户端重试——都会产生重复订单。PRG 模式（第 7 部分）挡住了浏览器刷新，但挡不住双击和重试。

深入 · 为什么"先查再插"不够，还要 catch 唯一索引冲突

"先查有没有，没有就插"这个模式在并发下有个天然的竞态窗口：两个线程可能同时查到"没有"，然后都去插。这个模式叫 check-then-act，是并发 bug 的经典形状。

解法不是加锁（那会拖慢所有请求），而是让数据库的唯一索引来做最终裁决——它是原子的，一定只有一个能成功。应用层的预查询只是优化（避免常见情况下走异常路径），真正的正确性由约束保证。

这个"乐观地做，让底层约束兜底"的模式值得记住，它在很多地方复用：注册时的邮箱唯一、并发创建目录、分布式锁的 SET NX。看到 check-then-act，就要问一句"两个线程同时走到中间会怎样"。

动手与思考 · 第 10 部分

Q1下单成功后要给用户发一封确认邮件。把 mailService.send(...) 直接写在 @Transactional 方法末尾，有什么问题？

思路提示

三个问题叠在一起。第一，事务被外部调用的耗时拖长——SMTP 慢一秒，数据库行锁就多持有一秒，并发能力直接下降。第二，邮件发出去了但事务回滚了：邮件已经在路上，无法撤回，用户收到"下单成功"却查不到订单。第三，邮件服务挂了导致下单失败——一个次要功能拖垮了核心链路。

正确做法是把副作用移到事务提交之后。Spring 提供了现成机制：

  • @TransactionalEventListener(phase = AFTER_COMMIT)——服务里 publishEvent(new OrderPlaced(id))，监听器只在提交成功后执行。
  • 更可靠的是 outbox 模式：在同一个事务里往 outbox 表插一条待发消息，另一个进程轮询发送。这样"要发邮件"这件事本身也具备了原子性。

一般规则：事务里只做数据库操作。 调用外部服务、发消息、写文件、清缓存，全都应该在提交之后。

Q2如果余额和库存分别放在两个不同的数据库（甚至两个微服务）里，本节的 @Transactional 还管用吗？

思路提示

不管用。@Transactional 是单个数据源的本地事务。跨两个数据库需要分布式事务（XA/两阶段提交），而 XA 在实践中代价很高：协调者是单点、锁持有时间跨网络、很多中间件不支持。

主流做法是放弃强一致，改用 Saga 模式：把长事务拆成若干本地事务，每一步都配一个补偿操作。扣库存失败？执行"退还余额"。关键在于每一步都要幂等（因为补偿本身可能重试）。

但更值得先问的问题是：这两份数据真的需要分开吗？ 很多分布式事务的痛苦，源头是不必要的服务拆分。库存和订单在业务上属于同一个一致性边界，硬拆开就得自己重新实现事务——这通常不划算。"哪些数据必须强一致"这个问题，应该在划分服务边界之前回答，而不是之后。

Q3怎么写一个测试来证明乐观锁真的生效了？只调用一次 checkout 显然测不出来。

思路提示

需要制造真实的并发。思路：用 ExecutorService 起两个线程，配合 CountDownLatch 让它们同时开跑，各自调用一次 checkout，然后断言两件事——最终余额是 880（不是 940），以及要么两单都成功、要么其中一个抛了 ObjectOptimisticLockingFailureException。

两个必须注意的点：这类测试必须用真实数据库（Testcontainers），H2 之类内存库的锁和隔离级别行为和 Postgres 不一样，测了等于没测；而且每个线程需要自己的事务，所以不能用 @Transactional 标在测试方法上（那会让所有操作跑在同一个事务里，根本不并发）。

更普适的一点：并发 bug 无法靠"多跑几次"来证明不存在，但可以靠精心构造的交错来证明它存在（或已修复）。所以针对已知的竞态点写确定性的并发测试是值得的，而"压测跑一万次没出问题"不能作为正确性证据。

动手与思考 · 第 11 部分

Q1项目里每个测试类都标 @SpringBootTest，跑一遍要 8 分钟。除了"改用切片测试"，还有什么办法能立刻见效？

思路提示

先查上下文缓存有没有生效。Spring 会按"配置指纹"缓存 ApplicationContext，同样配置的测试类共用一个上下文，只启动一次。但任何差异都会导致新建：不同的 @MockitoBean 组合、不同的 @ActiveProfiles、不同的 @TestPropertySource、类上多一个 @Import。八分钟里可能有七分钟是在反复启动近乎相同的上下文。

诊断办法：开 logging.level.org.springframework.test.context.cache=debug，日志会打出缓存命中/未命中和当前缓存了几个上下文。修法通常是把测试基类统一，让大批测试共享同一个配置指纹。

这个思路可以推广：遇到"慢"，先测量是什么慢，往往不是你以为的那个。 这里的直觉答案（测试太多）和真实答案（上下文重复启动）差别很大，而后者的修复成本低得多。

Q2如果只能为这个商城写三个测试，你会写哪三个？

思路提示

标准应该是"出错的代价 × 出错的概率"最高的三处，而不是"最难写的三处"或"覆盖率最高的三处"。我的选择：

  • 下单的完整集成测试：余额、库存、订单、明细四者一致。这是钱直接相关的路径，错了就是真金白银。
  • 授权矩阵：匿名 / 普通用户 / 管理员 × 几条关键路径。错了是数据泄露，而且改配置时最容易无声破坏。
  • 并发下单：证明乐观锁生效。错了是超卖，且只在生产的流量下才出现。

反过来说，"商品列表页能打开"这种测试价值很低——它坏了你第一时间就会发现。测试的价值和"坏了多久才会被发现"正相关。

Q3原书说单元测试"超出本书范围"。作为一本教初学者的书，这个取舍合理吗？

思路提示

这题没有唯一答案，但值得想清楚代价。支持的理由：篇幅有限，测试确实是独立的一大块，先跑通再谈质量对初学者更友好。

反对的理由更实质：这本书花了整整三章（8、9、15）讲"干净代码"——命名、编码规范、getter 封装。这些都是可读性层面的整洁，而测试是可验证性层面的整洁，后者对代码质量的影响大得多。一本以"clean"为卖点的书跳过测试，等于在讲整洁的同时省略了最能保证整洁不退化的手段。

更值得留意的一点：书里删掉 app.controller.spec.ts 那个动作，向读者传达的隐含信息是"测试是可以随手删掉的东西"。教学材料里的省略从来不是中立的——它同时在传达优先级。这也是读任何技术书时值得保持的一点警觉：作者没写什么，和写了什么一样有信息量。

配置外部化

规则很简单：任何随环境变化的值，都不该出现在代码库里。 Spring Boot 的配置来源有十几个，按优先级从高到低覆盖，你只需要记住常用的几个：

优先级来源用途
高命令行参数 --key=value临时覆盖，调试用
↑环境变量 STORE_MEDIA_DIR容器部署的主要方式；下划线大写会映射到 store.media.dir
↑application-{profile}.yml环境差异（dev / prod）
低application.yml各环境共同的默认值
安全 · 凭据不进 Git

原书第 29 章直接把 Clever Cloud 的数据库主机名、用户名、密码写进 ormconfig.json，还展示了真实值的截图。生产凭据一旦进过 Git，就等于永久泄露——删掉文件不够，历史里还在。

正确做法按成本递增：环境变量（最低成本，容器平台都支持）→ 平台的密钥管理（Kubernetes Secret、AWS Secrets Manager）→ Spring Cloud Vault / Config Server（需要动态轮换时）。本地开发用 .env 或 application-local.yml，并把它写进 .gitignore。

生产必备的几项配置

深入 · liveness 和 readiness 不是一回事

两个探针的语义完全不同，配错了会造成很有意思的故障：

readiness（就绪）：我现在能不能接收流量？答"否"时，负载均衡把我从后端列表里摘掉，但不重启我。适用场景：正在启动、依赖的数据库暂时不可用、正在优雅停机。

liveness（存活）：我是不是彻底废了、需要被杀掉重启？答"否"会触发重启。它不应该检查外部依赖——数据库挂了，重启应用毫无帮助，反而会让整个集群陷入重启风暴，在数据库恢复的瞬间用几百个冷启动实例再把它压垮。

可迁移的原则：把"我不健康"和"我依赖的东西不健康"分开表达。 混为一谈会让局部故障放大成全局故障。

动手与思考 · 第 12 部分

Q1应用要滚动升级：先起新实例、健康后再停老实例。server.shutdown: graceful 已经配了。还有什么会让用户遇到 500？

思路提示

至少三处：

  • 数据库迁移和新旧代码不兼容。 滚动期间新旧版本同时在跑，共用一个库。如果 V5 迁移删了一列而老实例还在读它，老实例立刻报错。解法是迁移必须向后兼容：删列要分两次发布（先改代码不再用它，下个版本再删列）；加非空列要先加可空列 + 回填 + 再加约束。
  • 会话在实例间不共享。 老实例被停掉，它内存里的会话（包括登录状态和购物车）就没了，用户被登出。要么会话外置到 Redis，要么接受这个代价。
  • readiness 探针配得太宽松。 新实例还没跑完 Flyway 迁移和连接池预热就被判定就绪，第一批请求会超时。

一般化的洞察："零停机部署"的难点几乎从不在应用进程本身，而在于它持有的状态——数据库 schema、会话、缓存、在途任务。 只要还有跨版本共享的状态，就必须保证新旧两个版本能同时正确运行。

Q2为什么 include-stacktrace: never 重要？把堆栈打给用户看，除了"不好看"还有什么风险？

思路提示

堆栈是给攻击者的一份免费情报：框架和库的精确版本（可以直接去查对应的 CVE）、包结构和类名（推断出内部架构）、有时还有SQL 语句片段（暴露表结构，辅助注入）、文件系统路径（暴露部署方式和用户名）。这一步在渗透测试里叫信息收集，通常是攻击链的第一环。

正确做法是：用户看到一个带追踪 ID 的友好错误页，完整堆栈进结构化日志，两者用这个 ID 关联。这样支持人员能凭用户提供的 ID 精确定位，而攻击者什么也拿不到。

一般原则：面向不同受众的输出，详略程度应该不同。 同样的思路适用于登录失败提示（"邮箱或密码不正确"而不是"该邮箱不存在"，后者能用来枚举注册用户）。

Q3原书部署时把上传的图片存在应用的本地目录里。部署到容器平台后会发生什么？

思路提示

三件事会依次出问题。容器重启，文件全没——容器文件系统是临时的，每次部署都是新的空目录。多个实例各存各的——上传落在实例 A，用户下次请求路由到实例 B，图片 404。无法水平扩展，因为实例之间不再等价。

这就是"十二要素应用"里说的无状态进程：应用实例不该持有任何需要长期存在的本地状态。图片该放对象存储（S3/OSS/MinIO），会话该放 Redis，日志该输出到 stdout 由平台收集。

好在第 7 部分的 MediaStorage 已经是一个接口形状的东西——换成对象存储只需要换一个实现，控制器和服务都不用动。这就是"先做简单的，但把接口设计成能替换的"在实际中的回报。
