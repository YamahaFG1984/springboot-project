三个缺口

  1. 没有异步。第一季的每个请求都是"进来—处理完—返回"。真实系统里总有一些事不能在请求里做完：发邮件、调支付、生成报表。一旦有了"稍后再做"，就有了"做失败了怎么办"和"做了两次怎么办"。
  2. 没有外部依赖。数据库是你的，它慢了你能查、挂了你能修。支付网关不是——它会超时，而超时既不是成功也不是失败，是"不知道"。整个第 08、09 部分都在处理这个"不知道"。
  3. 没有时间。第一季里唯一的时间是 createdAt。这一季有超时、有过期、有定时任务、有 TTL——而所有涉及时间的正确性问题，都会以并发问题的形式暴露出来。
对照 · 这一季和 Spring 那一季的关系

本文有一份姊妹篇：《在线商店 · 进阶》，同样的 13 个主题，用 Spring Boot 4 写。两边的结论几乎逐条相同——因为这一季讲的东西大多不属于框架层面：Redis 的丢失窗口、超时的三种真相、Outbox 的原理、限流算法的边界突发，换成任何语言都一样。

真正不同的只有三处，而且都值得留意：没有 Spring Cache 抽象（缓存要自己写，好处是没有隐式行为）、没有 @Scheduled 和 ShedLock（调度要自己决定放在哪，Postgres 咨询锁比 ShedLock 更轻）、单线程事件循环（这让"锁被 GC 暂停打断"这个经典问题在 Node 上换了个形态，见第 07 部分）。

深入 · 这一季不引入消息队列

讲到异步和事件，很容易顺手加一个 Kafka 或 RabbitMQ。我刻意不加，理由有两条：

第一，大多数团队在真正需要 MQ 之前就引入了它，然后把一个单体的复杂度换成了一个分布式的复杂度，却没有得到对应的收益。第 10 部分会用数据库表 + for update skip locked 实现一个完整的 Outbox，它能扛住每秒几百条投递——这个量级覆盖了绝大多数电商系统。

第二，也是更重要的：MQ 不能免除你思考幂等、顺序和重复。它只是把这些问题换个位置。先在一个能完全看清的实现里把这些概念搞懂，再决定要不要换成 MQ，顺序更划算。第 10 部分末尾会给出三个"该换真 MQ 了"的具体信号。

01

Redis 进场

加一个组件之前，先想清楚它什么时候会骗你。这一部分不写业务代码，只建立一条贯穿整季的判断线：什么数据可以放 Redis，什么数据放进去就是在赌。

Redis 快得让人放松警惕。但"快"是有代价的，代价就藏在它承认写入成功的那一刻，数据到底在哪。默认配置下，答案是"在一台机器的内存里，可能还没落盘，可能还没到副本"。这一节把这三个窗口画出来，之后每一次用到 Redis，我们都回到这张图上做判断。

客户端与键的约定

陷阱 · enableOfflineQueue 默认是 true

默认情况下，Redis 断开时 ioredis 会把命令攒在内存队列里，等重连后一起发出去。听起来很贴心，实际后果是：Redis 挂掉的那一分钟里，你的应用不是快速失败，而是每个请求都在等一个永远不会返回的 Promise，直到 commandTimeout 或者内存被队列吃光。

对缓存场景，我们要的恰恰相反：Redis 不可用时立刻报错，让调用方走回源逻辑。所以关掉离线队列、设短超时。第 13 部分会把这个决定的完整后果展开。

那个 v1 值得解释：缓存值的结构一旦改变，老数据就是毒药。比如你给 product 的缓存对象加了一个字段，新代码读到旧缓存会拿到 undefined——而它已经通过了类型检查（图 4 的教训在这里重演：JSON.parse 返回 any）。把版本号写进键前缀，发布时改成 v2，所有旧缓存自动作废，不需要写任何清理脚本，旧键靠 TTL 自己过期。

序列化：别用花哨的

深入 · 三个容易被 JSON 悄悄改掉的类型
  • Date：JSON.stringify(new Date()) 得到字符串，JSON.parse 不会还原成 Date。存进去是 Date，取出来是 string，而 TypeScript 类型上还写着 Date——这正是上面那个 safeParse 要挡的东西（用 z.coerce.date() 还原）。
  • undefined：JSON.stringify({ a: undefined }) 得到 {}。字段直接消失，而不是变成 null。
  • 大整数：超过 Number.MAX_SAFE_INTEGER 的值会静默丢精度。金额用整数分（第一季图 7）不会撞上，但如果你存了雪花 id 就会。

顺带说一句为什么不用 superjson 之类能保留类型的库：它们会在值里嵌入类型元信息，于是缓存里的数据和某个版本的类定义绑定了。跨版本读老数据时，出问题的方式会比"字段缺了"隐蔽得多。普通 JSON + 显式 schema 校验，笨但可控。

动手与思考 · 第 01 部分

先自己想，再展开思路。

Q1有人提议把商品库存放进 Redis 计数器，"扣减用 DECR，原子又快，比数据库行锁强多了"。按图 1 的框架，这个方案错在哪？有没有可以救的版本？

思路提示

错在库存属于第三类：清空 Redis 之后无法从 Postgres 重建——数据库里的 stock 是初始值，Redis 里的才是当前值，两者的差额（已经卖掉多少）只存在于那个易失的计数器里。窗口 ③ 一次故障切换，就可能把几百笔扣减凭空还回去，然后超卖。

可以救，但要换个说法：Redis 计数器只是一道闸门，不是账本。典型用法是秒杀——先用 DECR 挡掉 99% 注定失败的请求，剩下的 1% 仍然要去 Postgres 走第一季图 13 那条原子条件 UPDATE，以那里的结果为准。

这样即使 Redis 丢了数据，最坏结果是"闸门放宽了，更多请求打到数据库"，而不是"卖超了"。判据：Redis 出错时，错误的方向是性能变差还是数据变错。前者可以接受，后者不行。这条判据在第 06 和第 07 部分还会各用一次。

Q2Redis 是单线程处理命令的，Node 也是单线程跑事件循环的。这两个"单线程"叠在一起，会产生什么第一季没有的性能陷阱？

思路提示

两边各有一类，而且都不会报错，只表现为"莫名其妙变慢"。

Redis 侧：一条慢命令会阻塞所有客户端，因为它只有一个线程在执行命令。危险的有 KEYS *（生产环境禁用，用 SCAN）、对百万元素的集合做 SMEMBERS/HGETALL、以及写得不好的 Lua 脚本。你的应用会看到"所有 Redis 请求同时变慢"，而 Redis 的 CPU 只有一个核在满载。

Node 侧：如果你从 Redis 取回一个很大的字符串再 JSON.parse，解析是同步的、阻塞事件循环的。取回 5 MB 的商品列表缓存、解析 30 ms——这 30 ms 里整个进程处理不了任何其它请求，包括那些根本不碰 Redis 的。这比"这个请求慢了 30 ms"严重得多。

共同的教训：缓存值要小而多，不要大而少。与其缓存整个商品列表，不如按 id 缓存单个商品再用 MGET 批量取——网络往返一样是一次，但每个值都小，解析成本分散，而且命中率更高（一个商品变了只失效一个键）。

Q3键前缀里的 v1 解决了"缓存结构变了"的问题。但如果你只是修了一个 bug（比如价格算错了），已经缓存的错误数据要怎么清？

思路提示

三种手段，代价递增：

  • 等 TTL 过期。如果 TTL 是 5 分钟，那就是 5 分钟内还有人看到错价。够不够取决于错的是什么——排序错了可以等，价格错了不能等。这解释了为什么 TTL 不该统一设成一个值：数据的"错了能忍多久"决定它的 TTL。
  • 精确删键。知道是哪些商品受影响就 DEL 掉。前提是你的键设计允许精确定位——这也是"按 id 缓存"比"缓存整个列表"好的又一个理由。
  • 改版本号发布。v1 → v2，全部作废。最彻底，但代价是瞬间全部回源——所有缓存同时失效，数据库要接住全部流量。这就是第 04 部分要讲的雪崩，只不过这次是你自己造成的。

实践中我会这样组合：版本号只在结构变更时改（那种情况下必须全废）；bug 修复用精确删除；如果实在要全废，就分批删或者给新版本的 TTL 加随机抖动，让回源分散开。

还有一个常被忽略的准备工作：提前写好一个能按前缀批量清理的运维脚本（用 SCAN 而不是 KEYS），并且演练过。出事时现写脚本，第一版八成会用 KEYS *，然后把 Redis 卡死。

02

会话与购物车外置

第一季把会话和购物车都放在 PostgreSQL 里。这一部分把它们搬到 Redis——但先说清楚这笔买卖到底赚不赚，因为"会话当然要放 Redis"是一句流传很广却经常不成立的话。

搬家的动机通常被说成"性能"。真去量一下：第一季那条 sessions join users 的主键查询在 Postgres 上大约 0.2 ms，Redis 的 GET 大约 0.15 ms。差距在网络往返的噪声里。所以如果理由只是快，那就不必搬。真正的理由是另外两条，而它们各自带着代价。

陷阱 · pipeline 不是事务

pipeline() 只是把多条命令打包成一次网络往返，它们之间可以被其它客户端的命令插入，而且如果第二条失败了，第一条已经生效、不会回滚。

ioredis 里真正的事务是 multi()——它保证这批命令连续执行、中间不插入别人。但即便是 MULTI 也不是你熟悉的数据库事务：它没有回滚，某条命令执行时报错（比如对字符串做 HINCRBY），其它命令照常执行。

需要"读一个值、根据它决定写什么"这种原子操作时，MULTI 也不够（它不能在中途读到结果再分支）。那种情况只有一个正确工具：Lua 脚本——它在 Redis 里原子执行，可以读、可以判断、可以写。第 06 和第 11 部分各会用一次。

Q1购物车放 Redis 之后，运营说"用户反馈购物车里的东西不见了"。按图 1，这可能是正常的（丢失窗口）。你怎么判断到底是丢数据还是有 bug？怎么让这件事不再是猜？

思路提示

先分清三种"不见了"，它们的证据完全不同：

  • TTL 到期。30 天没动过的车被回收。可以查：如果用户上次操作是一个月前，就是它。这不是故障，但可能是产品决策错了——真实电商的购物车通常保留更久。
  • Redis 丢数据。特征是成批发生、时间点集中。所以监控里必须有 Redis 的重启/故障切换事件，并且能和用户反馈的时间对齐。没有这条时间线，你永远只能猜。
  • 合并逻辑 bug。特征是集中在"刚登录之后"。上面 mergeOnLogin 里 del(anonCartId) 如果在 hincrby 失败后仍然执行了，就是净丢失——pipeline 不是事务，这个风险是真的。

让它不再是猜，需要两件事：埋一个 cart.items.count 的指标（按小时聚合，突然的断崖一眼可见），以及在关键操作上打结构化日志（merge 了几项、清空是谁触发的）。

还有一个更根本的选择：如果购物车对业务真的重要（对电商来说通常是的——它是转化漏斗的最后一格），那就不该只放 Redis。可以 Redis 做读写主力、异步落一份到 Postgres 做备份，或者干脆退回第一季的方案。"购物车放 Redis"是这一季里我最不确定的一个决定，图 1 把它归到"有争议"就是这个意思。

Q2addItem 里先 HINCRBY 再判断结果 <= 0 才 HDEL。两个请求同时把数量从 1 减到 0 会怎样？用 Lua 重写会更好吗？

思路提示

两个并发的 HINCRBY key f -1 会得到 0 和 -1，两边都判定 <= 0，都发 HDEL。第二次 HDEL 删一个不存在的字段——无害。结果正确：字段没了。

但换个场景就不对了：一边减 1、一边加 1。可能的交错是 -1 得到 0 → +1 得到 1 → 然后第一个请求的 HDEL 才执行，把刚加回来的那一项删了。用户点了"加入购物车"，商品消失了。概率很低，但会发生。

Lua 能修好，因为它让"改数量 + 判断 + 可能的删除"变成一个原子步骤：

local n = redis.call('HINCRBY', KEYS[1], ARGV[1], ARGV[2]); if n <= 0 then redis.call('HDEL', KEYS[1], ARGV[1]); n = 0 end; redis.call('EXPIRE', KEYS[1], ARGV[3]); return n

值不值得？我认为值得，而且理由不是这个罕见 bug，是它顺便把三次往返变成一次。购物车增删是高频操作，一次往返的收益是稳定的；顺手拿到的正确性是白送的。

反过来提醒一句：Lua 脚本在 Redis 里是阻塞执行的（第 01 部分 Q2），所以脚本必须短、不能有循环遍历大集合。上面这段是三条命令，没问题。

几乎不值什么。具体算一下更有说服力：

  • 过期清理：一条 delete from sessions where expires_at < now()，每小时跑一次，几万行的表上是毫秒级。省掉的是十行代码和一个定时任务，不是运维负担。
  • 滑动续期的写入：QPS 300 意味着每秒 300 次 UPDATE。听起来多，但那是一张小表上的主键更新，Postgres 轻松承受；而且可以优化成"距上次续期超过 5 分钟才写"，写入量立刻降到几乎为零。这个优化只有两行代码，比引入一个新组件便宜得多。

怎么解释：不要说"Redis 没用"，要把讨论拉回到成本那一侧。引入 Redis 存会话意味着多一个必须高可用的组件、多一条故障路径（它挂了全站登出）、多一套要自己维护的反向索引、多一份运维知识。这些成本是确定的，而收益是假设的。

然后给一个可以验证的触发条件："等到会话表的写入占到数据库写入量的 20%，或者清理任务开始影响主库，我们就搬。"把决定挂在一个可测量的信号上，比争论谁的直觉对更有效——也让"以后要搬"这件事不会被遗忘。

顺带：这一季后面仍然要用 Redis（缓存、限流、锁），所以"引入 Redis"这个成本迟早会付。这时候把会话也放进去，边际成本确实低了很多。判断要看的是边际成本，不是绝对成本——这也是为什么同一个决定在不同阶段会有不同答案。

分页、动态查询与索引

这一部分排在缓存前面是刻意的：缓存不是慢查询的解药，是慢查询的止痛片。先把索引和分页做对，剩下的才轮到缓存——顺序反了，你会得到一个"平时很快、缓存一失效就雪崩"的系统。

商品列表是这个商店流量最大的页面，也是唯一一个可能被爬虫翻到第一万页的页面。第一季第 10 部分的 Q2 提过 keyset 分页，这里把它完整实现，并且把"怎么知道快不快"这件事一起讲了——因为不会读执行计划的话，索引优化就是在猜。

动态查询：Drizzle 的 $dynamic()

两个小技巧值得单独指出。limit + 1：多取一条就能知道有没有下一页，不用再发一条 count(*)——而 count 在大表上是全扫，经常比主查询还慢。行值比较 (a, b) < (x, y)：这是标准 SQL，语义正是字典序，而且 Postgres 能用它走复合索引；手工展开成 a < x or (a = x and b < y) 逻辑等价，但优化器不一定能用上索引。

索引：三条决定命中率的规则

规则说明
复合索引的列序等值条件的列在前，范围/排序的列在后。(published, created_at desc, id desc) 能同时服务 where published = true 和后面的排序；反过来 (created_at, published) 就用不上前缀。
部分索引create index … on products (created_at desc, id desc) where published = true。索引里只放已上架的商品——体积小得多，而且它天然表达了"我们只查这一部分"这个事实。
索引覆盖如果查询需要的列全在索引里，Postgres 可以只读索引不回表（Index Only Scan）。用 include (name, price_cents) 把展示用的列带上，代价是索引变大。先测量再上，这一条最容易过度优化。
深入 · ilike '%关键词%' 为什么用不了索引

B-tree 索引是按前缀有序的，所以 like 'abc%' 能用（定位到 abc 开头的区间），like '%abc%' 不能——开头是通配符，索引里没有任何一个区间对应"包含 abc"。数据库只能全表扫描，然后对每一行做字符串匹配。

第一季的搜索就是 ilike('%' + kw + '%')。商品表几千行时没人察觉，到几十万行时它会变成整个站点最慢的查询。

Postgres 的解法是 pg_trgm 扩展：把字符串切成三字母组（trigram），建 GIN 索引，于是"包含"也能走索引。

create extension pg_trgm;
create index products_name_trgm on products using gin (name gin_trgm_ops);

之后 name % '关键词'（相似度匹配）和 name ilike '%关键词%' 都能用上它。中文的效果比英文差一些（三字组切分对中文不理想），真要做中文搜索该上 pg_bigm 或全文检索，再往上就是独立的搜索引擎。但在"上专门的搜索服务"之前，trigram 索引能把你多撑很久。

思路提示

先分开看这两个需求，它们的代价完全不同。

总数：count(*) 在带筛选条件时是全扫（或全索引扫），几十万行上要几百毫秒。三种应对：

Q2你给 (published, created_at desc, id desc) 建了索引，但 EXPLAIN 显示还是 Seq Scan。列出你会依次检查的五件事。

思路提示

按从简单到复杂：

  1. 表太小。几千行的表上，全扫比走索引再回表更快，优化器的选择是对的。先确认表的真实规模——很多"索引没生效"的排查是在一个只有 200 行的开发库上做的。
  2. 统计信息过时。刚导入大量数据还没 ANALYZE，优化器以为表很小。跑一次 analyze products; 再看。
  3. 条件的选择性太低。如果 95% 的商品都是 published = true，那这个条件几乎不过滤任何行，走索引再回表反而更慢。这时该建的是部分索引（把 published 从索引列变成 where 条件），或者干脆接受全扫。
  4. 排序方向对不上。索引是 desc, desc，查询写的是 order by created_at desc, id asc——混合方向用不了同一个索引（Postgres 能反向扫整个索引，但不能只反其中一列）。
  5. 类型不匹配导致的隐式转换。where id = '123'（字符串比整数列）或者对列做了函数：where lower(name) = … 用不了 name 上的索引，要建表达式索引 on products (lower(name))。

调试手法：set enable_seqscan = off; 然后再 EXPLAIN ANALYZE。如果强制走索引之后更慢，说明优化器本来就是对的，问题不在索引；如果快很多，说明是统计信息或选择性估计出了问题。这个开关只用于诊断，绝不要留在生产配置里。

Q3有人说"这个列表页慢，加个 Redis 缓存就行了，不用折腾索引"。这句话在什么情况下是对的？在什么情况下会把问题变得更糟？

思路提示

对的情况：这个查询本身就无法再快（比如一个跨五张表的复杂聚合），且数据变化很慢，且能接受一定的陈旧。给它加缓存是合理的工程决定。

更糟的情况——而且这才是常态：缓存把一个"持续的性能问题"转换成了一个"偶发的可用性问题"。

具体机制是这样的：加缓存前，这个查询 800 ms，页面慢但每次都能出来，数据库负载平稳且可见。加缓存后，99% 的请求 5 ms，看起来治好了；但只要缓存失效——发布时改了版本号、Redis 重启、TTL 集中到期——全部流量在同一秒打到那条 800 ms 的查询上。数据库连接池瞬间打满，然后是全站不可用，而不只是这一个页面慢。

换句话说：缓存把慢查询的代价从"每次一点"攒成了"某一刻一次性爆发"。而爆发的时刻恰恰是系统已经不稳定的时候（重启、发布、故障），是最不该雪上加霜的时候。

所以顺序应该是：先让底下那条查询在没有缓存的情况下也能接受，再加缓存去削峰。这就是这一部分排在第 04 部分前面的全部理由。第 04 部分会给出缓存失效时的保护措施（互斥重建、TTL 抖动），但那些是补救，不是免罪符。

04

缓存：三种失效形态

Spring 有 @Cacheable 帮你把这层藏起来，Hono 没有。要自己写反而是好事——因为缓存的三种典型故障，恰恰都发生在那个注解替你隐藏的地方。

缓存的基本形态只有一种：先查缓存，没有就查库并回填（Cache-Aside）。二十行代码就能写完。真正需要学的是它的四种失败方式：查不到的东西反复穿透、热点键过期时全体涌向数据库、大批键同时过期、以及回填时把旧数据写了回去。

深入 · 进程内 single-flight 够不够

不够，但可能足够好。假设有 4 个实例，热点键过期时：没有 single-flight 是 500 个并发查询；有了进程内的，是 4 个——每个实例一个。

从 500 降到 4，问题基本解决了。要降到 1 得跨实例加锁（第 07 部分），但那意味着多一次 Redis 往返、多一套锁超时逻辑、以及"没拿到锁的实例要等多久"这个新问题。

为了把 4 变成 1 而引入分布式锁，我认为不划算——除非那条回源查询非常贵（比如几秒的报表聚合），4 个并发就能压垮数据库。判断标准很具体：实例数 × 单次回源成本，数据库扛不扛得住。扛得住就到此为止。

这是这一季反复出现的模式：先用最便宜的手段把问题削掉两个数量级，再评估剩下的那点值不值得处理。

失效：删，不要改

商品更新后，正确的动作是 DEL 缓存键，而不是 SET 成新值。理由有两条：并发下两个写入者 SET 的先后顺序无法保证（后写的可能反而是旧值）；而 DEL 是幂等的、无序的，谁先谁后都一样。代价是下一次读要回源一次，很便宜。

Q1上面用 {"hit":false} 这个信封表示"不存在"，而不是用某个特殊字符串当哨兵。这个选择背后的一般原则是什么？信封还能顺带解决什么问题？

思路提示

一般原则是：不要用"值域里的某个特殊值"表达"状态"。用 -1 表示没有、用空字符串表示 null、用某个魔法字符串表示未命中——这类设计的共同毛病是，总有一天那个特殊值会成为一个合法的业务值，而且出问题时极难排查。

信封顺带能解决三件事：

  • 细粒度的版本控制：信封里放 ver，读到不认识的版本就当未命中回源。比在键前缀里放版本更温和——不需要整批作废，可以逐个键自然过渡。
  • 可观测性：放一个 cachedAt，就能知道命中的数据有多旧。排查"用户说看到的是旧价格"时，这个字段能直接给出答案。
  • 过期不删的软过期：放一个 staleAfter，读到过了软过期时间的值就先返回它、同时后台异步刷新。这是击穿的另一种修法（图 4 中间那格提到的），而它需要信封才能实现。

代价是每个值多几十字节。相对于它换来的东西，这个价钱很便宜。

Q2图 4 下半部分那个窗口，有人提出"延迟双删"：改完库删一次缓存，等 500 ms 再删一次。这能解决问题吗？

思路提示

能缩小概率，不能消除。它的逻辑是：500 ms 之后，那个攥着旧值的读请求应该已经写完缓存了，再删一次就清掉了。

问题在于 500 这个数字凭什么。它必须大于"最慢的那次回源查询耗时"，而那是一个长尾分布——数据库偶尔抖一下，某次查询用了 2 秒，双删就漏了。调大间隔的话，缓存被无谓清空的时间变长，而且那个"稍后再删"的动作本身也可能失败（进程正好重启了呢）。

三个更实际的替代：

  • 接受它，靠 TTL 兜底。本项目的选择。TTL 5 分钟意味着最坏错 5 分钟，对商品描述完全可以接受。
  • 带版本号的条件写入：缓存值里存 updatedAt，回填时用 Lua 比较，只有比缓存里现有的新才写。能真正消除这个窗口，代价是多一次比较、并且要求数据里真有一个单调字段。
  • 让写入方来填（Write-Through）：改完库直接 SET 新值。但这引入了写入之间的顺序问题，通常更麻烦。

选择依据是这个数据错了会怎样：商品描述错 5 分钟没关系，库存显示错 5 分钟会让用户下单失败。所以真正的答案是——库存本来就不该走这套缓存（图 1 第三类）。大多数缓存一致性难题，追到最后是"这个数据不该缓存"。

思路提示

换来的是每一个决定都是显式的。@Cacheable 的默认行为里藏着几个你迟早要问的问题，而注解不会主动告诉你答案：Redis 挂了是抛异常还是回源（默认抛，要配 CacheErrorHandler 才降级）？null 缓不缓存（默认不缓，于是天然有穿透问题）？TTL 有没有抖动（没有）？并发未命中会不会击穿（会）？

换句话说：注解让你更快地写出一个带着这三种问题的缓存。它不制造问题，但它让问题更难被看见。

订单状态机

第一季图 12 里冒出来一个 pending_payment 状态，当时只说了"这不是缺陷，是如实建模"。这一部分把它变成一个完整的状态机——它是后面五个部分（超时关单、支付回调、乱序、Outbox、对账）共同的地基。

订单不是一条记录，是一个会随时间移动的东西。一旦有了外部系统和定时任务，就会有多个参与者同时想推动它：支付回调想把它推到已付，超时任务想把它推到已取消，用户想取消，客服想退款。谁赢？把答案写成一张表，而不是散落在十个 if 里。

深入 · 为什么用枚举而不是 smallint

用整数存状态（0=待支付，1=已支付…）省几个字节，代价是数据库里的数据不再自解释。半夜排查问题时，select status from orders where id = 8812 返回 3——你还得去翻代码才知道 3 是什么，而代码可能已经改过三版了。

Postgres 的 enum 类型有三个好处：占 4 字节（和 int 差不多）、查询结果直接可读、写入非法值会被数据库拒绝。最后一条是真正的价值——即使有人绕过应用直接跑 SQL，也写不进一个不存在的状态。

唯一的麻烦是加新状态需要一次迁移（alter type … add value）。这在 Postgres 里是安全且快速的，但注意：它不能在事务里执行（旧版本限制），而且不能删除已有的值。所以状态命名要想清楚再定。

唯一的入口

返回值是 "changed" | "already" 而不是 void，这一点很关键：调用方需要知道这次转移是不是真的发生了，因为"真的发生了"才应该触发副作用（发通知、扣库存、退款）。第 09 和第 10 部分全靠这个区分。

陷阱 · 所有状态写入都必须走这个函数

只要项目里还有一处 db.update(orders).set({ status: "paid" })，这套状态机就是装饰品。防线有三层：

  • 模块封装：orders 表定义不从 order/index.ts 导出，别的模块拿不到它（第一季第 07 部分那套边界规则）。
  • lint / review：搜索 set({ status，除了 transition.ts 都是可疑的。
  • 数据库触发器：极端情况下可以写一个 before update 触发器校验转移合法性。我一般不用——把业务规则放进触发器会让它难以测试和演进，但如果这个库有多个应用在写，它可能是唯一的办法。

Q1transitionTo 里既用了 for update 行锁，又在 UPDATE 上写了 and status = current 的条件。两个都要，是不是多余了？

思路提示

在这个函数里确实是冗余的——行锁已经保证了从 SELECT 到 UPDATE 之间没人能改这一行。但我仍然建议两个都写，理由有三：

  • 防止将来有人删掉 for update。那行 .for("update") 看起来像可以优化掉的东西（"加锁多慢啊"），条件 UPDATE 则明显是业务逻辑的一部分，不容易被误删。留着它，即使锁被拿掉，最坏结果是抛 ConcurrentTransition 而不是数据错乱。
  • 隔离级别可能被改。在 Read Committed 下 for update 会重新读到最新版本，行为符合直觉；换成 Repeatable Read，行为会变（可能直接报序列化错误）。条件 UPDATE 在任何隔离级别下语义都一样。
  • 它让并发冲突变成一个有名字的异常。rowCount !== 1 抛 ConcurrentTransition，调用方可以选择重试；而如果只靠锁，冲突会表现为"等待然后成功"，你永远不知道发生过冲突，也就没法在监控里看到它。

反过来，能不能只要条件 UPDATE 不要锁？可以，而且更快——但那样就没法在 UPDATE 之前读到 current.status 来做判断了，得改成"先无锁读一次、UPDATE 失败再重读判断是重复还是非法"。逻辑会绕一些，但在高并发下是更好的写法。本项目订单转移的并发度不高，选了更直白的版本。

Q2产品说要加一个"部分退款"：订单已付，退了其中一件商品，订单仍然有效。这个需求能塞进图 5 这个状态机吗？

思路提示

不能，而且硬塞会毁掉这个状态机。因为部分退款不是订单状态的变化，是订单某一行的状态变化——订单还是 paid，只是其中一个 order_item 被退了。

常见的错误做法是加一个 partially_refunded 状态。麻烦立刻来了：退第二件之后是什么状态？还是 partially_refunded？那怎么知道退到第几件了？全退完了要不要变成 refunded？状态机开始承载它表达不了的信息，于是各处又长出 if 来补。

正确的建模是引入第二个概念：退款单（refunds 表），它自己有状态机（requested → approved → refunded / rejected），并且关联到一个或多个 order_item。订单状态保持简单，"这个订单退了多少钱"是一个可以从退款单聚合出来的派生值，不是一个要维护的状态。

一般规律：当你想给状态机加一个形容词修饰的状态（部分…、临时…、待确认的…）时，通常是缺了一个实体。这个判断在建模上极其有用，值得记下来。

顺带：这也解释了为什么图 5 里的 refunding 是可疑的——它已经是"整单退款"这个简化假设的产物。真做起来，它多半也该变成退款单的状态而不是订单的状态。

Q3Spring 那一季在这里用的是 Java 枚举 + canTransitionTo 方法，本质和这里的 Record<OrderStatus, readonly OrderStatus[]> 一样。TypeScript 的类型系统能不能做得更多——比如让"非法转移"变成编译错误而不是运行时异常？

思路提示

能做一部分，而且很漂亮。用字面量类型可以让转移表推出一个精确的类型：

type Next<S extends OrderStatus> = (typeof ALLOWED)[S][number]

于是 transitionTo<"cancelled">(…, "paid") 编译不过——因为 ALLOWED["cancelled"] 是空数组，[number] 是 never。

但它救不了真正的场景。原因很直接：当前状态是从数据库读出来的，编译期不知道它是什么。你手里只有 OrderStatus 这个联合类型，编译器无法把它窄化到某一个成员，所以任何 OrderStatus → OrderStatus 的调用都得放行。

这正是第一季图 4 那条边界的又一次体现：类型只能约束你的代码内部，约束不了外部世界的取值。而"这个订单现在是什么状态"恰恰是外部世界的事实。

类型系统在这里仍有两个实在的贡献，值得用上：转移表必须穷尽所有状态（Record<OrderStatus, …> 少写一个键就编译不过，加新状态时不会漏），以及转移目标必须是合法的状态名（拼错 "payed" 立刻报错）。把类型用在"表本身的完整性"上，而不是幻想它能替代运行时检查——这是一个通用的分寸。

库存预占与超时释放

第一季的库存只有一列 stock，下单立刻扣。加上"先下单后支付"之后这样不行了——没付款的订单占着的货，既不能卖给别人，也不能算已经卖掉。需要第二个数。

这是这一季第一个真正的"时间"问题：一笔预占从产生到消失之间有一段可能长达半小时的空窗，而在这段时间里，系统必须同时对两件相反的事负责——不能超卖，也不能把货永远锁死。

深入 · 那两个 gte(reserved, qty) 是护栏，不是业务逻辑

正常情况下这两个条件永远成立——能走到转实扣，说明之前一定预占过。写上它们是为了让不该发生的事变成一个响亮的异常，而不是一个负数。

没有这层保护的话，某个 bug 导致重复释放，reserved 会变成 -3。而 stock - reserved 于是变大了——系统开始超卖，而所有 SQL 都执行成功了，监控上一片绿。这类"沉默地算错数"的故障是最难发现的一类，因为它不产生错误，只产生错误的数字。

更彻底的做法是在数据库层加约束：alter table products add constraint reserved_nonneg check (reserved >= 0 and reserved <= stock)。数据库拒绝写入是最后一道防线，它不依赖任何应用代码的正确性。凡是能表达成 check 约束的不变量，都应该写进去。

秒杀：Redis 只当闸门

第 01 部分 Q1 的答案在这里落地。大促时一件热门商品可能有上万请求同时打过来，全部去数据库做条件 UPDATE 会让那一行成为热点，请求排成长队。加一道 Redis 闸门：

闸门出错的方向后果可接受吗
闸门数字偏大（Redis 丢了扣减）更多请求打到数据库，数据库照样正确拒绝可以——只是慢一点
闸门数字偏小（多扣了）本来能买到的人被挡住，显示"已售罄"但实际有货不理想，但不出错账。定期用数据库的真实值重置闸门即可
闸门完全挂掉全部放行到数据库可以——退化成没有闸门的状态，正确性不受影响

三种错误方向都不会导致超卖，因为真正的判断始终在数据库那条条件 UPDATE 上。这就是"Redis 是性能优化，不是正确性保证"这句话的具体含义——它会在第 07 部分再出现一次。

Q1超时关单任务把订单从 pending_payment 改成 cancelled 并释放了库存。恰在同一时刻，支付回调到达说这笔钱已经付了。会发生什么？系统该怎么办？

思路提示

先看技术上发生了什么：两个事务都想改同一行订单，for update 让它们排队。先拿到锁的那个成功；后一个读到的已经是新状态。

  • 如果关单先赢：回调调用 transitionTo(paid)，当前状态是 cancelled，转移表里 cancelled → paid 不存在 → 抛 IllegalTransition。

  3. 准备好自动退款路径。对于"已取消但收到付款"这种情况，多数电商的处理是自动发起退款并通知用户。把它做成一个显式的流程，而不是等客服发现。

Q2如果不加 reserved 列，而是每次都用 select sum(qty) from order_items join orders where status = 'pending_payment' 算出预占量，行不行？

思路提示

逻辑上完全正确，而且它有一个很大的优点：不存在数据不一致的可能——预占量是算出来的，不是维护出来的，永远和订单表一致。图 6 右上角那条不变量会自动成立。

问题全在性能和并发上：

  • 每次判断库存都要跑一个跨表聚合。商品页、加购、下单都要判断，这个查询会成为最热的查询之一。
  • 更麻烦的是并发正确性：算出"预占 30"到执行 UPDATE 之间，别人可能又下了一单。这又回到了 check-then-act。要修就得锁住 orders 表的相关行，或者上 Serializable 隔离——两者代价都不小。

所以 reserved 列是一个典型的物化的派生值：用"可能不一致"换"可以原子判断"。这个交易在电商里几乎总是划算的。

但既然选了物化，就必须配上两件事：数据库层的 check 约束（前面说的 reserved between 0 and stock），以及定期对账——每小时跑一次那条聚合查询，和 reserved 列比对，不一致就告警。第 12 部分会把这个对账任务写出来。物化派生值必须配对账，这是一条没有例外的规矩。

Q3图 6 底部说键过期通知不可靠。那"定时轮询数据库找超时订单"就可靠吗？它的代价是什么？有没有第三种办法？

思路提示

轮询可靠，因为它的判据是数据库里的持久事实（created_at < now() - 30 min and status = 'pending_payment'）。进程挂了、重启了、漏跑了一轮，下一轮照样能找到那些订单。可靠性来自"状态可重建"，而不是来自"通知没丢"。这是图 1 那个问题的又一次应用。

代价有三个：

  • 延迟：轮询间隔决定了关单最晚会晚多久。1 分钟一轮通常够用。
  • 无效查询：大部分轮询会一无所获。加一个 (status, created_at) 的部分索引（where status = 'pending_payment'）之后，这个查询几乎不花钱——因为待支付订单在任何时刻都只有很少几条。
  • 多实例重复：这是第 07 部分要解决的。

第三种办法是延迟队列：下单时往一个有序集合里塞一条 (订单id, 到期时间戳)，工作进程轮询"到期时间 < 现在"的成员。它比全表轮询精确，延迟也更低。

但注意：如果这个有序集合放在 Redis 里，它就又变成"不能重建的状态"了——Redis 丢数据，那批订单就永远不会被关。所以要么把队列放在 Postgres 里（那和轮询订单表区别不大），要么保留数据库轮询作为兜底，Redis 队列只用来降低延迟。

这个"快路径 + 慢兜底"的组合是分布式系统里非常常见的模式：用不可靠但快的机制处理绝大多数情况，用可靠但慢的机制保证最终不漏。第 10 部分的 Outbox 也是同一个形状。

定时任务与分布式锁

第一季第 13 部分 Q3 提过一句：setInterval 在多实例下会跑 N 份。这一部分把它彻底解决，并且给出这一季最重要的一个结论——分布式锁不是正确性保证。

超时关单任务跑在三个实例上，就会有三份同时在扫同一批订单。直觉是"加把锁"，而这个直觉会把你引向一个比问题本身更微妙的东西。先看锁是怎么坏的，再决定要不要用它。

方案 ①：不抢锁，抢行

三个实例同时跑这段代码，结果是它们各自认领 100 条不同的订单——没有重复，而且吞吐是单实例的三倍。这比"选一个实例来跑、另外两个干等"好得多。

陷阱 · skipLocked 的两个前提

事务要短。被锁住的行在事务提交前一直锁着，别的实例一直跳过它们。如果一个批次要处理 5 分钟，这 5 分钟里这些行对其它实例是不可见的——万一这个事务最后回滚了，这 5 分钟就白等了。所以 batch 要小，宁可多跑几轮。

要有合适的索引。(status, created_at) 上的部分索引（where status = 'pending_payment'）是必需的，否则每轮轮询都是一次全表扫描——而这个任务每分钟跑一次。

方案 ②：Postgres 咨询锁

相比 Java 生态里的 ShedLock，这个版本少了一样东西：不需要 TTL。因为锁绑定在数据库连接上，进程崩溃时 TCP 连接断开，Postgres 立刻释放锁。图 7 那个双持有窗口在这里根本不存在——代价是这把锁只在一个数据库实例的范围内有效，而这对单库应用恰好足够。

深入 · Lua 比对只修好了一半

那段 Lua 解决的是"误删别人的锁"，这是真实且必须修的 bug。但它解决不了双持有——图 7 里 30 秒到 57 秒之间，A 和 B 确实在同时处理，而 Lua 脚本对此无能为力。

常见的补救是"看门狗"：后台定时给锁续期。在 Node 里这个补救格外脆弱——续期靠的是事件循环上的定时器，而事件循环被阻塞时，正是最需要续期的时候，定时器恰恰跑不了。看门狗和它要防的故障共享同一个失败原因。

所以这一部分的结论只能是：

Redis 锁是性能优化——它减少重复工作；它不是正确性保证。正确性必须由数据库的唯一约束、条件更新或状态机来兜底。

回头看第 06 部分的超时关单：即使没有任何锁，三个实例同时跑也是正确的——因为 transitionTo 用了行锁 + 条件更新 + 状态机，重复的那两个实例只会拿到 "already" 然后什么都不做。锁在那里的作用只是省掉重复查询，而不是防止数据错乱。这就是"正确性另有保证"的具体样子。

Q1如果 closeExpiredOrders 完全不加任何锁，三个实例同时跑会出什么错？请具体推演一遍。

思路提示

推演的结果是：不会出错，只会做重复的无用功。这正是这一部分想让你自己得出的结论。

逐步看：三个实例的 select … for update skip locked 会认领不同的行（这一步本身就防住了重复）。就算把 skipLocked 也去掉、改成普通 select，最坏情况是三个实例都读到同一批订单，然后：

  • 实例 B 在同一行上等锁，A 提交后 B 读到状态已是 cancelled，返回 "already"，不释放库存。
  • 实例 C 同理。

库存只被释放一次。数据完全正确。

代价是三倍的数据库查询和三倍的锁等待——这是性能问题，不是正确性问题。而这恰好就是"锁是性能优化"这句话的完整含义：加锁能省掉那两份无用功，但不加锁也不会错。

反过来问一句更有价值：如果去掉 transitionTo 里的状态检查，只保留锁，会怎样？那么锁一旦失效（图 7 那个场景），库存就会被释放两次，reserved 变成负数，开始超卖。说明真正在保护你的从来不是锁。

Q2图 7 说 Node 的事件循环阻塞对应 Java 的 GC 停顿。但 Node 是单线程的，这个差别会让问题更严重还是更轻？

思路提示

两个方向都有，需要分开看。

更严重的一面：Java 的 GC 停顿是运行时行为，你很难主动制造一次 27 秒的停顿；而 Node 的事件循环阻塞是你自己的代码造成的，而且非常容易写出来——一个 JSON.parse 解析 50 MB、一个 bcrypt.hashSync、一个对十万条记录的同步排序。门槛更低，所以更容易发生。

而且它的影响面更大：阻塞期间这个实例什么都做不了——不响应 HTTP、不发心跳、不续锁、健康检查也超时。在 Java 里至少还有别的线程在跑。

更轻的一面：正因为原因是你自己的代码，它是可以被消除的。定位手段也很直接：--trace-sync-io、事件循环延迟指标（perf_hooks 的 monitorEventLoopDelay）、以及在关键路径上禁用同步 API。相比之下 GC 停顿只能调优不能消除。

实践上该做三件事：把事件循环延迟做成一个监控指标并设告警（p99 超过 100 ms 就该查）；把 CPU 密集的活挪进 worker threads；以及——回到本部分的主题——不要把正确性建立在"我的进程一直在响应"这个假设上。

Q3本部分推荐 Postgres 咨询锁而不是 Redis 锁。但如果将来任务需要协调的资源不在数据库里（比如"同一时刻只能有一个实例在调用某个外部 API"），咨询锁还合适吗？

思路提示

技术上完全可以用——咨询锁的名字是任意字符串，锁什么和数据库无关。但这时值得停下来想一想故障域。

用咨询锁意味着：数据库挂了，这个和数据库无关的外部调用也停了。这可能是好事（数据库挂了你多半也不该继续调外部 API），也可能是坏事（这个任务本来能独立运行）。选锁的位置，本质上是在选"什么东西挂了，这件事就该停"。这个问题比"哪种锁更快"重要得多。

更关键的一点：题目里"同一时刻只能有一个实例调用外部 API"这个需求本身要仔细审视。如果重复调用会造成重复扣款，那么靠锁来防是错的——因为图 7 已经证明了锁会失效。正确的办法是幂等键：每次调用带一个业务上唯一的 key，对方保证同一个 key 只生效一次。这正是第 08 和第 09 部分的主题。

那锁还有什么用？限制并发度——对方的接口只允许每秒 10 次调用，你用锁或信号量来遵守这个约定。这是一个"违反了会被限流，但不会算错账"的场景，正是锁适合的地方：它优化行为，不承担正确性。

陷阱 · 没有超时的 fetch 会永远等下去

fetch 默认没有整体超时。Node 的 undici 有 headersTimeout 和 bodyTimeout 的默认值，但它们以分钟计，而且不覆盖"对方每隔 10 秒发一个字节"这种慢速拖死的情况。

后果是：对方挂起，你的请求也挂起，占着连接池的一个位置、占着一个 Promise、占着这个用户的浏览器标签。几百个这样的请求就能让实例失去响应能力——而这不需要对方"挂掉"，只需要它"变慢"。慢比挂更危险，因为挂掉会立刻报错，变慢会拖着你一起沉。

所以规矩是：每一个出站请求都必须有超时，没有例外。可以用 AbortSignal.timeout()，也可以在 Agent 上配；两者一起配最稳妥，因为它们管的层次不同。

Q1幂等键该用什么值？订单 id 行不行？crypto.randomUUID() 呢？

思路提示

关键判据：幂等键必须在"同一次业务意图"内保持不变，跨意图必须不同。

  • 每次调用生成新 UUID：错得最彻底。重试时 key 变了，对方认为是一笔新支付，扣两次。这完全违背了幂等键的目的。
  • 用订单 id：接近正确，而且有一个大优点——它天然稳定，进程重启后仍能算出同一个 key。但要小心"同一个订单需要付两次"的场景（第一次支付失败后用户换了张卡重新支付）。这时用订单 id 会被对方当成重复请求拒绝。
  • 用"支付尝试" id：最稳妥。为每次支付尝试在自己库里建一行 payment_attempts，把它的 id 当幂等键。同一次尝试的所有重试共享它；用户重新发起支付则是一次新尝试、新 key。

而且这张表还顺带解决了另外两个问题：它是超时之后去查询"这笔到底成没成"的凭据（图 8 规则 ③），也是第 12 部分对账任务的数据来源。一张表换三个能力，很划算。

最后一个细节：幂等键要有有效期的意识。多数支付平台只保证 24 小时内的幂等。所以"三天后重试同一个 key"可能会真的扣第二次——这也是为什么长时间未决的支付应该走查询而不是重试。

Q2熔断器的状态存在进程内存里。三个实例就有三个独立的熔断器。这是问题吗？要不要把状态放进 Redis 共享？

思路提示

大多数情况下不是问题，而且进程内反而更好。

理由是熔断器统计的是"我调用对方的失败率"，而这个数字本来就有实例间的差异：某个实例可能在一个网络分区里、可能连到了对方的一个坏节点。让每个实例独立判断，反而更准确地反映了它自己的处境。

而且共享状态引入了新问题：多一次 Redis 往返（在每个出站请求的路径上）、Redis 挂了熔断器怎么办、以及一个实例的异常观测会导致所有实例一起断开。你为了协调一致性，换来了一个新的单点。

进程内的代价是：故障发生时，每个实例都要独立"交学费"（各自失败几次才打开）。实例数不多时这个代价很小。

什么时候该共享：实例数非常多（几十上百）时，每个实例的样本量都不够统计出可靠的失败率，而且"每个实例各自试探"加起来就是一波不小的流量。那时可以考虑把统计放到共享存储，或者用更简单的办法——降低单实例的失败阈值。

顺带：这个判断和第 04 部分 single-flight 那个"要不要跨实例"的判断是同一个模式。先问"进程内够不够好"，再问"值不值得为剩下那点收益引入协调"。

Q3你为支付网关配了 8 秒超时。而用户点击"支付"之后浏览器在等这个请求。8 秒是个合理的数字吗？该怎么定？

思路提示

这个数字应该从两头夹出来。

下界来自对方的实际耗时分布：如果对方的 p99 是 3 秒，超时设成 2 秒会让 1% 的正常请求变成"不知道"——而每一个"不知道"都要走查询或对账流程，成本很高。超时设得太短，会把一个性能问题变成一个正确性问题。合理起点是 p99.9 再留点余量。

上界来自用户和调用链：浏览器等 8 秒已经很久了；如果你前面还有网关、负载均衡，它们各自的超时必须大于你的超时，否则它们会先掐断，你的重试和错误处理根本没机会跑。整条链路的超时必须从外到内递减——这是最常被配错的一件事。

但更重要的是换个设计：让用户不必等。第一季图 12 已经把支付调用移出了事务，这里可以再进一步——下单后立刻返回一个"支付处理中"的页面，支付结果通过回调（第 09 部分）异步到达，页面轮询或用 SSE 推送。

这样超时可以设得更从容（比如 15 秒），用户体验反而更好，因为他看到的是明确的进度而不是一个转圈的按钮。很多"超时该设多少"的难题，本质是"这件事不该同步做"。

09

异步回调与幂等

支付网关处理完之后，会往你的 POST /webhooks/payment 发一条通知。这个端点是整个系统里最不受你控制的入口：调用方是别人，重试策略是别人定的，顺序没有保证，而且它直接决定钱和货的归属。

回调处理的正确性由五道闸串起来，缺一道就有一类事故。这五道闸有一个共同特征：它们各自只挡一种问题，而且不能互相替代。最常见的错误是以为"我做了幂等"就万事大吉——幂等挡的是重复，挡不住乱序。

陷阱 · 这个路由必须避开所有读 body 的中间件

第一季第 08 部分讲过：请求体是一次性的流。如果全局挂了一个"记录请求体用于审计"的中间件，或者某个中间件调用了 c.req.parseBody()，那么这里的 arrayBuffer() 就拿不到原始字节——签名永远校验失败，而错误信息只会说"签名不对"，你会去查密钥、查算法、查编码，查上半天。

同样要小心的是反向代理或框架的 body 解析会不会改动字节（比如重新格式化 JSON）。把 webhook 路由挂在一棵干净的子树上、并写一个测试断言原始字节能被读到，是很划算的两分钟。

深入 · 什么时候该回 200，什么时候该回 5xx

回调的返回码是在指挥对方的重试行为，所以要按"希不希望它重发"来选，而不是按"我处理得顺不顺利"来选：

  • 处理成功 → 200。
  • 重复投递 → 200。已经处理过了，重发没有意义。
  • 签名错误、时间戳过期 → 401 / 400。这不是暂时性问题，重发一百次也一样；而且如果这是攻击，你更不希望它被重试。
  • 你自己的数据库挂了 → 500。这是唯一真正需要对方重发的情况——事件是合法的，你只是暂时处理不了。
  • 金额不匹配、状态机拒绝 → 这里要小心。我建议回 200 并告警，因为让对方无限重发一个永远处理不了的事件没有意义，只会让你的错误日志被刷屏，掩盖真正需要重发的那些。把它记进人工队列，比让它在重试队列里循环三天有用得多。

Q1幂等用的是 insert … on conflict do nothing。为什么不先 select 查一下这个 event_id 处理过没有，没有再插？

思路提示

因为"先查再插"是 check-then-act（第一季图 13）。支付网关在没收到 200 时会重发，而重发和原请求很可能同时到达（比如你的第一次响应慢了 5 秒，网关在第 5 秒重发，两个请求现在并行）。两个都查到"没处理过"，两个都往下走，订单被处理两次。

唯一索引是数据库层面的原子判断：无论多少个并发，只有一个能插进去。on conflict do nothing 加上 returning 让你能知道自己是不是那个赢家。

还有两个细节值得注意：

  • 这条 insert 必须和后面的业务处理在同一个事务里。如果先提交幂等记录再处理业务，业务处理失败回滚后，重发的请求会被幂等表挡住——这笔支付就永远丢了。
  • 反过来，如果业务处理很慢，这个事务会持有很久。所以要么处理足够快，要么把重活扔进 Outbox（第 10 部分），事务里只做状态转移。本项目选后者。

一个额外好处：webhook_events 表把原始 payload 存下来了。出问题时可以完整重放，这在和支付方对账扯皮时极其有用。记得给它加保留期清理，否则它会变成库里最大的表。

Q2支付网关说"我们保证至少投递一次"。这句话具体给了你什么承诺，又没有给你什么？

思路提示

给了你一条：只要你一直返回非 200，它会一直重发（在重试策略的期限内）。所以事件不会因为你临时挂了而丢失。

没给你的至少有四条，每一条都对应一个必须自己做的设计：

  • 没有"最多一次"：所以你必须幂等（闸 ④）。
  • 没有顺序保证：所以你必须有状态机（闸 ⑤）。
  • 没有时限保证：一条事件可能几秒后到，也可能因为对方积压几小时后到。所以不能假设"没收到回调就是没成功"——这正是图 8 规则 ③ 那个查询接口存在的理由。
  • 没有"你一定收得到"：如果你的服务连续挂了超过对方的重试期限（通常是三天），那条事件就真的丢了。所以必须有对账：定期把自己库里"还在 pending_payment"的订单拿去问对方，第 12 部分会写这个任务。

把这四条并排看，会发现一个规律："至少一次"这个承诺，把所有关于正确性的责任都推给了接收方。这不是支付网关偷懒——在分布式系统里，"恰好一次"投递本身就是不可实现的，能做的只有"至少一次投递 + 接收方幂等"。理解了这一点，第 10 部分的 Outbox 为什么长成那样就很自然了。

Q3回调处理里要发一封"支付成功"的邮件。直接在这个事务里调邮件服务行不行？如果不行，放在事务提交之后行不行？

思路提示

事务里调：不行，理由是第一季图 12——外部调用会把数据库连接和行锁占住几百毫秒，而这个事务锁着订单行。更糟的是邮件服务超时会导致事务回滚，于是一笔已经成功的支付被回滚了，就因为邮件没发出去。这个因果关系荒谬但真实存在。

事务提交之后调：好一些，但仍然有一个窗口——事务提交了，进程在调邮件服务之前崩溃了。这封邮件就永远不会发。

用户收不到邮件严不严重？取决于内容。"支付成功通知"丢了可能可以接受；但如果是"发货通知"或者一个包含取货码的邮件，丢了就是事故。而且你不会知道它丢了——没有任何记录说明"这封邮件本该发出"。

正确的做法是把"要发这封邮件"这件事作为数据写进同一个事务：往 outbox 表插一行。事务提交 = 意图被持久化了；投递失败可以重试，进程崩了下次启动会捡起来。这就是第 10 部分整章的内容，而它的动机就是这道题。

顺带一个判断标准，可以用在所有"要不要走 Outbox"的场合：如果这个副作用丢了，有没有任何机制能发现？没有的话，它就必须先落库。

10

事件、Outbox 与通知

第 09 部分 Q3 留下的问题：支付成功要发邮件、要通知仓库、要更新统计。这些副作用不能放进事务，放在事务之后又可能丢。这一部分给出那个既不放进去也不丢掉的做法。

问题有一个名字叫双写：你要同时改两个系统（数据库 + 消息/邮件），而这两次写入无法组成一个原子操作。无论先写哪个，中间崩溃都会留下不一致。这不是实现技巧问题，是没有分布式事务时的固有约束。

陷阱 · 投递放在事务里，事务就长了

上面这段代码把 deliver()（一次网络调用）放在了事务内——这正是第一季图 12 警告过的事。50 条 × 每条 200 ms = 10 秒的事务，持有 50 行的锁。

之所以还这么写，是因为它换来了一个重要性质：行锁保证了这一批不会被别的实例同时处理。这是一个真实的取舍，不是疏忽。三种改法：

  • 批次调小（10 条）、投递超时调紧（2 秒）。最简单，通常够用。
  • 两阶段：先用一个短事务把这批标记成 claimed_by = 实例id, claimed_at = now()，事务结束；然后在事务外投递；再用短事务标记完成。代价是要处理"认领了但没投递完就崩了"——靠 claimed_at 超时回收。
  • 并发投递：Promise.allSettled 一批一起发。事务时长变成最慢那一条，而不是总和。投产环境我会选这个 + 小批次。
深入 · 为什么不用 EventEmitter

Node 自带 EventEmitter，写起来最舒服：events.emit("order.paid", { orderId })。但它解决不了这一部分的问题，因为它只是一次函数调用：

  • 监听器在同一个进程、同一个事件循环里跑。进程崩了，事件就没了——和图 11 顺序 A 完全一样。
  • 没有重试。监听器抛异常就抛异常了，没有任何东西记得这件事没做成。
  • 更阴险的一点：emit 是同步的。如果监听器是 async 函数，emit 不会等它——异常变成未处理的 Promise rejection，默认会让进程退出。

那 EventEmitter 有什么用？用于进程内的、丢了也无所谓的解耦：打点、更新一个内存里的指标、刷新一个本地缓存。判据还是第 09 部分 Q3 那条：这个副作用丢了，有没有机制能发现？没有就必须走 Outbox。

降低延迟：LISTEN / NOTIFY

每秒轮询意味着通知平均晚 500 ms。可以用 Postgres 的 NOTIFY 把它降到几毫秒：写完 outbox 后 notify outbox_new，轮询器 LISTEN 到就立刻跑一轮。

陷阱 · NOTIFY 是加速器，不是队列

NOTIFY 的消息不持久化：没有连接在监听时发出的通知直接丢弃；连接断开重连期间的通知也补不回来。用它当唯一触发源，就回到了图 6 底部那个"键过期通知"的老问题。

正确用法是快慢结合：NOTIFY 负责让常见情况快（几毫秒），定时轮询负责保证不漏（每 5 秒兜一次）。这个组合在第 06 部分 Q3 出现过一次，在这里又出现一次——它是分布式系统里最实用的模式之一，值得单独记住。

什么时候该换成真的消息队列

信号为什么 Outbox 撑不住了
投递量超过每秒上千条轮询和行锁的开销开始占用数据库的可观份额，而这个数据库还要服务在线请求。
出现了多个独立消费者同一个事件要被三个团队各自消费，各有各的进度和重试。用 outbox 表做就得给每个消费者一份进度表——你正在手工实现消费组。
消费方不是你的服务跨团队、跨组织时，让对方来轮询你的数据库表是不可接受的耦合。这时需要一个双方都认的协议边界。

三条都没命中之前，Outbox 是更好的选择——它少一个需要运维的组件、少一个故障域，而且所有状态都在你能用 SQL 查询的地方。真要换的时候，Outbox 也不会白写：它本来就是往 MQ 投递的标准前置模式（先落 outbox，再由 relay 发到 MQ）。

Q1Outbox 保证至少一次，所以"支付成功"邮件可能发两封。怎么让它实际上只发一封？

思路提示

责任在消费方，也就是投递逻辑那一侧。三个层次，按可靠性递增：

  • 投递前查一下：select from notifications where outbox_id = ?。这是 check-then-act，两个实例并发时会漏——但配合 skip locked，同一行不会被两个实例同时处理，所以实际上够用。它防的是"崩溃后重投"，不是并发。
  • 唯一索引：notifications 表上 (outbox_id) 唯一。先插记录再发邮件，插不进去说明发过了。这是第 09 部分闸 ④ 的同一招，用在了发送侧。
  • 让下游幂等：多数邮件服务商支持 Idempotency-Key，传 outbox 行的 id 即可。这是最干净的做法——你不需要维护任何本地记录，重复由对方消解。

但有一个更实际的问题要先问：这封邮件发两封，代价有多大？用户收到两封"支付成功"通知，尴尬但无害。相比之下，"扣一次款"发两次是灾难。

所以我的建议是按副作用的性质分级：涉及钱和库存的，必须走唯一索引；纯通知类的，用下游幂等键，做不到就接受偶尔重复。为一封可能重复的邮件设计一套复杂的去重机制，是把成本花错了地方。

Q2Outbox 表会一直增长。已发送的行要删吗？删了会怎样，不删会怎样？

思路提示

要删，但不能立刻删，也不能用简单的 delete。

不删的后果：表会长到几千万行。查询本身不受影响（部分索引只包含 sent_at is null 的行，永远很小），但表本身占磁盘、拖慢备份、让 VACUUM 变贵。

立刻删的后果：丢掉了排查能力。"用户说没收到邮件"时，你想知道那条 outbox 记录存不存在、投递了几次、报了什么错。这些信息在事故排查时价值极高，删早了就没有了。

实践做法：保留 7～30 天，然后按批删除。要点在"按批"——

  • delete from outbox where sent_at < now() - interval '30 days' 一次删几百万行，会长时间持锁、产生巨量 WAL，可能把主库拖垮，还会拖累复制。
  • 正确写法是循环小批：delete from outbox where id in (select id from outbox where sent_at < $1 limit 5000)，每轮之间停一下。
  • 更好的方案是按时间分区：outbox 按月分区，过期直接 drop partition——瞬时完成，不产生 WAL，不需要 VACUUM。数据量大时这是唯一优雅的办法。

这条经验适用于所有"只增不减的日志型表"：webhook_events、order_status_changes、审计表。建表的时候就该想好它怎么删——等到它有一亿行时再想，选择余地会小很多。

不能保证，有两个原因：

  • 多实例并行：skip locked 让实例 A 拿到 order.paid、实例 B 拿到 order.shipped，两边同时投递，谁先到达下游取决于网络。
  • 失败重试：即使单实例，order.paid 投递失败要重试，而 order.shipped 在下一轮成功了——顺序就反了。
  • 还有一个更隐蔽的：id 的分配顺序不等于提交顺序。事务 A 先拿到 id=100，事务 B 后拿到 id=101，但 B 先提交。轮询器在这一刻只能看到 101，会先发它。

要保证同一订单内有序，标准做法是按聚合键串行化：给 outbox 加一列 aggregate_id（订单 id），投递时保证同一个 aggregate_id 的行不被并行处理——可以用咨询锁（第 07 部分），也可以在认领时排除"这个 aggregate 还有更早的未发送行"的情况。

但更值得问的是：下游真的需要有序吗？如果下游的处理是幂等的、并且用状态机保护（第 05 部分），那么乱序到达是安全的——shipped 先到会被状态机拒绝，等 paid 处理完再重试 shipped 就好了。

让消费方能容忍乱序，几乎总是比让投递方保证有序更便宜。因为保证有序意味着放弃并行、增加延迟、并且在一条消息卡住时阻塞它后面所有的消息——那个"队头阻塞"的代价通常比重试几次大得多。

限流与防刷

第一季第 09 部分提过一句"登录要按邮箱和 IP 两个维度限流"，当时没有 Redis 没法做。这一部分补上——顺便说清楚三种限流算法各自会在什么地方漏。

限流的目的有两个，而它们对算法的要求不同：保护自己（别被打垮）容忍短时突发，只关心平均速率；阻止滥用（撞库、刷券、爬数据）恰恰要卡住突发。选错算法，你会得到一个"看起来在限流、实际拦不住攻击"的中间件。

两个维度都要，因为它们挡的是两种不同的攻击：只按 IP 限，攻击者用代理池就绕过了；只按邮箱限，攻击者用一个常见密码去试一万个邮箱（密码喷洒）完全不受影响。

安全 · X-Forwarded-For 是可以伪造的

c.req.header("x-forwarded-for") 里的内容完全由客户端控制——直接拿它当客户端 IP，攻击者每个请求换一个假 IP，限流就形同虚设。更糟的是如果你把这个"IP"写进封禁名单，攻击者可以伪造成别人的 IP，让你封掉真实用户。

正确做法：X-Forwarded-For 是一个逗号分隔的链，只有最靠右的、由你自己的可信代理追加的那几段才可信。所以你必须知道自己前面有几层可信代理（记为 N），然后取倒数第 N+1 个。

const parts = xff.split(","); const ip = parts[parts.length - 1 - TRUSTED_PROXIES]?.trim();

这个 TRUSTED_PROXIES 必须是配置项，因为它随部署拓扑变化——本地开发是 0，套了一层 CDN 加一层负载均衡就是 2。配错的方向也很关键：配大了会取到客户端伪造的段（危险），配小了会取到自己代理的 IP（限流失效但不危险）。拿不准时宁可配小。

限流的用途Redis 挂了该怎么办理由

登录、改密码、发短信拒绝（或降级到进程内计数）放行等于在故障期间关闭了防爆破。而攻击者恰恰会挑这种时候

判据是第 06 部分那条的翻版：出错的方向是"慢一点"还是"错一笔"。前者放行，后者拒绝。第 13 部分会把整个系统的这类决定汇总成一张表。

还有一个折中方案值得知道：降级到进程内限流。Redis 不可用时，每个实例用本地内存计数，限额除以实例数。它不精确（实例间不共享），但比完全放开好得多，而且实现只要几行。

思路提示

最多 5000 个成员，每个成员是一个 UUID（36 字节）加一个分数（8 字节），加上 ZSET 的跳表开销，大约 400 KB 一个 key。一万个活跃 IP 就是 4 GB——只为了限流。

而且还有第 01 部分 Q2 那个问题：ZREMRANGEBYSCORE 清理几千个成员是一次相对耗时的操作，而 Redis 是单线程的，这条命令执行期间所有其它客户端都在等。

所以滑动窗口只适合低频接口。高频接口的三个替代：

  • 令牌桶：无论限额多大，永远只存两个数字。这就是图 12 右边那格适合"浏览、搜索"的原因。
  • 固定窗口：接受边界突发。对"保护自己"这个用途，2 倍突发通常无所谓——你的容量规划本来就该有余量。
  • 滑动窗口计数器（不是日志）：只存当前窗口和上一个窗口的计数，按时间加权估算。精度介于两者之间，存储和固定窗口一样小。这是很多商业限流器的默认实现。

顺带把成员改短也有帮助：用 now-随机数 而不是完整 UUID 能省一半内存。但这治标不治本——数量级不对的时候，优化常数没有意义。

Q2限流返回 429，前端收到后立刻重试。这会让情况变好还是变坏？服务端能做什么？

思路提示

变坏，而且这正是第 08 部分图 9 那个"重试放大"在自己身上的翻版：你告诉客户端"太多了"，客户端的回应是发得更多。

服务端能做三件事：

  • 返回 Retry-After 头（上面代码里那个）。它明确告诉客户端"等 N 秒"，规范的客户端会遵守。这是最便宜也最有效的一步。
  • 让 429 的响应尽可能便宜：不查数据库、不渲染完整页面、不写详细日志（否则日志本身会成为放大器）。被限流的请求应该在最外层就被挡掉。
  • 对持续违规者升级处置：连续触发限流 N 次的 IP，直接进一个短期黑名单，后续请求在更早的位置（甚至在 CDN / WAF 层）被拒。让攻击者的成本上升得比你快。

但最根本的一条是：限流不能只在应用层做。如果攻击流量已经打到你的 Node 进程，即使每个请求只花 1 ms，几万 QPS 也会把事件循环占满——你的正常用户照样受影响。真正的防线是分层的：CDN/WAF 挡掉明显的恶意流量，负载均衡做粗粒度限速，应用层只做业务语义的限流（"这个账号五分钟内只能试五次密码"）。

应用层限流的价值不在于扛住 DDoS，而在于表达业务规则——这一点想清楚了，就不会指望它做它做不到的事。

Q3限流的 key 用什么？IP、用户 id、还是两者都用？对一个已登录用户和一个匿名用户，策略应该一样吗？

思路提示

不一样，而且差别很大——因为身份的可信度不同，滥用的成本也不同。

  • 匿名用户只能按 IP 限，而 IP 是廉价的（代理池、移动网络的 NAT）。所以匿名限额应该紧，而且要接受"一个办公室共用一个出口 IP"这种误伤——这也是为什么很多站点会在触发限流时弹验证码而不是直接拒绝，给误伤的人一条出路。
  • 已登录用户可以按用户 id 限，这个身份要贵得多（注册要邮箱/手机号）。所以限额可以宽松，而且违规时的处置可以更重（封号）。
  • 两者都用是常见做法：按 user id 限单个账号的行为，同时按 IP 限"一个 IP 后面有多少账号在活动"——后者能抓到批量注册的小号。

还有两类 key 容易被忽略但很有用：按目标资源限（"同一个商品的库存查询每秒不超过 X 次"，防止热点）、按操作的稀缺性限（"这张优惠券全局每秒只能核销 100 次"）。后者其实已经不是限流，是配额——但用同一套机制实现。

最后提醒一句：限流的 key 里不要放用户可以随意变化的东西。比如按 User-Agent 或某个请求参数限流，攻击者改一下就绕过了。key 必须绑定在某种有成本的身份上，这是限流有效性的前提。

Q1图 13 的指标那一行特意标了"不带 requestId"。为什么指标不能带？如果带了会发生什么？

思路提示

因为指标系统是按标签组合存储时间序列的：每一个不同的标签组合就是一条独立的序列，各自占内存、占磁盘、占查询时间。这叫基数。

http_requests{route="/checkout", status="200"} 是一条序列。加上 requestId 之后，每一个请求都会创建一条新序列——每天一百万请求就是一百万条序列，而且它们永远不会再被写入第二个点。

后果是监控系统被撑爆（这有个专门的名字叫"基数爆炸"），查询变慢甚至崩溃。而且这通常不是缓慢恶化，是某次发布之后几小时内就出事。

规则：指标的标签只能是有限枚举——路由名（注意是路由模板 /products/:id，不是实际路径 /products/8812）、状态码、错误码、方法名。用户 id、订单 id、requestId、URL 全路径、IP，都不行。

那需要"某个具体请求的细节"怎么办？这正是三种信号分工的意义：指标回答"整体怎么样"（低基数、可聚合），日志回答"这一次发生了什么"（高基数、可搜索），链路追踪回答"这一次经过了哪些服务"。用错了工具，代价是把监控系统搞垮。

Q2图 13 下半部分第五条要和支付网关对账。这个任务具体怎么写？发现不一致时该自动修复还是只告警？

思路提示

写法：遍历自己库里"最近 24 小时内、状态仍是 pending_payment、且创建时间超过 30 分钟"的订单，拿 payment_attempts 里的凭据去调网关的查询接口（图 8 规则 ③），比对结果。反向也要做：拿网关的对账文件（多数支付方每天提供）比对我们这边是否都已入账——这一侧能发现"我们完全没收到过任何回调"的那些。

自动修复还是告警，按不一致的方向分：

  • 网关说成功，我们是 pending_payment：回调丢了。这个方向可以自动修复——走和回调完全相同的那段代码（transitionTo(paid) + 转实扣 + Outbox），因为那段代码本来就是幂等的。复用回调路径而不是新写一套，是这里的关键：新写一套意味着两条路径要各自维护，迟早会不一致。
  • 网关说失败/不存在，我们是 paid：绝不自动修复。这意味着我们凭空把一笔订单标成了已付——可能是伪造的回调（签名校验漏了？）、可能是代码 bug、也可能是网关那边的数据问题。把一个 paid 订单自动改回去，可能让一个真实付款的用户拿不到货。必须人工介入。
  • 金额不一致：一律人工。这是最严重的一类。

一般原则：自动修复只能用于"补做一件本来就该做的、且幂等的事"；凡是需要撤销已发生的事，都必须人工。这条原则也适用于这一季所有的对账场景。

最后一点：对账任务本身要有指标——"上次成功运行时间"和"本次发现的不一致条数"。一个悄悄挂掉的对账任务，比没有对账任务更危险，因为它给了你虚假的安全感。

Q3不变量核对该多久跑一次？跑得太频繁会给数据库压力，太稀疏又发现得晚。怎么定？

思路提示

按"错了多久会造成不可挽回的损失"来定，而不是按"查询有多贵"来定。逐条看：

  • 金额不一致：钱的问题，而且一旦发货就难以挽回。高频，甚至可以做成写入时的实时校验——在下单事务里加一句断言，或者干脆做成数据库的 check 约束/触发器。
  • Outbox 积压：几分钟内没发出的通知影响体验，几小时就是事故。做成指标 + 告警，而不是定时任务——它天然就是一个可以持续观测的量。
  • 预占泄漏：影响可售库存，但通常偏差很小、增长很慢。每小时一次足够。
  • 支付对账：受制于网关的接口速率限制，而且用户等着拿货。每 15 分钟扫一次近期的，每天做一次全量对账。

还有两个实用技巧：

把重的核对改成增量的。"reserved 等于聚合值"如果全表跑要几分钟，可以只核对最近有变动的商品（where updated_at > 上次核对时间）。全量的那次放在低峰期。

让核对跑在只读副本上。这些查询都是只读的、可以容忍轻微延迟的，放在副本上就完全不影响主库——于是"太贵所以不敢频繁跑"这个约束基本消失了。

最后强调一遍：不变量核对是这一季所有内容里，投入产出比最高的一项。它便宜（几条 SQL）、它抓的是最难发现的一类问题，而且它逼你把"这个系统里什么必须永远成立"想清楚——这个思考过程本身就值回票价。

  2. 断开 Redis（先用防火墙丢包，模拟"连不上但没报错"这种更难处理的情况；再用直接停进程模拟明确的连接拒绝）。
  3. 走一遍主流程：浏览、加购、登录、下单、支付回调。记录实际表现。
  4. 比对预测和实际。差异就是这张表要修的地方，也是最有价值的产出。
  5. 恢复 Redis，观察系统能不能自愈——很多系统挂得住却恢复不了，比如连接池没有重连、熔断器不再关闭、缓存被穿透打死。这一步经常比第 3 步发现的问题更多。

两个模拟方式的差别值得强调："丢包"比"停进程"难处理得多。停进程会立刻返回 ECONNREFUSED，你的 catch 马上生效；丢包会让每个请求都卡到超时（第 01 部分那个 commandTimeout: 500 就是为它准备的），如果超时配得太长或者没配，整个系统会被拖死——而这才是真实故障里更常见的形态。

Q1图 14 显示会话这一格无法降级。如果这个风险不可接受，有哪些改法？各自的代价是什么？

思路提示

四种，代价递增：

  • 退回 PostgreSQL 存会话（第一季的方案）。风险归零，代价是第 02 部分列的那两条收益也没了。如果你的规模没到，这就是正确答案。
  • 双写：Redis 为主，Postgres 为备；Redis 读不到就回源到 Postgres 并回填。风险基本消除，代价是每次登录多一次写、以及两边一致性的维护。
  • Redis 高可用（哨兵或集群）。降低了"完全不可用"的概率，但没有消除——切换期间仍有几秒到几十秒的不可用，而且图 1 的窗口 ③ 会让部分会话丢失。它把"必然发生的故障"变成"小概率的故障"，不是"不会发生"。
  • 把会话做成无状态令牌（签名 cookie 带用户 id 和过期时间）。Redis 完全不参与读路径，只用来存吊销名单——而吊销名单可以 fail-open（读不到就当没吊销）。代价是回到了第一季第 09 部分那张表里 JWT 的所有缺点：登出不能立刻生效、改权限不能立刻生效。

我的排序是 1 > 2 > 3 > 4。第一个之所以排最前，是因为这一季反复出现的一个教训：很多"高可用方案"要解决的问题，是上一个优化引入的。退回去往往比继续往前加层更划算——前提是你诚实地承认那个优化并没有带来预期的收益。

Q2图 14 里商品缓存那一格写着"如果数据库扛不住，这一格会变成全站故障"。怎么提前知道数据库扛不扛得住？

思路提示

三个层次，从便宜到贵：

  • 算一算。缓存命中率 95%、总 QPS 2000，意味着现在数据库承担 100 QPS。缓存全挂就是 2000 QPS——翻二十倍。你的数据库能不能扛 2000 QPS？这个数字通常一问就有答案，而且往往是"不能"。
  • 压测。在预发环境把缓存关掉，用真实流量比例压。这会告诉你确切的拐点在哪，以及先坏的是什么（多半是连接池，不是数据库 CPU）。
  • 观察真实的局部失效。每次发布改了缓存 key 前缀、每次 Redis 重启，都是一次免费的小规模演练。把这些时刻的数据库负载记下来，比任何压测都真实。

如果结论是"扛不住"，有三个方向：

限并发（上面那个信号量）——保证数据库不被打垮，代价是部分用户看到"系统繁忙"。这是最实际的一条：让一部分请求失败，好过让全部请求失败。

加一层进程内缓存——LRU + 短 TTL（几秒）。Redis 挂了它还在，能吃掉热点数据的绝大部分请求。代价是各实例数据可能不一致，所以只适合能容忍几秒陈旧的数据。这是最被低估的一招，几十行代码就能把回源量再降一个数量级。

降低对缓存的依赖——回到第 03 部分：让底下那条查询本身就不慢。这才是根治。

Q3这一季从第一季那个"单机同步系统"走到了现在。回头看，哪些复杂度是必须的，哪些是被引入的组件带来的？如果重新开始，你会怎么排序？

思路提示

把这一季的内容分成两堆，会发现界限相当清楚：

业务本身要求的（不引入任何组件也躲不掉）：订单状态机（05）、库存预占与超时释放（06）、支付回调的幂等与乱序（09）、Outbox（10）、不变量对账（12）。这些复杂度来自"钱和货要对得上"和"外部系统不可靠"——只要做电商就必须面对。

引入 Redis 带来的：丢失窗口的判断（01）、会话搬家的代价（02）、缓存三种失效形态（04）、分布式锁的不可靠（07）、降级矩阵（13）。这些是为了性能而付出的复杂度。

如果重新开始，我会这样排：

  1. 先做第 05、06、09、10。它们不需要 Redis，只需要 PostgreSQL。做完之后你已经有一个正确的电商系统了——慢，但正确。
  2. 然后做第 03 和第 12。索引和可观测性。这时你会拿到真实数据：到底哪里慢、慢多少。
  3. 最后才引入 Redis，而且只在第 2 步的数据指出确实需要的地方引入。很可能你只需要它的一两个用途，而不是六个。

这个顺序背后的判断是：正确性的复杂度躲不掉，性能的复杂度应该按需付费。而现实中最常见的错误恰恰相反——先引入 Redis（因为"电商都要用"），再在上面盖业务逻辑，最后发现状态机和幂等还没做。那时候再补，代价会大得多，因为要在一个已经有并发和缓存的系统里补正确性。

如果这一季只留下一句话，我希望是这句：先把系统做对，再把它做快；顺序反过来的话，你会得到一个又快又错的系统，而且很难知道它错在哪。
