第四种写法

同一个在线商店，这是第四遍。先说清楚 Javalin 在光谱上的位置——它既不是"轻量版 Spring"，也不是"Java 版 Express"，那两个说法都会让你在第三章开始困惑。

原书的教学设计我完整保留：一个贯穿始终的在线商店——首页、商品列表与详情、购物车、注册登录、我的订单、管理后台——每一章只推进一小步。变的是底下那一层，以及讲解停留的深度。

先说版本 · 这一条会影响你读到的每一段代码

Javalin 7 改掉了路由的注册方式：路由、异常处理器、事件监听器，全部必须在 Javalin.create(config -> …) 的配置块里注册完，start() 之后不能再加。

这意味着网上绝大多数 Javalin 教程和 StackOverflow 答案（都是 Javalin 6 及更早）在这一点上和你手里的版本对不上——它们写 app.get("/x", handler)，而你写了会编译不过。本文按 7.2.3 写，第 02 部分会专门讲这个改动为什么值得。

其它容易撞上的 7.x 变化：ctx.matchedPath() 变成 ctx.endpoint().path()；config.jetty.defaultPort 变成 config.jetty.port；校验器的 .get() 不再自动要求非空，要显式写 .required() 或 .getOrNull()；javalin-rendering 拆成了按引擎分的小模块。

怎么读最后一列

Javalin 的自我定位是"一个库，不是一个框架"——它不接管 main 方法，不要求你按它的方式组织代码，不做任何字节码增强。你 new 一个 Javalin 实例、告诉它有哪些路由、让它监听端口，仅此而已。整个 javalin 依赖树只有 Jetty 和 SLF4J。

这带来的最大差别是可读性：出问题时的调用栈是平的，没有 CglibAopProxy，没有十几层过滤器，断点打在哪停在哪。代价是那些 Spring 默认给你的东西——事务传播、安全默认拒绝、配置绑定、健康检查——全部要自己接上。这份教程有一半篇幅在讲怎么把它们接上，以及接的时候有哪些坑。

为什么值得学 Javalin

  • 它是理解 Spring 的最好方式。自己写一遍会话管理和权限拦截之后，你会真正明白 Spring Security 的过滤器链在解决什么问题——以及它为什么那么复杂。
  • 它适合一类真实项目：内部工具、批处理服务的管理界面、需要极快启动的容器化服务、以及"团队只有三个人，不想背 Spring 全家桶"的场景。
  • Java 生态照样能用。jOOQ、Flyway、HikariCP、Micrometer、Testcontainers、ArchUnit——这些库和 Spring 没有绑定关系，在 Javalin 里一样好用。你放弃的只是 Spring 的自动装配，不是 Java 的生态。

原书没讲、这里补上的

  • 事务。原书下单是三条独立写操作，中间失败就此不一致。
  • 并发。两个人同时买最后一件会怎样？原书没问过。
  • 迁移。原书开着 TypeORM 的 synchronize: true。这里用 Flyway——而且 jOOQ 的代码生成依赖迁移先跑，这个依赖关系本身就是一道保险。
  • 测试。原书全书零测试。javalin-testtools 让端到端测一个路由只要三行。
  • 钱。原书价格是 JS 的 number（浮点）。这里用 long 存分，第 05 部分讲为什么不用 BigDecimal 也不用 double。
  • N+1 与笛卡尔积。第 09 部分会用 jOOQ 的 MULTISET 给出一个 JPA 和 Drizzle 都做不到的解法。

00

工具链与项目骨架

对应原书第 2–4 章。Javalin 没有 start.spring.io，也没有 javalin new——它就是一个 jar。这一部分手工搭一遍，因为整个项目的配置加起来不到一百行，值得你知道每一行为什么在那儿。

Javalin 的依赖树只有 Jetty 和 SLF4J，压缩后不到 1 MB。这个数字解释了后面很多设计决定——它不打算替你做决定，所以每个决定都得你自己做。好消息是决定的数量比想象中少。

五分钟跑起来

./gradlew run，大约 200 毫秒后服务起来。这段代码里最值得盯住的是那个 config.routes——路由注册在配置块里面，而不是拿到 app 之后再加。这是 Javalin 7 的核心改动，第 02 部分会讲透它换来了什么。

陷阱 · 你在网上看到的代码大概率是旧的

Javalin 6 及更早是这样写的：

var app = Javalin.create().start(7070);
app.get("/", ctx -> ctx.result("Hello"));

在 Javalin 7 里这个 app.get(...) 根本不存在，不是废弃、是删掉了。搜到的教程、博客、AI 生成的代码，只要没明确说版本，八成是 6 的写法。看到 app.get( 就知道那篇文章需要翻译一下。

依赖：用版本目录管起来

陷阱 · 不加日志实现，Javalin 会当面骂你

Javalin 只依赖 SLF4J 的 API，不带实现。如果你不加 logback-classic（或别的绑定），启动时会打印一大段警告，然后所有日志静默消失——包括异常堆栈。第一次遇到的人通常会花二十分钟怀疑自己的异常处理器没生效。

另一个选择是用 io.javalin:javalin-bundle：它把 Javalin、Jackson、Logback、testtools 打包在一起。适合起步，不适合长期——它会把你不需要的东西也拖进来，而且遮住了"这个功能来自哪个依赖"这个信息。本项目用细粒度依赖。

最后那三行是这个项目的骨架里最有意思的一处：flywayMigrate → generateJooq → compileJava。它把"数据库结构"和"Java 代码"用构建依赖绑在了一起，而不是靠人记得同步。第 05 部分会讲这条链条为什么能消除一整类 bug。

项目骨架：按功能分，不按角色分

关键是 catalog/、cart/、order/ 这一层：按业务功能切，不按技术角色切。原书用的是 controllers/、services/、entities/，改一个功能要在三个目录之间跳，而且没有任何东西阻止 controllers/cart.ts 直接引用 entities/admin.ts。第 06 部分会用 ArchUnit 把这条边界变成一个能被测试断言的规则。

对照 · 这里没有"扫描"

Spring 靠 @ComponentScan 从入口类往下扫，Nest 靠 @Module 显式登记。Javalin 两者都没有：一个路由类不被 Routes.register 调用，它就完全不存在——不报错、不警告，那个 URL 返回 404。

这和 Hono 那一份是同一种失败模式（忘了写那一行），也和 Spring 挪错包导致全体控制器静默 404 是同一类故障。教训是同一条：让路由的注册位置集中且显眼。第 11 部分会用一个快照测试把这件事彻底钉死。

数据库：一份 compose.yaml

原书让读者装 XAMPP、开 phpMyAdmin、在图形界面里手工建表。这在 2022 年就已经过时，而且它有一个更根本的问题：那些手工点出来的表结构没有任何一份可执行的记录。换台机器就得重来，同事的库和你的不一样也没人知道。第 05 部分的迁移文件就是在解决这件事——而在这个项目里它还多一层作用：jOOQ 的代码生成读的就是它。

动手与思考 · 第 00 部分

先自己想，再展开思路。

Q1把 Routes.register 里的 CartRoutes.register(config) 注释掉，但类保留。./gradlew build 会失败吗？./gradlew test 呢？

思路提示

编译不会失败——一个"没被调用的公开静态方法"完全合法。Error Prone 和 Spotless 也不管这个。访问 /cart 会返回 404，而 404 是 Javalin 的正常响应，不是异常。

只有测试会——如果你写了断言 GET /cart 返回 200 的测试。这就是为什么在一个没有扫描、没有容器的框架里，"路由存在"本身需要被测试覆盖；Spring 里至少还有一个启动期的上下文加载能兜住一部分错误。

但 Javalin 7 提供了一个 Spring 和 Hono 都没有的抓手：因为所有路由必须在 start() 之前注册完，路由表在启动那一刻就是完整且不可变的。于是你可以在测试里直接把它整个拿出来做快照断言。第 11 部分会给出那三行代码——它是这个"upfront 注册"设计的直接红利。

顺带：开发时可以打开 config.bundledPlugins.enableRouteOverview("/routes")，浏览器访问就能看到全部已注册路由。生产环境记得关掉——它等于把你的攻击面目录公开了。

Q2Gradle 里写了 generateJooq dependsOn flywayMigrate。这意味着编译代码需要一个活着的数据库。这是优点还是缺点？CI 上怎么办？

思路提示

两面都很实在，值得掰开说。

缺点很直接：新同事 clone 下来不能直接 ./gradlew build，得先 docker compose up -d。CI 上要多起一个数据库容器。构建从"纯离线"变成了"有外部依赖"。

优点更根本：代码里的表结构和真实表结构不可能不一致——因为前者是从后者生成的。Hono 那一份里有一整张图在讲"Drizzle 的类型是从 schema.ts 推断的，schema 和真实表漂移了类型就在撒谎"，而这个问题在 jOOQ 这里结构上不可能发生。你改了表忘了跑迁移？代码生成不出来，编译失败。

CI 上的做法有两种：用 service container 起一个 Postgres（最直接）；或者用 Testcontainers 在 Gradle 任务里临时起一个，构建完就销毁——jOOQ 官方文档和 Testcontainers 都有这个组合的例子。后者更干净，因为连"CI 上那个数据库的结构是不是最新的"这个问题都消失了：每次都是从零迁移上来的。

还有一个折中：把生成的代码提交进版本库，这样普通构建不需要数据库，只有改了迁移时才重新生成。我不推荐——它把"生成物"变成了要 review 的东西，而且总有人忘记重新生成。真要这么做，至少在 CI 里加一步"重新生成后 git diff --exit-code"。

Q3Javalin 7 要求路由在 start() 之前全部注册完。这个限制让哪些做法变得不可能了？你能想出一个真正因此做不了的需求吗？

思路提示

变得不可能的是运行时动态增删路由：根据数据库里的配置注册 URL、插件热加载、多租户按租户加路由。

但仔细想，这些需求本身大多是可疑的：

  • "按配置注册 URL" 通常可以用一个通配路由 + 内部分发替代，而且那样更好测、更好观测。
  • "插件热加载" 在 JVM 上本来就很难做对（类加载器泄漏、状态残留），生产环境几乎不该用。
  • 多租户按租户加路由，正常做法是路径前缀或子域名 + 同一套路由。

换回来的是三样实在的东西：启动后路由表不可变（可以安全地缓存、快照、生成文档）；不存在"请求进来时路由还没注册完"的竞态（Javalin 6 里 start() 之后再加路由是合法的，于是这个竞态是真实存在的）；配置块读完就知道全貌。

这是一个我认为选得很对的取舍：用一个几乎没人真正需要的能力，换掉一整类启动期竞态。顺带一提，Spring 的路由表在容器刷新后同样是不可变的——Javalin 7 只是把这个性质变得显式了。

01

一次请求的完整旅程

对应原书第 5 章。原书用三句话讲完 MVC 就开始写代码。这一部分是整份教程的地基：把 GET /products 从网卡到 HTML 的每一跳摆出来，并指出哪一跳是框架的、哪一跳是你的。

Javalin 的核心是一个 Servlet。整个应用只有这一个 Servlet，它接下所有请求，查一张在启动时就冻结好的路由表，然后调用你写的 Handler。这句话和 Spring 的 DispatcherServlet 听起来一样，但两者的厚度差着数量级——Javalin 这一层大约两千行代码，你可以在一个下午读完。

逐跳解读

1 · Jetty：一个请求，一个线程

Jetty 从线程池里取一个线程来处理这个请求，这个线程会一直被占着，直到响应写完——包括你查数据库那 20 毫秒、调外部接口那 800 毫秒，它都在那儿等着。

这是 JVM 阻塞式模型和 Node 事件循环最根本的差别，而且两边的失败方式正好相反：Node 里一个慢的同步操作会卡住所有请求；Javalin 里一个慢请求只卡住它自己那个线程，但线程池耗尽时新请求会排队。

默认线程池上限是 250 左右。算一算：如果每个请求平均占用线程 200 毫秒，理论上限就是每秒 1250 个请求——不是 CPU 不够，是线程不够。第 12 部分会讲怎么调，以及虚拟线程如何几乎抹掉这个限制。

2 · JavalinServlet：查一张冻结的表

start() 被调用时，配置块里注册的所有路由被整理成一棵路径树，此后不可变。请求进来时按 HTTP 方法 + 路径匹配，找到那个 Handler。

对照 · 三种路由分发

Spring 的 HandlerMapping 在启动时扫描注解建立映射表，请求时用 PathPatternParser 匹配，中间还隔着 HandlerAdapter 和一整套参数解析器——所以你能写 list(@PathVariable Long id, @Valid Form form, Model model) 这样的方法签名。

Javalin 没有参数解析这一层：所有 handler 的签名都是 void handle(Context ctx)，想要什么自己从 ctx 里取。少了灵活性，换来的是没有"为什么这个参数没被注入"这类问题——因为根本没有注入。

Hono 介于两者之间：签名固定为 (c) => Response，但通过 zValidator 这类中间件把校验结果放进 c，取的时候有类型。Javalin 的 Validator 走的也是这个路子，见第 07 部分。

3 · Context：每请求一个的手提箱

陷阱 · ctx.attribute 没有类型

ctx.attribute("currentUser") 的返回类型靠目标类型推断，实际上是一次未检查的强制转换。写错名字（"curentUser"）得到 null，写错类型得到 ClassCastException——而且都发生在运行时。

Hono 用 Env["Variables"] 把这件事放进了类型系统，Javalin 没有对应机制。可行的补救是自己包一层类型安全的键：

record AttrKey<T>(String name, Class<T> type) {}，配一对 put/get 静态方法，把字符串收进一个常量类。三十行换来"名字写错编译不过"，在一个到处用 attribute 传值的项目里很值。

4 · Handler 就是你写的那个对象

Javalin 调用 handler 时没有反射、没有动态代理、没有字节码增强。Handler 是一个函数式接口，你的 lambda 就是它的实现，栈里看到的就是你写的那一行。

这条性质在调试时的价值很难高估。Spring 里一个 @Transactional 方法的调用栈会穿过五六层 CglibAopProxy；Javalin 的栈从 Jetty 直接到你的 lambda，中间只有 JavalinServlet 一层。

出错时走哪条路

深入 · exception 和 error 是两套机制

exception(Class, handler) 按抛出的异常类型匹配，走的是最具体优先——你注册了 BusinessException 和 Exception 两个，抛 BusinessException 时只有第一个会执行。

error(int, handler) 按最终的状态码匹配，在响应快要发出去之前执行。所以它能捕获两类情况：路由没匹配上（404）、以及 handler 自己 ctx.status(403) 设出来的码。

顺序是：handler 抛异常 → 找 exception 处理器 → 处理器设了状态码 → 再看有没有对应的 error 处理器。两者会叠加，这是很多人第一次遇到"我的错误页被渲染了两次"的原因。

Javalin 还内置了一组直接抛就有正确状态码的异常：NotFoundResponse、BadRequestResponse、UnauthorizedResponse、ForbiddenResponse、ConflictResponse。业务代码里抛它们比手工 ctx.status() 更清楚，因为抛出点就是决定点。

安全 · 别把异常原文吐给用户

上面第二个处理器只回一句话加一个编号。危险的写法是 ctx.result(e.getMessage())——JDBC 的异常消息里经常带着表名、列名甚至参数值；jOOQ 的异常可能带完整 SQL。对外一句话，对内一条带 requestId 的结构化日志，第 12 部分会把这条链路补完。

还有一个 Javalin 特有的点：如果你不注册任何 exception(Exception.class, …)，Javalin 默认返回 500 并且只打印堆栈到日志，不发给客户端。默认行为是安全的，是自己动手改的时候才容易改错。

Q1图 1 里那个红框说"线程全程阻塞"。一个商品详情页要串行调用三次数据库，各 20 毫秒。在 Javalin 里这占用多少线程时间？换成 Hono（单线程事件循环）呢？两者的瓶颈分别在哪？

Javalin：一个线程被占 60 毫秒，其中 60 毫秒几乎全是等 I/O，CPU 基本闲着。默认 250 个线程的话，理论吞吐是 250 ÷ 0.06 ≈ 每秒 4000 个请求。瓶颈是线程数，而线程是昂贵的（每个约 1 MB 栈内存，加上上下文切换）。

Hono：这 60 毫秒里事件循环是空闲的，可以去处理别的请求。单个请求的延迟一样是 60 毫秒，但不占用"并发额度"。瓶颈是CPU 和事件循环——只要没有同步阻塞代码，几千个并发连接也扛得住。

所以两者的调优方向完全不同：Javalin 要加线程（或换虚拟线程），Hono 要避免同步阻塞。

值得注意的是 Java 21 让这个差别几乎消失了：虚拟线程的创建成本是普通线程的千分之一，阻塞时会把载体线程让出去。开启之后 Javalin 的并发模型在效果上接近事件循环，但你的代码还是老老实实写同步的样子——这是 Loom 最大的价值：不用把代码改成回调或 async/await 就能拿到高并发。第 12 部分会讲怎么开，以及开之前必须检查什么。

Q2Spring 的安全过滤器在 DispatcherServlet 之前（Servlet Filter 层），Javalin 的权限检查在 beforeMatched 里（Servlet 之内）。这个位置差异有什么实际后果？

思路提示

三个后果，一个比一个实在。

① 默认值反了。Spring Security 一旦引入就默认拒绝所有未显式放行的路径，新加一个端点忘了配规则会 403——响亮的失败。Javalin 里新加一个路由忘了标 RouteRole，它默认可访问——静默的失败。第 08 部分会讲怎么把这个默认值扳回来（关键是让"没有角色标注"本身就等于拒绝）。

② 拦不住 Servlet 层的东西。beforeMatched 在 Javalin 内部，静态文件、WebSocket 升级、以及 Jetty 直接处理掉的请求不一定经过它。要覆盖这些，得注册真正的 Servlet Filter（Javalin 允许你通过 config.jetty.modifyServletContextHandler 加）。

③ 但它能看见路由信息——这是 Spring 过滤器做不到的。过滤器在匹配之前执行，只知道 URL 字符串；beforeMatched 在匹配之后执行，能拿到 ctx.routeRoles()，也就是"这个端点声明了需要什么权限"。这让"通用的鉴权逻辑 + 每个端点声明自己的要求"这种写法成为可能，而 Spring 要用配置 DSL 或方法注解另外表达一遍。

换句话说：Javalin 的位置更靠内，代价是覆盖面窄，好处是信息更全。两个都要的话，就是"Filter 做粗粒度的、beforeMatched 做业务粒度的"——这也正是 Spring 里 SecurityFilterChain 加 @PreAuthorize 的分工。

Q3把 config.routes.exception(Exception.class, …) 整个删掉，然后让某个 handler 抛 NullPointerException。用户看到什么？日志里有什么？这个默认行为算好还是不好？

思路提示

用户看到一个 500，响应体是 Javalin 的默认错误页（或 JSON，取决于 Accept 头），不包含任何堆栈信息。日志里有完整堆栈。

这个默认行为是好的，而且值得注意它好在哪：安全的默认值不需要你做任何事就生效。对比一下反例——某些框架默认在开发模式下把堆栈渲染到页面上，然后靠一个环境变量切换；只要那个变量配错一次，你的表名、文件路径、依赖版本就全公开了。

那为什么还要自己注册？三个理由：要渲染成站点风格的错误页（默认页很丑）；要把 requestId 显示给用户（第 12 部分那条链路的入口）；要区分业务异常和缺陷——前者是 4xx 加具体提示，后者是 5xx 加一句话，两者的日志级别和告警策略完全不同。

注册的时候要小心一点：exception(Exception.class, …) 会兜住一切，包括 Javalin 内置的 NotFoundResponse 这类本该有特定状态码的异常。所以要么按具体类型分别注册，要么在通用处理器里判断 e instanceof HttpResponseException 并原样放行。写错这一处，全站的 404 会变成 500——而且测试如果只覆盖正常路径，不会发现。

02

路由与 Handler 链

原书把横切逻辑拆成 Guard、Interceptor、Pipe、Filter 四种概念。Javalin 只有两种：请求前和请求后。但它们不是嵌套的——这一点和 Hono 的洋葱模型有个关键差别，写错了会丢日志。

Javalin 的处理器链是一条直线，不是一个洋葱。before 处理器和 after 处理器是两个独立的列表，依次执行，中间夹着端点处理器。没有 next()，没有嵌套，没有"包住内层"这回事。这个差别决定了几种常见写法在 Javalin 里要换个形状。

项目里的注册

深入 · 为什么这里不需要 try/finally

Hono 那一份里有一条规则：中间件里"必须发生"的收尾动作，一律放 finally。因为在洋葱模型里，内层抛异常会让 await next() 把异常继续往外抛，后面的统计代码就不执行了——结果是"出错的请求反而没有耗时记录"，而那恰恰是你最想看的。

Javalin 不需要这条规则，因为 after 处理器不是"next() 之后的代码"，它是一个独立的、框架保证会执行的阶段。异常被 exception 处理器接住之后，after 照常跑。

这是线性模型换来的一个实实在在的好处：框架替你保证了 finally 语义，你想忘也忘不掉。Spring 的 HandlerInterceptor.afterCompletion 也是同样的设计，而且理由相同。

对照 · 权限挂在树上，不挂在注解上

Nest 的 Guard 能读到"即将执行的那个 handler 上的元数据"（@Roles('admin')），Spring 有 @PreAuthorize。Javalin 的 RouteRole 走的是第三条路：角色是注册路由时的一个参数，可以按整棵子树设置。

好处和 Hono 那一份的结论一样：把"需要什么权限"编码进路由树的结构，"忘记加权限"就变成了物理上不可能——你没法把一个路由放进 /admin 那棵子树又不带上 ADMIN。

但 Javalin 比 Hono 多一样东西：ctx.routeRoles() 让鉴权逻辑本身可以是通用的一个处理器，而不用为每种角色写一个中间件。第 08 部分会把 Access::enforce 完整写出来，它只有十几行，却覆盖全站。

三个容易踩的地方

1 · before 里改不了响应

before 处理器执行时，端点还没跑，ctx 里还没有响应内容。想在这里设置响应头是可以的（会保留到最后），但想"看一眼响应再决定做什么"只能放在 after 里。

2 · after 里 ctx.status() 已经定了

在 after 里能读到最终状态码，也能改——但如果响应体已经开始往外写（比如用了流式输出），改状态码就来不及了。规则和 Hono 那份一样：一旦开始写响应体，头和状态码就已经发出去了。

3 · 静态文件不走这条链

config.staticFiles.add(...) 注册的静态资源由 Jetty 层处理，不经过 beforeMatched。如果你以为权限检查覆盖了所有路径，静态目录会是个缺口。要保护的文件不要放静态目录，走一个真正的路由发出去（第 07 部分的上传文件就是这么处理的）。

Q1注册两个 before（A、B）和两个 after（C、D）。请求一个不存在的路径，四个处理器各执行吗？如果 B 抛了异常呢？

思路提示

路径不存在：A、B 都执行（它们是 before，不是 beforeMatched），端点不存在，C、D 也都执行，最后返回 404。这就是图 2 上那条黄色虚线。

实际影响：你的日志 after 会记录所有 404，包括扫描器打过来的 /wp-login.php。这通常是想要的——但如果量大，记得别把它们记成 error 级别。

B 抛异常：A 已经执行完了，B 抛出，端点不执行，跳到 exception 处理器，然后 C 和 D 仍然执行。

这里有个容易出 bug 的地方：C 和 D 可能依赖 B 放进 ctx 的东西。比如 B 是"还原当前用户"，C 是"记录用户行为日志"——B 抛异常时 C 拿到的是 null，如果 C 没做判空，就会在异常处理的路径上再抛一个异常。

所以 after 处理器有一条纪律：必须假设前面的任何一步都可能没跑完。它是收尾逻辑，收尾逻辑不能挑食。上面那个日志 after 里 (long) ctx.attribute("startNanos") 其实就有这个隐患——如果第一个 before 之前就出错了，这里会 NPE。稳妥写法是 Long start = ctx.attribute(...); if (start != null) …。

Q3图 2 最后一行说线性模型"让外层决定内层要不要跑"做不到。举一个真实需求，是洋葱能做而 Javalin 做不了的。你会怎么绕？

思路提示

最典型的是"整个请求包在一个事务里"：洋葱模型可以写 await db.transaction(async () => { await next() })，一层中间件就把端点包进了事务。Javalin 做不到——before 开事务、after 提交的话，中间那段没有任何东西保证它们成对，而且异常路径上要靠 after 判断状态码来决定回滚，很脆。

另外两个：请求级重试（外层捕获特定异常后重跑内层）、超时包裹（内层超过 N 秒就取消）。

怎么绕，按推荐程度排：

  • 别在处理器层做事务。这是我的建议，也是本项目的做法：事务边界画在服务方法里（第 10 部分），一个 ctx 一次业务操作一个事务。这比"整个请求一个事务"更精确——一个页面可能既有读又有写，没必要全包进去。而且 Spring 那边 open-in-view 引发的一堆问题，根源正是"把事务边界拉到了请求级"。
  • 写一个包装 Handler。Javalin 的 Handler 是函数式接口，你可以自己写 Handler tx(Handler inner) 返回一个新的 handler，在里面调用 inner.handle(ctx)。这就把洋葱手工造回来了——注册路由时写 get("/x", tx(MyHandler::create))。
  • 需要全局生效时，用真正的 Servlet Filter（config.jetty.modifyServletContextHandler），那一层是有嵌套语义的。

第二条值得记住：缺少的不是能力，是语法糖。函数式接口 + 高阶函数能表达洋葱，只是要显式写在每个路由上——而这个"显式"某种程度上是好事，你一眼能看出这个端点被什么包住了。

03

视图层：JTE

对应原书第 6–9 章。原书用 Handlebars：模板里写错变量名没人管，页面上悄悄显示空白。JTE 把模板编译成 Java 类——参数写错是编译错误，而且它在编译期就知道每个插值落在 HTML 的哪个位置。

服务端渲染的本质是拼一个 HTML 字符串。三种做法：模板语言在运行时解析并挖洞（Thymeleaf、Handlebars）、用函数生成片段再拼（JSX）、把模板翻译成源码再编译（JTE）。第三种最不常见，却在两件事上明显更好：类型检查和转义。

最小可用：一个商品列表页

@param 那几行是这套东西的关键：模板的参数是有类型的。传少了、传错类型、字段名拼错（p.nmae()），全都是编译错误——因为 JTE 生成的是一个真正的 Java 类，它要和你的代码一起过编译器。

布局：模板调用模板

gg.jte.Content 是关键类型：它让"一段模板代码"可以作为参数传递，效果类似 Java 的 lambda。调用方用 @`…`（反引号）包住内容块传进来。布局的"洞"因此是有类型的——忘了传 title 就编译不过。

对照 · 四种布局机制

Handlebars（原书）：{{{ body }}} 挖洞，洞的类型是"任意字符串"。
Thymeleaf：th:fragment + th:replace，洞的类型是"任意片段"。
JSX：布局是接受 children 的函数，洞有类型（TypeScript）。
JTE：布局是接受 Content 参数的模板，洞有类型，而且是 Java 类型——参数可以是 List<Crumb>、可以有默认值、可以用命名参数调用。

后两者是同一个思路，差别只在类型系统属于谁。值得注意的是 JTE 这条路把模板拉进了编译期：重命名 record 的一个字段，IDE 的重构会连模板一起改——这是 Thymeleaf 和 Handlebars 做不到的。

开发时热重载，生产时预编译

陷阱 · 两个模式的行为不完全一样

Javalin 7 起，JavalinJte 默认从 classpath 加载预编译模板；directoryTemplateEngine() 才是从文件系统读并即时编译（也就是 Javalin 6 的默认行为）。升级上来的人容易在这里卡住：模板明明改了，页面却没变——因为跑的是 jar 里那份旧的。

更值得注意的是模板错误的暴露时机不同：目录模式下，一个写错的模板要等到有人访问那个页面才报错；预编译模式下，它在构建时就编译失败。所以 CI 必须跑预编译——否则"编译期类型安全"这个卖点只在生产环境生效，而那太晚了。

顺带：模板引擎是处理不可信输入的组件，要像对待安全组件那样跟进它的版本，别让它在依赖列表里躺三年。

原书在这里做错了什么

  • 用 {{{ }}} 输出商品描述。为了让描述里的 <br> 生效而关掉转义。描述来自管理后台的输入框——只要后台账号被拿下或存在越权写入，就是存储型 XSS。正确做法是存纯文本、渲染时把换行转成 <br>，或者存 Markdown、渲染时过消毒库。

思路提示

先说结论：不要这样写，即使 JTE 比别的引擎更懂上下文。

问题在于 <script> 标签体是一个特别麻烦的上下文：里面同时受 JavaScript 词法和 HTML 解析器的约束。最经典的坑是字符串里出现 </script>——HTML 解析器会在那里提前结束脚本标签，不管它在不在 JS 字符串里。所以哪怕做了完美的 JS 转义，一个商品名叫 </script><script>… 的商品仍然能逃出去。

正确做法是不要把数据放进 JS 上下文，改用 HTML 属性传递：

<div id="cart" data-cart="${cartJson}"></div>，然后 JS 里 JSON.parse(el.dataset.cart)。

这样数据落在属性上下文里，走的是引号转义那条规则，而且没有 </script> 的问题。这条建议对所有模板引擎都成立——Hono 那一份的图 3 第 4 格也是同一个结论。

另一个选择是 <script type="application/json" id="cart">：类型不是 JS 的 script 标签不会被执行，内容当纯文本读。但那个 </script> 的问题依然存在，还是要转义。属性方案更省心。

Q3模板编译成 Java 类，意味着改一个模板要重新构建。Thymeleaf 改完刷新就生效。这个差别在什么团队里是问题？怎么缓解？

思路提示

目录模式（directoryTemplateEngine()）已经解决了开发时的问题：改完刷新即可，JTE 会即时编译那一个模板。所以"要重新构建"在开发阶段是不成立的。

真正的差别在别处，而且更根本：

  • 模板不再是能用浏览器直接打开的 HTML。Thymeleaf 的"自然模板"是它的招牌卖点——设计师能双击打开 list.html 看到带假数据的效果。JTE 模板里有 @param、@for，浏览器打开就是一堆乱码。
  • 交付流程受影响。如果你的团队是"设计师交付静态 HTML，后端套页面"，JTE 会让这个交接变成一次重写。
  • 热修受影响。线上想改一句文案，Thymeleaf 理论上能替换模板文件重启了事，JTE 必须走完整的构建发布。不过这条其实是好事——绕过构建改生产代码本来就不该成为常规操作。

缓解办法主要是流程上的：把可能频繁变的文案抽成配置或数据库内容，而不是硬编码在模板里；给设计师一个能跑的开发环境而不是让他们靠打开文件预览。

判断标准和 Hono 那一份里的一样：你的交付流程里有没有"HTML 交接"这一步。有，Thymeleaf 更顺；没有（写页面的和写接口的是同一批人），JTE 的类型安全和性能几乎是白赚的。

04

代码规范与质量门禁

对应原书第 10 章（ESLint 与 Prettier）。原书装完插件、贴完配置就结束了，没说过任何一条规则为什么存在。这一部分讲 Java 这边的四道关卡，以及其中一道是 Java 独有的免费午餐，另一道是 Java 独有的欠债。

"代码规范"这个说法容易让人以为它关乎风格。缩进和引号确实是风格，交给工具自动改掉就行。值得花心思的是另一半：那些能在提交之前挡住真 bug 的检查，以及它们在哪一道关卡生效。同一个错误，在编译器里发现和在生产环境发现，成本差三个数量级。

接进构建

那一行 @NullMarked 是这一部分性价比最高的一行代码。加上之后，String name 的含义从"可能是 null"变成了"保证不是 null"，想表达可空必须写 @Nullable String name——而 NullAway 会检查你有没有在用之前判空。

Error Prone 里值得开成 error 的几条它拦的是什么
NullAway见上。这一条的价值超过其它所有加起来。
ReferenceEquality用 == 比较对象。"a" == "a" 在字符串常量池里碰巧为真，从数据库读出来就为假——这类 bug 在测试里往往不复现。
ReturnValueIgnored丢弃了有意义的返回值。str.trim(); 什么也没干（String 不可变），但看起来像干了。
FormatString日志和 String.format 的占位符数量对不上。这类错误往往发生在异常处理路径上——本来要记录错误，结果自己抛了个错。
MissingOverride本想覆写却拼错了方法名。加上 @Override 后编译器会替你确认。
UnusedVariable算了一半忘了用的结果。经常是"少写了一行"的信号。
陷阱 · 别把 -Werror 开在所有警告上

把所有警告变成错误听起来很好，直到某天你升级一个依赖，它废弃了一个方法，于是整个项目编译不过——而你本来只是想修个安全漏洞。

所以上面的配置写的是 -Xlint:all,-deprecation：打开全部检查，但把废弃警告排除在外。废弃应该进一个待办清单，而不是变成阻塞发布的红灯。真正该"错误化"的是 Error Prone 里那几条明确指向 bug 的规则。

同样的道理适用于 jOOQ 生成的代码——配置里的 excludedPaths 就是干这个的。生成的代码不该受你的代码规范约束，它不是给人读的。

对照 · 三套工具链的分工

Hono / TypeScript：Biome 一个工具管格式 + 检查（100 毫秒），空安全由语言自带，模块边界靠 dependency-cruiser。

Spring Boot：Spotless + Checkstyle + Error Prone + NullAway，加上 Spring Modulith 做边界。

Javalin：和 Spring 那套完全一样——因为这些工具都和 Web 框架无关。这是"放弃 Spring 不等于放弃 Java 生态"最直接的例子：你丢掉的只有自动装配，Error Prone、ArchUnit、Testcontainers、Micrometer 一个都没丢。

唯一的差别是 Javalin 项目通常更小，所以这套工具链的相对成本更低。

Q1加上 @NullMarked 之后，第一次编译冒出 200 个 NullAway 错误。你会怎么办？逐个修完再提交，还是有别的路子？

思路提示

逐个修完是最糟的选择——一个 200 处改动的 PR 没人能认真 review，而且中间任何一处改错都会被淹没。

三条更实际的路子：

  • 按包渐进。NullAway:AnnotatedPackages 可以只写 com.example.store.catalog，先让一个模块干净，再一个个加。这是我推荐的做法——每个包一个小 PR，改动集中，容易 review。
  • 先降级成警告，把清单拉出来，按"这一处如果真是 null 会怎样"排序。你会发现大部分是无害的（构造函数里的字段），少数是真 bug（外部输入没判空）。先修那少数。
  • 新代码严格，老代码豁免。把遗留包排除掉，新写的代码从第一天就干净。

还有一个观察值得留意：那 200 个错误里，出现最多的位置往往能告诉你架构问题在哪。如果大量集中在"从数据库读出来的对象"上，说明你的数据层没有把"可能不存在"这件事表达清楚——第 05 部分会用 fetchOptional 处理它。

Q2图 4 说 NullAway"信任注解，不验证第三方库"。这个限制在什么地方会真的咬到你？

思路提示

咬人的地方全在边界上，而且有三类：

  • 没标注的库返回 null。某个库的 find() 找不到时返回 null，但它没标 @Nullable。NullAway 按配置放过，于是你直接用，运行时 NPE。这一类最危险，因为你以为已经被保护了。
  • Map.get()、ctx.attribute() 这类本质上就返回 null 的方法。第 01 部分说的那个类型安全 attribute 包装，在这里又多了一个理由。
  • 反射和 Jackson 反序列化。Jackson 可以把一个 @NullMarked 的 record 字段填成 null（JSON 里就是 null），编译器完全不知道。这就是为什么反序列化之后必须校验——和 Hono 那一份里"类型在运行时消失"是同一条边界。

应对办法：在每个进程边界上做一次显式检查，然后内部就可以信任类型。具体到这个项目就是三处：HTTP 输入（第 07 部分的 Validator）、数据库读取（第 05 部分的 fetchOptional）、配置解析（Config 启动时校验）。

这三处做对了，NullAway 在剩下 95% 的代码里就是可靠的。它不是万能，但它把"哪里需要小心"从"到处"缩小到了"三个地方"——这才是它真正的价值。

Q3团队里有人说"这套工具让构建慢了 15 秒，我们又不是大项目，能不能只留 Spotless"。你怎么回应？

思路提示

先承认代价是真的，然后把讨论拉到每一项各自的成本收益上，而不是打包接受或打包拒绝：

  • Spotless：几乎免费，收益是终结格式争论。留。
  • NullAway：它是 Error Prone 的一个插件，共用同一次编译，额外开销很小。而它拦的是 Java 头号运行时异常。这一项最不该砍。
  • Error Prone 的其它规则：开销主要来自它需要接管编译。可以只开一个精选子集（上面那张表里那几条），把默认的一大堆警告关掉。
  • ArchUnit：它是测试，不在编译路径上。如果慢，是因为它在扫全部类——可以缓存，或者只在 CI 跑。

更重要的是问一句：这 15 秒加在哪一步？如果加在开发者每次改代码后的增量编译上，那确实要认真优化（Gradle 的增量编译 + 构建缓存能让绝大多数改动不触发全量 Error Prone）。如果只加在 CI 的全量构建上，15 秒不值得讨论。

我会给出一个具体提议而不是辩论：本地默认只跑 Spotless + NullAway，完整检查交给 ./gradlew check 和 CI。让快的路径保持快，让严的路径无法绕过——这和 Hono 那一份里"钩子要快、CI 要严"是同一条原则。

05

数据层：jOOQ 与 Flyway

对应原书第 11–14 章。原书用 TypeORM 并开着 synchronize: true——启动时让 ORM 按实体定义自动改表结构。这一部分换成 Flyway + jOOQ，而它们的组合有一个别的方案给不了的性质：代码和表结构不可能不一致。

jOOQ 的定位和 JPA、TypeORM 都不同：它不是"把对象映射成表"，而是"从表生成类型安全的 SQL DSL"。没有实体管理、没有一级缓存、没有懒加载代理、没有脏检查。你写的 DSL 长什么样，发出去的 SQL 就长什么样——而且列名写错是编译错误。

三种方向：谁是事实来源

注意最后那个部分索引（where published）：索引里只放已上架的商品，体积小得多，而且它把"我们只查这一部分"这个事实写进了 schema。这类东西手写 SQL 迁移比让 ORM 生成更容易表达——这是方案 ③ 顺带的一个好处：你在用数据库真正的能力，而不是 ORM 支持的那个子集。

isPojos = false 和 isDaos = false 是刻意的。jOOQ 能替你生成一整套 POJO 和 DAO，但那样就退回成了一个平庸的 ORM——而 jOOQ 的价值恰恰在于让你直接写 SQL 的形状。我们只要它生成表和列的元数据（Tables.PRODUCTS、PRODUCTS.PRICE_CENTS），剩下的自己写。

连接池与 DSLContext

陷阱 · leakDetectionThreshold 值得默认打开

Java 这边最常见的一类生产事故是连接泄漏：某个代码路径拿了连接却没归还（通常是没用 try-with-resources，或者在异常路径上漏了）。症状是连接池慢慢耗尽，几小时后全站超时，而且重启就好——所以经常被误判成"内存问题"。

HikariCP 的泄漏检测会在连接借出超过阈值时打印一条带完整堆栈的警告，直接告诉你是哪一行借的。这个功能几乎零开销，却能把一次通宵排查变成一分钟。

jOOQ 用 DSL.using(dataSource, ...) 时会自己管理连接的借还，正常写法不会泄漏。危险的是你手工 ds.getConnection() 的地方——那些必须写成 try-with-resources。

查询：贴着 SQL 的形状

三处值得注意。select(...) 里显式列出要的列：返回类型精确到这几个字段，页面上不小心用到 description 就是编译错误——投影既省带宽又更安全。DSL.noCondition()：表达"这个条件不生效"，比拼字符串干净。fetchOptional：把"可能没有"放进类型里，配合第 04 部分的 NullAway，调用方想忽略这个情况都做不到。

深入 · 参数化与 SQL 注入

上面 likeIgnoreCase("%" + keyword + "%") 里有字符串拼接，看起来危险。它不危险——整个 %keyword% 作为一个值被绑定成参数，生成的 SQL 是 … like ?。用户输入 ' OR 1=1 -- 只会被当成一个搜索关键词。

jOOQ 里唯一能拼出注入的是 DSL.field(String)、DSL.table(String) 和 DSL.sql(String) 这几个接受裸字符串的方法——它们把内容原样嵌进 SQL。与之相对，DSL.field("x = {0}", val) 这种带占位符的形式是安全的。

规矩很简单：裸字符串版本的参数必须来自你自己的代码，永远不能来自请求。典型的误用是动态排序：orderBy(DSL.field(ctx.queryParam("sort")))——正确做法是白名单映射，把用户传的 "price" 映射到 PRODUCTS.PRICE_CENTS 这个类型安全的字段对象。

钱：Java 有三个选项，两个是坑

原书的商品价格是 JavaScript 的 number，也就是浮点数。Java 这边看似有更好的选择（BigDecimal），但它带着一个非常容易踩的陷阱。

times 和 scale 分开是刻意的：乘数量是精确的，乘比例是要舍入的，混成一个方法就会让舍入变得随机。而 Math.addExact 这一族方法值得成为习惯——溢出时抛 ArithmeticException，比悄悄变成负数强得多。

陷阱 · jOOQ 默认把 numeric 映射成 BigDecimal

如果你在迁移里写了 price numeric(12,2)，jOOQ 生成的字段类型就是 BigDecimal，图 6 中间那一格的问题会顺着进你的代码。

本项目在 SQL 层就用 bigint price_cents，所以生成出来是 Long，干净。如果你接手的是一个已有 numeric 列的库，jOOQ 支持自定义类型转换器（Converter<BigDecimal, Money>），在代码生成时绑定上去——这样业务代码里看到的一律是 Money，永远接触不到 BigDecimal。

这个技巧值得记住，它不止用于金额：数据库里的 text 状态列可以直接映射成 Java 枚举，timestamptz 可以映射成 Instant。把类型转换收在生成层，业务代码就不用到处做转换。

Q1你要给 products 加一列 sku text not null，表里已有 5 万行。直接写这条 DDL 会发生什么？正确做法要分几步？滚动发布时还有额外约束吗？

思路提示

直接执行会失败：已有的 5 万行没有 sku 值，违反 not null，Postgres 拒绝整条语句。

正确做法是三步，而且要分三次部署：

  1. 加可空列：alter table products add column sku text。在 Postgres 里这是瞬时的（不重写表）。新旧版本代码都能跑。
  2. 回填 + 双写：新版本代码开始写 sku，同时用后台任务分批回填历史行（update … where sku is null limit 1000 循环）。一次性全表 update 会长时间持锁。
  3. 加约束：确认没有 null 之后 alter column sku set not null。

滚动发布的额外约束是每一次迁移都必须兼容上一个版本的代码——因为迁移跑完之后、新代码全部上线之前，旧代码还在访问这个已经变了的库。

这里有一个 jOOQ 特有的好消息和一个坏消息。好消息：加列之后重新生成代码，旧代码用不到新列，编译照样通过——加列是安全的。坏消息：删列会让所有引用它的代码编译失败，这看起来烦，实际上是保护——它逼你在删列之前先把代码里的引用清干净，也就是天然强制了"扩展-收缩"的顺序。

Q2购物车小计：单价 1999 分、数量 7、会员折扣 0.85。price.times(7).scale(0.85) 和 price.scale(0.85).times(7) 分别得到多少？哪个对？

思路提示

第一种：1999 × 7 = 13993，× 0.85 = 11894.05，四舍五入 11894 分。

第二种：1999 × 0.85 = 1699.15 → 1699，再 × 7 = 11893 分。差一分。

哪个"对"没有数学答案，只有约定答案。要点是：

  • 选一个，写进代码注释和测试，别让它随实现漂移。
  • 倾向于尽量晚舍入（第一种），因为中间步骤的舍入误差会被数量放大。
  • 更重要的是：展示给用户的分项加起来必须等于总计。如果页面上按行显示"折后单价 ¥16.99 × 7"，用户会自己算出 ¥118.93，而你收 ¥118.94——这是客服工单。要么按行舍入并让总计等于分项之和，要么不展示折后单价。

顺带一个 Java 特有的提醒：scale() 的参数我写成了 BigDecimal 而不是 double。如果传 double，0.85 这个字面量本身就已经不精确了——BigDecimal.valueOf(0.85) 还好（它走 Double.toString），但 new BigDecimal(0.85) 会得到 0.84999999999999997779…。这是 BigDecimal 的第二个陷阱：构造器和 valueOf 的行为不一样。

Q3JPA 有一级缓存：同一个事务里查两次同一个实体只发一次 SQL。jOOQ 没有。这是缺陷还是取舍？什么时候你会怀念它？

思路提示

是取舍，而且我认为方向是对的。一级缓存解决的问题是"代码分散在各层，谁也不知道别人查没查过"，它用一个隐式缓存吃掉重复查询。代价是：你无法通过读代码知道会发出几条 SQL，外加一整套"实体是托管态还是游离态"的心智负担。

jOOQ 的立场是"查询是显式的"：写两次就查两次。想去重就自己在方法入口查一次、把结果传下去——这恰好也让数据流更清楚。

会怀念它的场景：页面结构很深，比如订单详情要展示每一行商品的分类，而分类只有几个、被反复引用。JPA 会自动缓存，jOOQ 会老实地查 N 次。

解法不是把缓存加回来，而是换查询形状：一次性把用到的分类全查出来（where id in (...)），在内存里做成 Map。这在 jOOQ 里是几行代码，而且它是显式的。第 09 部分会把这个模式完整写一遍，并且给出一个 jOOQ 独有的、更好的解法。

还有一个容易被忽略的角度：一级缓存在多线程下是危险的假象。它只在一个持久化上下文内有效，而 Javalin 是一个请求一个线程、没有环境上下文的模型——就算你想要，也没有一个自然的地方挂它。与其模拟一个半吊子的缓存，不如接受"查询就是查询"。

组装与模块边界

对应原书第 15–17 章（Nest 的模块与依赖注入）。Javalin 没有 DI 容器，也没有模块概念。这一部分回答两个问题：对象之间怎么连起来，以及没有模块系统时边界靠什么守住——Java 在第二个问题上有一件别的语言没有的武器。

先说一句可能有点扫兴的话：在 Javalin 项目里，"依赖注入"这个问题大部分时候不存在。DSLContext 是一个线程安全的单例，服务是无状态的，参数就是它的依赖。真正需要注入的只有极少数东西，识别出那几个才是重点。

组装：一个 main 方法就够了

依赖的种类怎么处理理由

深入 · 为什么 Clock 值得单独拎出来

Instant.now() 散落在业务代码里，是一个很难察觉的可测试性杀手："订单在跨月零点创建会怎样"、"优惠券恰好在过期那一秒被使用"——这类测试要么写不出来，要么只能靠 mock 静态方法（需要额外的库，而且很脆）。

把 java.time.Clock 作为依赖传进来之后，测试里写 Clock.fixed(Instant.parse("2026-01-31T23:59:59Z"), UTC) 就完了。零依赖、零魔法、JDK 自带。

这条规则可以推广：凡是"不确定的东西"——时间、随机数、UUID、当前用户——都该从参数进来；确定的东西直接用。Hono 那一份里的结论一模一样，只是那边传的是 now: Date。

边界：Java 有一件别人没有的武器

第一层：用可见性表达门面

关键不在于"导出了什么"，而在于没导出什么。order 模块下单时需要商品的名字和价格，那就通过 CatalogService 拿；它不需要知道 catalog 内部怎么查、表叫什么、有没有缓存。这样 catalog 改内部实现时，只要 public 签名不变，就不必担心弄坏别人——而"不必担心"这件事是编译器保证的，不是靠自觉。

陷阱 · 一个包一个目录，别再分子包

package-private 的作用域是包，而且 Java 的包没有嵌套关系——com.example.store.catalog.internal 里的包级可见类，对 com.example.store.catalog 来说也是不可见的，反之亦然。

所以如果你按习惯建了 catalog/service/、catalog/repository/ 这样的子包，包级可见性立刻失效——为了让它们互相调用，你不得不把一切都写成 public，第一层防线就没了。

这是"按功能分包"在 Java 里的一个额外理由：让一个功能模块正好是一个包，内部类之间互相可见，对外只暴露少数 public 类型。模块大到必须拆分时，那通常是该拆成两个功能模块的信号。

（Java 模块系统 JPMS 能表达更细的导出规则，但对一个单体应用来说，它引入的复杂度远大于收益。包级可见性已经够用。）

第二层：ArchUnit 补上编译器管不到的

最后那条规则其实是多余的——CatalogQueries 是包级可见，别的模块根本编译不过。但把它写出来仍然有价值：它记录了意图。将来有人为了图方便把 CatalogQueries 改成 public，编译器不会反对，而这条测试会立刻失败并且告诉他为什么不该这么做。ArchUnit 的规则描述里那句 because(...)，就是失败时打印出来的解释。

深入 · Java 的循环依赖为什么比 JS 温和

Hono 那一份里循环依赖是个真问题：ESM 的循环会让某个模块在初始化到一半时被读取，得到 undefined 或者 ReferenceError，而且函数声明的提升会掩盖问题，直到运行时某条路径第一次走到才炸。

Java 这边编译器完全接受类之间的循环引用，运行时也没问题——类加载是惰性且线程安全的，A 用到 B 时 B 才被加载。只有一种情况会出事：两个类的静态初始化块互相引用，那会得到一个初始化到一半的类（字段是默认值）。这个坑存在，但比 JS 那边窄得多。

所以在 Java 里禁止循环依赖主要是为了可维护性，不是为了避免崩溃：有环意味着两个模块无法独立理解、无法独立测试、无法独立提取。这是一个架构判断，而不是安全判断——也正因如此，它适合用 ArchUnit 这样的"架构测试"来表达，而不是靠语言机制。

Q2jOOQ 生成的 Tables.PRODUCTS 是 public 的，五个功能模块都能 import 它。这算不算破坏了模块边界？值得管吗？

思路提示

算，而且是这套结构里最大的一处漏洞：order 模块能直接 import static …Tables.PRODUCTS 然后写任意查询，CatalogService 那个门面就形同虚设了。而且 jOOQ 把所有表生成在一个包里，你没法用 package-private 来分。

  • 用 ArchUnit 管。写一条规则：只有 catalog 包能访问 PRODUCTS，只有 order 能访问 ORDERS。这一档很便宜，我推荐做。规则本身就是一份"哪个模块拥有哪张表"的文档。

我的判断：做第一档，并且明确接受"共享一个数据库"这个事实。真正要防的不是"共享表定义"，而是"两个模块都写同一张表"——那才是让不变量无处安放的根源。可以再加一条规则：每张表只允许一个模块写，其它模块只读或走门面。

思路提示

  • DSLContext：不会。测试里用真数据库（Testcontainers）比用假的更能发现问题——第 11 部分会展开。
  • 日志：几乎不会。真要在测试里静音，改配置比注入简单。
  • Clock：会，但它是 JDK 的抽象类，不需要你自己定义接口。

一个可以直接用的经验法则：先直接调用具体实现，等到第二次真的需要替换时再抽接口。这个顺序几乎不会让你付返工的代价，因为"把静态方法改成接口方法"是一次机械重构，而 IDE 很擅长做这件事。

还有一个 Java 特有的提醒：无状态的服务写成静态方法完全没问题。Spring 教育了一整代人"什么都要是 Bean"，但那是因为 Spring 需要代理它们来加事务和 AOP。Javalin 没有代理，一个纯函数就该是一个静态方法——它更好测（不用构造对象）、更好读（没有隐藏状态）、也更快。

表单、校验与文件上传

对应原书第 18–22 章。原书在 service 里手写 if (!name) errors.push(…)，用 multer 接文件并相信客户端给的 MIME 类型，然后把文件存进 public/ 目录。三处都值得重写。

表单是 Web 应用里最脏的一段：所有字段都是字符串，所有字段都可能缺失，所有字段都可能是攻击者精心构造的。Javalin 的 Validator 把这段脏东西收拢成一条链——取值、转换、校验、要求非空，四步各自可以失败，失败信息统一收集。

一次完整的表单提交

陷阱 · checkbox 和"空字符串"

两个几乎每个项目都会撞一次的坑：

checkbox 不勾选时，浏览器不发送这个字段——不是发空值，是完全没有。所以判断方式是"字段存不存在"，而不是"值是什么"。如果表单用了隐藏字段配合 checkbox（为了在取消勾选时也发一个值），那就要判断具体值，而 Boolean.parseBoolean("false") 是 false、Boolean.parseBoolean("on") 也是 false——得自己列清楚哪些字符串算真。

空的文本框发的是空字符串，不是缺失。所以 .required() 挡不住"用户什么都没填就提交"——那个字段是存在的，只是内容为空。必须配一条 .check(s -> !s.isBlank(), …)。这一条漏掉的话，你会在数据库里看到一堆空名字的商品。

那个 "values", ctx.formParamMap() 是原书缺的一环：原书校验失败就重定向回表单页，用户填的十个字段全部清空。正确做法是直接渲染表单页并把原值填回去。

深入 · 为什么必须是 303 而不是 302

这是 POST-Redirect-GET 模式：写操作成功后不要直接渲染页面，而是重定向到一个 GET 页面。否则用户按 F5 会重新提交表单，创建出第二件商品；浏览器那个"确认重新提交"弹窗就是在为这个设计缺陷擦屁股。

状态码的差别很实在：302 的规范语义没有规定方法是否改变，历史上浏览器把它当 303 处理，但某些客户端（自己写的 HTTP 客户端、爬虫、旧代理）会保持 POST 方法跟随重定向——于是你的重定向目标收到了一个 POST。303 See Other 明确要求"用 GET 请求新地址"，没有歧义。

Javalin 里写成 ctx.redirect(url, HttpStatus.SEE_OTHER)；不传第二个参数时默认是 302。这是一个"默认值不是最优解"的地方，值得每次都显式写。

上传：读字节，别读声明

安全 · 魔数也不是万能的

一个文件可以同时是合法的 JPEG 和一段可执行内容——著名的例子是 GIFAR（既是 GIF 又是 JAR），以及在图片注释段里塞 HTML/JS 的 polyglot 文件。魔数校验挡住了"改个后缀就传 .jsp"，但挡不住这类。

真正让这类攻击失效的是怎么把文件发回去：从独立域名（或至少独立路径 + 严格 CSP）提供、始终显式设置 Content-Type、带上 X-Content-Type-Options: nosniff 阻止浏览器嗅探、非图片一律 Content-Disposition: attachment。做到这些，即便文件里藏了 HTML，浏览器也不会把它当页面执行。

再往上一档是重新编码：用 ImageIO 或 imgscalr 把图片解码再编码一遍，元数据和附加段全部丢掉。代价是 CPU，收益是攻击面几乎归零，顺便还能统一尺寸、生成缩略图、剥掉 EXIF 里的 GPS 坐标——最后这一条是隐私问题，很多人没想到。做电商商品图，我会做这一步。

陷阱 · 路径穿越，以及 Java 的正确写法

如果你用了用户提供的文件名（哪怕只是拼一部分），../../etc/passwd 这类输入会让文件写到目录之外。上面的代码用 UUID 生成文件名，从根上避开了——但如果你必须保留原名，正确的检查是：

Path target = mediaDir.resolve(name).normalize();
if (!target.startsWith(mediaDir)) throw new BadRequestResponse();

关键是 normalize() 之后再比较，而且用 Path.startsWith（按路径段比较）而不是 String.startsWith（按字符比较，会被 /media-evil/ 这种前缀骗过去）。

Q1价格字段用了 BigDecimal.class。Javalin 怎么知道把字符串转成 BigDecimal？如果我想直接转成自定义的 Money 类型呢？

思路提示

Javalin 内置了一组常见类型的转换器（Integer、Long、Double、Boolean、BigDecimal、Instant 等）。自定义类型需要注册一个转换器，大致是：

JavalinValidation.register(Money.class, s -> Money.ofCents(new BigDecimal(s).movePointRight(2).longValueExact()));

注册之后就能直接写 ctx.formParamAsClass("price", Money.class)。具体的注册入口在不同版本略有差别，以文档为准。

但要不要这么做值得想一下。直接转成 Money 的问题是错误消息会变差：转换失败时你只知道"转不了"，而用户可能是输了 "abc"、也可能是输了三位小数。分两步（先转 BigDecimal 拿到可读的失败，再 .check() 精度，最后 .then() 变成 Money）能给出精确得多的提示。

一般原则：转换器适合"格式明确、失败只有一种原因"的类型（日期、枚举、UUID）；需要区分多种失败原因的，拆成转换 + 校验两步。用户看到"价格格式不正确"和看到"价格最多两位小数"，体验差很多。

Q2图 8 上半部分说 Javalin 7 的 .get() 不再隐含"必须存在"。如果你从 Javalin 6 升级上来，旧代码 ctx.queryParamAsClass("page", Integer.class).get() 会怎样？这个改动是好是坏？

思路提示

旧代码在 Javalin 6 里，字段缺失会抛校验异常（400）；升到 7 之后，.get() 返回可空的值。如果调用方没判空，就变成了一个 NPE（500）——从"给用户一个明确的 400"退化成了"服务器内部错误"。

更麻烦的是这个改动不会让编译失败（Java 没有语言级空安全），所以升级时不会有任何提示。这正是第 04 部分那个 NullAway 的用武之地：如果 Javalin 的 API 标注了 @Nullable 返回值，NullAway 会在编译期把每一处未判空的 .get() 都标出来。没有 NullAway 的话，这个升级只能靠逐个搜索和测试覆盖。

这个改动本身我认为是好的：它把"这个参数是不是必需的"从一个隐含约定变成了显式选择。旧 API 的问题在于 .get() 这个名字承诺不了它的行为——读代码的人无法知道字段缺失时会发生什么。现在 .required().get() 和 .getOrNull() 一眼可辨。

顺带一个升级建议：先全局搜 AsClass(，逐个决定语义，再动别的。这类"行为变了但编译通过"的破坏性改动，是升级大版本时最该优先处理的一类——比那些直接编译失败的危险得多。

Q3校验在服务端做，用户绕过前端 JS 直接发请求照样被拦。那前端还要不要写一遍？如果要，两份规则怎么保持一致？

思路提示

要写，但目的完全不同：前端校验是为了体验，服务端校验是为了安全和数据完整。前者可以有漏洞，后者不能有。搞混这一点会导致两种错误：以为有了前端校验就能省掉服务端（灾难），或者以为有了服务端就不需要前端（用户要等一个往返才知道邮箱格式写错了）。

保持一致的手段，从便宜到贵：

  • HTML 原生属性：required、maxlength、pattern、type="email"、step="0.01"。零 JS，浏览器原生提示，无障碍免费。本项目主要用这个——它覆盖了 80% 的场景。
  • 从校验规则生成 HTML 属性：把 ProductForm 里的约束抽成一个描述对象，模板里读它渲染成 maxlength 等属性。JTE 是类型安全的，这个做法在这里比在别的模板引擎里更顺。
  • 把规则声明成注解（Bean Validation），前后端各自读同一份元数据。代价是引入 Hibernate Validator 和一整套注解体系——对一个刻意避开注解魔法的 Javalin 项目来说，这有点自相矛盾。

值得强调的一点：不一致本身并不危险，只要不一致的方向是"前端更宽松"。前端漏了一条规则，用户会看到服务端返回的错误，体验差一点；前端比服务端更严格才是真问题——用户被拦住却不知道为什么，而这条规则服务端根本不认。

认证与授权

对应原书第 23–27 章。原书用 bcrypt 存密码、用内存会话、用一句 if (req.session.user.role === 'admin') 做授权。Javalin 这边有一个额外的陷阱：它开箱就给你一个会话 API，而那个 API 在多实例下是错的。

认证回答"你是谁"，授权回答"你能做什么"。两者都容易写出"看起来能用"的版本——登录能进、退出能出——而漏洞恰恰藏在那些正常使用时永远不会走到的路径上。这一部分还要处理 Javalin 特有的一个默认值问题：没标角色的路由默认是公开的。

safeNext 那两个条件都不能少。//evil.com 是一个协议相对 URL——浏览器会把它当成 https://evil.com，于是你的登录页变成了一个钓鱼跳板。只检查 startsWith("/") 是挡不住的，这是开放重定向最常见的一种写法错误。

密码：Argon2id，参数按 OWASP 来

陷阱 · 用 char[] 而不是 String 装密码

Java 的 String 不可变、会进字符串常量池、而且你无法主动清除它——一个密码字符串可能在堆里存活到下一次 GC 之后，期间任何一次堆转储（OOM 时自动生成的、或者运维手动抓的）都会把明文密码写进文件。

char[] 可以在用完后 Arrays.fill(pw, '\0') 主动擦掉。这是 JDK 自己的 API 设计里就体现的取舍（Console.readPassword() 返回的正是 char[]）。

说实话：在一个 Web 应用里这个防护是有限的——密码从 HTTP 请求体进来时，它已经以 String 的形式在解析器里存在过了。但在你自己控制的这一段减少暴露仍然值得做，而且成本几乎为零。

安全 · 登录接口的三个细节
  • 用户不存在时也要跑一次哈希校验。否则"邮箱不存在"响应飞快、"密码错误"要等 50 毫秒，攻击者据此就能枚举出哪些邮箱注册过。做法是准备一个固定的假 hash，用户不存在时对它做一次 verify。
  • 错误消息只能有一条："邮箱或密码不正确"。分开提示对用户帮助有限，对攻击者帮助极大。
  • 限流按"邮箱 + IP"两个维度都要有。只按 IP 挡不住撞库（代理池），只按邮箱挡不住密码喷洒（一个密码试一万个邮箱）。

登录：换一个新的会话 id

深入 · __Host- 前缀和会话固定

__Host- 前缀是一个容易被忽略的加固：带这个前缀的 cookie 必须是 Secure、必须 Path=/、并且不能带 Domain 属性。这意味着子域名——哪怕被攻陷——也无法覆盖它。浏览器会拒绝不符合这些条件的 Set-Cookie，所以它是一个由浏览器强制的约束，不是靠你记得配。

会话固定攻击：攻击者先让受害者的浏览器带上一个他已知的 sid（通过子域写 cookie、URL 参数、或 XSS），如果登录时不换 id，受害者登录后那个 sid 就变成了已登录会话——而攻击者手里也有。所以第 ① 步的删除不是可选项。

顺带说一句为什么会话 id 不需要签名：如果它是 32 字节的密码学随机数，攻击者猜中一个有效值的概率是 2⁻²⁵⁶，签名要防的正是"伪造一个有效值"，因此没有增加任何安全性。签名真正有用的场景是 cookie 里存了有意义的数据（role=admin、购物车内容）——那些值攻击者能猜出格式，需要签名证明"这是服务端发的"。

陷阱 · 角色不等于权限

图 9 最后一格标了灰：required.contains(user.role()) 只能表达"是不是管理员"，表达不了"这是不是你的订单"。后者叫对象级授权，是 Web 应用里最常见的漏洞类别。

典型形态：GET /orders/1042 只检查了登录，没检查这个订单属不属于当前用户。改一下 URL 里的数字就能看别人的订单。

正确做法不是"查出来再判断"，而是把归属条件写进查询本身：

dsl.selectFrom(ORDERS).where(ORDERS.ID.eq(id)).and(ORDERS.USER_ID.eq(user.id())).fetchOptional()

查不到就是 404。这样即使有人忘了写判断，也写不出漏洞——因为那个 and 是查询的一部分，不是可选的一步。第 10 部分的订单查询全部这样写。

Q3本项目用 SameSite=Lax + Origin 校验防 CSRF，没有用 token。这在什么情况下不够？如果要加 token，Javalin 里该放在哪一层？

思路提示

SameSite=Lax 的规则是：跨站请求不带 cookie，除非是顶层导航的 GET。所以它挡住了跨站 POST，但留了口子：

  • 状态变更的 GET。如果你有 GET /cart/clear 这种路由，一个诱导点击的链接是顶层导航，会带 cookie。所以真正的第一道防线是：GET 永不改变状态。
  • 浏览器差异。旧版本浏览器可能不认 SameSite；部分浏览器对新建 cookie 有短暂的宽限策略。
  • 需要跨域的场景。一旦前端部署在另一个域名，Lax 会让正常请求也带不上 cookie，你就不得不改成 SameSite=None; Secure——而那等于关掉了这层防护，此时 token 是必需的。

加 token 的话，Javalin 里放在beforeMatched最合适，理由有二：它能拿到 ctx.routeRoles()（可以对公开的只读端点豁免），而且它在端点之前、在 body 被业务代码读取之前。

实现上有一个 Javalin 特有的注意点：如果 token 放在表单字段里，读它就意味着解析了 multipart body，而 Jetty 的 multipart 解析是一次性的。对文件上传的表单，更稳妥的是把 token 放在请求头（需要 JS）或者查询串里，避开这个顺序问题。这和第 07 部分那个"魔数读完要 reset"是同一类问题：流只能读一次。

关联查询与购物车

对应原书第 28–29 章。原书的购物车页面在循环里查数据库——教科书式的 N+1。这一部分给出三种常规解法，然后给出一个 JPA 和 Drizzle 都做不到的第四种：jOOQ 的 MULTISET。

关联数据有三种常规取法，代价完全不同：循环里一条条查（最直观、最慢）、一次 join 查完（最快但产生重复行）、分两次批量查再在内存里拼（最灵活但要手写拼装）。jOOQ 提供了第四种，它同时拿到了前两者的好处。

三种常规写法的代码

陷阱 · in 列表的三个坑

空集合：PRODUCTS.ID.in(Set.of()) 会生成 in () 或恒假条件，不同数据库行为不一。jOOQ 通常会替你处理成 1 = 0，但显式短路是两行代码的事，别指望。

过长的列表：PostgreSQL 的绑定参数上限是 65535。几万个 id 塞进 in (…) 会直接报错。超过几百个就该改用 = any(?)（一个参数传数组）——jOOQ 里是 PRODUCTS.ID.eq(DSL.any(idsArray))，只占一个参数位。

预编译语句缓存被打爆：这一条是 JDBC 特有的。in (?)、in (?,?)、in (?,?,?) 是三条不同的 SQL，每种长度都会在数据库端生成一个新的预编译语句。购物车长度从 1 到 50 变化，就是 50 条不同的语句在缓存里占位。= any(?) 顺带也解决了这个问题——无论多少个 id，SQL 文本永远相同。

购物车怎么建模

购物车有一个原书完全回避了的问题：没登录的人也能加购物车。三种做法：

方案好处代价
全放签名 cookie不查库、不落库、匿名天然支持cookie 有 4 KB 上限；每个请求都在传；改价格要重新算

这里用了 insert … select … on conflict do update：整个合并是一条 SQL，不是一个循环。(cart_id, product_id) 上的唯一索引不只是让这个语法能用——它还是"同一件商品在一个购物车里只能有一行"这条不变量的唯一可靠保证。靠应用代码先查再插，在并发下必然插出两行。

Q1商品详情页要展示商品 + 多张图片 + 最近 5 条评价。用一条带两个 join 的查询会返回多少行？用 MULTISET 呢？

思路提示

两个 join 的行数是图片数 × 评价数。3 张图 × 5 条评价 = 15 行，每行都重复携带完整的商品字段、一份图片、一份评价。这是两个一对多集合的笛卡尔积。

更糟的是它不正确：如果这个商品有 3 张图但 0 条评价，inner join 会让整个商品消失，left join 又引入 null 行要处理。而且"最近 5 条评价"这个 limit 根本没法在这条语句里表达——你没法只限制其中一个集合。

MULTISET 可以放两个甚至更多，每个子查询独立，各自可以有自己的 order by 和 limit：

select(P.NAME, multiset(select…from IMAGES…), multiset(select…from REVIEWS.orderBy(desc).limit(5)))

返回一行，里面嵌着两个正确的列表。这是 MULTISET 相对所有其它方案最明显的胜出场景——Hibernate 会直接抛 MultipleBagFetchException 阻止你抓两个集合，Drizzle 会发多条查询。

但仍然要测。三个 MULTISET 意味着三个相关子查询，数据库要为每一行主记录执行它们。主记录只有一行时（详情页）这非常划算；主记录有几百行时就要看执行计划了。

Q2商品列表用 limit 20 offset 4000 翻到第 200 页很慢。为什么？keyset 分页在 jOOQ 里怎么写？

思路提示

offset 4000 不是"跳过"——数据库仍然要找出并排序前 4020 行，再丢掉前 4000 行。代价随页码线性增长。

keyset 改成"从上一页最后一条之后继续"。jOOQ 对这个有一等支持，写法非常干净：

.orderBy(PRODUCTS.CREATED_AT.desc(), PRODUCTS.ID.desc())
.seek(lastCreatedAt, lastId)
.limit(20)

seek() 会生成标准的行值比较 (created_at, id) < (?, ?)，配上 (created_at desc, id desc) 的索引，任意一页代价相同。这比手写条件不容易出错——手写时很容易写成 a < ? or (a = ? and b < ?)，逻辑等价但优化器不一定能用上索引。

三个代价：不能跳页（只有"下一页"）；排序键必须唯一（所以要带上 id，否则同一时刻的两行会重复或遗漏）；游标要编码（别把时间戳和 id 裸露在 URL 里，base64 包一层，将来换排序方式时不会破坏已有链接）。

实践建议：面向用户的列表用 keyset，管理后台的表格用 offset。后台数据量小、需要跳页，offset 的缺点不成立；前台随时可能被爬虫翻到第一万页。

Q3JPA 有懒加载：order.getItems() 第一次访问时才发 SQL。jOOQ 没有。这让写代码变麻烦了，换来了什么？

思路提示

换来的是"这段代码会发几条 SQL" 变成可以靠读代码回答的问题。

JPA 的懒加载让 N+1 极其容易发生且难以发现：一个模板里的 ${order.items}、一个日志里的 order.toString()、一个不小心访问了关联属性的 equals——都可能在你完全没意识到的地方触发几百条查询。而且它还带来一整套额外概念：持久化上下文的边界、LazyInitializationException、open-in-view 该不该开。

jOOQ 的立场是：数据要么你查了，要么它就不在。OrderView 这个 record 里有没有 lines 字段，是你在写查询时决定的；没查就没有这个字段，用了就是编译错误。

代价确实存在：领域对象不再是"活的"，跨层传递时要想清楚"这一层需要哪些字段"。但这个思考本身有价值——它逼你在写查询时就回答"这个页面需要什么数据"，而不是让模板去决定发什么 SQL。

值得注意的是 Java 生态整体在往这个方向走：Spring Data JDBC、jOOQ、以及 JPA 里越来越被推荐的 DTO 投影，本质上都是在放弃懒加载换取可预测性。这不是"绕过 ORM 的旁门左道"，是同一个教训的多次学习。而 JTE 那边也是同一个模式：把"运行时才知道"的东西挪到编译期。

下单：事务与并发

原书全书没有出现过一次事务。它的下单流程是三条独立写操作：扣库存、建订单、清购物车。任何一步失败，数据就此不一致，而且没有任何补救机制。这是原书和"能上线的系统"之间最大的一道鸿沟。

这是整份教程最难也最值钱的一段。Javalin / jOOQ 在这里比 Spring 更"裸"——没有 @Transactional、没有代理、没有传播行为。好消息是它因此毫无歧义：回调里的就在事务里，回调外的就不在。

最小可用：一个正确的下单

深入 · 为什么订单行要存价格快照

原书的 order_items 只有 product_id 和 quantity，价格靠 join products 实时取。这意味着管理员改一次商品价格，所有历史订单的金额都跟着变了——已付款的订单，详情页显示的总额和用户实际支付的对不上。更麻烦的是商品下架或删除后，历史订单直接查不出商品名。

所以 order_items 要存三样快照：单价、商品名、以及必要的规格描述。它们在下单那一刻被复制一份，此后与商品表脱钩。

这不是冗余，是不同的语义：products.price_cents 是"现在卖多少钱"，order_items.unit_price_cents 是"当时成交价"。它们碰巧在下单那一刻相等，但它们是两个不同的事实。

把事务上下文传下去：一个绕不开的麻烦

注意每个辅助方法的第一个参数都是 DSLContext tx。这就是没有环境事务的代价：凡是要参与这个事务的数据库操作，都必须拿到同一个 tx。用 deps.dsl() 而不是 tx，那条语句会从连接池另取一个连接、开另一个事务，回滚时它不会被撤销。

怎么防做法评价
类型约束所有数据访问方法第一个参数强制为 DSLContext，且这些方法是包级可见的，只有本模块的 Service 能调推荐。把"必须在事务里"变成签名的一部分
ArchUnit 规则禁止 Deps.dsl() 在功能模块里被直接调用，只允许 Service 层的入口方法用能抓住直接调用，抓不住间接调用
不要用 ThreadLocal 藏事务见下方把 @Transactional 的坑搬过来
陷阱 · 用 ThreadLocal 做"环境事务"是在重造 @Transactional

Javalin 是一个请求一个线程，所以用 ThreadLocal<DSLContext> 做隐式当前事务在技术上完全可行，写起来也确实清爽。但它会带回 Spring 里那套熟悉的困惑：

  • 看代码看不出事务边界。一个方法到底在不在事务里，取决于谁调用了它。
  • 嵌套语义要自己定。里层又开一个事务，是复用外层、开保存点、还是新连接？这就是 Spring 的 Propagation 那七个选项，你得自己实现一遍。
  • 一旦用了线程池或虚拟线程做并行，上下文就丢了。而且丢了不报错——只是悄悄用回了池里的另一个连接。第 12 部分开虚拟线程时，这个坑会变得更容易踩。

我的判断：在一个只有五六处事务的项目里，显式传 tx 的成本远低于引入隐式上下文的认知成本。它丑，但它诚实——而事务恰恰是最不该有惊喜的地方。

两个人同时买最后一件

深入 · 隔离级别不会替你解决这个问题

常见的误解是"开个更高的隔离级别就好了"。事实是：

  • Read Committed（PostgreSQL 默认）：图 11 那个场景会原样发生。
  • Repeatable Read：第二个 UPDATE 会因为检测到并发修改而报 could not serialize access，事务失败。这确实防住了超卖——但代价是你必须自己写重试逻辑，否则用户看到 500。
  • Serializable：能防住更复杂的模式，代价是更高的冲突率和同样必需的重试。

换句话说，高隔离级别把"数据错了"变成"事务失败了"——这是巨大的进步，但它没有免除你处理失败的责任。而方案 ① 连失败都不会有，它把冲突消解在了一条语句内部。

实践建议：默认用 Read Committed + 原子语句/显式锁；只有当业务不变量确实跨多行多表、难以用单条语句表达时，才升到 Serializable 并配上重试。升隔离级别是一个需要配套工作的决定，不是一个开关。

事务里绝对不能做的事

放在事务里后果
调用支付网关（800 ms）连接被独占 800 ms，其中 99.6% 的时间什么也没干。连接池 10 个，这台机器每秒最多处理 12.5 个下单请求——而且行锁也一直没放，任何想改同一件商品库存的请求都在等。
发邮件、写文件、调任何外部接口同上。而且外部服务超时会导致事务回滚——一笔已经成功的支付因为邮件没发出去被回滚了，这个因果关系荒谬但真实存在。
Thread.sleep 或等锁同上，而且更难发现。
大批量的循环插入事务时长随数据量线性增长。用 tx.batch(...) 一次发出去（上面下单代码里就是这么写的），而不是循环 execute()。

规则：事务内不做任何网络 I/O、不读文件、不 sleep、不等锁。事务应该短到用毫秒计——它持有的是整个系统里最稀缺的两种资源：连接和行锁。

那支付怎么办？拆成两个事务：第一个事务扣库存 + 建订单（状态 pending_payment），事务外调用支付网关，第二个事务把状态改成 paid。代价是中间出现了一个"订单已建但未支付"的状态——这不是缺陷，是如实建模，现实中这个状态本来就存在。它带来两个必须做的配套：一个定时任务把超时未支付的订单关掉并把库存还回去，以及支付回调必须幂等。

陷阱 · HikariCP 的池大小不是越大越好

直觉是"池小了会排队，那就调大"。但连接不是免费的：每个数据库连接在 PostgreSQL 服务端是一个进程，几百个连接会让数据库自己忙于上下文切换。经验公式是 核心数 × 2 + 有效磁盘数，对一台 4 核数据库来说大约是 10——比大多数人的直觉小得多。

如果 10 个连接不够用，正确的反应是问"为什么每个请求占用连接这么久"，而不是调大池。上面那张表里的每一行都是常见答案。

Q1购物车里有三件商品，扣第三件时库存不足抛了异常。前两件的库存被扣掉了吗？如果 reserveStock 里不小心用了 deps.dsl() 而不是 tx，答案有变化吗？

思路提示

正确实现下：没有。异常从 transactionResult 的回调里抛出，jOOQ 发 ROLLBACK，前两条 UPDATE 一起撤销。这正是事务的意义。

怎么防：把 DSLContext 作为必填的第一参数，并且让数据访问方法是包级可见的（第 06 部分那个 Java 独有的武器）——这样别的模块连调用它的机会都没有，只能走 Service 门面，而门面负责开事务。

Q2jOOQ 的事务回调里可以再调用 tx.transaction(...)。这会开一个新事务吗？如果内层抛异常但被外层 catch 住了，会发生什么？

思路提示

不会开新事务——jOOQ 的嵌套事务默认是保存点（SAVEPOINT）。内层开始时打一个保存点，内层抛异常时回滚到那个保存点，外层可以继续。

所以"内层失败、外层 catch 住继续"是可行且语义正确的：内层做的改动被撤销了，外层之前做的改动还在。这和 Spring 的 Propagation.NESTED 是同一个机制。

但有两个坑要知道：

  • 保存点不是万能的。如果内层的失败是数据库级的错误（比如违反约束），PostgreSQL 会把整个事务标记成 aborted 状态——除非你确实回滚到了保存点。jOOQ 会替你做，但如果你自己 catch 了异常而没有让它传出内层回调，保存点就不会被回滚，后续所有语句都会报 current transaction is aborted。要 catch 就在内层回调外面 catch。
  • 别用嵌套事务来模拟"这一步失败了不要紧"。那通常说明这一步根本不该在事务里——比如记审计日志。正确做法是把它挪出事务，或者接受它和主流程同生共死。

更一般的建议：嵌套事务是一个应该很少用到的工具。在这个项目里我一次都没用——如果你发现自己需要它，先问问是不是事务边界画错了。

Q3Spring 的 @Transactional 有个著名的坑：同类方法内部调用不走代理，事务不生效。jOOQ 没有代理，所以没这个坑。但它有没有别的"看起来在事务里其实不在"的情况？

思路提示

有，而且不止一种：

  • 用了 dsl() 而不是 tx。Q1 说过，这是最直接对应 Spring 那个坑的一种——只不过在 Spring 里你看不出来，在这里它至少是字面上可见的。
  • 在回调里起了新线程。CompletableFuture.supplyAsync(() -> tx.select()…)：tx 绑定在一个 JDBC 连接上，而 JDBC 连接不是线程安全的。两个线程同时用它，行为未定义——可能报错，可能拿到错乱的结果。第 12 部分开虚拟线程之后，"顺手并行一下"的诱惑会更大，这一条要格外小心。
  • 回调里捕获了异常但没有重新抛出。try { … } catch (Exception e) { log.error(...) }——回调正常返回了，于是 COMMIT，把一个失败到一半的状态提交了。这一条最隐蔽，因为写这段代码的人本意是"让错误不要中断流程"。
  • DDL 语句。PostgreSQL 的 DDL 是事务性的（这点比 MySQL 好），但某些语句（alter type … add value、create index concurrently）不能在事务块里执行。这在迁移脚本里会撞到。

值得注意的是这几条都有一个共同特征：它们都是"显式边界 + 共享可变资源"这个模型的固有风险，而不是某个框架的设计缺陷。Spring 的坑源于隐式代理，这里的坑源于显式传递——两者都需要知道机制才能避开，只是要知道的东西不同。

对照 · 该 mock 什么

Java 这边的习惯是用 Mockito 把仓库层替换掉，理由是"单元测试不该碰数据库"。这个理由在 2010 年成立（起一个数据库要几分钟），今天不成立（Testcontainers 起一个 PostgreSQL 要两秒，而且整个测试会话复用）。

本项目的立场：只 mock 你不拥有、且调用有代价或副作用的东西——支付网关、邮件、短信。而且用手写的假实现（一个实现了 PaymentGateway 接口的类），不用 mock 框架。手写假实现能表达"第三次调用失败"这类场景，而且它是类型安全的：接口变了，假实现编译不过。

数据库不 mock。mock 掉数据库的测试能通过而真实代码出错，是所有测试策略里最糟的一种失败模式——它给你信心，但那个信心是假的。第 10 部分那个"用了 dsl() 而不是 tx"的 bug，在 mock 的世界里根本测不出来。

时间也不用 mock：第 06 部分把 Clock 做成了依赖，测试里传 Clock.fixed(...) 就行——JDK 自带，零依赖。

Q1端点测试里怎么伪造一个"已登录"的请求？直接往 ctx 里塞用户行不行？

思路提示

不行——JavalinTest 给你的是一个 HTTP 客户端，拿不到中间的 ctx。这其实是好事：它逼你走真实路径。

三种做法，推荐程度递减：

  • 真的建一个会话：在测试库里插一行 sessions，请求时带上对应的 cookie。这条路径和生产完全一致，连"会话过期了会怎样"都能顺便测到。需要真数据库，而这正是你已经有的。

  • 构造一个测试专用的 app，把 Access.enforce 换成一个总是放行的版本。快，但测的不是真正跑在生产的那套配置——如果真实的 App 忘了注册 beforeMatched，这个测试照样通过。

我选第一种，封装成 sessionCookieFor(user)。判据是：这个测试要防的 bug，会不会被这种伪造方式绕过？鉴权类的测试尤其不能用第三种，因为它伪造掉的正是被测对象。

顺带一个 Javalin 特有的便利：JavalinTest.test() 的第一个参数是一个 Javalin 实例，所以你可以在测试里构造一个使用测试数据库、但路由和处理器链完全相同的 app。把 App.build(Deps) 抽成一个纯函数、main 只负责组装依赖和 start()，这件事就变得很自然——这也是第 06 部分那个组装点设计的又一个回报。

思路提示

我对全局百分比门禁持保留态度，理由是它奖励错误的行为：最容易涨覆盖率的是给 record 的访问器、DTO、视图组件补测试，而这些地方几乎不出 bug；最难覆盖的是错误分支和并发路径，而那才是 bug 藏身之处。于是团队会本能地去刷容易的那部分。

更有用的几种替代：

  • 按包设不同的线：order、catalog 这些放着不变量的包要求 90%，视图和生成代码不设线（jOOQ 生成的代码必须排除，否则数字完全失真）。
  • 只看增量覆盖率：这个 PR 新增的代码有没有被测到。存量欠债慢慢还，新债不许欠。
  • 盯未覆盖的分支而不是行：catch 块、if (!ok) 分支、updated == 1 的否定路径——这些是覆盖率报告里最该看的地方。

一个具体建议：与其定 80%，不如列一张"必须有测试的清单"——每一处金额计算、每一个权限判断、每一条数据库唯一约束、每一处并发写。这张清单是可以被 review 的，而百分比不是。

打包、配置与上线

对应原书第 30–31 章。原书把代码推到平台，环境变量在网页控制台里点着填，synchronize: true 原样带上生产。这一部分讲怎么把一个 Javalin 应用变成可以放心重启、可以滚动更新、出事能查的东西。

上线要解决三个独立的问题：配置怎么进来（并且配错时立刻知道）、进程怎么优雅地停下来（不掐断正在处理的请求）、出事了怎么定位（日志能不能拼成一条链路）。最后还有一个 Java 独有的机会：虚拟线程。

配置：启动时炸，别在半夜炸

启动时失败是最好的失败：部署流水线会立刻发现，流量还没进来。相比之下，"少配了一个变量，两小时后第一个用户点了支付才崩"是最坏的一种。注意那个 missing 列表——一次报出全部问题，比修一个跑一次强得多。

镜像：多阶段构建

陷阱 · 容器里的 JVM 内存配置

不设 -Xmx 时，JVM 会按"物理内存的 1/4"来定堆上限。现代 JVM 能识别容器的 cgroup 限制，所以这个 1/4 是按容器限额算的——但 1/4 通常太保守，剩下的内存白白浪费。用 -XX:MaxRAMPercentage=75 更合适。

-XX:+ExitOnOutOfMemoryError 也值得默认加上：OOM 之后的 JVM 状态是不可信的——某些线程死了、某些锁没释放、健康检查可能还在返回 200。直接退出让编排系统重启它，比留一个半死不活的实例接流量好得多。

再补一条 Java 特有的加速：AppCDS（类数据共享）。构建时把类元数据预先归档，启动时直接映射进内存，能把冷启动再削掉 30%~40%。对一个本来就只要 200 毫秒启动的应用，这让它更适合频繁扩缩容的场景。

停机与线程模型

深入 · liveness 和 readiness 是两个不同的问题

liveness（/healthz）回答"这个进程还活着吗"，失败的后果是重启。所以它必须极其简单——不查数据库、不调外部服务。一旦你在 liveness 里查了数据库，数据库抖动就会让编排系统把所有健康的应用实例全部重启，把一次短暂故障放大成一次全站宕机。

readiness（/readyz）回答"现在能不能给我发流量"，失败的后果是摘除但不重启。这里可以（也应该）检查数据库连通性——数据库连不上时这个实例确实没法干活。

把两者写成同一个端点是很常见的错误，而且它的危害只在故障时显现——正是你最不希望雪上加霜的时候。

日志：一条链路要能拼起来

陷阱 · MDC 是 ThreadLocal，用完必须清

Javalin 的线程来自 Jetty 的线程池——这个线程处理完你的请求，会被回收去处理下一个请求。如果不 MDC.clear()，下一个请求的日志会带着上一个请求的 requestId。

这个 bug 的可怕之处在于它只在排查问题时才伤害你：平时没人看日志，一旦出事你按 requestId 搜出来的是几个不相干请求混在一起的记录，而你完全不知道它们是混的。

清理必须放在 after 里而不是端点末尾——因为 after 是框架保证会执行的（第 02 部分），异常路径上也不会漏。这又是那条线性流水线设计的一次回报。

另外两条：输出 JSON 而不是拼接字符串（日志系统才能按字段筛选和聚合，Logback 配一个 JSON encoder 即可）；永远不要把请求体整个记下来（里面有密码和地址）。

Q1部署流程是"跑迁移 → 滚动更新应用"。滚动更新期间新旧两版代码同时在跑。这对迁移提出了什么约束？"把 user_name 改名成 full_name"要怎么做？

思路提示

约束是：每一次迁移都必须同时兼容上一个版本的代码。因为迁移跑完之后、新代码全部上线之前，旧代码还在访问这个已经变了的库。

改列名不能一步到位（旧代码会立刻报 "column does not exist"），要拆成四次部署：

  1. 迁移：add column full_name（可空）。旧代码不受影响。
  2. 部署代码 A：同时写两列，读仍读旧列。再回填历史数据。
  3. 部署代码 B：改成读新列。此时两列都对，随时可以回滚到 A。
  4. 迁移：drop column user_name。确认没有回滚需求之后才做，通常等一两周。

这套流程叫"扩展-收缩"。看起来啰嗦，但对比一下代价：四次部署每次几分钟；而一次不兼容的迁移可能意味着几分钟的全站 500，外加一个没法回滚的处境——回滚代码容易，回滚已经删掉的列不容易。

jOOQ 在这里帮了一个额外的忙：第 4 步执行后重新生成代码，任何还在引用 USER_NAME 的地方都会编译失败。也就是说，你没法在代码还引用旧列的时候把列删掉——构建会拦住你。这是第 05 部分那条"表即事实"的信息流方向带来的又一个好处。

Q2图 13 说打开虚拟线程后吞吐可能没变。那什么情况下它确实有明显收益？怎么判断自己属于哪种？

思路提示

先看瓶颈在哪。做一次简单的判断：压测时观察线程池使用率和连接池等待时长。

  • 线程池满了、连接池不满 → 虚拟线程有明显收益。典型场景是请求里有大量非数据库的等待：调用多个外部 API、读对象存储、等待下游服务。这些等待不消耗连接，只消耗线程——而线程正是虚拟线程要解决的东西。
  • 连接池等待时长很长 → 虚拟线程帮不上。瓶颈在数据库，先去看第 03 部分的索引和第 10 部分的事务时长。
  • CPU 打满 → 两者都帮不上，该加机器或优化算法了。

还有一种收益是非吞吐性的，但同样重要：过载时的表现。平台线程模型下，线程池满了之后新请求在队列里等，队列满了就直接拒绝——表现是断崖式的。虚拟线程下，请求都能被接住并进入下游的排队，降级是渐进的。用户体验上，"慢一点"通常好过"连不上"。

但要配合限流：能接住不等于该接住。如果一万个请求都在等那 10 个数据库连接，每个都会超时——不如在入口就拒绝一部分，让剩下的能正常完成。虚拟线程让你有能力接住更多请求，同时也让你更需要主动限流。

Q3Spring Boot 打成 jar 是一条命令，还有 Buildpacks、原生镜像等一整套工具。Javalin 这边要自己配 Shadow 插件、写 Dockerfile。这个差距在实践中有多重要？

思路提示

比想象中小，而且方向是双向的。

Spring 那边省的：确实省事——bootJar 开箱可用，Buildpacks 能自动选基础镜像、配内存参数、做分层缓存。对一个不想碰 Dockerfile 的团队，这个价值是真的。

Javalin 这边省的：一个 Javalin fat jar 大约 15~25 MB，Spring Boot 的通常是 40~60 MB；启动 200 毫秒对 2 秒。在需要频繁扩缩容、或者按调用次数计费的环境里，这个差别直接变成钱。而且 Dockerfile 是显式的——你知道基础镜像是什么、JVM 参数是什么，出问题时能改。

更根本的一点：这两套东西都是一次性成本。写一次 Dockerfile 花半小时，之后三年不用动。而你每天都要面对的是启动速度、调用栈深度、以及"这个行为是从哪来的"这类问题——那些是持续成本。

我的建议：不要用"打包是否方便"来选框架。值得据此选的是团队规模和运维成熟度——如果团队里没人愿意维护 Dockerfile 和 JVM 参数，Spring Boot 的那套自动化确实更合适；如果有人乐意管这些（或者已经有一套统一的容器构建流水线），Javalin 的显式反而更省心。

顺带：如果要追求极致启动速度，Javalin 也能编译成 GraalVM 原生镜像——而且比 Spring 容易得多，因为它几乎不用反射，需要的配置元数据非常少。这算是"没有魔法"的一个意外红利。

Javalin 坐在中间。把它和左右两端并排读，几个结论会变得很清楚：

  • 和 Spring 比：少了容器和代理，多了 package-private 这道编译器强制的边界；事务从注解变成回调，坑的位置换了但没有消失。
