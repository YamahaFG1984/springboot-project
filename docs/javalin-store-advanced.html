三个缺口

  1. 没有异步。第一季每个请求都是"进来—处理完—返回"。真实系统里总有些事不能在请求里做完：发邮件、调支付、生成报表。一旦有了"稍后再做"，就有了"做失败了怎么办"和"做了两次怎么办"。
  2. 没有外部依赖。数据库是你的，它慢了你能查、挂了你能修。支付网关不是——它会超时，而超时既不是成功也不是失败，是"不知道"。整个第 08、09 部分都在处理这个"不知道"。
  3. 没有时间。第一季里唯一的时间是 created_at。这一季有超时、有过期、有定时任务、有 TTL——而所有涉及时间的正确性问题，都会以并发问题的形式暴露出来。
对照 · 这一季和另外两条线的关系

同样的 13 个主题，Spring Boot 线和 Hono 线各有一份。三边的结论几乎逐条相同——因为这一季讲的东西大多不属于框架层面：Redis 的丢失窗口、超时的三种真相、Outbox 的原理、限流算法的边界突发，换成任何语言都一样。

深入 · 这一季不引入消息队列

讲到异步和事件，很容易顺手加一个 Kafka 或 RabbitMQ。我刻意不加，理由有两条：

第一，大多数团队在真正需要 MQ 之前就引入了它，然后把一个单体的复杂度换成了一个分布式的复杂度，却没有得到对应的收益。第 10 部分会用一张数据库表 + for update skip locked 实现完整的 Outbox，它能扛住每秒几百条投递——这个量级覆盖了绝大多数电商系统。

第二，也更重要：MQ 不能免除你思考幂等、顺序和重复。它只是把这些问题换个位置。先在一个能完全看清的实现里把这些概念搞懂，再决定要不要换成 MQ，顺序更划算。第 10 部分末尾会给出三个"该换真 MQ 了"的具体信号。

01

Redis 进场

加一个组件之前，先想清楚它什么时候会骗你。这一部分不写业务代码，只建立一条贯穿整季的判断线，外加一个 Java 独有的、能直接变成远程代码执行的坑。

Redis 快得让人放松警惕。但"快"是有代价的，代价藏在它承认写入成功的那一刻，数据到底在哪。默认配置下，答案是"在一台机器的内存里，可能还没落盘，可能还没到副本"。这一节把三个窗口画出来，之后每次用到 Redis 都回到这张图上做判断。

Lettuce：一个连接就够，因为它线程安全

深入 · Lettuce 和 Jedis 的关键差别

Lettuce 的 StatefulRedisConnection 是线程安全的，多个线程可以同时用同一个连接发命令——底层是 Netty，命令被复用到同一条 TCP 连接上（pipelining）。所以你只需要一个连接，不需要连接池。

Jedis 不是。一个 Jedis 实例代表一条连接，且不能并发使用，所以必须配 JedisPool，然后每次 try (var jedis = pool.getResource())。忘了归还就是连接泄漏——这是 Jedis 项目里最常见的一类事故。

有两个例外需要独占连接，用 Lettuce 时也要注意：阻塞命令（BLPOP 等，会占住连接）和事务（MULTI/EXEC，状态绑定在连接上）。这两种情况要单独 client.connect() 拿一条专用连接。本项目两者都不用——需要原子性时一律走 Lua（第 06、11 部分）。

虚拟线程下这个差别更明显：几千个虚拟线程各自去 JedisPool 抢连接，池会成为新瓶颈；Lettuce 的共享连接则完全不受影响。这是第一季第 12 部分那个"虚拟线程不会凭空变出下游容量"的一个反例——在 Redis 这一侧，它确实不需要额外容量。

陷阱 · disconnectedBehavior 默认会攒命令

Lettuce 默认在连接断开时把命令缓存在内存队列里，等重连后一起发出去。听起来贴心，实际后果是：Redis 挂掉的那一分钟里，你的应用不是快速失败，而是每个请求都在等一个可能永远不返回的 Future，直到超时——或者内存被队列吃光。

对缓存场景我们要的恰恰相反：Redis 不可用时立刻抛异常，让调用方走回源逻辑。所以设 REJECT_COMMANDS，并配一个短的命令超时。第 13 部分会把这个决定的完整后果展开。

键名：只在一个地方构造

那个 v1 值得解释：缓存值的结构一旦改变，老数据就是毒药。比如你给缓存对象加了一个字段，新代码读到旧 JSON 会拿到 null——而它已经通过了编译。把版本号写进键前缀，发布时改成 v2，所有旧缓存自动作废，不需要清理脚本，旧键靠 TTL 自己过期。

序列化：这里有一个能变成 RCE 的坑

安全 · 绝对不要在 Redis 上用 Java 原生序列化

Java 有一个诱人的捷径：给对象实现 Serializable，用 ObjectOutputStream 写成字节存进 Redis，读的时候 ObjectInputStream.readObject()。一行代码不用写映射，什么类型都能存。

这是一个远程代码执行漏洞。readObject() 会在反序列化过程中调用被反序列化类的方法——攻击者只要能往那个 Redis 键里写入精心构造的字节，就能借助 classpath 上的"gadget 链"执行任意代码。而"能往 Redis 里写"这件事比想象中容易：Redis 没有密码或绑到了 0.0.0.0、内网横向移动、某个能写任意键的业务漏洞、甚至一次配置失误。

这不是理论风险，是 Java 生态里最经典的一类真实漏洞。规矩：跨进程边界的数据，一律用 JSON（或其它数据格式），永不用 Java 原生序列化。

顺带，即使抛开安全，原生序列化还有两个实际问题：字节格式和类结构绑定（加个字段、改个包名，老缓存全部读不出来，抛 InvalidClassException），以及只有 Java 能读（运维想用 redis-cli 看一眼都做不到）。

两个细节：FAIL_ON_UNKNOWN_PROPERTIES 关掉，这样"新代码读到多了字段的旧缓存"不会炸；解析失败当未命中，回源重建即可。而绝不开启 Jackson 的 default typing——那等于把"实例化哪个类"的决定权交给了 JSON 内容，是原生序列化那个漏洞的 JSON 版本。

思路提示

错在库存属于第三类：清空 Redis 之后无法从 PostgreSQL 重建——数据库里的 stock 是初始值，Redis 里的才是当前值，两者的差额（已经卖掉多少）只存在于那个易失的计数器里。窗口 ③ 一次故障切换，就可能把几百笔扣减凭空还回去，然后超卖。

可以救，但要换个说法：Redis 计数器只是一道闸门，不是账本。典型用法是秒杀——先用 DECRBY 挡掉 99% 注定失败的请求，剩下的 1% 仍然要去 PostgreSQL 走第一季图 11 那条原子条件 UPDATE，以那里的结果为准。

这样即使 Redis 丢了数据，最坏结果是"闸门放宽了，更多请求打到数据库"，而不是"卖超了"。判据：Redis 出错时，错误的方向是性能变差还是数据变错。前者可以接受，后者不行。这条判据在第 06 和第 07 部分还会各用一次。

Q2Redis 是单线程处理命令的，Java 这边是多线程 + 一个共享的 Lettuce 连接。这两个模型叠在一起，会产生什么第一季没有的性能陷阱？

思路提示

两边各有一类，而且都不报错，只表现为"莫名其妙变慢"。

Redis 侧：一条慢命令会阻塞所有客户端，因为它只有一个线程执行命令。危险的有 KEYS *（生产禁用，用 SCAN）、对百万元素的集合做 SMEMBERS/HGETALL、以及写得不好的 Lua 脚本。你会看到"所有 Redis 请求同时变慢"，而 Redis 的 CPU 只有一个核在满载。

Java 侧：所有线程共享一条 TCP 连接，命令在 Netty 的事件循环上排队。一条大响应（比如 5 MB 的商品列表缓存）会占住这条连接的读取和反序列化，后面排队的命令都要等。而且 Jackson 解析 5 MB JSON 是一次可观的 CPU 开销，落在 Netty 的 I/O 线程上——这会拖慢所有人，不只是发起这次请求的线程。

共同的教训：缓存值要小而多，不要大而少。与其缓存整个商品列表，不如按 id 缓存单个商品再用 MGET 批量取——网络往返一样是一次，但每个值都小，解析成本分散，而且命中率更高（一个商品变了只失效一个键）。

Lettuce 还有一个针对性的选项：可以给某些操作用独立的连接，把大对象的读取和高频小命令隔开。这是"隔板"思想在客户端层的应用，和第 08 部分要讲的是同一个道理。

Q3键前缀里的 v1 解决了"缓存结构变了"的问题。但如果你只是修了一个 bug（比如价格算错了），已经缓存的错误数据要怎么清？

思路提示

三种手段，代价递增：

  • 等 TTL 过期。TTL 5 分钟就是 5 分钟内还有人看到错价。够不够取决于错的是什么——排序错了可以等，价格错了不能等。这解释了为什么 TTL 不该统一设成一个值：数据"错了能忍多久"决定它的 TTL。
  • 精确删键。知道是哪些商品受影响就 DEL 掉。前提是键设计允许精确定位——这也是"按 id 缓存"比"缓存整个列表"好的又一个理由。
  • 改版本号发布。v1 → v2，全部作废。最彻底，但代价是瞬间全部回源——所有缓存同时失效，数据库要接住全部流量。这就是第 04 部分要讲的雪崩，只不过这次是你自己造成的。

实践中我会这样组合：版本号只在结构变更时改（那种情况下必须全废）；bug 修复用精确删除；实在要全废就分批删，或者给新版本的 TTL 加随机抖动让回源分散开。

还有一个常被忽略的准备工作：提前写好一个能按前缀批量清理的运维入口（用 SCAN 而不是 KEYS），并且演练过。出事时现写脚本，第一版八成会用 KEYS *，然后把 Redis 卡死——在一个本来就在出事的时刻。

02

会话与购物车外置

第一季把会话和购物车都放在 PostgreSQL 里。这一部分把它们搬到 Redis——但先说清楚这笔买卖到底赚不赚，因为"会话当然要放 Redis"是一句流传很广却经常不成立的话。

搬家的动机通常被说成"性能"。真去量一下：第一季那条 sessions join users 的主键查询在 PostgreSQL 上大约 0.2 ms，Redis 的 GET 大约 0.15 ms。差距在网络往返的噪声里。所以如果理由只是快，那就不必搬。真正的理由是另外两条，而它们各自带着代价。

深入 · 为什么是 Lua 而不是 MULTI

Redis 的 MULTI/EXEC 常被称作"事务"，但它不是你熟悉的那种事务：没有回滚（某条命令执行时报错，其它命令照常生效），而且不能在中途读到结果再分支——所有命令是一次性排队提交的。

上面这段逻辑需要"改完数量、看结果决定要不要删"，这正是 MULTI 做不到的。Lua 脚本是 Redis 上唯一的原子读改写手段：它在服务端单线程执行，中途不会被别的客户端插入。

不用 Lua 会怎样？HINCRBY 返回 0，你发 HDEL；但在这两条命令之间，另一个线程可能刚 HINCRBY +1 把它加了回来——于是你把刚加进去的商品删了。概率很低，但会发生，而且没有任何日志。

顺带一个实际收益：Lua 把四次往返变成一次。购物车增删是高频操作，这个收益是稳定的；顺手拿到的正确性算是白送。

但脚本必须短。它在 Redis 的单线程上阻塞执行——第 01 部分 Q2 那条规则在这里同样适用。四条命令没问题，遍历大集合就不行。

先分清三种"不见了"，它们的证据完全不同：

  • TTL 到期。30 天没动过的车被回收。可以查：如果用户上次操作是一个月前，就是它。这不是故障，但可能是产品决策错了——真实电商的购物车通常保留更久。
  • Redis 丢数据。特征是成批发生、时间点集中。所以监控里必须有 Redis 的重启/故障切换事件，并且能和用户反馈的时间对齐。没有这条时间线，你永远只能猜。
  • 合并逻辑 bug。特征是集中在"刚登录之后"。

让它不再是猜，需要两件事：埋一个"购物车总条目数"的指标（按小时聚合，突然的断崖一眼可见），以及在关键操作上打结构化日志（merge 了几项、清空是谁触发的）。

还有一个更根本的选择：如果购物车对业务真的重要（对电商来说通常是的——它是转化漏斗的最后一格），那就不该只放 Redis。可以 Redis 做读写主力、异步落一份到 PostgreSQL 做备份，或者干脆退回第一季的方案。"购物车放 Redis"是这一季里我最不确定的一个决定，图 1 把它归到"有争议"就是这个意思。

Q2会话值用 Jackson 序列化成 JSON。如果某天给 SessionValue 加了一个字段（比如 tenantId），已经在 Redis 里的旧会话会怎样？

思路提示

取决于 Jackson 的配置和字段类型：

  • 新字段是对象类型（Long、String）：旧 JSON 里没有它，反序列化后是 null。代码里如果没判空就 NPE——而第一季那个 @NullMarked 帮不上忙，因为 Jackson 通过反射赋值，绕过了编译期检查。这正是第一季第 04 部分 Q2 说的第三类边界。
  • 新字段是基本类型（long）：得到 0。更隐蔽——不会崩，只会算错。
  • 如果 SessionValue 是 record 且用了规范构造器校验：可能直接抛异常。而我们的 Codec.decode 把异常转成了"未命中"，于是用户被登出——行为是安全的，但会有一批用户莫名其妙要重新登录。

三种应对：新字段一律给默认值（record 的紧凑构造器里补）；改结构就改键前缀版本号（v1 → v2，旧会话全部作废，代价是全站重新登录，适合安排在低峰期）；或者接受"解析失败 = 未命中"这个降级，只要它对用户的表现是可接受的。

会话这个场景我倾向第一种：加字段时给默认值，不动版本号——因为把全站用户登出的代价，通常大于容忍几天的旧数据。而商品缓存那种场景就该直接改版本号，反正回源就重建了。同一个问题在不同数据上答案不同，判据仍然是"丢了会怎样"。

Q3图 2 说会话搬到 Redis 的真实收益是"省掉过期清理"和"省掉每请求一次写库"。如果你的会话只有几万个、QPS 几百，这两条值多少？你会怎么向团队解释"我们不搬"？

思路提示

几乎不值什么。具体算一下更有说服力：

  • 过期清理：一条 delete from sessions where expires_at < now()，每小时跑一次，几万行的表上是毫秒级。省掉的是十行代码和一个定时任务，不是运维负担。
  • 滑动续期的写入：QPS 300 意味着每秒 300 次 UPDATE。听起来多，但那是小表上的主键更新，PostgreSQL 轻松承受；而且可以优化成"距上次续期超过 5 分钟才写"，写入量立刻降到几乎为零。这个优化只有两行代码，比引入一个新组件便宜得多。

怎么解释：不要说"Redis 没用"，要把讨论拉到成本那一侧。引入 Redis 存会话意味着多一个必须高可用的组件、多一条故障路径（它挂了全站登出）、多一套要自己维护的反向索引、多一份运维知识。这些成本是确定的，而收益是假设的。

然后给一个可验证的触发条件："等到会话表的写入占到数据库写入量的 20%，或者清理任务开始影响主库，我们就搬。"把决定挂在一个可测量的信号上，比争论谁的直觉对更有效——也让"以后要搬"这件事不会被遗忘。

顺带：这一季后面仍然要用 Redis（缓存、限流、闸门），所以"引入 Redis"这个成本迟早会付。这时候把会话也放进去，边际成本确实低了很多。判断要看边际成本，不是绝对成本——这也是为什么同一个决定在不同阶段会有不同答案。

03

分页、动态查询与索引

这一部分排在缓存前面是刻意的：缓存不是慢查询的解药，是慢查询的止痛片。先把索引和分页做对，剩下的才轮到缓存——顺序反了，你会得到一个"平时很快、缓存一失效就雪崩"的系统。

商品列表是这个商店流量最大的页面，也是唯一可能被爬虫翻到第一万页的页面。第一季第 09 部分 Q2 提过 keyset 分页，这里完整实现，并且把"怎么知道快不快"一起讲了——不会读执行计划的话，索引优化就是在猜。

动态查询：条件列表 + noCondition()

三个小技巧值得单独指出。where(Collection<Condition>)：不用手工 and() 串联，空列表也能正常工作。seek()：生成 (created_at, id) < (?, ?) 这种行值比较，语义正是字典序，而且 PostgreSQL 能用它走复合索引——手工展开成 a < ? or (a = ? and b < ?) 逻辑等价，但优化器不一定能用上索引。limit + 1：多取一条就知道有没有下一页，不用再发一条 count(*)——而 count 在大表上是全扫，经常比主查询还慢。

索引：三条决定命中率的规则

规则说明
复合索引的列序等值条件的列在前，范围/排序的列在后。(published, created_at desc, id desc) 能同时服务 where published 和后面的排序；反过来 (created_at, published) 就用不上前缀。
部分索引create index … on products (created_at desc, id desc) where published。索引里只放已上架的商品——体积小得多，而且它把"我们只查这一部分"这个事实写进了 schema。第一季的 V1__init.sql 里已经建了。
索引覆盖查询需要的列全在索引里时，PostgreSQL 可以只读索引不回表（Index Only Scan）。用 include (name, price_cents) 把展示列带上，代价是索引变大。先测量再上，这一条最容易过度优化。
深入 · likeIgnoreCase('%关键词%') 为什么用不了索引

B-tree 索引按前缀有序，所以 like 'abc%' 能用（定位到 abc 开头的区间），like '%abc%' 不能——开头是通配符，索引里没有任何区间对应"包含 abc"。数据库只能全表扫描，逐行做字符串匹配。

第一季的搜索就是 PRODUCTS.NAME.likeIgnoreCase("%" + kw + "%")。商品表几千行时没人察觉，到几十万行时它会变成整个站点最慢的查询。

PostgreSQL 的解法是 pg_trgm 扩展：把字符串切成三字母组建 GIN 索引，于是"包含"也能走索引。迁移里加：

create extension if not exists pg_trgm;
create index products_name_trgm on products using gin (name gin_trgm_ops);

jOOQ 这边用 DSL.condition("{0} % {1}", PRODUCTS.NAME, DSL.val(kw)) 表达相似度操作符——注意用带占位符的 condition，不是 DSL.sql(拼接字符串)，前者会正确绑定参数（第一季第 05 部分那条规矩）。

中文的效果比英文差一些（三字组切分对中文不理想），真要做中文搜索该上 pg_bigm 或全文检索，再往上是独立的搜索引擎。但在上专门的搜索服务之前，trigram 索引能把你多撑很久。

陷阱 · 用 jOOQ 时怎么知道真正发出去的 SQL

jOOQ 的 DSL 读起来像 SQL，但它不是 SQL——某些写法生成的语句可能出乎意料（尤其是 MULTISET、隐式 join、以及带绑定值的 in）。两个必须会用的工具：

单条查询：query.getSQL(ParamType.INLINED) 把绑定值也内联进去，可以直接粘进 psql 跑 EXPLAIN。

全局：配一个 ExecuteListener，把执行超过 N 毫秒的语句连同参数打进日志。这是这个技术栈里最划算的一个观测点——它不需要数据库侧的 pg_stat_statements 权限，而且能直接关联到应用的 requestId（第 12 部分）。

Q1产品要求列表页显示"共 3,847 件商品"和页码 1…193。keyset 分页给不了这两样。你怎么办？

思路提示

先分开看，两个需求的代价完全不同。

总数：count(*) 带筛选时是全扫，几十万行上要几百毫秒。三种应对：显示近似值（"约 3,800 件"——用户对这个数字的精度需求其实为零）；只在第一页算一次，翻页时带着走；或者设上限——select count(*) from (select 1 from products where … limit 1000) t，显示"1000+ 件"。GitHub、Google 都这么干。

页码跳转：这个需求要先问清楚——用户真的会点第 87 页吗。绝大多数电商的数据是：翻页深度超过 5 页的会话不到 1%。如果确实如此，正确答案是改产品设计：用"加载更多"或无限滚动，配合更好的筛选和排序，让用户不需要深翻。

如果确实要保留页码（比如后台表格），那就分场景：后台数据量小、需要跳页，offset 完全没问题；前台用 keyset。不必全站统一一种分页，这是个常见的过度一致性。

Q2你给 (published, created_at desc, id desc) 建了索引，但 EXPLAIN 显示还是 Seq Scan。列出你会依次检查的五件事。

思路提示

按从简单到复杂：

  1. 表太小。几千行的表上全扫比走索引再回表更快，优化器的选择是对的。先确认表的真实规模——很多"索引没生效"的排查是在一个只有 200 行的开发库上做的。
  2. 统计信息过时。刚导入大量数据还没 ANALYZE，优化器以为表很小。跑一次 analyze products; 再看。
  3. 条件的选择性太低。如果 95% 的商品都是 published = true，这个条件几乎不过滤任何行，走索引再回表反而更慢。这时该建部分索引（把 published 从索引列变成 where 条件），或者接受全扫。
  4. 排序方向对不上。索引是 desc, desc，查询写的是 desc, asc——混合方向用不了同一个索引。
  5. 类型不匹配或对列做了函数。where lower(name) = ? 用不了 name 上的索引，要建表达式索引。jOOQ 这边还要留意自动的类型转换——比如把 Long 传给一个 integer 列，可能生成 cast 而让索引失效。

调试手法：set enable_seqscan = off; 然后再 EXPLAIN ANALYZE。如果强制走索引之后更慢，说明优化器本来就是对的；如果快很多，说明是统计信息或选择性估计出了问题。这个开关只用于诊断，绝不要留在生产配置里。

Q3有人说"这个列表页慢，加个 Redis 缓存就行了，不用折腾索引"。这句话在什么情况下是对的？什么情况下会把问题变得更糟？

思路提示

对的情况：这个查询本身就无法再快（比如一个跨五张表的复杂聚合），且数据变化很慢，且能接受一定的陈旧。给它加缓存是合理的工程决定。

更糟的情况——而且这才是常态：缓存把一个"持续的性能问题"转换成了一个"偶发的可用性问题"。

具体机制：加缓存前，这个查询 800 ms，页面慢但每次都能出来，数据库负载平稳且可见。加缓存后，99% 的请求 5 ms，看起来治好了；但只要缓存失效——发布时改了版本号、Redis 重启、TTL 集中到期——全部流量在同一秒打到那条 800 ms 的查询上。连接池瞬间打满（第一季讲过默认才 10 个），然后是全站不可用，而不只是这一个页面慢。

换句话说：缓存把慢查询的代价从"每次一点"攒成了"某一刻一次性爆发"。而爆发的时刻恰恰是系统已经不稳定的时候（重启、发布、故障），是最不该雪上加霜的时候。

所以顺序应该是：先让底下那条查询在没有缓存的情况下也能接受，再加缓存去削峰。这就是这一部分排在第 04 部分前面的全部理由。第 04 部分会给出缓存失效时的保护措施，但那些是补救，不是免罪符。

04

缓存：三种失效形态

Spring 有 @Cacheable 帮你把这层藏起来，Javalin 没有。要自己写反而是好事——因为缓存的三种典型故障，恰恰都发生在那个注解替你隐藏的地方。

缓存的基本形态只有一种：先查缓存，没有就查库并回填（Cache-Aside）。三十行就能写完。真正需要学的是它的四种失败方式：查不到的东西反复穿透、热点键过期时全体涌向数据库、大批键同时过期、以及回填时把旧数据写了回去。

自己写的缓存助手

陷阱 · 别在 computeIfAbsent 里做慢活

最直觉的 single-flight 写法是：inflight.computeIfAbsent(key, k -> CompletableFuture.supplyAsync(loader))，甚至直接在映射函数里同步调用 loader.get()。后者是一个真实的坑。

ConcurrentHashMap.computeIfAbsent 在执行映射函数时持有该桶的锁。如果映射函数里做一次 500 ms 的数据库查询，那 500 ms 内所有哈希到同一个桶的键都会阻塞——你本想只让一个线程查一个键，结果顺带卡住了一批不相干的键。

更糟的是：如果映射函数里又对同一个 map 调用了 computeIfAbsent（比如嵌套缓存），JDK 会抛 IllegalStateException: Recursive update，某些版本上甚至可能死锁。

正确写法就是上面那样：computeIfAbsent 里只创建一个空的 CompletableFuture（瞬时完成），真正的加载放在锁外面做，完成后 complete() 唤醒所有等待者。finally 里的 remove 同样重要——不移除的话，一次失败会让这个键永久返回那个已失败的 future。

这段代码里的每个 catch 都是一个决定含义
读失败 → 当未命中缓存故障不能变成业务故障。Lettuce 在 REJECT_COMMANDS 下会快速抛异常（第 01 部分），这里接住它。
写失败 → 忽略下次还得回源，但不影响这次的正确结果。
结构对不上 → 删键坏数据主动清掉，而不是每次都解析失败再回源。
finally 里移除 inflight不移除的话，loader 抛异常时这个键会永久卡住。
深入 · 进程内 single-flight 够不够

不够，但可能足够好。假设有 4 个实例，热点键过期时：没有 single-flight 是 800 个并发查询（每实例 200 个 Jetty 线程）；有了进程内的，是 4 个——每实例一个。

从 800 降到 4，问题基本解决。要降到 1 得跨实例加锁（第 07 部分），但那意味着多一次 Redis 往返、多一套锁超时逻辑、以及"没拿到锁的线程要等多久"这个新问题。

为了把 4 变成 1 而引入分布式锁，我认为不划算——除非那条回源查询非常贵（几秒的报表聚合），4 个并发就能压垮数据库。判断标准很具体：实例数 × 单次回源成本，数据库扛不扛得住。扛得住就到此为止。

这是这一季反复出现的模式：先用最便宜的手段把问题削掉两个数量级，再评估剩下的那点值不值得处理。

失效：删，不要改

商品更新后，正确的动作是 DEL 缓存键，而不是 SET 成新值。理由有两条：并发下两个写入者 SET 的先后顺序无法保证（后写的可能反而是旧值）；而 DEL 是幂等的、无序的，谁先谁后都一样。代价是下一次读要回源一次，很便宜。

Q1上面用 Envelope 记录表示"不存在"，而不是用某个特殊字符串当哨兵。这个选择背后的一般原则是什么？信封还能顺带解决什么问题？

思路提示

一般原则是：不要用"值域里的某个特殊值"表达"状态"。用 -1 表示没有、用空字符串表示 null、用某个魔法字符串表示未命中——这类设计的共同毛病是，总有一天那个特殊值会成为一个合法的业务值，而且出问题时极难排查。

信封顺带能解决三件事：

  • 细粒度的版本控制：信封里放 schemaVersion，读到不认识的版本就当未命中回源。比在键前缀里放版本更温和——不需要整批作废，可以逐个键自然过渡。
  • 可观测性：cachedAtMillis 让你知道命中的数据有多旧。排查"用户说看到旧价格"时，这个字段能直接给出答案。
  • 软过期：再放一个 staleAfter，读到过了软过期时间的值就先返回它、同时后台异步刷新。这是击穿的另一种修法，而它需要信封才能实现。

代价是每个值多几十字节。相对它换来的东西，这个价钱很便宜。

顺带一个 Java 细节：Envelope 写成 record 时，Jackson 需要能构造它——要么加 @JsonCreator，要么开 -parameters 编译参数让 Jackson 拿到参数名。这是 record + Jackson 组合最常见的一个卡点，值得在 build.gradle.kts 里一次性配好。

Q2图 4 下半部分那个窗口，有人提出"延迟双删"：改完库删一次缓存，等 500 ms 再删一次。这能解决问题吗？

思路提示

能缩小概率，不能消除。它的逻辑是：500 ms 之后，那个攥着旧值的读线程应该已经写完缓存了，再删一次就清掉了。

问题在于 500 这个数字凭什么。它必须大于"最慢的那次回源查询耗时"，而那是一个长尾分布——数据库偶尔抖一下，某次查询用了 2 秒，双删就漏了。调大间隔的话，缓存被无谓清空的时间变长，而且那个"稍后再删"的动作本身也可能失败（进程正好重启了呢——而在 Java 里，用 ScheduledExecutorService 安排的延迟任务在进程退出时默认就丢了）。

三个更实际的替代：

  • 接受它，靠 TTL 兜底。本项目的选择。TTL 5 分钟意味着最坏错 5 分钟，对商品描述完全可以接受。
  • 带版本号的条件写入：缓存值里存 updatedAt，回填时用 Lua 比较，只有比缓存里现有的新才写。能真正消除这个窗口，代价是多一次比较、并且要求数据里真有一个单调字段。
  • 让写入方来填（Write-Through）：改完库直接 SET 新值。但这引入了写入之间的顺序问题，通常更麻烦。

选择依据是这个数据错了会怎样：商品描述错 5 分钟没关系，库存显示错 5 分钟会让用户下单失败。所以真正的答案是——库存本来就不该走这套缓存（图 1 第三类）。大多数缓存一致性难题，追到最后是"这个数据不该缓存"。

Q3Spring 的 @Cacheable 一个注解就搞定了上面这几十行。自己写换来了什么？什么时候你会希望有那个注解？

思路提示

换来的是每一个决定都是显式的。@Cacheable 的默认行为里藏着几个你迟早要问的问题，而注解不会主动告诉你答案：Redis 挂了是抛异常还是回源（默认抛，要配 CacheErrorHandler 才降级）？null 缓不缓存（默认不缓，于是天然有穿透问题）？TTL 有没有抖动（没有）？并发未命中会不会击穿（会）？

换句话说：注解让你更快地写出一个带着这三种问题的缓存。它不制造问题，但它让问题更难被看见。

还有一个 Spring 特有的坑值得一提：@Cacheable 是基于代理的，所以同类方法内部调用不走缓存——和 @Transactional 那个著名的坑一模一样。而在 Javalin 这边，cache.get(...) 是一次普通方法调用，不存在"生效不生效"的问题。

什么时候会希望有它：当缓存点变多的时候。三五处手写没问题，三十处就会开始不一致——有人忘了加抖动、有人忘了 catch。这时正确的做法不是引入框架，而是把自己写的这个 Cache 类变成唯一入口，用 ArchUnit 断言"没有别的地方直接调 redis.cmd().get()"（第一季第 06 部分那套规则）。本质上就是造一个小 @Cacheable，只不过默认值是你自己选的。

05

订单状态机

第一季第 10 部分末尾冒出一个 pending_payment 状态，当时只说了"这不是缺陷，是如实建模"。这一部分把它变成完整的状态机——它是后面五个部分（超时关单、支付回调、乱序、Outbox、对账）共同的地基。

订单不是一条记录，是一个会随时间移动的东西。一旦有了外部系统和定时任务，就会有多个参与者同时想推动它：支付回调想推到已付，超时任务想推到已取消，用户想取消，客服想退款。谁赢？把答案写成一张表，而不是散落在十个 if 里。

深入 · Java 的枚举在这里比 TypeScript 强一点

EnumSet 和 EnumMap 不只是"能用"——它们是专门为枚举优化的实现：EnumSet 内部是一个位向量（枚举少于 64 个时就是一个 long），contains 是一次位运算；EnumMap 内部是一个数组，用 ordinal() 做下标。没有哈希、没有装箱。

更重要的是穷尽性检查。Java 21 的 switch 表达式对枚举要求覆盖所有分支：

String label = switch (status) { case PENDING_PAYMENT -> "待支付"; case PAID -> "已支付"; … };

不写 default 的话，加一个新状态会让所有这样的 switch 编译失败——编译器会精确告诉你哪些地方必须处理这个新状态。这是"加状态"这件事最好的安全网。

所以有一条反直觉的建议：不要图省事写 default -> "未知"。那一行会让编译器闭嘴，于是新状态在页面上显示成"未知"而不是编译失败——你把一个编译期错误换成了一个线上 bug。只有在真的要处理"未来可能新增的值"时才写 default，而订单状态不属于这一类。

数据库那一侧

用 PostgreSQL 的 enum 类型而不是 smallint，理由有三：占 4 字节（和 int 差不多）、查询结果直接可读（半夜排查时 select status 返回 PAID 而不是 3）、以及写入非法值会被数据库拒绝——即使有人绕过应用直接跑 SQL，也写不进一个不存在的状态。

陷阱 · jOOQ 会替你生成一个枚举，但可能不是你想要的那个

jOOQ 的 PostgreSQL 代码生成器看到 enum 类型时，会自动生成一个 Java 枚举放在 com.example.store.jooq.enums 下。于是你有了两个枚举：生成的那个，和你自己写的 OrderStatus（带转移表的那个）。

两个都留会很难受——到处都要转换。两种解法：

  • 让 jOOQ 直接绑定到你的枚举：在代码生成配置里加一个 forcedType，把 order_status 映射到 com.example.store.order.OrderStatus，用 EnumConverter。这样 ORDERS.STATUS 的类型就是你的枚举，转移表和数据库字段是同一个类型。推荐这个。
  • 或者接受生成的枚举，把转移表写成一个操作它的工具类。少配一点东西，但你的领域逻辑就依赖生成代码了——而生成代码在第一季图 5 那条流水线里是随时会被重新生成的。

还要注意：给 PostgreSQL 枚举加新值用 alter type … add value，它不能在事务块里执行（旧版本限制），而且不能删除已有的值。所以状态命名要想清楚再定。

唯一的入口

返回 Outcome 而不是 void，这一点很关键：调用方需要知道这次转移是不是真的发生了，因为"真的发生了"才应该触发副作用（发通知、扣库存、退款）。第 09 和第 10 部分全靠这个区分。

陷阱 · 所有状态写入都必须走这个方法

只要项目里还有一处 tx.update(ORDERS).set(ORDERS.STATUS, …)，这套状态机就是装饰品。三层防线：

  • 可见性：Transitions 和 ORDERS 的写操作收在 order 包内，别的模块用不到（第一季第 06 部分那个 package-private 的用法）。
  • ArchUnit：断言只有 com.example.store.order 能访问 ORDERS.STATUS 这个字段。这条规则本身就是一份文档。
  • 数据库触发器：极端情况下可以写一个 before update 触发器校验转移合法性——第一季第 05 部分的《参考取舍》里给过写法。作为"有人绕过应用直连生产库"的最后防线。

Q1transitionTo 里既用了 forUpdate() 行锁，又在 UPDATE 上写了 and status = current 的条件。两个都要，是不是多余了？

思路提示

在这个方法里确实是冗余的——行锁已经保证了从 SELECT 到 UPDATE 之间没人能改这一行。但我仍然建议两个都写，理由有三：

  • 防止将来有人删掉 forUpdate()。那一行看起来像可以优化掉的东西（"加锁多慢啊"），条件 UPDATE 则明显是业务逻辑的一部分，不容易被误删。留着它，即使锁被拿掉，最坏结果是抛 ConcurrentTransitionException 而不是数据错乱。
  • 隔离级别可能被改。Read Committed 下 for update 会重新读到最新版本；换成 Repeatable Read 行为会变。条件 UPDATE 在任何隔离级别下语义都一样。
  • 它让并发冲突变成一个有名字的异常。updated != 1 抛 ConcurrentTransitionException，可以在指标里数它；而如果只靠锁，冲突表现为"等待然后成功"，你永远不知道发生过冲突。

反过来，能不能只要条件 UPDATE 不要锁？可以，而且更快——但那样就没法在 UPDATE 之前读到 current 来区分"重复"和"非法"了，得改成"UPDATE 失败后再读一次判断"。逻辑会绕一些，但在高并发下是更好的写法。本项目订单转移的并发度不高，选了更直白的版本。

Q2产品说要加"部分退款"：订单已付，退了其中一件商品，订单仍然有效。这个需求能塞进图 5 这个状态机吗？

思路提示

不能，而且硬塞会毁掉这个状态机。因为部分退款不是订单状态的变化，是订单某一行的状态变化——订单还是 PAID，只是其中一个 order_item 被退了。

常见的错误做法是加一个 PARTIALLY_REFUNDED。麻烦立刻来了：退第二件之后是什么状态？还是它？那怎么知道退到第几件了？全退完要不要变成 REFUNDED？状态机开始承载它表达不了的信息，于是各处又长出 if 来补。

顺带：这也解释了为什么图 5 里的 REFUNDING 是可疑的——它已经是"整单退款"这个简化假设的产物。真做起来，它多半也该变成退款单的状态而不是订单的状态。

Q3Java 21 的 switch 表达式能对枚举做穷尽性检查，加新状态时编译失败。这个保护在哪些地方不生效？

思路提示

四个缺口，每一个都值得知道：

  • 写了 default 的地方。上面说过，这是自己放弃的保护。
  • 用 if-else 而不是 switch 的地方。if (status == PAID) … else if (status == SHIPPED) … 没有任何穷尽性检查。这是把 if 链重构成 switch 表达式的一个实在理由。

06

库存预占与超时释放

第一季的库存只有一列 stock，下单立刻扣。加上"先下单后支付"之后这样不行了——没付款的订单占着的货，既不能卖给别人，也不能算已经卖掉。需要第二个数。

这是这一季第一个真正的"时间"问题：一笔预占从产生到消失之间有一段可能长达半小时的空窗，而在这段时间里，系统必须同时对两件相反的事负责——不能超卖，也不能把货永远锁死。

深入 · 那两个 RESERVED.ge(qty) 是护栏，不是业务逻辑

正常情况下这两个条件永远成立——能走到转实扣，说明之前一定预占过。写上它们是为了让不该发生的事变成一个响亮的异常，而不是一个负数。

没有这层保护的话，某个 bug 导致重复释放，reserved 会变成 -3。而 stock - reserved 于是变大了——系统开始超卖，而所有 SQL 都执行成功了，监控上一片绿。这类"沉默地算错数"的故障是最难发现的一类，因为它不产生错误，只产生错误的数字。

而那条 check 约束是最后一道防线：它不依赖任何应用代码的正确性。凡是能表达成 check 约束的不变量，都应该写进去——即使应用层已经检查过。两层是冗余的，但冗余在这里正是目的。

秒杀：Redis 只当闸门

第 01 部分 Q1 的答案在这里落地。大促时一件热门商品可能有上万请求同时打过来，全部去数据库做条件 UPDATE 会让那一行成为热点，请求排成长队。加一道 Redis 闸门：

闸门出错的方向后果可接受吗
闸门数字偏大（Redis 丢了扣减）更多请求打到数据库，数据库照样正确拒绝可以——只是慢一点
闸门数字偏小（多扣了）本来能买到的人被挡住，显示"已售罄"但实际有货不理想，但不出错账。定期用数据库的真实值重置即可
闸门完全挂掉全部放行到数据库可以——退化成没有闸门的状态，正确性不受影响

三种错误方向都不会导致超卖，因为真正的判断始终在数据库那条条件 UPDATE 上。这就是"Redis 是性能优化，不是正确性保证"这句话的具体含义——它会在第 07 部分再出现一次。

Q1超时关单任务把订单从 PENDING_PAYMENT 改成 CANCELLED 并释放了库存。恰在同一时刻，支付回调到达说这笔钱已经付了。会发生什么？系统该怎么办？

先看技术上发生了什么：两个事务都想改同一行订单，forUpdate() 让它们排队。

  • 如果关单先赢：回调调用 transitionTo(PAID)，当前状态是 CANCELLED，转移表里没这一条 → 抛 IllegalTransitionException。

所以数据是安全的。但第一种情况下用户真的付了钱，而订单是取消状态——这不是技术问题，是业务问题，必须有人处理。

三层做法：

  1. 不要吞掉这个异常。它必须进告警和一个人工处理队列，附带订单号和支付流水号。这就是图 5 里"非法转移要响亮失败"的实际用途。
  2. 缩小窗口。支付网关通常有自己的超时（比如 15 分钟就关闭支付页），把我们的关单时间设得比它更长（30 分钟），窗口就小得多。两个系统的超时时间必须协调，这是最容易漏的一步。
  3. 准备好自动退款路径。对"已取消但收到付款"，多数电商的处理是自动发起退款并通知用户。把它做成显式流程，而不是等客服发现。

值得注意：无论怎么设计，这个窗口都消除不了——用户在第 29 分 59 秒点了支付，钱到账要几秒。能做的只是让它罕见、可见、有处理办法。

Q2如果不加 reserved 列，而是每次都用 select sum(qty) from order_items join orders where status = 'PENDING_PAYMENT' 算出预占量，行不行？

思路提示

逻辑上完全正确，而且有一个很大的优点：不存在数据不一致的可能——预占量是算出来的，不是维护出来的，图 6 右上角那条不变量自动成立。

问题全在性能和并发上：

  • 每次判断库存都要跑一个跨表聚合。商品页、加购、下单都要判断，这个查询会成为最热的查询之一。
  • 更麻烦的是并发正确性：算出"预占 30"到执行 UPDATE 之间，别人可能又下了一单。这又回到 check-then-act。要修就得锁住 orders 表的相关行，或者上 Serializable——两者代价都不小。

所以 reserved 列是一个典型的物化的派生值：用"可能不一致"换"可以原子判断"。这个交易在电商里几乎总是划算的。

但既然选了物化，就必须配上两件事：数据库层的 check 约束（上面那条），以及定期对账——每小时跑一次那条聚合查询，和 reserved 列比对，不一致就告警。第 12 部分会把这个对账任务写出来。物化派生值必须配对账，这是一条没有例外的规矩。

Q3图 6 底部说键过期通知不可靠。那"定时轮询数据库找超时订单"就可靠吗？它的代价是什么？有没有第三种办法？

思路提示

轮询可靠，因为它的判据是数据库里的持久事实（created_at < now() - 30 min and status = 'PENDING_PAYMENT'）。进程挂了、重启了、漏跑了一轮，下一轮照样能找到那些订单。可靠性来自"状态可重建"，而不是"通知没丢"。这是图 1 那个问题的又一次应用。

代价有三个：延迟（轮询间隔决定关单最晚会晚多久，1 分钟通常够）；无效查询（大部分轮询一无所获——但有了上面那个部分索引，这个查询几乎不花钱，因为待支付订单在任何时刻都只有很少几条）；多实例重复（这是第 07 部分要解决的）。

第三种办法是延迟队列：下单时往一个有序集合里塞 (订单id, 到期时间戳)，工作线程轮询"到期时间 < 现在"的成员。比全表轮询精确，延迟也更低。

但注意：如果这个有序集合放在 Redis 里，它就又变成"不能重建的状态"了——Redis 丢数据，那批订单永远不会被关。所以要么把队列放在 PostgreSQL 里（那和轮询订单表区别不大），要么保留数据库轮询作为兜底，Redis 队列只用来降低延迟。

这个"快路径 + 慢兜底"的组合是分布式系统里非常常见的模式：用不可靠但快的机制处理绝大多数情况，用可靠但慢的机制保证最终不漏。第 10 部分的 Outbox 也是同一个形状。

07

定时任务与分布式锁

第一季没有定时任务。加上超时关单之后，第一个问题是"跑在哪"，第二个问题是"三个实例会不会跑三遍"。这一部分给出答案，以及这一季最重要的一个结论——分布式锁不是正确性保证。

超时关单任务跑在三个实例上，就会有三份同时在扫同一批订单。直觉是"加把锁"，而这个直觉会把你引向一个比问题本身更微妙的东西。先看锁是怎么坏的，再决定要不要用它。

方案 ①：不抢锁，抢行

三个实例同时跑这段代码，结果是各自认领 100 条不同的订单——没有重复，而且吞吐是单实例的三倍。这比"选一个实例来跑、另外两个干等"好得多。

陷阱 · skipLocked 的两个前提

事务要短。被锁住的行在事务提交前一直锁着，别的实例一直跳过它们。如果一个批次要处理 5 分钟，这 5 分钟里这些行对其它实例不可见——万一这个事务最后回滚了，这 5 分钟就白等了。所以 batch 要小，宁可多跑几轮。

要有合适的索引。第 06 部分那个 where status = 'PENDING_PAYMENT' 的部分索引是必需的，否则每轮轮询都是一次全表扫描——而这个任务每分钟跑一次。

方案 ②：PostgreSQL 咨询锁

相比 Java 生态里常用的 ShedLock，这个版本少了一样东西：不需要 TTL。因为锁绑定在数据库连接上，进程崩溃时 TCP 连接断开，PostgreSQL 立刻释放锁。图 7 那个双持有窗口在这里根本不存在——代价是这把锁只在一个数据库实例的范围内有效，而这对单库应用恰好足够。

陷阱 · scheduleAtFixedRate 的任务抛异常后会永久停止

这是 Java 里最容易踩、也最容易被忽略的一个坑：ScheduledExecutorService.scheduleAtFixedRate 提交的周期任务，只要抛出一次未捕获异常，后续所有周期都不会再执行——而且默认什么都不打印。

症状是：关单任务跑了三周好好的，某天数据库抖了一下抛了个异常，从此再也没跑过。没有报错、没有告警，只是库存慢慢被待支付订单占满。等有人发现时，已经过去很多天。

所以任务体必须自己兜住所有异常：

scheduler.scheduleWithFixedDelay(() -> { try { runOnce(deps, 100); } catch (Throwable t) { log.error("job failed", t); } }, 0, 60, SECONDS);

注意是 Throwable 不是 Exception——Error 同样会杀死周期任务。另外优先用 scheduleWithFixedDelay（上一次结束后再等 N 秒）而不是 scheduleAtFixedRate（按固定节奏触发）：后者在任务耗时超过周期时会让任务连续排队执行，把问题放大。

这个坑是"把调度交给平台"的一个有力论据——平台的 CronJob 失败会有明确的失败记录和告警，而不是静默消失。

安全 · 那个内部端点必须挡住外面

POST /internal/jobs/* 如果能被公网访问，任何人都能触发你的批处理任务。三层防护：网络层只允许集群内访问；一个共享密钥头（用 MessageDigest.isEqual 做恒定时间比较）；以及任务本身幂等——被调用一百次和一次的结果相同。第三条最根本，因为前两条都可能配错。

还有一点：这些端点在第一季那套 RouteRole 体系里必须显式标注。别忘了它们也是路由，同样受"没标角色就拒绝"这条规则约束——这正是那条规则的价值。

深入 · 看门狗救不了你

Redis 锁的常见补救是"看门狗"：后台线程定时给锁续期。Redisson 就内置了这个。

但在 JVM 上这个补救格外脆弱：续期靠的是一个后台线程，而 Full GC 是 stop-the-world 的——它把看门狗线程也停了。正是最需要续期的时候，续期线程跑不了。看门狗和它要防的故障共享同一个失败原因。

怎么观察这件事：打开 -Xlog:gc*,safepoint:file=gc.log，看有没有超过几百毫秒的停顿。如果你的应用有秒级停顿，那么任何 TTL 小于停顿时长的锁都是不可靠的——而你不能把 TTL 设成"比最坏停顿还长"，因为那意味着进程崩溃后锁要等那么久才释放。

所以这一部分的结论只能是：

Redis 锁是性能优化——它减少重复工作；它不是正确性保证。正确性必须由数据库的唯一约束、条件更新或状态机来兜底。

回头看上面的关单任务：即使没有任何锁，三个实例同时跑也是正确的——因为 transitionTo 用了行锁 + 条件更新 + 状态机，重复的那两个实例只会拿到 ALREADY 然后什么都不做。锁在那里的作用只是省掉重复查询。这就是"正确性另有保证"的具体样子。

Q1如果关单任务完全不加任何锁，三个实例同时跑会出什么错？请具体推演一遍。

思路提示

推演的结果是：不会出错，只会做重复的无用功。这正是这一部分想让你自己得出的结论。

逐步看：三个实例的 forUpdate().skipLocked() 会认领不同的行（这一步本身就防住了重复）。就算把 skipLocked 也去掉、改成普通 select，最坏情况是三个实例都读到同一批订单，然后：

  • 实例 A 的 transitionTo(id, CANCELLED) 拿到行锁，成功，返回 CHANGED，释放库存。
  • 实例 B 在同一行上等锁，A 提交后 B 读到状态已是 CANCELLED，返回 ALREADY，不释放库存。
  • 实例 C 同理。

库存只被释放一次。数据完全正确。

代价是三倍的数据库查询和三倍的锁等待——这是性能问题，不是正确性问题。而这恰好就是"锁是性能优化"这句话的完整含义：加锁能省掉那两份无用功，但不加锁也不会错。

反过来问一句更有价值的：如果去掉 transitionTo 里的状态检查，只保留锁，会怎样？那么锁一旦失效（图 7 那个场景），库存就会被释放两次，reserved 变成负数——好在第 06 部分那条 check 约束会拦住它，让它变成一个响亮的异常而不是超卖。三层防护里，最外面那层（锁）是最不可靠的一层。

Q2图 7 说 JVM 的主角是 GC 停顿。现代的 ZGC / Shenandoah 号称停顿在毫秒级。那这个问题是不是消失了？

思路提示

变小了，但没有消失，而且把它当成"消失了"是危险的。

低延迟收集器确实解决了大部分 GC 停顿：ZGC 的停顿基本与堆大小无关，通常在亚毫秒级。如果你的停顿只有 1 毫秒，那么 30 秒 TTL 的锁在实践中几乎不会因为 GC 而失效。

但"进程失去时间"的原因不止 GC：

  • 安全点（safepoint）：某些 JVM 操作（偏向锁撤销、栈追踪、部分 JIT 去优化）需要所有线程到达安全点，这和 GC 算法无关。
  • 操作系统层面：内存换出、CPU 被同宿主的邻居抢占、cgroup 限流（容器 CPU quota 用完会被硬性挂起）、宿主机迁移。容器里 CPU 被限流是很常见的，而且症状和 GC 停顿一模一样。
  • 网络分区：A 到 Redis 的网络断了几十秒，A 什么都没停，但它的锁照样过期了——这一条和停顿无关，任何低延迟收集器都救不了。

最后一条最关键：锁失效的根本原因不是"进程慢"，是"持有者和锁之间隔着网络"。只要这个结构在，就存在持有者认为自己有锁而实际没有的窗口。这是分布式系统的本质约束，不是实现质量问题。

所以正确的态度不是"换个 GC 就不用担心了"，而是永远不让正确性依赖锁。低延迟收集器让锁更好用（更少的无用重试），但不改变这条结论。

Q3本部分推荐 PostgreSQL 咨询锁而不是 Redis 锁。但如果将来任务要协调的资源不在数据库里（比如"同一时刻只能有一个实例在调某个外部 API"），咨询锁还合适吗？

思路提示

技术上完全可以用——咨询锁的名字是任意字符串，锁什么和数据库无关。但这时值得停下来想故障域。

用咨询锁意味着：数据库挂了，这个和数据库无关的外部调用也停了。这可能是好事（数据库挂了你多半也不该继续调外部 API），也可能是坏事。选锁的位置，本质上是在选"什么东西挂了，这件事就该停"。这个问题比"哪种锁更快"重要得多。

更关键的一点：题目里"同一时刻只能有一个实例调外部 API"这个需求本身要审视。如果重复调用会造成重复扣款，那么靠锁来防是错的——图 7 已经证明了锁会失效。正确的办法是幂等键：每次调用带一个业务上唯一的 key，对方保证同一个 key 只生效一次。这正是第 08 和第 09 部分的主题。

那锁还有什么用？限制并发度——对方的接口只允许每秒 10 次调用，你用锁或信号量来遵守这个约定。这是一个"违反了会被限流，但不会算错账"的场景，正是锁适合的地方：它优化行为，不承担正确性。

Java 这边还有一个更轻的选项值得知道：如果只是单实例内限流，Semaphore 或 Resilience4j 的 Bulkhead 就够了，根本不用分布式锁。先问"真的需要跨实例协调吗"，很多时候不需要。

08

对外集成：支付网关

到这里为止，系统里所有东西都是你的：数据库是你的，Redis 是你的，它们出错你能查能修。支付网关不是。它会慢、会超时、会返回你没见过的错误码，而且不会在你方便的时候这么做。

和外部系统打交道的全部难点，可以压缩成一句话：超时既不是成功也不是失败，是"不知道"。这一部分先把这个"不知道"讲透，再谈重试、熔断和限并发——因为那三样东西的设计，全都取决于你怎么理解它。

把超时配对

陷阱 · JDK 的 HttpClient 没有默认请求超时

HttpClient.newBuilder().connectTimeout(...) 只管建立连接那一段。连接建好之后，如果对方接了请求却一直不返回，send() 会永远阻塞下去——没有任何默认上限。

后果是：对方挂起，你的 Jetty 线程也挂起，占着线程池的一个位置。几百个这样的请求就能让实例失去响应能力——而这不需要对方"挂掉"，只需要它"变慢"。慢比挂更危险，因为挂掉会立刻报错，变慢会拖着你一起沉。

所以规矩是：每一个出站请求都必须在 HttpRequest.newBuilder().timeout(...) 上显式设超时，没有例外。两个超时管的层次不同，都要配。

顺带：超时触发时抛的是 HttpTimeoutException（IOException 的子类），而连接失败抛 ConnectException。这两个异常类型的区别，正是图 8 那三条规则里第 ① 条能落地的原因——JDK 恰好把"没连上"和"连上了但没回来"分成了不同的类型。

重试：只重试可证明没到的那一种

slowCallRateThreshold 值得单独指出：只统计"失败率"是不够的——一个每次都在第 7.9 秒才返回成功的下游，失败率是 0%，但它已经把你的线程池吃光了。把"慢"也计入熔断条件，是 Resilience4j 相对很多简易实现的一个实在优势。

陷阱 · 装饰顺序反了，熔断统计就是错的

如果把熔断放在重试里面，那么一次业务调用的 3 次重试会被记成 3 次失败——熔断器会比预期早三倍打开。而且半开状态下"放行 3 个请求"实际上只放行了 1 次业务调用。

正确的心智模型是：熔断统计的是"业务调用"，重试是业务调用内部的细节。Resilience4j 的 Decorators 构建器里，越靠后调用的越靠外——记住这一点，或者干脆写个注释。

Q1幂等键该用什么值？订单 id 行不行？UUID.randomUUID() 呢？

思路提示

关键判据：幂等键必须在"同一次业务意图"内保持不变，跨意图必须不同。

  • 每次调用生成新 UUID：错得最彻底。重试时 key 变了，对方认为是新支付，扣两次。完全违背了幂等键的目的。
  • 用订单 id：接近正确，天然稳定，进程重启后仍能算出同一个 key。但要小心"同一个订单需要付两次"的场景（第一次失败后用户换张卡重新支付）——这时用订单 id 会被对方当成重复请求拒绝。
  • 用"支付尝试" id：最稳妥。为每次支付尝试在自己库里建一行 payment_attempts，把它的 id 当幂等键。同一次尝试的所有重试共享它；用户重新发起则是新尝试、新 key。

而且这张表还顺带解决另外两个问题：它是超时之后去查询"这笔到底成没成"的凭据（图 8 规则 ③），也是第 12 部分对账任务的数据来源。一张表换三个能力，很划算。

最后一个细节：幂等键要有有效期的意识。多数支付平台只保证 24 小时内的幂等。所以"三天后重试同一个 key"可能会真的扣第二次——这也是为什么长时间未决的支付应该走查询而不是重试。

Q2Resilience4j 的熔断器状态存在进程内存里。三个实例就有三个独立的熔断器。这是问题吗？要不要放进 Redis 共享？

思路提示

大多数情况下不是问题，而且进程内反而更好。

理由是熔断器统计的是"我调用对方的失败率"，而这个数字本来就有实例间的差异：某个实例可能在一个网络分区里、可能连到了对方的一个坏节点。让每个实例独立判断，反而更准确地反映了它自己的处境。

共享状态会引入新问题：多一次 Redis 往返（在每个出站请求的路径上）、Redis 挂了熔断器怎么办、以及一个实例的异常观测会导致所有实例一起断开。你为了协调一致性，换来了一个新的单点。

进程内的代价是：故障发生时每个实例都要独立"交学费"（各自失败几次才打开）。实例数不多时这个代价很小。

什么时候该共享：实例数非常多（几十上百）时，每个实例的样本量都不够统计出可靠的失败率，而且"每个实例各自试探"加起来就是一波不小的流量。那时可以降低单实例的失败阈值，或者把统计放到共享存储。

这个判断和第 04 部分 single-flight 那个"要不要跨实例"是同一个模式：先问"进程内够不够好"，再问"值不值得为剩下那点收益引入协调"。

Q3你为支付网关配了 8 秒超时。而用户点了"支付"之后 Jetty 的一个线程在等这 8 秒。这个数字怎么定？有没有更好的设计？

思路提示

这个数字应该从两头夹出来。

下界来自对方的实际耗时分布：如果对方 p99 是 3 秒，超时设成 2 秒会让 1% 的正常请求变成"不知道"——而每一个"不知道"都要走查询或对账，成本很高。超时设得太短，会把一个性能问题变成一个正确性问题。合理起点是 p99.9 再留点余量。

上界来自调用链：如果前面还有网关、负载均衡，它们的超时必须大于你的超时，否则它们会先掐断，你的重试和错误处理根本没机会跑。整条链路的超时必须从外到内递减——这是最常被配错的一件事。

但 Java 这边还有一层特有的账要算：8 秒 × 并发下单量 = 被占住的 Jetty 线程数。默认 250 个线程，如果每秒有 40 笔下单，就有 320 个线程在等支付——线程池被打满，连商品列表页都打不开了。这就是第一季图 1 那个红框的实际后果。

两个应对：加一道 Bulkhead 限制并发支付调用数（比如最多 50 个），超出的快速失败——牺牲一部分下单，保住整站；或者开虚拟线程（第一季第 12 部分），让"等待"不再消耗平台线程。

但最好的答案是换个设计：让用户不必等。第一季图 12 已经把支付调用移出了事务，这里可以再进一步——下单后立刻返回"支付处理中"页面，支付结果通过回调（第 09 部分）异步到达，页面轮询或用 SSE 推送。这样超时可以设得更从容，用户体验反而更好，因为他看到的是明确的进度而不是一个转圈的按钮。很多"超时该设多少"的难题，本质是"这件事不该同步做"。

09

异步回调与幂等

支付网关处理完之后，会往你的 POST /webhooks/payment 发一条通知。这个端点是整个系统里最不受你控制的入口：调用方是别人，重试策略是别人定的，顺序没有保证，而且它直接决定钱和货的归属。

回调处理的正确性由五道闸串起来。这五道闸有一个共同特征：它们各自只挡一种问题，而且不能互相替代。最常见的错误是以为"我做了幂等"就万事大吉——幂等挡的是重复，挡不住乱序。

陷阱 · 别让任何东西先碰了请求体

Javalin 会缓存请求体，所以 ctx.bodyAsBytes() 多次调用是安全的——比 Hono 那边"流只能读一次"宽容。但 Servlet 层有一个更隐蔽的坑：

如果请求的 Content-Type 是 application/x-www-form-urlencoded，而某个 before 处理器调用了 ctx.formParam(...)，Servlet 容器会把请求体解析成参数并消费掉输入流——之后你拿到的原始字节可能是空的。签名于是永远校验失败，而错误信息只会说"签名不对"，你会去查密钥、查算法、查编码，查上半天。

两个防护：webhook 路由挂在一棵干净的子树上，不经过任何会碰 body 的全局处理器；以及写一个测试断言原始字节能被读到——发一个已知 body，断言 bodyAsBytes() 的长度和内容正确。两分钟的事，省掉一次通宵。

还要注意 config.http.maxRequestSize：超过这个大小的请求体不会被缓存，只能流式读一次。webhook 通常很小，但如果对方会发大 payload，这一条要检查。

安全 · Arrays.equals 和 MessageDigest.isEqual 的差别

Arrays.equals(a, b) 逐字节比较，遇到第一个不同就返回。这意味着比较耗时和"前面有多少字节是对的"相关——攻击者反复提交、测量响应时间，就能一个字节一个字节地把正确签名试出来。这叫时序攻击，在本地网络上是真实可行的。

MessageDigest.isEqual(a, b) 在现代 JDK 里是恒定时间实现：它会比较完所有字节再返回结果。这是 JDK 里为数不多的、专门为安全场景提供的比较方法，值得记住它的存在。

顺带：长度不同时它会立刻返回——所以长度本身是会泄露的。对 HMAC 来说无所谓（长度是固定的），但如果你在比较别的秘密值，要意识到这一点。

深入 · 什么时候该回 200，什么时候该回 5xx

回调的返回码是在指挥对方的重试行为，所以要按"希不希望它重发"来选，而不是按"我处理得顺不顺利"来选：

  • 处理成功 → 200。
  • 重复投递 → 200。已经处理过了，重发没有意义。
  • 签名错误、时间戳过期 → 401 / 400。这不是暂时性问题，重发一百次也一样；而且如果这是攻击，你更不希望它被重试。
  • 你自己的数据库挂了 → 500。这是唯一真正需要对方重发的情况——事件是合法的，你只是暂时处理不了。
  • 金额不匹配、状态机拒绝 → 这里要小心。我建议回 200 并告警，因为让对方无限重发一个永远处理不了的事件没有意义，只会让错误日志被刷屏，掩盖真正需要重发的那些。把它记进人工队列，比让它在重试队列里循环三天有用得多。

Javalin 这边要留意一个细节：如果你抛的是未捕获异常，默认会返回 500——也就是"请重发"。所以那些"不该重发"的业务异常必须被显式映射成 4xx，否则你会得到一个无限重试的循环。这正是第一季第 01 部分那个 exception 处理器要分类型注册的原因。

Q1幂等用的是 insert … onConflictDoNothing。为什么不先 select 查一下这个 event_id 处理过没有，没有再插？

思路提示

因为"先查再插"是 check-then-act（第一季图 11）。支付网关在没收到 200 时会重发，而重发和原请求很可能同时到达（你的第一次响应慢了 5 秒，网关在第 5 秒重发，两个请求现在并行）。两个都查到"没处理过"，两个都往下走，订单被处理两次。

唯一索引是数据库层面的原子判断：无论多少并发，只有一个能插进去。onConflictDoNothing() 的返回值（影响行数）让你知道自己是不是那个赢家。

还有两个细节值得注意：

  • 这条 insert 必须和后面的业务处理在同一个事务里。如果先提交幂等记录再处理业务，业务失败回滚后，重发的请求会被幂等表挡住——这笔支付就永远丢了。
  • 反过来，如果业务处理很慢，这个事务会持有很久。所以要么处理足够快，要么把重活扔进 Outbox（第 10 部分），事务里只做状态转移。本项目选后者。

一个额外好处：webhook_events 表把原始 payload 存下来了（用 jsonb）。出问题时可以完整重放，这在和支付方对账扯皮时极其有用。记得给它加保留期清理，否则它会变成库里最大的表。

Q2支付网关说"我们保证至少投递一次"。这句话具体给了你什么承诺，又没有给你什么？

思路提示

给了你一条：只要你一直返回非 200，它会一直重发（在重试策略的期限内）。所以事件不会因为你临时挂了而丢失。

没给你的至少有四条，每一条都对应一个必须自己做的设计：

  • 没有"最多一次"：所以你必须幂等（闸 ④）。
  • 没有顺序保证：所以你必须有状态机（闸 ⑤）。
  • 没有时限保证：一条事件可能几秒后到，也可能因为对方积压几小时后到。所以不能假设"没收到回调就是没成功"——这正是图 8 规则 ③ 那个查询接口存在的理由。
  • 没有"你一定收得到"：如果你的服务连续挂了超过对方的重试期限（通常三天），那条事件就真的丢了。所以必须有对账：定期把自己库里"还在 PENDING_PAYMENT"的订单拿去问对方，第 12 部分会写这个任务。

把这四条并排看，会发现一个规律："至少一次"这个承诺，把所有关于正确性的责任都推给了接收方。这不是支付网关偷懒——在分布式系统里，"恰好一次"投递本身就是不可实现的，能做的只有"至少一次投递 + 接收方幂等"。理解了这一点，第 10 部分的 Outbox 为什么长成那样就很自然了。

Q3回调处理里要发一封"支付成功"的邮件。直接在这个事务里调邮件服务行不行？如果不行，放在事务提交之后行不行？

思路提示

事务里调：不行。第一季第 10 部分那张表已经说明——外部调用会把数据库连接和行锁占住几百毫秒，而这个事务锁着订单行。更糟的是邮件服务超时会导致事务回滚，于是一笔已经成功的支付被回滚了，就因为邮件没发出去。这个因果关系荒谬但真实存在。

事务提交之后调：好一些，但仍有一个窗口——事务提交了，进程在调邮件服务之前崩溃了。这封邮件就永远不会发。

用户收不到邮件严不严重？取决于内容。"支付成功通知"丢了可能可以接受；但如果是"发货通知"或包含取货码的邮件，丢了就是事故。而且你不会知道它丢了——没有任何记录说明"这封邮件本该发出"。

正确的做法是把"要发这封邮件"这件事作为数据写进同一个事务：往 outbox 表插一行。事务提交 = 意图被持久化了；投递失败可以重试，进程崩了下次启动会捡起来。这就是第 10 部分整章的内容，而它的动机就是这道题。

顺带一个判断标准，可以用在所有"要不要走 Outbox"的场合：如果这个副作用丢了，有没有任何机制能发现？没有的话，它就必须先落库。

事件、Outbox 与通知

第 09 部分 Q3 留下的问题：支付成功要发邮件、要通知仓库、要更新统计。这些副作用不能放进事务，放在事务之后又可能丢。这一部分给出那个既不放进去也不丢掉的做法。

问题有一个名字叫双写：你要同时改两个系统（数据库 + 邮件/消息），而这两次写入无法组成一个原子操作。无论先写哪个，中间崩溃都会留下不一致。这不是实现技巧问题，是没有分布式事务时的固有约束。

代价说清楚：如果实例在阶段二崩溃，那一批会在 STALE 之后被别人重新认领并重投一次。这不是缺陷——图 11 底部那句话本来就成立：Outbox 提供的是至少一次投递，消费方必须幂等。两阶段只是把"重复投递的窗口"从"崩溃即重复"变成了"崩溃后一分钟内重复"，换来的是事务从几秒缩到几毫秒。

陷阱 · 长事务会冻住整个库的空间回收

这是把 deliver() 放在事务里的第二个代价，比锁更隐蔽：PostgreSQL 的 UPDATE 是"写新版本 + 标记旧版本死亡"，而死亡的行只有在没有任何更老的事务可能看到它时才能被回收。

一个跑了 10 秒的事务，会让这 10 秒内整个数据库产生的死元组都无法被回收——不只是 outbox 表，而是所有表。几个这样的 relay 循环叠在一起，你会看到一个奇怪的现象：某张完全无关的热点表开始膨胀。

select * from pg_stat_activity where state = 'idle in transaction' 是排查这类问题的第一条命令。而更根本的解法就是上面那个两阶段写法。

深入 · 为什么不用进程内的事件总线

Java 里做"发布订阅"很容易：一个 List<Consumer<Event>>，或者 Guava 的 EventBus。写起来最舒服：events.post(new OrderPaid(orderId))。

但它解决不了这一部分的问题，因为它只是一次方法调用：

  • 监听器在同一个进程、同一个线程里跑。进程崩了，事件就没了——和图 11 顺序 A 完全一样。
  • 没有重试。监听器抛异常就抛异常了，没有任何东西记得这件事没做成。
  • 更阴险的一点：同步的事件总线会把监听器的耗时算进调用方。你以为"发个事件"是瞬时的，实际上它在事务里同步发了一封邮件——回到了这一部分开头那个问题。
  • 而如果改成异步（@Subscribe 配线程池），事件就可能在事务提交之前被处理，监听器查数据库看不到那条订单。这是一个真实且难查的竞态。

那事件总线有什么用？用于进程内的、丢了也无所谓的解耦：打点、更新一个内存里的指标、刷新本地缓存。判据还是第 09 部分 Q3 那条：这个副作用丢了，有没有机制能发现？没有就必须走 Outbox。

降低延迟：LISTEN / NOTIFY

每秒轮询意味着通知平均晚 500 ms。可以用 PostgreSQL 的 NOTIFY 把它降到几毫秒：写完 outbox 后 notify outbox_new，一个后台线程 LISTEN 到就立刻跑一轮。

陷阱 · NOTIFY 是加速器，不是队列；而且 JDBC 这边用起来有点别扭

可靠性上：NOTIFY 的消息不持久化——没有连接在监听时发出的通知直接丢弃；连接断开重连期间的通知也补不回来。用它当唯一触发源，就回到了第 06 部分图里那个"键过期通知"的老问题。

API 上：pgjdbc 没有回调式的监听接口。你需要一条专用连接（不能从 HikariCP 池里借，因为它会被归还），把它转成 PGConnection，然后在一个后台线程里循环调用 getNotifications(timeout)——这是一个阻塞轮询，不是推送。写起来大概二十行，而且要自己处理重连。

正确用法是快慢结合：NOTIFY 负责让常见情况快（几毫秒），定时轮询负责保证不漏（每 5 秒兜一次）。这个组合在第 06 部分 Q3 出现过一次，在这里又出现一次——它是分布式系统里最实用的模式之一，值得单独记住。

说句实在话：如果延迟从 500 ms 降到 5 ms 对业务没有实际价值，就别做。那二十行连接管理代码是要长期维护的。

什么时候该换成真的消息队列

信号为什么 Outbox 撑不住了
投递量超过每秒上千条轮询和行锁的开销开始占用数据库的可观份额，而这个数据库还要服务在线请求。
出现了多个独立消费者同一个事件要被三个团队各自消费，各有各的进度和重试。用 outbox 表做就得给每个消费者一份进度表——你正在手工实现消费组。
消费方不是你的服务跨团队、跨组织时，让对方来轮询你的数据库表是不可接受的耦合。这时需要一个双方都认的协议边界。

三条都没命中之前，Outbox 是更好的选择——它少一个需要运维的组件、少一个故障域，而且所有状态都在你能用 SQL 查询的地方。真要换的时候，Outbox 也不会白写：它本来就是往 MQ 投递的标准前置模式（先落 outbox，再由 relay 发到 MQ）。即使上了 Kafka，Outbox 也不会消失——因为"改数据库"和"发消息"之间的原子性问题，MQ 本身解决不了。

Q1Outbox 保证至少一次，所以"支付成功"邮件可能发两封。怎么让它实际上只发一封？

思路提示

责任在消费方，也就是投递逻辑那一侧。三个层次，按可靠性递增：

  • 投递前查一下：select from notifications where outbox_id = ?。这是 check-then-act，两个实例并发时会漏——但配合 skipLocked 和 claimed_at，同一行不会被两个实例同时处理，所以实际上够用。它防的是"崩溃后重投"，不是并发。
  • 唯一索引：notifications 表上 (outbox_id) 唯一。先插记录再发邮件，插不进去说明发过了。这是第 09 部分闸 ④ 的同一招，用在了发送侧。
  • 让下游幂等：多数邮件服务商支持 Idempotency-Key，传 outbox 行的 id 即可。这是最干净的做法——你不需要维护任何本地记录，重复由对方消解。

但有一个更实际的问题要先问：这封邮件发两封，代价有多大？用户收到两封"支付成功"通知，尴尬但无害。相比之下，"扣一次款"发两次是灾难。

所以我的建议是按副作用的性质分级：涉及钱和库存的，必须走唯一索引；纯通知类的，用下游幂等键，做不到就接受偶尔重复。为一封可能重复的邮件设计一套复杂的去重机制，是把成本花错了地方。

Q2Outbox 表会一直增长。已发送的行要删吗？删了会怎样，不删会怎样？

思路提示

要删，但不能立刻删，也不能用简单的一条 delete。

不删的后果：表会长到几千万行。查询本身不受影响（部分索引只包含 sent_at is null 的行，永远很小），但表占磁盘、拖慢备份、让 VACUUM 变贵。

立刻删的后果：丢掉排查能力。"用户说没收到邮件"时，你想知道那条 outbox 记录存不存在、投递了几次、报了什么错。这些信息在事故排查时价值极高。

实践做法：保留 7～30 天，然后按批删除。要点在"按批"——

  • 一次删几百万行会长时间持锁、产生巨量 WAL，可能把主库拖垮，还会拖累复制。
  • 正确写法是循环小批：每次删 5000 行，每轮之间停一下。
  • 更好的方案是按时间分区：outbox 按月分区，过期直接 drop partition——瞬时完成，不产生 WAL，不需要 VACUUM。数据量大时这是唯一优雅的办法。

但要注意 jOOQ 这边的一个连带影响：分区表在代码生成时会把每个分区也生成成一个表类，让生成的代码变得很乱。可以在代码生成配置里 excludes 掉分区子表，只保留父表。这是"表即事实"那条流水线的一个小摩擦点，值得提前配好。

这条经验适用于所有"只增不减的日志型表"：webhook_events、order_status_changes、审计表。建表的时候就该想好它怎么删。

Q3轮询器用 order by id 取，看起来是有序的。但"同一个订单的两个事件"能保证按顺序投递吗？

思路提示

不能保证，有三个原因：

  • 多实例并行：skipLocked 让实例 A 拿到 order.paid、实例 B 拿到 order.shipped，两边同时投递，谁先到达下游取决于网络。
  • 失败重试：即使单实例，order.paid 投递失败要重试，而 order.shipped 在下一轮成功了——顺序就反了。
  • id 的分配顺序不等于提交顺序：事务 A 先拿到 id=100，事务 B 后拿到 101，但 B 先提交。轮询器在这一刻只能看到 101，会先发它。这一条最容易被忽略，而且它在任何用自增 id 排序的场景里都成立。

要保证同一订单内有序，标准做法是按聚合键串行化：给 outbox 加一列 aggregate_id（订单 id），投递时保证同一个 aggregate_id 的行不被并行处理——可以用咨询锁（第 07 部分），也可以在认领时排除"这个聚合还有更早的未发送行"的情况。

但更值得问的是：下游真的需要有序吗？如果下游的处理是幂等的、并且用状态机保护（第 05 部分），那么乱序到达是安全的——shipped 先到会被状态机拒绝，等 paid 处理完再重试 shipped 就好了。

让消费方能容忍乱序，几乎总是比让投递方保证有序更便宜。因为保证有序意味着放弃并行、增加延迟、并且在一条消息卡住时阻塞它后面所有的消息——那个"队头阻塞"的代价通常比重试几次大得多。

限流与防刷

第一季第 08 部分提过一句"登录要按邮箱和 IP 两个维度限流"，当时没有 Redis 没法做。第一季第 12 部分又说"虚拟线程让你更需要主动限流"。这一部分把两笔账一起还了。

限流的目的有两个，而它们对算法的要求不同：保护自己（别被打垮）容忍短时突发，只关心平均速率；阻止滥用（撞库、刷券、爬数据）恰恰要卡住突发。选错算法，你会得到一个"看起来在限流、实际拦不住攻击"的中间件。

两个维度都要，因为它们挡的是两种不同的攻击：只按 IP 限，攻击者用代理池就绕过了；只按邮箱限，攻击者用一个常见密码去试一万个邮箱（密码喷洒）完全不受影响。

安全 · Javalin 的 ctx.ip() 默认是安全的，但你可能会亲手弄坏它

好消息：Javalin 的 ctx.ip() 返回的是TCP 连接的对端地址，不看任何请求头。这个值伪造不了。

坏消息：一旦你部署在反向代理后面，ctx.ip() 就永远是代理的 IP，限流按它来等于没限。于是几乎所有人都会改成读 X-Forwarded-For——而那个头完全由客户端控制。直接拿它当客户端 IP，攻击者每个请求换一个假 IP，限流形同虚设；更糟的是如果你把这个"IP"写进封禁名单，攻击者可以伪造成别人的 IP，让你封掉真实用户。

正确做法：X-Forwarded-For 是一个逗号分隔的链，只有最靠右的、由你自己的可信代理追加的那几段才可信。所以你必须知道自己前面有几层可信代理（记为 N），然后取倒数第 N+1 个。

这个 N 必须是配置项，因为它随部署拓扑变化——本地开发是 0，套一层 CDN 加一层负载均衡就是 2。配错的方向也很关键：配大了会取到客户端伪造的段（危险），配小了会取到自己代理的 IP（限流失效但不危险）。拿不准时宁可配小。

Q1滑动窗口的 ZSET 里每次请求存一个成员。如果给商品列表接口配"每分钟 5000 次"，一个热门 IP 的 ZSET 里会有多少数据？这有问题吗？

思路提示

最多 5000 个成员，每个成员是一个 UUID（36 字节）加一个分数（8 字节），加上 ZSET 的跳表开销，大约 400 KB 一个 key。一万个活跃 IP 就是 4 GB——只为了限流。

而且还有第 01 部分 Q2 那个问题：ZREMRANGEBYSCORE 清理几千个成员是一次相对耗时的操作，而 Redis 是单线程的，这条命令执行期间所有其它客户端都在等。

所以滑动窗口只适合低频接口。高频接口的三个替代：

  • 令牌桶：无论限额多大，永远只存两个数字。这就是图 12 右边那格适合"浏览、搜索"的原因。
  • 固定窗口：接受边界突发。对"保护自己"这个用途，2 倍突发通常无所谓——容量规划本来就该有余量。
  • 滑动窗口计数器（不是日志）：只存当前窗口和上一个窗口的计数，按时间加权估算。精度介于两者之间，存储和固定窗口一样小。这是很多商业限流器的默认实现。

顺带把成员改短也有帮助：用 now-随机数 而不是完整 UUID 能省一半内存。但这治标不治本——数量级不对的时候，优化常数没有意义。

Q2限流返回 429，前端收到后立刻重试。这会让情况变好还是变坏？服务端能做什么？

思路提示

变坏，而且这正是第 08 部分图 9 那个"重试放大"在自己身上的翻版：你告诉客户端"太多了"，客户端的回应是发得更多。

服务端能做三件事：

  • 返回 Retry-After 头（上面代码里那个）。它明确告诉客户端"等 N 秒"，规范的客户端会遵守。这是最便宜也最有效的一步。
  • 让 429 的响应尽可能便宜：不查数据库、不渲染完整页面、不写详细日志（否则日志本身会成为放大器）。被限流的请求应该在最外层就被挡掉——所以限流处理器要注册在 before 链的前面。
  • 对持续违规者升级处置：连续触发限流 N 次的 IP，直接进一个短期黑名单，后续请求在更早的位置（甚至在 CDN / WAF 层）被拒。让攻击者的成本上升得比你快。

但最根本的一条是：限流不能只在应用层做。如果攻击流量已经打到你的 Jetty 线程池，即使每个请求只花 1 ms，几万 QPS 也会把线程占满——正常用户照样受影响。真正的防线是分层的：CDN/WAF 挡掉明显的恶意流量，负载均衡做粗粒度限速，应用层只做业务语义的限流（"这个账号五分钟内只能试五次密码"）。

应用层限流的价值不在于扛住 DDoS，而在于表达业务规则——这一点想清楚了，就不会指望它做它做不到的事。

Q3第一季说"虚拟线程让你更需要主动限流"。为什么？开了虚拟线程之后，限流的设计要变吗？

思路提示

因为平台线程池本身就是一道隐式的限流。250 个线程意味着最多 250 个请求同时在处理，第 251 个在队列里等，队列满了就直接拒绝。这道闸门很粗糙，但它确实存在，而且它保护的是下游——数据库、Redis、支付网关都不会同时收到超过 250 个请求。

开了虚拟线程之后，这道闸门消失了：一万个请求可以同时进来，各自创建一个虚拟线程，然后一起去抢那 10 个数据库连接。结果是：

  • 每个请求都拿不到连接，全部在 HikariCP 的队列里等到超时。
  • 一万个请求全部失败，而如果只放进来 250 个，其中大部分能成功。

这就是"能接住不等于该接住"——把负载吸进来再全部失败，比在入口拒绝一部分更糟。

所以开虚拟线程时，限流的设计要补上原来由线程池承担的那部分职责：

  • 给关键下游加隔板（Resilience4j 的 Bulkhead 或一个 Semaphore）：限制同时访问数据库/支付网关的请求数，和连接池大小对齐。
  • 入口做并发数限流，而不只是速率限流。"每秒 1000 次"和"同时最多 200 个在处理"是两回事，后者才对应资源。
  • 快速失败优于排队：拿不到隔板许可就立刻返回 503 + Retry-After，而不是排队等。

一句话总结：虚拟线程把"拒绝"的位置从框架挪到了你的代码里。它没有让容量变大，只是让你必须自己决定容量在哪。

错误处理与可观测性

前面十一个部分往系统里加了 Redis、外部网关、定时任务、Outbox。每一样都引入了新的静默失败方式——不报错，只是数字慢慢变得不对。这一部分讲怎么让这些失败变得可见。

监控错误率是不够的。这一季埋下的问题里，最危险的几个不产生任何错误：预占泄漏、回调丢失、Outbox 卡住、缓存返回旧值。它们只会让某个数字慢慢偏离——所以除了日志和指标，还需要第三样东西：定期核对那些本该恒成立的等式。

陷阱 · MDC 不会跟着任务进线程池

MDC 底层是 ThreadLocal。Javalin 一个请求一个线程，所以在请求处理链里它工作得很好。但只要你把活儿丢给别的线程，上下文就断了：

executor.submit(() -> sendEmail(order)); // 这个任务里 MDC 是空的

标准做法是手工搬运：var ctxMap = MDC.getCopyOfContextMap(); 然后在任务开头 MDC.setContextMap(ctxMap)、结尾 MDC.clear()。写成一个 ContextAwareExecutor 包装类一劳永逸。

虚拟线程不改变这一点：每个虚拟线程有自己的 ThreadLocal（所以在虚拟线程里 MDC 能用），但"提交任务时不会自动继承"这条依然成立。Java 21 引入的 ScopedValue 是为这类问题设计的结构化替代品，配合结构化并发能自动向子任务传播；它在不同 JDK 版本里的稳定程度不同，用之前确认一下你的目标版本。

最后一条纪律：那个 MDC.clear() 要放在 finally 里。Javalin 的 after 处理器本身是框架保证执行的（第一季第 02 部分），但处理器内部的日志语句如果抛异常，清理就漏了——而线程会带着脏 MDC 回到池里。

错误分两类，处理方式完全不同

Q1图 13 的指标那一行特意标了"不带 requestId"。为什么指标不能带？带了会怎样？

思路提示

因为指标系统按标签组合存储时间序列：每个不同的标签组合就是一条独立的序列，各自占内存、占磁盘、占查询时间。这叫基数。

http_requests{route="/checkout",status="200"} 是一条序列。加上 requestId 之后，每个请求都会创建一条新序列——每天一百万请求就是一百万条序列，而且它们永远不会再被写入第二个点。

后果是监控系统被撑爆（有个专门的名字叫"基数爆炸"），查询变慢甚至崩溃。而且这通常不是缓慢恶化，是某次发布后几小时内就出事。

规则：指标的标签只能是有限枚举——路由模板（注意是 ctx.endpoint().path() 给的 /products/{id}，不是实际路径 /products/8812）、状态码、错误码、方法名。用户 id、订单 id、requestId、URL 全路径、IP，都不行。

Javalin 的 Micrometer 插件默认就是按路由模板打标签的，这个默认值是对的。但如果你自己写 Counter.builder(...).tag("path", ctx.path())，那就是在制造基数爆炸——差一个方法调用，差一个数量级的存储。

需要"某个具体请求的细节"怎么办？这正是三种信号分工的意义：指标回答"整体怎么样"（低基数、可聚合），日志回答"这一次发生了什么"（高基数、可搜索），链路追踪回答"这一次经过了哪些服务"。

Q2图 13 下半部分第五条要和支付网关对账。这个任务具体怎么写？发现不一致时该自动修复还是只告警？

思路提示

写法：遍历自己库里"最近 24 小时内、状态仍是 PENDING_PAYMENT、且创建超过 30 分钟"的订单，拿 payment_attempts 里的凭据去调网关的查询接口（图 8 规则 ③），比对结果。反向也要做：拿网关的对账文件比对我们这边是否都已入账——这一侧能发现"我们完全没收到过任何回调"的那些。

自动修复还是告警，按不一致的方向分：

  • 网关说成功，我们是 PENDING_PAYMENT：回调丢了。这个方向可以自动修复——走和回调完全相同的那段代码（transitionTo(PAID) + 转实扣 + Outbox），因为那段代码本来就是幂等的。复用回调路径而不是新写一套，是这里的关键：新写一套意味着两条路径各自维护，迟早不一致。
  • 网关说失败/不存在，我们是 PAID：绝不自动修复。这意味着我们凭空把一笔订单标成了已付——可能是伪造的回调（签名校验漏了？）、可能是 bug、也可能是网关那边的数据问题。把一个 PAID 订单自动改回去，可能让一个真实付款的用户拿不到货。必须人工介入。
  • 金额不一致：一律人工。这是最严重的一类。

一般原则：自动修复只能用于"补做一件本来就该做的、且幂等的事"；凡是需要撤销已发生的事，都必须人工。

最后一点：对账任务本身要有指标——"上次成功运行时间"和"本次发现的不一致条数"。一个悄悄挂掉的对账任务，比没有对账任务更危险，因为它给了你虚假的安全感。而在 Java 里"悄悄挂掉"格外容易发生——第 07 部分那个 scheduleAtFixedRate 吞异常的坑就是最常见的原因。

Q3不变量核对该多久跑一次？跑得太频繁给数据库压力，太稀疏又发现得晚。怎么定？

思路提示

按"错了多久会造成不可挽回的损失"来定，而不是按"查询有多贵"来定。逐条看：

  • 金额不一致：钱的问题，一旦发货就难以挽回。高频，甚至可以做成写入时的实时校验——在下单事务里加一句断言，或者干脆做成数据库的 check 约束。
  • Outbox 积压：几分钟内没发出的通知影响体验，几小时就是事故。做成指标 + 告警，而不是定时任务——它天然就是一个可以持续观测的量。
  • 预占泄漏：影响可售库存，但通常偏差很小、增长很慢。每小时一次足够。
  • 支付对账：受制于网关的接口速率限制，而且用户等着拿货。每 15 分钟扫一次近期的，每天做一次全量对账。

两个实用技巧：把重的核对改成增量的（只核对最近有变动的商品，全量那次放低峰期）；让核对跑在只读副本上——这些查询都是只读、可容忍轻微延迟的，放副本上就完全不影响主库，于是"太贵所以不敢频繁跑"这个约束基本消失了。

最后强调一遍：不变量核对是这一季所有内容里，投入产出比最高的一项。它便宜（几条 SQL）、抓的是最难发现的一类问题，而且它逼你把"这个系统里什么必须永远成立"想清楚——这个思考过程本身就值回票价。

Redis 挂了会怎样

这一季往系统里加了一个新组件，并在六个地方用了它。那就有六个新的失败方式。这一部分把它们逐个列出来，每一格填上答案——这张表本该在引入 Redis 的那一天就填好。

"Redis 挂了会怎样"这个问题，最坏的答案不是"全站不可用"，而是"不知道"。不知道意味着故障发生时你要现场推理，而现场推理的准确率很低、时间很贵。所以这一部分的产出不是代码，是一张表。

把降级写进代码

这段代码体现两件事。第一，fail-open 不等于"什么都不做"——缓存挂掉时无限制地回源，等于把一个组件的故障放大成数据库的故障，降级动作本身必须是受控的。第二，Java 这边有一个格外划算的第二层：Caffeine 是纯内存的，Redis 挂了它照样工作，5 秒 TTL 就能把热点商品的回源量再降一个数量级。几十行代码，不引入任何新的外部依赖。

陷阱 · Semaphore 的许可必须在 finally 里释放

这是 Java 并发里最经典的一个泄漏：tryAcquire 成功之后，如果 loader.get() 抛异常而没有 finally，那个许可就永远回不来了。

症状极具迷惑性：刚开始一切正常，随着偶发异常累积，可用许可越来越少，最终所有请求都拿不到许可——而此时数据库和 Redis 都是健康的，你会往完全错误的方向排查。

同类问题还有 ReentrantLock.unlock()、Connection.close()、以及第 02 部分那个 setAutoFlushCommands(true)。凡是"拿了要还"的资源，还的动作一律进 finally，没有例外。能用 try-with-resources 的就用它。

PostgreSQL 挂了呢

答案很短：整个系统不可用，而且这是正确的。数据库是所有事实的来源，没有它，任何写操作都不该被接受——强行让下单在数据库不可用时"先记在 Redis 里"，是这一季讲的所有原则的反面。

能做的只有三件：只读页面尽量还能出（有 Caffeine 本地缓存的话）、健康检查如实反映（第一季图 13 的 readiness）、以及错误页面要说人话，而不是把 PSQLException 的堆栈甩给用户。

深入 · 这张表要怎么验证

表填完了不等于对。唯一能验证它的办法是真的把 Redis 关掉。在预发环境做一次，按下面的顺序：

  1. 先预测。让每个人写下自己认为会发生什么。这一步不能省——它把"我们以为的"和"实际的"分开了。
  2. 断开 Redis：先用防火墙丢包（模拟"连不上但没报错"这种更难处理的情况），再直接停进程（模拟明确的连接拒绝）。
  3. 走一遍主流程：浏览、加购、登录、下单、支付回调。记录实际表现。
  4. 比对预测和实际。差异就是这张表要修的地方，也是最有价值的产出。
  5. 恢复 Redis，观察系统能不能自愈——很多系统挂得住却恢复不了：连接池没有重连、熔断器不再关闭、缓存被穿透打死。这一步经常比第 3 步发现的问题更多。

两个模拟方式的差别值得强调："丢包"比"停进程"难处理得多。停进程会立刻返回连接拒绝，你的 catch 马上生效；丢包会让每个请求卡到超时（第 01 部分那个 timeoutOptions(500ms) 就是为它准备的），如果超时配得太长或没配，整个 Jetty 线程池会被拖死——而这才是真实故障里更常见的形态。

Q2图 14 里商品缓存那一格写着"如果数据库扛不住，这一格会变成全站故障"。怎么提前知道数据库扛不扛得住？

思路提示

三个层次，从便宜到贵：

  • 算一算。缓存命中率 95%、总 QPS 2000，意味着现在数据库承担 100 QPS。缓存全挂就是 2000 QPS——翻二十倍。你的数据库能不能扛 2000 QPS？这个数字通常一问就有答案，而且往往是"不能"。而且别忘了连接池只有 10 个——真正的限制往往先撞在这里。

如果重新开始，我会这样排：

  1. 先做第 05、06、09、10。它们不需要 Redis，只需要 PostgreSQL——jOOQ 的 skipLocked()、条件 UPDATE、唯一索引、枚举状态列就够了。做完之后你已经有一个正确的电商系统了：慢，但正确。
  2. 然后做第 03 和第 12。索引和可观测性。这时你会拿到真实数据：到底哪里慢、慢多少。
  3. 最后才引入 Redis，而且只在第 2 步的数据指出确实需要的地方引入。很可能你只需要它的一两个用途，而不是六个。

这个顺序背后的判断是：正确性的复杂度躲不掉，性能的复杂度应该按需付费。而现实中最常见的错误恰恰相反——先引入 Redis（因为"电商都要用"），再在上面盖业务逻辑，最后发现状态机和幂等还没做。那时候再补，代价会大得多，因为要在一个已经有并发和缓存的系统里补正确性。

如果这一季只留下一句话，我希望是这句：先把系统做对，再把它做快；顺序反过来的话，你会得到一个又快又错的系统，而且很难知道它错在哪。
