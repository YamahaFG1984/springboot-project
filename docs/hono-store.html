读这一列的正确方式

最右边那一列几乎每一格都写着"自己来"。这不是缺点，也不是优点，是一次交易。你付出的是要自己写、自己记得写；换回来的是启动只要几十毫秒、行为完全可预测、出问题能一路读源码读到底——没有代理、没有反射、没有"某个注解在某个我没读过的自动配置里悄悄生效了"。

原书没讲、这里补上的

原书 31 个短章，胜在流畅，输在深度。以下这些它一处也没有，而它们恰恰是"能跑的 demo"和"敢上线的服务"之间的全部距离：

  • 事务。原书下单流程是三条独立的写操作，中间任何一步失败，数据就此不一致，没有任何补救。
  • 并发。两个人同时买最后一件商品会怎样？原书没有问过这个问题。
  • 迁移。原书开着 TypeORM 的 synchronize: true——启动时让 ORM 按实体定义自动改表结构。Drizzle 有一个一模一样的功能叫 drizzle-kit push，第 6 部分会讲为什么它只配出现在你的笔记本上。
  • 测试。原书全书零测试。而 Hono 恰恰是我见过最好测的服务端框架之一，不写实在可惜——第 12 部分会讲原因。
  • 钱。原书商品价格是 JavaScript 的 number。这是浮点数。第 6 部分有一张图专门讲这件事有多糟。
  • N+1 与笛卡尔积。原书的购物车页面在循环里查数据库。Drizzle 不会像 JPA 那样"偷偷"帮你查，但也正因如此，它更容易被写成显式的 N+1。

工具链与项目骨架

对应原书第 2–4 章。原书用 nest new 一条命令生成一切，然后说"目录结构如上"。这里我们不用脚手架，手工搭一遍——因为 Hono 项目小到值得你知道每一个文件为什么存在。

Spring Boot 有 start.spring.io，Nest 有 nest new，Hono 也有 npm create hono@latest。但一个 Hono 项目的全部配置文件加起来不到一百行，手搭一遍的收益远大于成本：之后每一个"为什么它不工作"的问题，答案都在这一百行里。

五分钟跑起来

只有 hono 一个是框架。它自身零依赖——node_modules/hono 里没有任何第三方包，压缩后不到 20 KB。这个数字值得记住，它解释了后面很多设计决定。

npx tsx src/index.ts，服务就起来了。冷启动大约 50 毫秒。

一个 Request 进去，一个 Response 出来。这两个类型来自 Web 标准（fetch 规范），浏览器里有、Node 18+ 有、Deno 有、Bun 有、Cloudflare Workers 有。@hono/node-server 的全部工作就是把 Node 的 IncomingMessage 翻译成标准 Request，再把返回的 Response 写回 ServerResponse。换一个运行时，就换一个适配器，app 一行不用改。第 13 部分会兑现这个承诺，也会讲清楚它的边界在哪。

tsconfig.json：六个选项决定项目手感

选项不开会怎样
strict类型系统基本失效。strictNullChecks 关掉后，user.name 在 user 可能是 undefined 时也不报错——你会在生产环境读到 Cannot read properties of undefined。
noUncheckedIndexedAccessarr[0] 的类型是 T 而不是 T | undefined。Drizzle 的查询返回数组，rows[0].id 在空结果时崩溃，而编译器一声不吭。这一项对本项目尤其重要。
exactOptionalPropertyTypes{ name?: string } 可以被赋成 { name: undefined }。写进数据库时这两者含义完全不同：一个是"不改这一列"，一个是"把这一列设成 NULL"。
verbatimModuleSyntax类型导入和值导入混在一起，打包时可能把只用于类型的模块也拖进产物。开启后你必须写 import type { X }，边界更清楚。
jsxImportSource写成 "react" 的话，编译产物会去 import { jsx } from "react/jsx-runtime"——运行时报模块找不到。第 3 部分会讲这个 jsx() 函数到底做了什么。
lib 含 DOMRequest、Response、FormData、File 这些 Web 标准类型全部报 Cannot find name。它们定义在 DOM lib 里，尽管我们跑在服务端。
陷阱 · noEmit 意味着什么

我们用 tsx（开发）和 tsc --noEmit（检查）分工：tsx 只剥掉类型、不做类型检查，所以它跑得飞快，但类型错误不会阻止它运行。这是 esbuild/swc 系工具的通性，也意味着 npm run typecheck 必须进 CI，否则类型系统只是编辑器里的装饰。第 5 部分会把这件事做成门禁。

项目骨架：按功能分，不按角色分

关键是 catalog/、cart/、order/ 这一层：按业务功能切，不按技术角色切。原书用的是 controllers/、services/、entities/ 这种切法，改一个功能要在三个目录之间来回跳，而且没有任何东西阻止 controllers/cart.ts 直接 import entities/admin.ts。

对照 · 这里没有"扫描"

Spring 靠 @ComponentScan 从入口类所在的包往下扫，Nest 靠 @Module 显式登记。Hono 两者都没有：一个路由文件不被任何人 import，它就完全不存在——不报错，不警告，只是那个 URL 返回 404。

这和 Spring 挪错包导致全体控制器静默 404 是同一类故障，但成因相反：Spring 是"扫描范围没覆盖到"，Hono 是"你忘了写那行 import"。两边的教训是同一条：让路由的注册位置集中且显眼。我们把它全部收在 src/app.ts 里。

src/index.ts 只剩下"起服务"这一件事，app.ts 则可以被测试直接 import 而不启动任何端口。这个拆分在第 12 部分会变得非常划算。

陷阱 · 为什么 import 路径要带 .js

源文件明明是 routes.ts，为什么写 ./catalog/routes.js？因为 module: "NodeNext" 下 TypeScript 遵循 ESM 的解析规则：路径指的是产物的路径，而不是源码的路径。写 .ts 反而会报错。觉得别扭的话可以改用 "moduleResolution": "bundler" 允许省略扩展名，但那样就必须始终经过打包器。本教程选前者，因为它跑得离 Node 的真实行为最近。

数据库：一份 compose.yaml

原书让读者装 XAMPP、开 phpMyAdmin、在图形界面里手工建表。这在 2022 年就已经过时了，而且它有一个更根本的问题：那些手工点出来的表结构，没有任何一份可执行的记录。换台机器就得重来，同事的库和你的库长得不一样也没人知道。第 6 部分的迁移文件就是在解决这件事。

先自己想，再展开思路。

Q1把 app.ts 里 .route("/cart", cartRoutes) 这一行删掉，但 cart/routes.ts 文件保留。tsc --noEmit、biome check、vitest run 三个命令里，有哪个会告诉你出事了？

思路提示

前两个都不会。类型检查器看到的是一个"没被人用的导出"，这完全合法；Biome 默认也不把未使用的导出当错误（它只管未使用的局部变量）。访问 /cart 会返回 404，而 404 是 Hono 的正常响应，不是异常。

只有测试会——如果你写了一个断言 GET /cart 返回 200 的测试。这就是为什么在一个没有扫描、没有容器的框架里，"路由存在"本身需要被测试覆盖；在 Spring 里你至少还有一个启动期的上下文加载能兜住一部分错误。第 12 部分会给出一个只用几行就能覆盖全部路由清单的写法。

额外一层保险：Biome 可以开 noUnusedImports 之外的规则，或者用 knip 这类工具专门查"没有任何人引用的导出"。但更根本的办法还是让路由清单集中在一个文件里，人眼扫一遍就能发现缺口。

Q2把 tsconfig.json 里的 noUncheckedIndexedAccess 关掉，然后写 const p = (await db.select().from(products).where(eq(products.id, id)))[0]; return p.name;。编译通过吗？线上什么时候会崩？

思路提示

关掉后编译通过，p 的类型是 Product。但查询在商品不存在时返回空数组，[0] 是 undefined，p.name 抛 TypeError。触发条件是"有人访问了一个已下架商品的 URL"——测试很少覆盖，用户很容易撞上。

开启后 p 的类型变成 Product | undefined，编译器强迫你处理。这一个选项对 Drizzle 项目的价值极高，因为Drizzle 的所有查询都返回数组，[0] 会在代码里出现几十次。

更好的写法是让"取一条"这件事本身带上语义，比如封装一个 findOne 在找不到时抛 HTTPException(404)，或者返回 Result 类型。第 4 部分会给出我们项目里的约定。

Q3Nest 需要在 @Module 里显式列出 controller 和 provider，Spring 靠包扫描自动发现，Hono 靠 import + .route()。这三种"登记方式"，哪一种最容易在重构中出错？为什么？

思路提示

值得注意的是三者的失败模式不同，而不是简单排个高下：

  • Spring 的包扫描：重构时移动包名可能让整个子树离开扫描范围，失败是批量的、静默的——一次挪错，几十个端点同时消失。
  • Nest 的 @Module：登记是显式的，但登记信息和实现分离，删了类忘了删登记会在启动时炸（这算好事，早失败）；反过来加了类忘了登记，则是静默的。
  • Hono 的 import：失败是局部的——忘了挂一个子路由只影响那一组 URL。而且 IDE 的"查找引用"能直接告诉你某个 routes.ts 有没有被人用，因为这是真正的 import，不是字符串或元数据。

我个人认为 Hono 这种最容易排查：没有中间层。但它对"集中登记"这个约定的依赖最强——如果有人开始在各个模块里零散地 app.route()，可追踪性立刻崩塌。第 7 部分会用 dependency-cruiser 把这个约定变成一条能被 CI 断言的规则。

01

一次请求的完整旅程

对应原书第 5 章。原书用三句话讲完 MVC 就开始写代码。这一部分是整份教程的地基：把 GET /products 从网卡到 HTML 的每一跳都摆出来，并指出其中哪一跳是"你的代码"。

Hono 的核心可以用一句话说完：它是一个把 Request 变成 Response 的函数。这句话听起来像是简化，其实是字面意思——app.fetch 真的就是那个函数，你可以直接调用它，不需要网络、不需要端口、不需要容器。后面第 12 部分讲测试时，这一点会变成一个巨大的便利。

逐跳解读

1 · 适配层：唯一"不可移植"的一段

serve() 内部起了一个 node:http 服务器，每来一个请求就做三件事：把 IncomingMessage 的 method / url / headers 包成标准 Request，body 包成 ReadableStream；调用 app.fetch(request)；拿到 Response 后把 status / headers / body 写回 ServerResponse。

整个项目里只有这一段知道 Node 存在。换到 Bun，是 Bun.serve({ fetch: app.fetch })；换到 Cloudflare Workers，是 export default app。这不是营销话术，是这个架构的直接推论。代价在第 13 部分兑现：一旦你在业务代码里写了 fs.writeFile，这份可移植性就作废了。

2 · 路由匹配：工作发生在启动时

这是 Hono 最有意思的实现细节。app.get("/products/:id", …) 并不会在每次请求时逐条比对——Hono 在第一次请求到来时，把所有注册过的路由合并编译成少数几个正则表达式，之后每个请求只跑一次匹配。

默认的 new Hono() 用的是 SmartRouter。你几乎不需要动它，但知道它的存在能解释一个现象：第一个请求比后续请求慢一点，因为编译发生在那一刻。

对照 · 三种路由分发

Spring 的 HandlerMapping 在启动时扫描注解建立映射表，请求时用 PathPatternParser 匹配；Nest 底下是 Express 的路由数组，请求时逐条用正则试。Hono 的做法在这两者之间：像 Spring 一样提前准备，但准备出来的是一个正则而不是一张表。

实际影响：Express 风格的逐条匹配在路由数量上千时会成为可测量的开销，Hono 的合并正则不会。这在"每个请求都是冷的" 边缘环境里尤其重要。

3 · Context：每请求一个的手提箱

c 是你在 handler 里唯一拿得到的东西，它把请求相关的一切都装在里面：

c.set / c.get 是 Hono 里"请求作用域状态"的全部机制。Spring 用 @RequestScope 的 Bean 加作用域代理来做同一件事，背后是 ThreadLocal；Hono 就是把值挂在这个每请求新建的对象上。更简单，也更诚实：值从哪来、到哪去，全在类型里写着——第 4 部分会讲怎么让 c.get("user") 有正确的类型而不是 any。

4 · handler 就是你写的那个函数

值得单独强调：Hono 调用 handler 时没有反射、没有动态代理、没有字节码增强。你在栈里看到的就是你写的函数名，断点打在哪停在哪，console.log 加在哪就打在哪。

这条性质在调试时的价值很难高估。Spring 里一个 @Transactional 方法的调用栈会穿过五六层 CglibAopProxy；Nest 里一个请求要经过 Guard、Interceptor、Pipe 三套元数据驱动的机制。Hono 的栈是平的。

出错时走哪条路

三种"非正常"结局，各自有各自的出口：

安全 · 别把异常原文吐给用户

默认情况下 Hono 对未捕获异常返回 500 Internal Server Error 一行文本，这是安全的。危险的是自己动手改成 return c.text(err.message, 500)——数据库驱动的错误消息里经常带着表名、列名甚至参数值，Zod 的错误里带着字段结构。对外一句话，对内一条结构化日志，中间用 requestId 串起来，这是第 13 部分的做法。

还有第三种：中间件不调用 next()，直接返回响应。这是权限拦截的正常路径，不是错误——它甚至不会进入 onError。第 2 部分讲清楚这条路径。

Q1不启动服务器，直接在 Node REPL 里执行 await app.fetch(new Request("http://localhost/products"))，你会拿到什么？为什么这在 Express 里做不到？

思路提示

你会拿到一个完整的 Response 对象，可以 await res.text() 看 HTML、看 res.status、看 res.headers。整个过程没有 socket、没有端口、没有异步 I/O 等待。

Express 做不到，因为它的 handler 签名是 (req, res, next)，其中 res 是一个可写流——它绑定在一个真实的 TCP 连接上。要测试就必须起服务器（supertest 就是这么做的：起一个临时端口，发真实 HTTP 请求）。

差别的根源是响应是"返回值"还是"副作用"。Hono 选了返回值，于是整个 app 变成一个可以在任何地方调用的纯函数。这是它最被低估的设计决定，第 12 部分整章都在花这笔红利。

Q2图 1 里，Spring 的安全过滤器在 DispatcherServlet 之前，属于框架之外；Hono 的 session/csrf 中间件在链里，属于你的代码。这个位置差异会带来什么实际后果？

思路提示

最直接的后果是默认值反了。Spring Security 一旦引入，默认拒绝所有未显式放行的路径——你新加一个 /admin/reports 却忘了配规则，它会 403，是个响亮的失败。Hono 里你新加一个路由却忘了挂鉴权中间件，它直接可访问，是个静默的失败。

补救办法不是"更小心"，而是把结构改成同样默认拒绝：把需要鉴权的路由全部挂在一个已经带了鉴权中间件的子 app 上（const admin = new Hono(); admin.use(requireAdmin); …; app.route("/admin", admin)），这样"忘记"就变成了"没挂到那棵子树上"，而没挂上的路由压根不存在。第 9 部分会把这个结构完整写出来。

第二个后果是顺序由你负责：把 csrf() 写在 session 中间件之后还是之前、把 logger() 写在最外还是最内，效果都不一样。Spring 的过滤器有内建的排序体系，Hono 就是数组下标。第 2 部分正是讲这个。

Q3Hono 在首次请求时才编译路由正则。如果一个函数计算平台每处理几个请求就销毁实例，这个设计是优势还是负担？换成哪个路由器更合适？

思路提示

是负担。编译成本被摊销到了极少的请求上，而 RegExpRouter 的编译恰恰是几个路由器里最贵的。这种场景应该用 LinearRouter：new Hono({ router: new LinearRouter() })——它注册最快、匹配是线性扫描，在"注册 N 个路由只处理 M 个请求且 M 很小"时总成本最低。

更值得注意的是这个提问方式本身："哪个更快"没有答案，"在什么负载形状下更快"才有。Hono 把路由器做成可替换的构造参数，就是承认这件事没有全局最优解。类似地，第 6 部分会问"预编译语句在短连接下还划不划算"，第 13 部分会问"启动时做的事在 serverless 下算不算浪费"。

顺带一提，如果你不确定，就别动默认的 SmartRouter——它在长驻服务下是对的，而绝大多数人跑的是长驻服务。

02

中间件：洋葱模型

原书把横切逻辑拆成 Guard、Interceptor、Pipe、Exception Filter 四种概念，各有各的生命周期。Hono 只有一种：函数。但正因为只有一种，顺序和 await 就成了必须自己想清楚的事。

中间件是 Hono 里唯一的横切机制。日志、鉴权、CSRF、限流、响应头、错误兜底——全都是同一个形状的函数。学会它，等于学会了 Hono 的一半。

三段结构，一个函数。next() 这一行是分界线：它之前的代码在请求进入时按注册顺序执行，它之后的代码在响应返回时按相反顺序执行。

深入 · 那个 try/finally 不是装饰

假如写成没有 try 的版本：await next(); const ms = …。当内层 handler 抛异常时，await next() 会把异常继续往外抛，后面那行统计代码永远不执行。结果就是：正常请求都有耗时记录，唯独出错的请求没有——而那些恰恰是你最想看耗时的请求（超时？死锁等待？）。

规则很简单：中间件里"必须发生"的收尾动作，一律放 finally。日志、指标上报、释放资源、解锁，都属于这一类。只有"仅在成功时才做"的事（比如给成功响应加缓存头）才写在 next() 之后的正常位置。

这条规则在 Spring 里由框架替你保证（HandlerInterceptor 的 afterCompletion 无论如何都会被调用），在 Hono 里由你自己保证。这就是序里说的"交回给你的东西"的一个具体样本。

三个最常见的错误

1 · 忘了 await

next() 返回一个 Promise。不 await，出栈阶段的代码会在内层还没跑完时就执行——c.res 尚未被 handler 赋值，你设的响应头写在了一个即将被替换掉的响应上。症状是间歇性的：内层如果恰好是同步的，它能正常工作；一旦内层多了一次 await db.query()，头就丢了。

Biome 的 noFloatingPromises 类规则能抓到一部分这种写法，值得开。

2 · 用 c.res = 替换响应

3 · 在中间件里做只有部分路由需要的重活

app.use(session) 会给每一个请求都查一次数据库，包括 /health、静态资源、以及所有不关心用户是谁的页面。三个改法，按代价从小到大：

  • 限定路径：app.use("/cart/*", session)——Hono 的 use 第一个参数可以是路径模式。
  • 挂到子 app 上：只有需要会话的那棵子树带这个中间件。这是本项目采用的做法，第 9 部分展开。
  • 惰性求值：中间件只把"怎么取用户"这个函数放进 c，真正查库推迟到第一次 await c.get("currentUser")()。灵活但会让"这个请求到底查没查库"变得难以预测，除非你有好的追踪。
对照 · 四种概念 vs 一种

Nest 把横切逻辑分成 Guard（能不能进）、Interceptor（包住前后）、Pipe（转换与校验参数）、Exception Filter（兜异常）四类，各有各的注册方式和执行时机；Spring 有 Filter、HandlerInterceptor、AOP 三套并存。Hono 全部是同一个函数签名。

好处是没有"这段逻辑该写成哪一类"的困惑，也没有"这四类之间谁先谁后"的记忆负担。代价是框架不再表达意图：一个中间件到底是在做鉴权还是在做日志，只能靠命名和放置位置传达。约定因此变得重要——我们把中间件按用途分目录，鉴权类一律以 require 开头。

Q1写两个中间件 A 和 B，各自在 next() 前后打印一行。注册顺序是 A、B。四行输出的顺序是什么？如果把 B 改成不调用 next()，输出变成几行？

思路提示

正常情况：A-in → B-in → B-out → A-out。这是栈的形状，不是队列。

B 不调用 next()：A-in → B-in → B-out → A-out——还是四行。这是最容易想错的一点：短路的是"更内层"，不是"外层的出栈阶段"。B 之后的 handler 不会执行，但 B 自己 next() 之后的代码照常跑，A 的出栈阶段也照常跑。

实际影响：一个返回 403 的鉴权中间件，仍然会被外层的 logger 记录、被外层的 requestId 加上响应头。这正是你想要的。反过来，如果你在某个外层中间件的出栈阶段假设"到这里说明 handler 成功了"，那就错了——要判断结果得看 c.res.status。

Q2你想加一个"给所有 200 响应加 Cache-Control: public, max-age=60"的中间件，但不能影响登录后的个性化页面。写在 next() 之后还是 finally 里？判断条件该怎么写？

思路提示

写在 next() 之后（不是 finally）——因为这件事只在成功时才该做，异常路径上加缓存头是有害的。

条件至少要包含三项：c.res.status === 200、请求方法是 GET/HEAD、以及这个响应不因用户而异。第三项最容易漏。判断方式不是"看有没有登录"，而是看这次渲染有没有真的用到用户信息——最稳的做法是让需要个性化的 handler 主动打标记（c.set("private", true)），中间件只在没有标记时才加缓存头，即默认不缓存。

反过来做（默认缓存、个性化页面主动关掉）会在某天有人新写一个页面时把张三的购物车缓存给李四看。这是一类经典事故，而且 CDN 会把它放大到全网。凡是"漏配置就泄露"的设计，都应该反过来。

顺带：真要做这件事，还得确保 Vary: Cookie 存在，否则中间层缓存不会区分带不带会话的请求。

Q3Nest 的 Guard 有一个 Hono 中间件没有的能力：它能拿到"即将执行的那个 handler 上的元数据"（比如 @Roles('admin')），从而写出一个通用的鉴权 Guard。Hono 里怎么表达同样的意图？

思路提示

Hono 里没有"handler 元数据"这个概念——中间件在执行时并不知道内层是谁。所以不能照搬，要换个思路：把"需要什么权限"编码进路由树的结构，而不是编码进某个注解。

做法是分组挂载：const adminApp = new Hono(); adminApp.use(requireRole("admin")); adminApp.get("/products", …)。权限从"handler 上的一个标签"变成了"handler 所在的位置"。

两种表达各有得失。注解式更灵活（同一组路由里可以逐个不同），但配置和实现分离，容易漏；结构式更笨，却让"忘记加权限"变成物理上不可能——你没法把一个路由放进 adminApp 又不经过它的中间件。对一个电商后台来说，我认为后者的取舍更划算。

如果确实需要在同一组里做例外，Hono 支持在单条路由上插中间件：app.get("/x", requireRole("admin"), handler)。但例外一多就该考虑重新分组了。

03

视图层：hono/jsx

对应原书第 6–9 章。原书用 Handlebars，要手工注册 partial、手工配 hbs-utils、模板里的每个变量名都拼错了也没人管。这里用 JSX——它不是 React，它只是被编译成字符串拼接的函数调用。

服务端渲染的本质是拼一个 HTML 字符串。模板语言（Handlebars、Thymeleaf、EJS）是"在字符串里挖洞"，JSX 是"用函数生成片段再拼起来"。第二种方式的好处是：模板里的每一个变量名、每一个组件参数，都能被 TypeScript 检查。原书那种"模板里写错字段名，页面上悄悄显示空白"的问题，在这里是编译错误。

最小可用：一个商品列表页

注意是 class 而不是 className——hono/jsx 输出的是 HTML，不是 DOM 属性，所以用 HTML 的名字。这是它和 React 的第一个可见差别。

布局：jsxRenderer

每个页面都要有 <html><head>…，这部分用 jsxRenderer 中间件抽出来。它本质上是往 c 里塞了一个渲染函数：

c.render(content, props) 把内容塞进布局的 children，props 传给布局本身。管理后台想换一套骨架，只要在 adminRoutes 上 use(adminLayout) 即可——布局是挂在路由树上的，不是全局的。

对照 · 三种布局机制

Handlebars（原书）：注册一个 layout.hbs，用 {{{ body }}} 挖洞——注意是三花括号，因为内容本身是 HTML 不能被转义。这个洞的类型是"任意字符串"。

Thymeleaf：th:fragment="page(content)" + th:replace，靠模板片段做装饰器。类型也是"任意片段"。

JSX：布局就是一个接受 children 的组件。它的"洞"有类型——你可以要求 title: string，忘了传就编译不过；也可以要求 breadcrumbs: Crumb[]，结构写错立刻报错。这是把模板变成函数之后最实在的收益。

要不要用流式渲染

陷阱 · 流式渲染的代价

一旦开始流式输出，响应头和状态码就已经发出去了。此后再发现"其实该返回 404"或"该重定向"，已经来不及——你只能在 body 中间插一段错误提示，或者插一段 <script>location.href=…</script>，两种都很丑。

对一个商品详情页，值得流式化的只有"推荐商品"这类可有可无的模块。主体内容不该流式：它决定状态码。本项目除了这一处示例，其余全部用普通渲染——首屏 HTML 只有几十 KB，收益不足以抵消复杂度。

原书在这里做错了什么

  • 用 {{{ }}} 输出商品描述。为了让描述里的 <br> 生效，原书关掉了转义。商品描述来自管理后台的输入框——只要后台账号被拿下，或者存在越权写入，就是存储型 XSS。正确做法是存纯文本、渲染时把换行转成 <br>，或者存 Markdown、渲染时经过消毒库。
  • 模板里的变量名没有任何检查。原书某处 controller 传的是 viewData['products']，模板里写的是 {{#each product}}——少了个 s。Handlebars 对不存在的变量渲染成空，页面就是一片空白，没有报错。
  • partial 要手工注册。原书专门有一段讲怎么配 hbs-utils 来自动注册 partial 目录。JSX 里这个问题不存在：组件就是 import 进来的函数，忘了 import 就编译不过。

Q2hono/jsx 有 useState 之类的 hook，但在服务端渲染里它们没用。为什么？如果你确实需要交互（比如购物车数量增减），在这个技术栈里该怎么做？

思路提示

因为服务端渲染只发生一次：组件函数被调用、返回字符串、结束。没有"重新渲染"这回事，所以 setState 无处可去。hono/jsx 提供 hook 是为了它的客户端模式（可以在浏览器里当一个极小的 React 替代品用），服务端渲染时用不上。

做交互有三档，按复杂度递增：

  • 表单 + 整页刷新。数量增减就是一个 POST，改完重定向回来。慢一点，但零 JS、零状态同步问题、天然可用无障碍。原书和本教程主线都用这个。
  • 局部替换。用 htmx 之类的库让服务端返回一个 HTML 片段替换掉页面的一块。仍然是服务端渲染，仍然没有客户端状态，但没有整页闪烁。这是 Hono 项目里最顺手的一档——返回片段就是少套一层 Layout 而已。
  • 局部水合。真需要复杂交互（比如一个带筛选的商品筛选器）时，单独打包一小段客户端 JS 挂到某个容器上。代价是你现在有两套渲染逻辑了。

判断标准：这块交互的状态需要被服务端知道吗。购物车数量需要（要落库），所以走表单；一个纯展示的图片轮播不需要，那就是几行原生 JS 的事。

Q3模板语言（Thymeleaf、Handlebars）有一个 JSX 没有的优点：模板文件本身就是合法 HTML，设计师可以直接用浏览器打开看效果。放弃这个优点换来了什么？在什么样的团队里这笔交易是亏的？

思路提示

换来的是三样东西：类型检查（组件参数写错编译不过）、真正的复用（组件是函数，能接受函数、能组合、能有默认值，不像 partial 只能传一堆散装变量）、一个语言（不用在 TS 和模板 DSL 之间切换心智）。

亏的情况也很具体：

  • 团队里有专职前端/设计师，交付物是 HTML 静态页，然后由后端"套页面"。JSX 会让这个交接变成一次重写。
  • 页面主要由非程序员维护（营销落地页、内容页）。
  • 项目已经有一套成熟的模板体系和一大堆 partial，迁移成本大于收益。

反过来，如果写页面的和写接口的是同一批人（大多数小团队的现实），JSX 几乎全赢。值得注意的是这个判断和技术优劣关系不大，它取决于你的交付流程里有没有"HTML 交接"这一步。

04

路由组织与类型安全

Hono 的类型推断是它一半的价值。这一部分讲怎么把路由拆成子 app 而不丢类型，以及一个更根本的问题：TypeScript 的类型在运行时是不存在的——那么"类型安全"到底安全在哪一段？

先说结论：类型系统只在你的代码内部可信。任何从进程外面来的东西——HTTP 请求、环境变量、数据库返回、第三方响应——在运行时都只是字节，类型是你单方面的声明。安全的项目结构，是让这些声明只在一个地方发生，并且在那个地方做真校验。

把类型接到 Hono 上：Env

注意 user 的类型带 | null。这是刻意的：会话中间件对未登录用户也会执行，只是放进去 null。让类型如实反映这一点，编译器就会强迫每个用到 user 的地方处理未登录分支——而不是等到线上报 Cannot read properties of null。

深入 · 想要"这里一定有 user"怎么办

在管理后台里，每个 handler 都写一遍 if (!user) return … 很烦，而且那个分支永远不会执行——因为 requireAdmin 中间件已经挡住了。

解法是给那棵子树一个更窄的 Env：

type AdminEnv = Env & { Variables: { user: SessionUser } }，然后 new Hono<AdminEnv>()。子 app 里的 c.get("user") 类型就是 SessionUser，不带 null。

这个技巧的意义超出了省几行代码：它把"这条路径上一定登录过"这个不变量写进了类型。以后有人不小心把一个 admin 路由挂到别的树上，类型就对不上，编译期就发现了。用类型表达路由树的结构约束，是 Hono 项目里最值得学的一招。

子 app：路由怎么拆

写法什么时候用
app.route("/cart", sub)标准做法。子 app 独立可测，中间件作用域清晰。
app.basePath("/api/v1")给整个 app 加前缀，常用于 API 版本化。返回的是同一个 app，不是新的。
app.mount("/legacy", otherFetch)挂一个非 Hono 的 fetch handler 进来，比如逐步迁移时把老应用挂在一个前缀下。
链式 .get().post()推荐。链式调用会让类型逐步累积，typeof app 里就带着全部路由信息——这是 RPC 客户端的前提。分开写 app.get(…); app.post(…); 类型会丢。

Q2项目里 productId 和 userId 都是 number。getOrdersForUser(productId) 这种调错参数的 bug，类型系统抓得住吗？怎么让它抓得住？

思路提示

解法是标称类型（branded type），用一个不存在的属性给类型打标记：

  • type ProductId = number & { readonly __brand: "ProductId" }
  • 只能通过一个构造函数产生：const toProductId = (n: number) => n as ProductId
  • 之后 getOrdersForUser(pid) 就编译不过了

值得注意的是这里唯一合法的 as 就在那个构造函数里——这正是"断言应该集中在一处"的例子。Zod 也直接支持：z.number().int().brand<"ProductId">()，于是校验和打标记是同一步。

要不要用？我的判断是：ID 类型多于三种、或者代码里有大量"拿着 A 的 id 去查 B"的地方时值得。小项目里它带来的样板可能超过收益。但金额类型一定要 brand（第 6 部分），因为把"分"当成"元"传下去是会赔钱的。

代码规范与质量门禁

对应原书第 10 章（ESLint 与 Prettier）。原书装完插件、贴完配置文件就结束了，没有说过任何一条规则为什么存在，也没有把检查接进流程——于是它只是编辑器里的一片黄色波浪线。

"代码规范"这个说法容易让人以为它关乎风格。缩进和引号确实是风格，交给工具自动改掉就行，值得花心思的是另一半：那些能在提交之前挡住真 bug 的规则，以及它们在哪一道关卡生效。同一个错误，在编辑器里发现和在生产环境发现，成本差三个数量级。

Biome：一个工具，两件事

Biome 把 ESLint 和 Prettier 合成了一个 Rust 写的二进制。在这个项目规模下，全量检查大约 100 毫秒——快到可以挂在保存时，而这个速度差异会直接改变你的工作方式：慢的工具你会关掉，快的工具你会依赖。

规则为什么值得开成 error
noExplicitAnyany 不是"未知类型"，是"关掉这一段的类型检查"。它会顺着数据流往下传染——一个 any 参数会让整条调用链失去检查。想表达未知就用 unknown，它逼你在使用前窄化。
noDoubleEquals== 的强制转换规则是 JS 里最容易记错的部分之一。"0" == false 是 true，null == undefined 是 true 但 null == 0 是 false。
useImportType配合 verbatimModuleSyntax，让"这个 import 只用于类型"变成显式的。好处在第 7 部分：模块边界检查工具能据此区分"真依赖"和"只依赖类型"。
noNonNullAssertion开成 warn 而非 error：x! 偶尔确实是对的，但它应该刺眼。每一个 ! 都是一句"相信我"。
陷阱 · Biome 看不见类型

这是选型时必须知道的一件事：Biome 的检查主要基于语法树，而不是类型信息。这换来了它的速度，但也意味着某些最有价值的规则它做不到或做得不完整——最典型的是"浮动的 Promise"（忘了 await，第 2 部分那个 bug）：要可靠地判断一个表达式是不是 Promise，必须有完整的类型信息。

三种应对：（1）接受这个缺口，靠 code review 和测试补；（2）在 CI 里额外跑一遍 typescript-eslint 的类型感知规则，慢但只在 CI 跑；（3）关注 Biome 的类型感知能力进展，它在逐步补齐。

本项目选（1）+（2）：日常开发用 Biome 保持快，CI 里加一道 typescript-eslint 只开三条类型感知规则（no-floating-promises、no-misused-promises、await-thenable）。这三条在一个到处是 async 的 Web 项目里的价值，值得多花那两分钟 CI 时间。

接进流程

最后那一步是第 4 部分 Q1 的答案落地。它便宜、可靠，而且能防住一类会静默烂掉数据的错误。

对照 · Java 那边的同一套东西

Spring 项目里对应的是 Spotless（格式）+ Checkstyle（风格）+ Error Prone（bug 模式）+ NullAway（空安全）。四个工具、四份配置、加起来的构建时间以分钟计。

Biome 用一个工具、一份配置、100 毫秒覆盖了前两个和一部分第三个。但第四个——空安全——在 TypeScript 里是语言自带的（strictNullChecks），根本不需要工具。这是 TS 相对 Java 的一个实打实的优势：可空性在类型系统里，不在注解里。

在类型安全性上，一样坏——as unknown as T 是绕过类型系统的标准手法，效果和 as any 完全等同。

06

数据层：Drizzle 与迁移

对应原书第 11–14 章。原书用 TypeORM 并开着 synchronize: true——启动时让 ORM 按实体定义自动改表结构。Drizzle 有一个一模一样的功能，而这一部分有一半篇幅在讲为什么不用它。

Drizzle 的定位和 TypeORM、JPA 都不同：它不是"把对象映射成表"，而是"给 SQL 加上类型"。没有实体管理、没有一级缓存、没有懒加载代理、没有脏检查。你写的查询长什么样，发出去的 SQL 就长什么样。这让它比 JPA 好预测得多，代价是很多 JPA 帮你做的事得自己做。

schema.ts：唯一的事实来源

$inferSelect 和 $inferInsert 的区别值得注意：前者是"从库里读出来的样子"（所有列都在，有默认值的列也已经有值），后者是"插入时要提供的样子"（有默认值和自增的列变成可选）。手写一份 interface Product 会同时丢掉这个区分和自动同步。

迁移：这一部分的核心

陷阱 · 别在应用启动时跑迁移

把 migrate() 写进 src/index.ts 看起来很方便，但一旦你跑多个副本，N 个实例会同时执行同一批 DDL。Drizzle 的迁移器会取一个 Postgres 咨询锁，所以通常不会互相破坏，但你会得到：启动时间不可预测、一个实例在跑长 DDL 时其它实例干等、以及最糟的——滚动发布期间新旧版本代码同时面对一个改到一半的表结构。

正确做法是把迁移当成部署流水线里独立的一步：先跑迁移（一个一次性任务），成功后再滚动更新应用。第 13 部分会给出完整的顺序，包括"迁移必须向后兼容旧版本代码"这条约束为什么是滚动发布的前提。

钱：JavaScript 最危险的一处

原书的商品价格是 @Column('decimal') price: number——TypeORM 读出来给你一个 JS number，也就是 IEEE 754 双精度浮点。这个选择会一路错到对账。

三十行代码，换来的是"金额只能通过这几个函数运算"这条可以被编译器执行的纪律。times 和 scale 分开是刻意的：乘数量是精确的，乘比例是要舍入的，把它们混成一个函数就会让舍入变得随机。

查询：两套 API

两点值得注意。第一，and() 会自动忽略 undefined 参数——这让"可选筛选条件"不需要拼字符串。第二，select({...}) 里显式列出要的列：返回类型会精确到只有这四个字段，页面上不小心用到 description 就是编译错误。这是"投影"，比 select * 再挑字段既省带宽又更安全。

深入 · 参数化与 SQL 注入

上面 ilike(products.name, `%${keyword}%`) 里有模板字符串，看起来像在拼 SQL。它不是——整个 %${keyword}% 作为一个值被当成参数传给驱动，生成的 SQL 是 … ilike $1。用户输入 ' OR 1=1 -- 只会被当成一个搜索关键词。

Drizzle 里唯一能拼出注入的是 sql.raw()：它接受一段字符串原样拼进去。与之相对，sql 标签模板（sql`select * from t where id = ${id}`）是安全的，插值会变成参数。

所以规矩很简单：sql 模板随便用，sql.raw 的参数必须来自你自己的代码，永远不能来自请求。典型的合法用法是动态排序列名——而那种情况正确做法是白名单映射，不是把用户传的列名塞进 raw。

预编译语句

省掉的是每次请求时 Drizzle 在 JS 侧构造 SQL 字符串的开销。收益通常很小——除非这个查询每秒跑几千次。放在这里是因为它经常被误解成"性能银弹"：真正的瓶颈几乎总是缺索引或多跑了一次往返，不是构造 SQL 字符串。先测量，再优化。

Q1你要给 products 加一列 sku text not null，表里已经有 5 万行数据。直接写这条 DDL 会发生什么？正确的做法要分几步？

思路提示

直接执行会失败：已有的 5 万行没有 sku 值，违反 not null。Postgres 会拒绝整条语句。

正确的做法是三步，而且要分三次部署：

  1. 加可空列：alter table products add column sku text。这一步在 Postgres 里是瞬时的（不重写表）。此时新旧版本代码都能跑。
  2. 回填 + 双写：新版本代码开始写入 sku，同时用一个后台任务分批回填历史行（update … where sku is null limit 1000，循环）。一次性 update 全表会长时间持锁。
  3. 加约束：确认没有 null 之后再 alter column sku set not null。Postgres 12+ 可以先加一个 not valid 的 check 约束再 validate，避免全表锁。

这就是图 6 想说的核心："schema 变更"在有数据、有流量的系统里不是一个原子操作，而是一个需要设计的过程。而 push 这类工具的整个心智模型是"让库变成 schema 描述的样子"，它根本没有表达这个过程的能力。

顺带一个约束：滚动发布期间新旧代码同时在跑，所以每一次迁移都必须对上一个版本的代码向后兼容。这条约束比"不用 push"更根本。

Q2购物车小计的计算：单价 1999 分、数量 3、会员折扣 0.85。用 scale(times(price, 3), 0.85) 和 times(scale(price, 0.85), 3) 分别得到多少？哪个对？

思路提示

第一种：1999 × 3 = 5997，5997 × 0.85 = 5097.45，四舍五入 5097 分。

第二种：1999 × 0.85 = 1699.15，四舍五入 1699，再乘 3 得 5097 分。这次碰巧一样。

换成数量 7 就不一样了：第一种 1999×7=13993，×0.85=11894.05 → 11894；第二种 1699×7 = 11893。差一分。

哪个"对"没有数学答案，只有约定答案。要点是：

  • 选一个，写进代码注释和测试，别让它随实现漂移。
  • 倾向于尽量晚舍入（第一种），因为中间步骤的舍入误差会在数量上被放大。
  • 更重要的是：展示给用户的分项加起来必须等于总计。如果页面上按行显示"折后单价 ¥16.99 × 7"，用户会自己算出 ¥118.93，而你收 ¥118.94——这是客服工单。要么按行舍入并让总计等于分项之和，要么不展示折后单价。

这类问题在原书里完全不存在，因为它连折扣功能都没有。但凡真做一个商店，它是第一周就会撞上的。

Q3JPA 有一级缓存：同一个事务里查两次同一个实体，只发一次 SQL。Drizzle 没有。这是缺陷还是取舍？在什么情况下你会怀念它？

思路提示

是取舍，而且我认为方向是对的。一级缓存解决的问题是"代码分散在各层，谁也不知道别人查没查过"，它用一个隐式的缓存把重复查询吃掉。代价是：你无法通过读代码知道会发出几条 SQL，以及一整套"实体是托管态还是游离态"的心智负担。

Drizzle 的立场是"查询是显式的"：写两次就查两次。想去重就自己在函数入口查一次、把结果传下去——这恰好也让数据流更清楚。

会怀念它的场景：一个请求里要渲染的页面结构很深，比如订单详情要展示每一行商品的分类，而分类只有几个、被反复引用。JPA 会自动缓存，Drizzle 会老实地查 N 次。

解法不是把缓存加回来，而是换查询形状：一次性把用到的分类全查出来（where id in (...)），在内存里做成 Map。这在 Drizzle 里是几行代码，而且它是显式的——读代码的人能看见"这里查了一次分类"。第 10 部分会把这个模式完整写一遍，它同时也是 N+1 的通用解法。

组装与模块边界

对应原书第 15–17 章（Nest 的模块与依赖注入）。Hono 没有 DI 容器，也没有模块概念。这一部分回答两个问题：对象之间怎么连起来，以及没有模块系统时，边界靠什么守住。

先说一句可能有点扫兴的话：在 Hono 项目里，"依赖注入"这个问题大部分时候不存在。数据库连接是一个模块级单例，直接 import { db } 就能用；服务是纯函数，参数就是它的依赖。真正需要注入的只有极少数东西，而识别出那几个才是这一部分的重点。

组装：三种写法，用哪一种

ESM 模块只会被求值一次，所以这就是一个单例，不需要任何容器。用起来是 import { db }。

陷阱 · 单例的求值时机

这个模块在第一次被 import 时就会建立连接池，而 import 发生在整个模块图加载期间——也就是说，src/index.ts 里任何一行代码执行之前，连接池已经建好了。

后果之一：如果 config 的解析失败（少了环境变量），错误会发生在模块加载阶段，堆栈可能不太好看。后果之二：测试文件只要间接 import 到任何用了 db 的模块，就会试图连数据库——哪怕这个测试根本不碰库。

解法是把连接建立包在一个惰性函数里，或者接受它并让测试环境总有一个可用的库（第 12 部分用 Testcontainers 就是这个思路）。本项目选后者：与其为了测试把生产代码复杂化，不如让测试环境更真实。

把 now 作为参数传进来，而不是在函数里调 new Date()。这一个小改动让"订单在跨月零点的行为"变成可测试的，而不需要任何 mock 库。凡是不确定的东西——时间、随机数、外部请求——都该从参数进来；确定的东西（比如 db）直接 import 就好。

依赖的种类用哪种写法理由
数据库连接直接 import 单例测试里用真数据库，没有替换需求
配置直接 import 单例启动时解析一次，全程不变
时间、随机数、UUID函数参数要在测试里控制它们，而 mock 全局对象是最脏的做法

对照 · 少掉 DI 容器丢了什么

丢了三样：作用域管理（singleton / request / prototype 由容器负责）、生命周期回调（@PreDestroy 之类）、启动期的连线校验（Spring 在启动时就能发现"这个 Bean 找不到依赖"）。

前两样在 Hono 里的替代很直接：请求作用域就是 c，生命周期就是在信号处理里手写关闭逻辑（第 13 部分）。第三样是真的丢了——但也真的还回来了一部分：因为依赖是 import，缺失的依赖在编译期就是错误，而不是启动期。Spring 的启动期校验之所以是个卖点，恰恰因为 Java 那边没法在编译期知道容器里有什么。

边界：没有模块系统，就用工具画线

深入 · ESM 的循环依赖为什么特别阴险

CommonJS 的循环会给你一个不完整的 exports 对象；ESM 的循环则依赖提升和暂时性死区，表现更微妙：

  • function 声明会被提升，所以 A 和 B 互相 import 函数通常能跑——这是最危险的情况，因为它掩盖了问题。
  • const / class 不会。如果 A 在模块顶层就使用了 B 的 const，而 B 还没求值完，你会得到 ReferenceError: Cannot access 'x' before initialization。
  • 最坏的一种：const 在函数体里用（不是顶层），于是模块加载时不报错，直到运行时某条路径第一次走到才炸。而这条路径可能是"用户第一次下单"。

所以 no-circular 这条规则不是洁癖。它拦的是一类会延迟到线上才暴露、且堆栈毫无提示的故障。

门面文件长什么样

关键不在于"导出了什么"，而在于没导出什么。order 模块下单时需要商品的名字和价格，那就通过 getProductsByIds 拿；它不需要知道 catalog 内部是怎么查的、有没有缓存、表叫什么。这样 catalog 改内部实现时，只要门面签名不变，就不必担心弄坏别人。

Q3有人主张"既然没有容器，就把所有依赖都用工厂函数注入进来，这样最灵活"。于是 createCatalogService({ db, clock, logger })、createOrderService({ db, clock, catalog, payment })……组装代码越写越长。这样做错了吗？

  • db：不会。测试里用真数据库（Testcontainers）比用假的更能发现问题。注入它只换来了组装样板。
  • logger：几乎不会。真要在测试里静音，改配置比注入简单。

一个可以直接用的经验法则：先直接 import，等到第二次真的需要替换实现时再抽接口。这个顺序几乎不会让你付返工的代价，因为把 import 改成参数是一次机械重构。

深入 · 为什么必须是 303 而不是 302

这是 POST-Redirect-GET 模式：写操作成功后不要直接渲染页面，而是重定向到一个 GET 页面。否则用户按 F5 会重新提交表单，创建出第二件商品；浏览器的"确认重新提交"弹窗就是在为这个设计缺陷擦屁股。

状态码的差别很实在：302 的规范语义没有规定方法是否改变，历史上浏览器把它当成 303 处理，但某些客户端（尤其是自己写的 HTTP 客户端、爬虫、旧版代理）会保持 POST 方法跟随重定向——于是你的重定向目标收到了一个 POST。303 See Other 明确要求"用 GET 请求新地址"，没有歧义。

顺带：如果是 API 而不是页面，创建成功该返回 201 Created + Location 头，不重定向。

Q1表单里 published 是一个 checkbox。不勾选时浏览器根本不发这个字段；勾选时发的是 published=on。z.coerce.boolean() 能正确处理这两种情况吗？

思路提示

不能，而且失败方式很隐蔽。z.coerce.boolean() 做的是 JS 的 Boolean(v)："on" → true（对了），undefined → false（碰巧也对）。看起来能用。

但换个场景就错了：如果表单用隐藏字段配合 checkbox（常见做法，为了在取消勾选时也发一个值），未勾选时会发 published="" 或 published="false"。Boolean("false") 是 true——因为非空字符串都是真值。用户取消勾选，商品反而上架了。

可靠写法是显式枚举而不是靠 coerce：

published: z.enum(["on", "true", "1"]).optional().transform((v) => v !== undefined)

更一般的教训：z.coerce 借用的是 JavaScript 的转换规则，而 JavaScript 的转换规则是出了名的反直觉。z.coerce.number() 也有类似问题：Number("") 是 0 而不是 NaN，所以空的数字输入框会被当成 0 通过校验。要挡住它得先 z.string().min(1) 再 transform。

值得为此写测试——表单校验是少数几个"写测试比写代码快"的地方。

思路提示

因为中间件读走了流。图 9 上半部分就是这件事：await c.req.raw.text() 消费了 body，后面的 parseBody() 拿到的是一个已经用完的流。

三种改法，各有取舍：

  • 只记元数据：路径、方法、Content-Length、字段名列表，不记内容。审计需求通常这样就够了，而且顺带避免把密码、信用卡号写进日志——这本身就是个好理由。

Q3Zod 的校验是在服务端做的，用户绕过前端 JS 直接发请求照样被拦。那前端还要不要写一遍校验？如果要，两份规则怎么保持一致？

思路提示

要写，但目的完全不同：前端校验是为了体验，服务端校验是为了安全和数据完整。前者可以有漏洞，后者不能有。搞混这一点会导致两种错误：以为有了前端校验就能省掉服务端（灾难），或者以为有了服务端就不需要前端（用户要等一个往返才知道邮箱格式写错了）。

保持一致的手段，从便宜到贵：

  • HTML 原生属性：required、maxlength、pattern、type="email"。零 JS，浏览器原生提示，无障碍也免费。本项目主要用这个——它覆盖了 80% 的场景。
  • 把 Zod schema 也发到浏览器：同一份 schema 编译进客户端包，用它做实时校验。真正的单一事实来源，代价是引入了客户端构建。
  • 从 schema 生成 HTML 属性：写一个小函数，把 z.string().max(120) 变成 maxlength="120"。折中方案，无需客户端 JS 又能同步。

值得强调的一点：不一致本身并不危险，只要不一致的方向是"前端更宽松"。前端漏了一条规则，用户会看到服务端返回的错误，体验差一点；前端比服务端更严格才是真问题——用户被前端拦住却不知道为什么，而这条规则服务端根本不认。

深入 · 为什么会话 id 不需要签名

Hono 提供了 setSignedCookie，很多教程会用它。但如果会话 id 是 32 字节的密码学随机数，签名没有增加任何安全性——攻击者猜中一个有效 id 的概率是 2⁻²⁵⁶，而签名要防的正是"伪造一个有效值"。

签名真正有用的场景是 cookie 里存了有意义的数据：role=admin、cart=[…]、flash=…。这些值攻击者能猜出格式，所以需要签名证明"这是服务端发的"。第 10 部分的匿名购物车 cookie 就是这种情况。

判据：cookie 的值是"随机不可猜的凭证"就不用签，是"服务端声明的事实"就必须签。

密码：argon2id 的参数

bcrypt（原书）argon2id（本项目）
抗 GPU / ASIC较弱：内存占用固定且很小（4 KB），显卡能并行跑几万路强：内存代价可调，19 MiB × 几万路就需要几百 GB 显存

那个 72 字节的限制值得单独说：如果用户用了一个很长的口令短语，bcrypt 会静默截断。更糟的组合是"先 SHA-256 再 bcrypt"这种民间做法——如果中间那一步产出的是 base64，有效熵可能进一步下降。argon2 没有这个坑。

安全 · 登录接口的三个细节
  • 用户不存在时也要跑一次哈希校验。否则"邮箱不存在"响应得飞快、"密码错误"要等 50 毫秒——攻击者据此就能枚举出哪些邮箱注册过。做法是准备一个固定的假 hash，用户不存在时对它做一次 verify。
  • 错误消息只能有一条："邮箱或密码不正确"。分开提示对用户帮助有限，对攻击者帮助极大。
  • 限流按"邮箱 + IP"两个维度都要有。只按 IP 挡不住撞库（攻击者用代理池），只按邮箱挡不住喷洒攻击（一个密码试一万个邮箱）。

授权：让"忘记加权限"变成不可能

这就是第 01 部分 Q2 说的"把默认值反过来"。权限不是每个 handler 各自记得加的一件事，而是它所在位置的属性。

陷阱 · 角色不等于权限

user.role !== "admin" 这种检查只能表达"是不是管理员"，表达不了"这是不是你的订单"。后者叫对象级授权，是 Web 应用里最常见的漏洞类别（OWASP 排第一）。

典型形态：GET /orders/1042 只检查了登录，没检查这个订单属不属于当前用户。改一下 URL 里的数字就能看别人的订单。

正确做法不是"查出来再判断"，而是把归属条件写进查询本身：where orders.id = $1 and orders.user_id = $2。查不到就是 404。这样即使有人忘了写判断，也写不出漏洞——因为那个 and 是查询的一部分，不是可选的一步。第 11 部分的订单查询全部这样写。

Q1SameSite=Lax 已经能挡住绝大多数跨站请求，为什么还要 csrf() 中间件？反过来，有了 csrf() 还需要 SameSite 吗？

思路提示

SameSite=Lax 的规则是：跨站请求不带 cookie，除非是顶层导航的 GET。所以它挡住了跨站 POST，但留了两个口子：

  • 状态变更的 GET。如果你有 GET /cart/clear 这种路由，攻击者放一个 <img src="…/cart/clear">……嗯，img 不是顶层导航所以不带 cookie；但一个诱导点击的链接是顶层导航，会带。所以真正的第一道防线是：GET 永不改变状态。
  • 浏览器差异和历史行为。部分浏览器对新建的 cookie 有 "Lax + 2 分钟宽限" 之类的兼容策略；老版本浏览器可能完全不认 SameSite。

反过来，有了 csrf()（校验 Origin/Referer 是否在白名单里）也仍然要 SameSite：Origin 头在极少数情况下会缺失，而缺失时你得决定放行还是拒绝——放行就有洞，拒绝就可能误伤。两者是纵深防御，不是二选一。

本项目用 hono/csrf 的 Origin 校验而不是 token 方案，因为在服务端渲染 + 同源部署的场景下它零成本且够用。如果将来要支持跨域的前端，就得换成 double-submit token。

  • 把真正公开的路由（首页、商品列表、登录注册、健康检查、静态资源）收进一个单独的子 app，挂载在 requireUser 之前。

Q1商品详情页要展示商品 + 它的多张图片 + 最近 5 条评价。用一条带两个 join 的查询会返回多少行？为什么这是一个必须拆开的场景？

思路提示

行数是图片数 × 评价数。3 张图 × 5 条评价 = 15 行，每一行都重复携带完整的商品字段和一份图片、一份评价。这是两个一对多集合的笛卡尔积。

更糟的是它不正确：如果这个商品有 3 张图但只有 2 条评价，join 出来是 6 行；你在 JS 里去重能拼回正确结果，但如果有一侧为空，用 inner join 会让整个商品消失，用 left join 又会引入 null 行要处理。

正确做法是三次查询：商品一次、图片一次、评价一次（评价那次带 order by created_at desc limit 5）。三次往返换来的是每条查询都能独立分页、独立加索引、独立缓存。

一条通用规则：一条 SQL 里最多抓取一个一对多集合。Hibernate 会直接抛 MultipleBagFetchException 来阻止你抓两个，Drizzle 不管——所以这条规则得记在脑子里。

Drizzle 的 db.query.…findMany({ with: { images: true, reviews: true } }) 在这一点上比手写 join 好：它会发多条查询而不是一条大 join，正好避开这个问题。代价是你不容易看出它到底发了几条——所以开发环境一定要开 SQL 日志。

Q2商品列表页用 limit 20 offset 4000 翻到第 200 页，很慢。为什么 offset 会慢？keyset 分页怎么写？它有什么代价？

思路提示

offset 4000 并不是"跳过"——数据库仍然要找出并排序前 4020 行，再丢掉前 4000 行。代价随页码线性增长，翻到第 1000 页就是扫 20020 行。

keyset（游标）分页改成"从上一页最后一条之后继续"：

where (created_at, id) < ($1, $2) order by created_at desc, id desc limit 20

配上 (created_at desc, id desc) 的索引，任意一页都是同样的代价——数据库直接定位到索引里那个位置往后读 20 行。

三个代价：

  • 不能跳页。只有"下一页"，没有"第 200 页"。对无限滚动是天然契合，对传统页码列表就不行。
  • 排序键必须唯一。只按 created_at 排，同一毫秒的两条记录会在翻页时重复或遗漏——所以要带上 id 组成复合键。
  • 游标要编码。别把 created_at 和 id 裸露在 URL 里，用 base64 包一层，将来换排序方式时不会破坏已有链接。

实践建议：面向用户的列表用 keyset，管理后台的表格用 offset。后台数据量小、需要跳页，offset 的缺点不成立；前台随时可能被爬虫翻到第一万页，keyset 是唯一扛得住的。

Q3JPA 有懒加载：order.getItems() 第一次访问时才发 SQL。这带来了 N+1，但也带来了便利。Drizzle 没有懒加载——这让写代码变麻烦了，换来了什么？

思路提示

换来的是"这段代码会发几条 SQL" 变成可以靠读代码回答的问题。

JPA 的懒加载让 N+1 极其容易发生且难以发现：一个模板里的 ${order.items}、一个日志里的 order.toString()、一个不小心访问了关联属性的 equals——都可能在你完全没意识到的地方触发几百条查询。而且它还带来了一整套额外概念：持久化上下文的边界、LazyInitializationException、open-in-view 该不该开。

Drizzle 的立场是：数据要么你查了，要么它就不在。items 字段的类型里就写着它有没有被查出来——你没在 with 里要，它压根不在返回类型上，用了就是编译错误。

代价确实存在：领域对象不再是"活的"，跨层传递时要想清楚"这一层需要哪些字段"。但这个思考本身是有价值的——它逼你在写查询的时候就回答"这个页面需要什么数据"，而不是让模板去决定发什么 SQL。

值得注意的是 Java 生态也在往这个方向走：Spring Data JDBC、jOOQ、以及 JPA 里越来越推荐的 DTO 投影，本质上都是在放弃懒加载换取可预测性。这不是"脚本语言不如 Java 严谨"，恰恰相反，是同一个教训的两次学习。

下单：事务与并发

原书全书没有出现过一次事务。它的下单流程是三条独立的写操作：扣库存、建订单、清购物车。任何一步失败，数据就此不一致，而且没有任何补救机制。这是原书和"能上线的系统"之间最大的一道鸿沟。

这一部分是整份教程里最难的一段，也是收益最大的一段。Hono / Drizzle 在这里比 Spring 更"裸"——没有 @Transactional、没有环境事务、没有代理，事务边界完全由你用一个回调函数画出来。好消息是它因此毫无歧义：回调里的就在事务里，回调外的就不在。

最小可用：一个正确的下单

深入 · 为什么订单行要存价格快照

原书的 order_items 只有 product_id 和 quantity，价格靠 join products 表实时取。这意味着管理员改一次商品价格，所有历史订单的金额都跟着变了——已经付过款的订单，详情页上显示的总额和用户实际支付的对不上。

更麻烦的是商品下架或删除后，历史订单直接查不出商品名。所以 order_items 要存三样快照：单价、商品名、以及必要的规格描述。它们在下单那一刻被复制一份，此后与商品表脱钩。

这不是冗余，是不同的语义：products.price 是"现在卖多少钱"，order_items.unit_price_cents 是"当时成交价"。它们碰巧在下单那一刻相等，但它们是两个不同的事实。

把 tx 传下去：一个绕不开的麻烦

注意上面每个辅助函数的第一个参数都是 tx。这就是没有环境事务的代价：凡是要参与这个事务的数据库操作，都必须拿到同一个 tx 对象。用 db 而不是 tx，那条语句会走另一个连接、开另一个事务，回滚时它不会被撤销。

怎么防做法评价
类型约束所有数据访问函数第一个参数强制为 Tx，模块内不导出直接用 db 的版本推荐。把"必须在事务里"变成签名的一部分
lint 规则禁止在 transaction 回调体内出现标识符 db能抓住直接调用，抓不住间接调用
AsyncLocalStorage把 tx 放进异步上下文，数据访问层自动取当前事务见下方，慎用
陷阱 · AsyncLocalStorage 是把 @Transactional 搬过来，连同它的坑

Node 的 AsyncLocalStorage 能做到"隐式当前事务"，写起来确实清爽。但它会带回 Spring 里那套熟悉的困惑：

  • 看代码看不出事务边界。一个函数到底在不在事务里，取决于谁调用了它。
  • 嵌套语义要自己定。里层又开一个事务，是复用外层、还是开保存点、还是新连接？这就是 Spring 的 Propagation 那七个选项，你得自己实现一遍。
  • 上下文会在某些边界丢失。用了非标准的调度、某些第三方库的回调、或者 setTimeout 之外的原生异步原语时，上下文可能传不过去。丢了之后不报错——只是悄悄用回了池里的另一个连接。

我的判断：在一个只有五六处事务的项目里，显式传 tx 的成本远低于引入隐式上下文的认知成本。它丑，但它诚实——而事务恰恰是最不该有惊喜的地方。等到项目里有五十处事务、传参变成真正的负担时再考虑，那时你也更清楚自己需要哪种嵌套语义。

深入 · 隔离级别不会替你解决这个问题

常见的误解是"开个更高的隔离级别就好了"。事实是：

  • Read Committed（Postgres 默认）：图 13 那个场景会原样发生。
  • Repeatable Read：Postgres 下第二个 UPDATE 会因为检测到并发修改而报 could not serialize access，事务失败。这确实防住了超卖——但代价是你必须自己写重试逻辑，否则用户看到的是 500。
  • Serializable：能防住，且能防住更复杂的模式（比如"读 A 写 B、读 B 写 A"这种交叉）。代价是更高的冲突率和同样必需的重试。

换句话说，高隔离级别把"数据错了"变成"事务失败了"，这是巨大的进步，但它没有免除你处理失败的责任。而图 13 的方案 ① 连失败都不会有——它把冲突消解在了一条语句内部。

Q1购物车里有三件商品，扣第三件时库存不足抛了异常。前两件的库存被扣掉了吗？如果 reserveStock 里不小心用了 db 而不是 tx，答案有变化吗？

思路提示

正确实现下：没有。异常从 transaction 的回调里抛出，Drizzle 发 ROLLBACK，前两条 UPDATE 一起撤销。这正是事务的意义。

如果用了 db：前两件的库存永久少了两件，而订单没有创建。而且不会有任何报错——那两条 UPDATE 各自在自己的自动提交事务里成功了。

思路提示

处理方式是一个定时任务：找出 status = 'pending_payment' and created_at < now() - interval '30 minutes' 的订单，关掉并把库存加回去。

会撞车，而且这是必须正面处理的：定时任务读到订单准备关闭的同时，支付回调到达并把它标成 paid。如果不管，可能出现"订单已支付但库存被退回了"。

解法是把状态转移本身做成原子的条件更新，和图 13 是同一个道理：

update orders set status = 'cancelled' where id = $1 and status = 'pending_payment'

如果支付回调先到，status 已经是 paid，这条 UPDATE 影响 0 行，定时任务就知道"这单已经不归我管了"，跳过退库存。反之亦然：支付回调也写成 where status = 'pending_payment'，如果已被取消就影响 0 行，此时应该走退款流程而不是把订单标成已支付。

更一般的表述：把订单状态建模成一个显式的状态机，所有转移都写成"从哪个状态到哪个状态"的条件更新。这样并发的两个转移里必然只有一个成功，另一个能明确知道自己失败了并做出正确反应。这是订单系统里最重要的一个模式。

还有一层要考虑：多个应用实例会同时跑这个定时任务。要么用 select … for update skip locked 让它们各取各的，要么用一个分布式锁保证只有一个实例在跑。前者更好——它天然支持并行处理。

Q3Spring 的 @Transactional 有一个著名的坑：同类方法内部调用不走代理，事务不生效。Hono / Drizzle 没有代理，所以没有这个坑。但它有没有别的、同样"看起来在事务里其实不在"的情况？

思路提示

有，而且不止一种：

  • 用了 db 而不是 tx。Q1 说过，这是最常见的一种，也是最直接对应 Spring 那个坑的一种——只不过在 Spring 里你看不出来，在这里它至少是字面上可见的。
  • 没有 await。tx.insert(…) 忘了 await，回调函数就提前返回了，Drizzle 发出 COMMIT，而那条 insert 可能还在路上。结果是不确定的——可能报"事务已结束"，可能莫名其妙地成功了。
  • 在回调里 Promise.all 并发跑多条语句。一个事务绑定在一个连接上，而连接是串行的。多数驱动会排队执行，但语义上你失去了顺序保证；某些驱动会直接报错。事务里的语句应该老老实实一条条 await。
  • 回调里捕获了异常但没有重新抛出。try { … } catch (e) { logger.error(e) }——回调正常返回了，于是 COMMIT，把一个失败到一半的状态提交了。这一条最隐蔽，因为写这段代码的人的本意是"让错误不要中断流程"。

值得注意的是这四条都有一个共同特征：它们都是"异步 + 显式边界"这个模型的固有风险，而不是某个框架的设计缺陷。Spring 的坑源于隐式代理，Hono 的坑源于显式 await——两者都需要知道机制才能避开，只是要知道的东西不同。

这个测试有一点要注意：它不能保证每次都真的并发——两个 Promise 可能碰巧串行执行完。要提高触发概率，可以把并发数提到 10、跑几轮，或者在扣库存前后插入可控的延迟点。即便如此，它仍然有价值：它至少在真并发发生时会失败，而没有它则永远不会失败。

对照 · 该 mock 什么

Java 那边的习惯是 @MockitoBean 把仓库层替换掉，理由是"单元测试不该碰数据库"。这个理由在 2010 年成立（起一个数据库要几分钟），今天不成立（Testcontainers 起一个 Postgres 要 2 秒，而且可以整个测试会话复用）。

本项目的立场：只 mock 你不拥有、且调用有代价或副作用的东西——支付网关、邮件服务、短信。它们用手写的假实现（一个实现了 PaymentGateway 接口的对象），而不是 mock 库。手写假实现能表达"第三次调用失败"这类场景，而且它是类型安全的：接口变了，假实现编译不过。

数据库不 mock。mock 掉数据库的测试能通过而真实代码出错，是所有测试策略里最糟的一种失败模式——它给你信心，但那个信心是假的。

Q1路由测试里怎么伪造一个"已登录"的请求？直接 c.set("user", …) 行不行？

思路提示

不行——app.request() 只给你 Request 和 Response，拿不到中间的 c。这其实是好事：它逼你走真实路径。

三种做法，推荐程度递减：

  • 真的建一个会话：在测试库里插一行 sessions，然后请求时带上对应的 cookie。这条路径和生产完全一致，连"会话过期了会怎样"都能顺便测到。需要第 3 层的数据库，但这正是你已经有的。
  • 走登录接口：先 POST /login，从响应的 Set-Cookie 里取出 cookie 再用。最真实，但每个测试多一次往返，而且登录接口一旦改了所有测试都受影响。
  • 注入一个测试专用中间件：构造一个 new Hono().use(fakeAuth(user)).route("/", cartRoutes)。快，但测的不是真正跑在生产的那棵路由树——如果真实的 app.ts 忘了挂鉴权，这个测试照样通过。

我选第一种，并把它封装成一个 sessionCookieFor(user) 辅助函数。判据是：这个测试要防的 bug，会不会被这种伪造方式绕过？鉴权类的测试尤其不能用第三种，因为它伪造掉的正是被测对象。

Q2渲染类的断言写成 expect(html).toContain("羊毛围巾") 很脆——改一下文案测试就红。有更好的做法吗？还是说这类测试根本不该写？

Q3团队想定一个"覆盖率不低于 80%"的门禁。你支持吗？如果支持，怎么定才不会变成刷数字？

思路提示

我对全局百分比门禁持保留态度，理由是它奖励错误的行为：最容易涨覆盖率的是给 getter、DTO、视图组件补测试，而这些地方几乎不出 bug；最难覆盖的是错误分支和并发路径，而那才是 bug 藏身之处。于是团队会本能地去刷容易的那部分。

更有用的几种替代：

  • 按目录设不同的线：src/order、src/catalog/stock.ts 这些放着不变量的地方要求 90%，视图目录不设线。
  • 只看增量覆盖率：这个 PR 新增的代码有没有被测到。存量欠债慢慢还，新债不许欠。
  • 盯未覆盖的分支而不是行：catch 块、if (!ok) 分支、rowCount === 0 的处理——这些是覆盖率报告里最该看的地方。
  • 变异测试（Stryker）：把 >= 改成 >，看有没有测试因此失败。它直接回答"这些测试真的在验证行为吗"，比覆盖率诚实得多。代价是跑得慢，适合每周跑一次而不是每次提交。

一个具体建议：与其定 80%，不如列一张"必须有测试的清单"——每一条状态转移、每一处金额计算、每一个权限判断、每一条数据库唯一约束。这张清单是可以被 review 的，而百分比不是。

停机与可移植性

深入 · liveness 和 readiness 是两个不同的问题

liveness（/healthz）回答"这个进程还活着吗"。失败的后果是重启。所以它必须极其简单——不查数据库、不调外部服务。一旦你在 liveness 里查了数据库，数据库抖动就会让编排系统把所有健康的应用实例全部重启，把一次短暂故障放大成一次全站宕机。

readiness（/readyz）回答"现在能不能给我发流量"。失败的后果是摘除，但不重启。这里可以（也应该）检查数据库连通性——数据库连不上时这个实例确实没法干活，摘掉它是对的。

把两者写成同一个端点是很常见的错误，而且它的危害只在故障时显现——正是你最不希望雪上加霜的时候。

日志：一条链路要能拼起来

两条纪律：输出 JSON 而不是拼接的字符串（日志系统才能按字段筛选和聚合）；永远不要把请求体整个记下来（第 8 部分 Q2 说过，那里面有密码和地址）。第 01 部分的 requestId 中间件在这里回本。

Q1部署流程是"跑迁移 → 滚动更新应用"。滚动更新期间新旧两版代码同时在跑。这对迁移提出了什么约束？"把 user_name 列改名成 full_name"这个需求要怎么做？

思路提示

约束是：每一次迁移都必须同时兼容上一个版本的代码。因为迁移跑完之后、新代码全部上线之前，旧代码还在访问这个已经变了的库。

改列名不能一步到位（旧代码会立刻报"column user_name does not exist"），要拆成四次部署：

  1. 迁移：add column full_name（可空）。旧代码不受影响。
  2. 部署代码 A：同时写 user_name 和 full_name，读仍然读 user_name。再回填历史数据。
  3. 部署代码 B：改成读 full_name。此时两列都是对的，随时可以回滚到 A。
  4. 迁移：drop column user_name。确认没有回滚需求之后才做，通常等一两周。

这套流程叫"扩展-收缩"（expand-contract）。它看起来很啰嗦，但请对比一下代价：四次部署，每次几分钟；而一次不兼容的迁移可能意味着几分钟的全站 500，外加一次没法回滚的处境——因为回滚代码容易，回滚已经删掉的列不容易。

这也解释了为什么第 6 部分要那么坚决地反对 push：push 的心智模型里根本没有"上一个版本的代码"这个概念。

Q2图 15 的第 ② 步"等几秒"看起来很粗糙——为什么不直接等负载均衡确认摘除完成？

思路提示

因为应用通常没有办法知道。负载均衡的健康检查是拉取式的：它每隔 N 秒来问一次 /readyz，连续失败 M 次才把你摘掉。应用这边看不到这个计数器，也收不到"你已被摘除"的通知。

所以这个等待时间不是拍脑袋，而是由健康检查配置算出来的：检查间隔 × 失败阈值 + 一点余量。间隔 2 秒、失败 3 次判定不健康，那就至少等 6 秒，配 8 秒比较稳。这个数字应该和运维配置写在一起，改了一边要改另一边。

有些平台确实提供了更好的机制——比如 Kubernetes 的 preStop 钩子会在发 SIGTERM 之前执行，可以在那里 sleep，这样应用代码里就不用管第 ② 步了。能用平台机制就用平台机制，应用里的 sleep 是没有更好选择时的兜底。

另外提醒：terminationGracePeriodSeconds 必须大于"② 的等待 + ④ 的超时"，否则平台会在你走完流程之前直接 SIGKILL，前面的功夫全白费。这三个数字必须一起调。

Q3图 15 那张表显示，只要你用了 node:fs 存图片、用了 setInterval 跑定时任务，就跑不上 Workers 了。为了保住可移植性而放弃这两样，值得吗？

思路提示

这题的关键在于分清"可移植"和"能移植"。

如果你现在跑在 Node 上、也没有迁移计划，那么为了一个假想的未来而放弃本地文件系统（改成对象存储要多一个依赖、多一份配置、本地开发要起 MinIO），是在为期权付现金。

但有两个具体情况会让这笔投资划算：

  • 你迟早要多实例。这才是真正的理由——一旦有两个实例，写本地磁盘就已经错了：用户在实例 A 上传，实例 B 上读不到。对象存储的必要性来自水平扩展，而不是来自 Workers。同理，setInterval 在多实例下会同时跑 N 份，本来就需要改成带锁的调度或外部触发。
  • 你想在边缘跑一部分。比如商品页在 Workers 上渲染（快、离用户近），后台和下单留在 Node 上。这种混合部署下，"哪些代码必须保持可移植"就是一个明确的、有边界的问题。

我的建议：不要为可移植性做设计，要为多实例做设计。后者是几乎所有项目迟早要面对的现实，而它顺手带来的约束（无本地状态、无进程内定时器、配置从环境来）恰好就是可移植性需要的那些。目标对了，可移植性是副产品。

读完之后

这一份走完的是"把一个商店做对"。真实系统还有一层没碰：缓存、异步、外部依赖、以及规模——Redis 里该放什么、订单状态机怎么建模、支付回调重复和乱序怎么防、限流怎么做、慢查询怎么找。这些主题在《在线商店 · 进阶》里有完整一季，虽然那一季用的是 Spring Boot，但除了代码语法，结论几乎逐条适用于这里——分布式系统的问题不挑语言。

如果想看同一个商店在重型框架下是什么样，《Spring Boot 4 在线商店》是这份教程的姊妹篇，章节一一对应。对照着读，最能看清哪些是框架的选择，哪些是问题本身的形状。

同一个商店，重型框架的写法
