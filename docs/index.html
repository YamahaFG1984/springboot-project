三条线得出的同一批结论

写完六册之后，这些是三边一字不差的部分——它们不属于任何框架，属于问题本身。

  1. 模块边界该画在哪，和用什么框架无关。变的只是用什么手段守住它：容器、静态分析，还是编译器。
  2. 金额永远不用浮点。Java 用整数分或 BigDecimal、JS 用整数分，理由是同一个；而舍入必须显式，运算顺序会改变结果。
  3. 先检查后执行，在并发下必然失效。修法只有一种形状：让检查和修改在数据库里成为一个不可分割的动作。
  4. 事务里不能等外部调用。它持有的是系统里最稀缺的两种资源：连接和行锁。
  5. 超时既不是成功也不是失败，是"不知道"。所以幂等键不是优化，是和外部系统交互的必需品。
  6. 分布式锁是性能优化，不是正确性保证。正确性必须由数据库的唯一约束、条件更新或状态机兜底。
  7. "恰好一次"投递不可实现。能做到的只有"至少一次投递 + 接收方幂等"——你在 Outbox 里是发送方，在支付回调里是接收方。
  8. 缓存不是慢查询的解药，是止痛片。它把持续的性能问题换成了偶发的可用性问题，而爆发时刻恰好是系统已经不稳定的时候。
  9. 先把系统做对，再把它做快。顺序反过来，你会得到一个又快又错的系统，而且很难知道它错在哪。
