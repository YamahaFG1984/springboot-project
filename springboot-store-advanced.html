加进 Redis 之后的样子

贯穿全季的一条判断线：什么数据能放 Redis

Redis 在教程里最容易被写成万能锤——缓存、会话、锁、队列、计数器、排行榜全塞进去。但有一个前提必须先说清楚：Redis 默认配置下，数据是会丢的。

  • RDB 快照是周期性的，两次快照之间宕机，中间的写全部丢失。
  • AOF 用推荐的 appendfsync everysec，最坏情况丢 1 秒的写；改成 always 则性能大幅下降。
  • 主从复制是异步的。主节点确认了你的写、然后宕机、从节点被提升为主——那笔写就消失了，而且客户端收到的是成功。

这不是 Redis 的缺陷，是它换取速度所做的取舍。问题只在于你有没有把数据放对地方。所以这一季每次用到 Redis，都会先回答一个问题：这份数据丢了会怎样？

丢了无所谓

缓存、限流计数、热点排行。丢了只是慢一点、放过几个多余请求。Redis 是对的选择，而且可以放心用内存淘汰策略。

丢了有代价，可接受

会话、购物车。会话丢了用户重新登录；购物车丢了损失一次转化。是否可接受取决于你的规模——第 02 部分会给出判断方法。

绝不能丢

订单、余额、库存的最终数值、幂等键、审计记录。权威副本必须在关系库里。Redis 至多做加速或预扣减，事后必须能从数据库重建。

深入 · 这条判断线为什么比 API 更值钱

第一季第 09 部分讲购物车时说过一句话："客户端和会话里的副本只能用于展示，权威数据要在最后一刻从权威来源重新读取。" 这一季的 Redis 是同一条原则在基础设施层的展开——系统里每多一个存数据的地方，你就多欠一份"当它和别人不一致时谁说了算"的说明。

这个问题在缓存、读写分离、CQRS、事件溯源、多活部署里是同一个形状。先在 Redis 这个最简单的场景里把它想透，后面遇到更复杂的架构会省很多力气。

01

Redis 进场

先把它接进来，然后花大部分篇幅讲三件容易踩的事：它什么时候会丢数据、键怎么命名、值怎么序列化。API 本身是这一部分里最简单的部分。

接进来

沿用第一季的 compose.yaml，加一个服务。Spring Boot 的 docker-compose 支持会自动拉起它并把连接信息注入——不需要在 application.yml 里写 host 和 port。

对照 · 三个抽象层次，按需下沉

Spring 给 Redis 提供了三层 API，越上层写得越少、控制力越弱。默认选最上层，不够用再下沉：

① 声明式：@Cacheable、Spring Session、@SchedulerLock。完全看不到 Redis，配置驱动。第 02、04、07 部分用它。
② StringRedisTemplate：手写 key 和命令，但值都是字符串。做计数器、限流、幂等标记时用它——简单、可预测、redis-cli 里能直接看懂。第 11 部分用它。
③ RedisTemplate<String, Object> + 自定义序列化器：存结构化对象。功能最全，也最容易踩序列化的坑（见下）。

它什么时候会丢数据

这是决定"什么能放 Redis"的唯一依据，值得先看清楚。一笔 SET 从发出到"真正安全"，中间有三个各自独立的窗口：

键的命名

Redis 是一个全局扁平的键空间，没有表、没有 schema、没有外键。约束只能靠约定。用一套固定的命名结构，能一次性解决四个问题：看得懂、不冲突、能批量清理、能按前缀统计内存。

深入 · 为什么键里要带一个版本号

假设你把商品缓存的值结构改了——加了个字段、或者把 price 从字符串换成数字。上线的一瞬间，Redis 里还存着几十万个旧结构的值，新代码读到它们会反序列化失败或静默拿到错数据。

常见的应对是"上线前手动 FLUSHDB"——但这需要人记得做、需要停机窗口、而且滚动发布期间新旧代码同时在跑，清了也会被旧实例立刻写回去。

把版本号编进键前缀（v1 → v2），新代码天然读不到旧键，等于一次无需协调的缓存切换：旧键自然过期消失，不需要停机，不需要人工操作，滚动期间新旧代码各读各的互不干扰。第一季讲密码哈希的 {bcrypt} 前缀时用的是同一个思路——任何要长期存储且格式会演进的数据，都应该自带版本标识。

序列化：默认值是个陷阱

RedisTemplate 的默认序列化器是 JDK 序列化。它能用，但有三个实打实的问题：

  • 值在 redis-cli 里是一堆乱码，排查问题时看不懂存了什么。
  • 和 Java 类名强耦合：序列化结果里写死了全限定类名和 serialVersionUID。重命名或移动一个类，所有已缓存的值全部失效——而且是抛异常而不是当作未命中，等于把缓存变成了故障源。
  • 反序列化任意类是已知的攻击面。如果攻击者能往 Redis 写入（比如通过一个键注入漏洞，或 Redis 未鉴权暴露在内网），JDK 反序列化可能被利用成远程代码执行。
安全 · Redis 默认不需要密码

Redis 的默认配置没有认证、绑定所有网卡。历史上被大规模利用过：扫到开放的 6379 端口，写入一个 crontab 或 SSH 公钥，直接拿下机器。生产环境三件事必须做：requirepass（或 ACL 用户）、只监听内网地址、rename-command 禁用 FLUSHALL / KEYS / CONFIG。托管服务（ElastiCache、阿里云 Redis）默认帮你处理了前两条，自建的话必须自己配。

另外，永远不要在生产上执行 KEYS *。Redis 是单线程处理命令的，KEYS 会遍历整个键空间并阻塞其它所有请求，几百万键的实例上足以造成一次全站超时。需要扫描时用 SCAN（游标式，分批返回）。同理还有 FLUSHALL、大 key 上的 DEL（用 UNLINK 异步删除）。

每个键都必须有过期时间

Redis 的内存是有限且昂贵的。一个没有 TTL 的键会永远存在，直到内存打满触发淘汰策略——而默认策略 noeviction 的行为是拒绝所有写入，也就是整个系统同时失去缓存、会话、锁和限流。

动手与思考 · 第 01 部分

先自己想，再展开思路。

Q1有人提议："既然 Redis 有 AOF appendfsync always，那它就是持久化的，订单可以直接存 Redis，省掉一个数据库。" 这个论证错在哪？

思路提示

错在把"持久化"等同于"可以当权威存储"。appendfsync always 确实解决了图 1 的窗口 ①，但窗口 ②（异步复制）依然存在——主节点 fsync 成功后立刻宕机，从节点被提升，那笔写照样没了。要堵住这个洞需要 WAIT 命令等待从节点确认，而那会把延迟拉到和数据库同一个量级，Redis 的速度优势就没了。

但更根本的问题不是持久性，是Redis 没有关系数据库的其它保证：没有跨键的 ACID 事务（MULTI 不是事务，它不回滚也不隔离）、没有外键、没有唯一约束、没有 check、没有可重复的查询计划、没有成熟的备份恢复与时间点还原。第一季反复强调的"数据库约束是唯一无法绕过的防线"，在 Redis 里根本不存在。

可迁移的判断方式：评估一个存储时，别只问"数据会不会丢"，还要问"它能替我保证哪些不变量"。 订单系统真正依赖的是"余额不能为负""同一个幂等键只能有一条订单"这类约束，而不只是"字节还在"。

Q2为什么建议用 GenericJackson2JsonRedisSerializer 但不开启 activateDefaultTyping（即不把类名写进 JSON）？不写类名的话，读出来怎么知道是什么类型？

思路提示

不写类名，读取时就必须由调用方指定目标类型——ops.get(key) 拿到的是 Map，你要显式转成 ProductView.class。多打几个字，但换来两件事。

第一是安全：把类名写进 JSON 意味着反序列化时会根据数据内容去加载并实例化任意类。这正是 Jackson 历史上一长串 CVE 的成因（各种 gadget chain）。攻击者只要能控制 Redis 里的一个值，就可能触发代码执行。不写类名，这条路径直接不存在。

第二是解耦：类名写进数据里，等于把 Java 的包结构变成了存储格式的一部分。重构一次包名，缓存全炸。

一般化的原则：反序列化时，类型应该由代码决定，而不是由数据决定。 这条同样适用于 JSON API、消息队列的消息体、配置文件——凡是让外部数据来指定"实例化哪个类"的设计，都是潜在的攻击面。

Q3第一季说"数据库约束是最后一道防线"。Redis 没有约束。那把购物车放进 Redis 之后，用什么保证"数量不能是负数"？

思路提示

只能靠应用层，这是必须承认的能力下降。所以真正的问题变成：这个不变量被破坏的后果有多严重、有没有下游能兜住。

购物车的情况还好——它不是权威数据。即使 Redis 里出现了 数量 = -3，结算时 CheckoutService 会重新校验（第一季 reserve() 里的 if (quantity <= 0) throw），数据库的 check (stock >= 0) 也还在。脏数据进不了订单，最坏是用户看到一个奇怪的购物车。

这反过来解释了为什么"能不能放 Redis"要按数据分层：不是因为购物车不重要，而是因为它下游还有一道带约束的关卡。如果某份数据是链路的终点、后面没有任何校验，那它就必须待在有约束的地方。

顺带一个实践建议：把这类"Redis 里理论上不该出现的状态"写成断言并上报指标（第 12 部分），而不是假设它不会发生。失去了约束，就要用监控补上可观测性——否则数据悄悄坏掉，你要等到用户投诉才知道。

02

会话与购物车外置

还第一季第 07 部分 Q1 和第 09 部分 Q3 的账。这是 Redis 最容易见效的一个用途，加一个依赖 + 一行配置就能工作——但"能工作"和"想清楚了"之间还有几步。

第一季的应用把会话存在 JVM 内存里。单实例时毫无问题；一旦起三个实例、负载均衡又不做会话粘滞，用户就会随机登出、购物车随机清空、闪存消息随机消失——而且是间歇性的，最难排查的那一类故障。

接上去

就这样。HttpSession 的实现被换成了 Redis 支持的版本，你的控制器代码一行不用改。Spring Security 的 SecurityContext 本来就存在会话里，所以登录状态自动跟着走了——第一季第 08 部分讲的会话固定防护（登录时换发新会话 ID）在这里依然有效，只是新 ID 落在 Redis 而不是堆内存。

陷阱 · 会话里的对象必须能被序列化

会话从"堆里的对象引用"变成了"要在网络上来回搬的字节"。放进去的东西现在必须能序列化——第一季的 Cart 已经 implements Serializable 了，但如果你往会话里塞过 JPA 实体，问题会立刻出现：懒加载代理无法序列化，或者序列化时把整棵对象图都拉出来，一个会话几百 KB。

规则：会话里只放小而扁平的值——id、几个标志位、必要的字符串。 需要完整对象就用 id 去查（有缓存的话很快）。这条约束反过来是好事，它逼你不把会话当成本地缓存用。

购物车：先问要不要搬

第一季的 Cart 是个 @SessionScope 的 Bean。会话搬到 Redis 之后，它已经自动跟着搬过去了——不需要任何改动，跨实例也能用了。

深入 · 合并策略没有"正确答案"，但有"必须做的决定"

匿名购物车里有"商品 A × 1"，账号购物车里也有"商品 A × 2"。登录后应该是 1、2 还是 3？

三种都有人用：相加（最符合"合并"的字面意思，但会造成用户明明只想要 1 件却下单 3 件）、取较大值（假设两次操作是同一个意图的重复表达，出错时倾向于保留用户更明确的那次）、让用户选（最准确，但多一个打断转化的弹窗）。

我在上面选了取较大值，理由是出错方向更可接受：多买了不需要的东西会导致退货和投诉，少买了用户会自己再加一件。当没有客观正确答案时，按"哪个方向的错误更容易被用户自行修正"来选。

但真正的要点是：这个决定必须被显式做出并写下来。 不写就等于默认了实现里碰巧的那个行为，而且没人知道它是有意的还是 bug。

动手与思考 · 第 02 部分

Q1会话超时设成 30 分钟。用户在结算页填了 10 分钟地址，期间没有发出任何请求，然后点提交。会发生什么？怎么改？

思路提示

10 分钟没超过 30 分钟，这次没事。但把数字换一下——用户去接了个电话，35 分钟后回来点提交——会话已失效，Spring Security 把他重定向到登录页，填的所有内容丢失，购物车如果还在会话里也一起没了。

几个层次的解法：购物车独立存储 + 更长 TTL（上面已经做了，30 天），这样至少数据不丢；前端定时心跳续期会话（简单，但等于所有开着页面的用户永不超时，削弱了超时的安全意义）；失效后保留原始请求——Spring Security 的 RequestCache 默认就会记住用户原本想去的 URL，登录后跳回去，但它不保存 POST 请求体，所以表单内容还是没了；真要保住表单，得在前端把草稿存进 localStorage。

值得记住的一点："会话超时"这个安全措施的成本是由用户承担的，而且承担方式很不均匀——手快的人从不遇到，被打断的人每次都遇到。定这个值时应该分场景：银行 5 分钟合理，购物网站 30 分钟偏短，很多电商实际用的是几天。安全参数不该照抄，要按这个系统被攻破的后果来定。

Q2会话搬进 Redis 后，每个请求都要多一次 Redis 往返来读会话。有人提议在应用里再加一层本地缓存（Caffeine）缓存会话对象。这个想法有什么问题？

思路提示

它把刚解决的问题重新引入了。本地缓存意味着会话状态又回到了各实例的内存里，于是：实例 A 缓存了会话，管理员调用 revokeAll() 删掉了 Redis 里的会话，但实例 A 在缓存过期前仍然认为这个人是登录的——主动踢人失效了，而这正是我们选方案 ② 的主要理由之一。

更微妙的问题：用户在实例 A 上改了会话（比如往购物车加了东西），实例 B 上的缓存副本是旧的，两边写回 Redis 时后写的覆盖先写的——第一季第 10 部分的"丢失更新"，换了个地方重演。

可迁移的判断：给可变的、有一致性要求的数据加缓存，是在用一致性换延迟。 值不值取决于"不一致的窗口内会发生什么"。会话的不一致会导致安全控制失效，代价太高。如果真的测出来 Redis 往返是瓶颈（先测量），更好的方向是减少往返次数（flush-mode、少往会话里放东西）或者部署得离 Redis 更近，而不是加一层副本。

Q3匿名购物车的键是 store:v1:cart:anon:{随机 id}，这个 id 写在 cookie 里。如果攻击者伪造别人的匿名 id，能做什么？这算漏洞吗？

思路提示

能读到和修改那个匿名用户的购物车。危害有限但真实：可以窥探别人在看什么商品（隐私）、可以往别人购物车里塞东西（骚扰）、如果 id 可预测还能批量扫描。

算不算漏洞取决于你把它定位成什么。关键在于这个 id 必须是"不可猜测"而不只是"唯一"——用 UUID.randomUUID()（底层是 SecureRandom）没问题，用自增数字或时间戳就是明确的漏洞。另外这个 cookie 也该带 HttpOnly 和 SameSite。

一般化：每个标识符都有一个隐含的"信任等级"，扩展它的用途时必须重新评估这个等级是否还够。 会话 ID、API key、分享链接里的 token，都适用。

分页：两行代码，和一个藏起来的成本

陷阱 · 排序字段必须是全序

sort = "price" 看起来没问题，直到出现两个同价商品。数据库对相同排序键的行不保证稳定顺序，于是同一个商品可能在第 2 页和第 3 页各出现一次，另一个商品一次都不出现——而且是随机的、无法稳定复现的。

深翻页为什么会越来越慢

LIMIT 24 OFFSET 24000 的语义是：把前 24000 行全部找出来，然后扔掉。 数据库没有办法"跳到第 24001 行"——它必须真的走过去。

深入 · 什么时候用哪种

OFFSET 分页：需要显示"共 1234 页"、需要跳到任意页。适合后台管理列表——数据量可控，用户确实会跳页。

keyset 分页：只需要"加载更多"或"下一页"。适合面向用户的信息流、无限滚动、导出。它还有一个常被忽略的好处：翻页期间有新数据插入时不会重复或漏掉——OFFSET 分页在这种情况下，第 2 页会重复显示第 1 页的最后一条。

务实的折中：前 N 页用 OFFSET（能跳页），超过 N 页就不给跳了。多数电商就是这么干的——搜索结果最多给你翻 100 页，不是技术做不到，是超过这个深度的请求几乎全是爬虫。

Q1商品列表页用 Page<Product>，页面上显示"共 12345 件商品"。有人说这条 COUNT 查询很贵，建议改成 Slice。但产品经理坚持要显示总数。有哪些出路？

思路提示

先确认它是不是真的贵——带 where 且有合适索引的 COUNT 通常不慢，无条件的全表 COUNT 在大表上才是问题。explain analyze 一下再说。

值得练习的思路：遇到"技术上很贵"的需求，先回去看这个需求解决的是什么问题。 "显示总数"背后的真实诉求可能是"让用户知道结果多不多"，那么"约 12000 件"完全够用，成本却差几个数量级。把需求当成待求解的问题而不是待实现的规格，往往能找到便宜得多的解。

Q2你给 products 表建了 8 个索引来覆盖各种筛选组合。写入变慢了。除了"索引太多"这个笼统的说法，具体是哪些操作变慢了、为什么？

思路提示

每一次 INSERT / UPDATE / DELETE 都要同步维护所有相关索引：插入一行要在 8 棵 B 树里各插一个条目，可能触发页分裂；更新某列要在包含该列的每个索引里删旧条目、插新条目。所以写放大是实打实的 8 倍级别，而且是随机 I/O。

还有两个不那么明显的代价：优化器的选择空间变大，可能选错索引（尤其统计信息不准时）；Postgres 的 HOT 更新失效——更新一个不被任何索引包含的列时，Postgres 可以走 HOT 优化不动索引，一旦这个列进了某个索引，这条快路就没了。

实践方法：查 pg_stat_user_indexes 的 idx_scan，把从来没被用过的索引删掉。真实项目里"建了但从没被使用的索引"比例常常高得惊人——因为索引是加需求时顺手建的，而删索引没人敢做。索引和缓存、监控告警一样，属于"只增不减会持续劣化"的资产，需要定期回收。

Q3本部分开头说"缓存不是缺索引的替代品"。具体会怎么出事？

思路提示

典型剧本：某个查询要 800 ms，没人去查原因，直接加了 10 分钟缓存。上线后一切正常——因为 99.9% 的请求命中缓存。然后某天缓存集中失效（重启、发布、TTL 撞在一起、或者第 04 部分要讲的雪崩），所有请求同时打到数据库，每个都要 800 ms，连接池瞬间耗尽，整站 502。

关键在于：缓存改变的是"多久打一次数据库"，没有改变"打一次要多久"。 它把一个持续的性能问题转成了一个偶发的可用性问题——而后者更难排查，因为平时完全看不出来，出事时又是所有指标同时红。

正确顺序是：先用 explain 把 800 ms 降到 5 ms（通常就是缺一个索引），然后再决定要不要加缓存。此时缓存的作用变成锦上添花，即使全部失效，数据库也扛得住。

可迁移的原则：用缓存、重试、超时这类手段"绕过"一个慢操作之前，先确认这个操作本身没有明显可修的问题。 否则你只是把故障推迟到一个更糟糕的时刻。

陷阱 · @Cacheable 和 @Transactional 一样怕自调用

两者都是代理实现的。同一个类里 this.findView(id) 调用自己标了 @Cacheable 的方法，缓存完全不生效，而且没有任何提示。第一季第 10 部分讲过这个陷阱，在这里会再犯一次——因为缓存不生效不会报错，只是变慢，很难被发现。

三种失效形态

深入 · 为什么要缓存空值，尽管它看起来很浪费

disableCachingNullValues() 是个很自然的默认设置——缓存"没有"这件事听起来毫无价值。但穿透正是利用了这一点：攻击者用随机 id 发请求，每一次都必然未命中、必然落库。

所以商品详情这类参数由用户控制、且大部分取值不存在的查询，应该缓存空值，TTL 设短一些（60 秒足够挡住暴力刷）。而内部调用、参数来自可信来源的查询就不需要。

一般化："缓存什么"要看攻击者能控制什么，而不只是看正常用户会请求什么。 这条思路和第一季讲上传时的"虚线左边全是攻击者可控的输入"是同一个视角。

缓存和数据库怎么保持一致

这是缓存最难的部分，也是唯一一个没有完美解的部分。先看标准做法 Cache-Aside 是怎么破的：

深入 · 三个常见提议，和它们各自的问题

"改成先删缓存再更新数据库" —— 更糟。删完之后、更新提交之前，任何读请求都会读到旧值并回填，窗口比图 5 大得多，而且是必然发生而不是偶发。

"更新数据库后直接把新值写进缓存，而不是删除" —— 引入了新的竞态：两个并发写线程，DB 里最终是 B 的值，但写缓存的顺序可能是 B 先 A 后，缓存里留下 A 的值。删除比写入安全，因为删除是幂等的、没有顺序问题。

"延迟双删：更新后删一次，睡 500ms 再删一次" —— 能把窗口概率压得很低，但那个 500ms 是猜的：读请求慢于 500ms 时照样漏。而且它让写操作变慢、代码里出现一个无法解释的魔数。它降低概率，不改变性质。

诚实的结论：Cache-Aside + 合理 TTL 就是答案。 承认存在一个短暂的不一致窗口，用 TTL 保证它有界，然后只对能容忍这个窗口的数据用缓存。商品名和描述可以，库存和余额不行——后者必须每次读库（第一季第 09 部分那条原则）。

失效范围：比想象中大

改一个商品的价格，要清掉哪些缓存？product:1042 是显然的。但它还出现在：商品列表第 3 页、分类页、搜索结果、首页推荐、购物车里的价格快照、"猜你喜欢"……缓存的失效范围往往远大于被修改的实体本身。

两条务实的策略：把聚合型缓存的 TTL 设得很短（列表页 2 分钟，反正它本来就在变），只对单实体缓存做精确失效；或者用缓存名做粗粒度清除（allEntries = true），代价是误伤，但正确性有保障。先用粗粒度，等测出来它真的是瓶颈再细化。

动手与思考 · 第 04 部分

Q1击穿的解法里提到"重建时加互斥锁，只放一个请求进去"。这个锁用 Redis 实现（第 07 部分要讲的那种）。但第 07 部分会说 Redis 锁不保证正确性。这里为什么可以用？

思路提示

因为这里的锁是性能优化，不是正确性保证——这恰好是第 07 部分那条结论的正面用例。

假设锁失效了，两个请求同时拿到锁去重建缓存。后果是什么？数据库多执行了一次查询，缓存被写了两次相同的值。 没有任何正确性问题。锁的作用只是把"3000 次查询"变成"1 次查询"，偶尔变成 2 次、5 次都完全可以接受。

对比一下扣库存：锁失效意味着超卖，那是真实损失，所以那里必须靠数据库的乐观锁或唯一约束兜底。

值得提炼的判断方法：用任何"尽力而为"的机制之前，先问"它失效时会发生什么"。 答案是"稍微慢一点"就放心用；答案是"数据错了"就必须换成有保证的机制。这个问题能帮你区分绝大多数看起来相似的技术选择。

Q2商品缓存 TTL 是 30 分钟。运营在后台改了价格，代码里 @CacheEvict 也执行了。但用户反馈"还是看到旧价格"。可能是哪里出了问题？

思路提示

可能性从高到低：

  • 失效范围漏了。 单个商品缓存清了，但列表页、搜索结果、首页推荐里的价格没清。用户看的多半不是详情页。
  • 自调用导致 @CacheEvict 根本没生效（本部分开头的陷阱）。
  • 清缓存发生在事务提交之前。 @CacheEvict 默认在方法返回时执行，而 @Transactional 的提交也在方法返回时——两者顺序是"先清缓存后提交"，中间任何读请求都会把旧值重新加载回来。解法是 @CacheEvict(beforeInvocation = false) 配合 TransactionAwareCacheManagerProxy，让清除延到提交之后。
  • 浏览器或 CDN 缓存。 问题可能根本不在 Redis。

排查顺序上有个通用技巧：先确认"缓存到底有没有被清"，再讨论为什么。 直接 redis-cli GET 看一眼，一秒钟就能把问题域砍掉一半——是没清掉，还是清掉了又被写回来了，这两条路径的原因完全不同。

Q3"给所有 Service 方法都加上 @Cacheable，反正缓存了总比不缓存快。" 反驳这个说法。

思路提示

几个层面：

正确性：写方法和读了就要立刻用的数据（库存、余额、锁状态）加缓存，直接制造 bug。缓存的前提是"允许读到稍旧的数据"，不是所有查询都满足。

性能：缓存本身有成本——序列化、网络往返、内存占用。一个本来 2 ms 的索引查询，加上缓存后变成 1 ms 网络 + 0.5 ms 反序列化，收益接近于零，却多占了内存、多了一个失效点。缓存低价值数据会挤占高价值数据的内存，反而降低整体命中率。

可维护性：每个缓存都是一处需要考虑失效的地方。加 20 个缓存就是加 20 处潜在的"数据不一致"来源，而它们的 bug 都表现为"偶尔看到旧数据"，极难排查。

可迁移的原则：缓存是有成本的资产，不是免费的加速。 加之前应该有数据支撑——这个查询多慢、QPS 多高、命中率预计多少、数据能容忍多旧。同样的思维适用于索引、日志、监控指标、特性开关：凡是"加了没坏处"的东西，通常都有你还没看到的成本。

订单状态机

第一季的订单只有"已创建"一个状态，所以后面几部分想讲的东西——超时关闭、退款、重复回调——全都无处安放。状态机是这一季剩下部分的地基。

加状态字段很容易，难的是保证它只按允许的路径变化。真实系统里的订单 bug 大多不是"状态存错了"，而是"从一个不该能到达的状态到达了另一个状态"——已取消的订单被发货，已退款的订单又被支付，超时关闭的订单收到了支付回调。

深入 · 为什么 status == target 直接返回，而不是抛异常

这一行是这个类里最重要的一行。第 09 部分会讲支付网关的回调一定会重复投递——网络抖动、平台重试机制、人工补发，同一笔支付的"成功"通知可能到达三次。

所以要严格区分两件事："非法转换"是 bug，必须响亮地失败；"重复到达同一状态"是分布式系统的常态，必须安静地成功。 这就是幂等性在状态机上的具体形态——把它放在实体这一层，所有调用方自动获得，不需要每处都记得判断。

为什么不用 Spring StateMachine

对照 · 工具的复杂度要匹配问题的复杂度

Spring StateMachine 是个完整的状态机框架：支持嵌套状态、并行区域、状态持久化、守卫与动作、事件驱动。它适合状态图本身很复杂、会频繁变化、需要可视化或由业务人员配置的场景——比如工单流转、审批流、设备控制。

订单状态机不是那种问题。它只有 8 个状态、10 条边，一年也未必改一次。用枚举 + 一张 Map，全部逻辑 20 行、零依赖、可以直接单元测试、任何人打开就看懂。引入框架反而要学一套 DSL、多一层间接、调试时看不清发生了什么。

可迁移的判断：先写出最朴素的实现，只有当它开始变得笨拙时才升级工具。 "以后可能会变复杂"通常不是引入框架的充分理由——因为等它真的复杂了，你对问题的理解也更清楚了，那时的选择会更准。

状态变更是一等公民

注意 transitionTo 里往 history 加了一条记录。状态机最该被审计的不是当前状态，而是变化过程。 一张 order_status_changes 表（订单 id、从什么状态、到什么状态、原因、操作者、时间）能回答几乎所有客服问题："这个订单为什么被取消了" —— 查一下就知道是用户点的、还是超时任务扫的、还是运营手工操作的。

Q1上面的 SQL 里最后一条索引带了 where status = 'CREATED'。为什么不建成普通的 (status, created_at)？

思路提示

这是部分索引。定时任务只关心待支付订单，而待支付订单在总量里占比极小——绝大多数订单最终是 COMPLETED。普通索引会为每一行都建条目，部分索引只为满足条件的行建。

差别在真实数据上很夸张：100 万订单里可能只有 500 条是 CREATED，部分索引就只有 500 个条目，小到能常驻内存，扫描接近瞬时。而且索引会随着订单被支付而自动收缩——行的状态一变就从索引里移除，维护成本也低。

可迁移的模式："待处理队列"型的查询几乎总是部分索引的最佳场景。 待发送的 outbox 记录（第 10 部分）、待重试的任务、未读消息、未审核内容——它们的共同特征是"符合条件的行占比很小，且会不断流出"。看到这个特征就该想到部分索引。

Q2用户点"取消订单"的同时，支付回调到达了。两个请求并发，一个想 CREATED → CANCELLED，一个想 CREATED → PAID。会发生什么？应该发生什么？

思路提示

没有并发控制的话，两个请求都读到 CREATED、都认为转换合法、都写入——最后落库的那个赢，另一个的效果被覆盖。如果 CANCELLED 赢了，用户的钱已经付出去但订单是取消状态；如果 PAID 赢了，用户以为取消成功但商品会发出去。两种结果都是真实的客诉。

技术上的解法是第一季的 @Version：后提交的那个更新影响 0 行，抛 ObjectOptimisticLockingFailureException，事务回滚。这保证了只有一个能成功——状态机的合法性检查必须和乐观锁一起用，单独任何一个都不够。转换表挡的是"路径非法"，版本号挡的是"读到的状态已经过时"。

一般化：并发冲突时，让"外部世界已经发生了不可撤销的事实"的那一方赢。 钱、发货、发送出去的邮件都属于这一类。

思路提示

不能，而且这暴露了一个建模层次的问题：退款状态被放在了错误的对象上。

当前设计里 REFUNDING/REFUNDED 是订单的状态，隐含假设"退款是整单的"。部分退款意味着一个订单可以同时"一部分在退款、一部分已发货"——单个状态字段表达不了两个并行的事实。

几种改法：给 Item 也加状态（订单状态变成对明细状态的聚合视图）；或者把退款提升为独立的聚合根 Refund（有自己的状态机，通过 order_id 关联，一个订单可以有多个退款单）。后者是多数电商的实际做法，因为退款还需要自己的审核流、凭证、财务对账。

值得记住的信号：当你发现"一个对象需要同时处于两个状态"时，说明状态机建在了错误的粒度上。 解法通常是把并行的那部分拆成独立对象，各自持有自己的状态机——而不是往枚举里加 PARTIALLY_REFUNDED 这类组合状态。组合状态会让状态数量随着维度指数增长，是状态机腐化的典型开端。

超时释放：为什么必须用定时任务

很自然会想到一个巧妙方案：往 Redis 写一个 30 分钟过期的键，监听 keyspace notification 的过期事件，收到就释放库存。这个方案是错的，而且错得很隐蔽：

陷阱 · Redis 过期通知不是可靠投递

三个独立的问题，每一个都足以丢事件：

① 通知是即发即忘的。 Redis 的 pub/sub 没有确认、没有重投、没有持久化。订阅者那一刻正好在重启或网络抖动，事件就永远消失了——库存被锁死，没有任何人知道。

② 过期事件的触发时机不确定。 Redis 的惰性删除意味着键"逻辑上过期"和"实际被删除并发出通知"之间可能隔很久——如果没人访问这个键，要等后台采样任务碰到它。延迟可能是几分钟。

③ Redis 本身可能重启。 第 01 部分图 1 说过，未落盘的数据会丢，那些待过期的键连同它们的"定时器"一起消失。

结论：凡是"漏了会造成资金或库存损失"的延迟任务，都必须以数据库为准。 Redis 可以做加速，但兜底的必须是一个能扫描出"所有本该处理但还没处理"的持久化查询。

深入 · 这段代码里的四个设计决定

① 分批 + 每单独立事务。 一个事务处理 200 单意味着 200 行的锁要持有到最后，而且一单失败全部回滚。拆开后失败被隔离，锁的持有时间也短。

② 拿到后重新检查状态。 查询和处理之间存在时间差，订单可能刚好被支付了。这个二次检查配合行锁（findByIdForUpdate）才安全——查询给出候选，锁内的检查给出结论。

③ 失败只记日志不抛出。 因为这个任务是可重入的：没处理成功的订单下一分钟还会被扫到。有了这个性质，就不需要复杂的错误处理——只要保证"漏掉的下次还能扫到"，任务本身可以很朴素。

④ 幂等由状态机保证。 即使同一个订单被处理两次，第二次 transitionTo 会因为状态已是 EXPIRED 而直接返回（第 05 部分那一行），库存不会被释放两次。

这四点合起来是一个可复用的模式："扫描待处理 → 逐个加锁重检 → 幂等地处理 → 失败留给下一轮"。它比"精确的定时器"健壮得多，因为它不依赖任何一次执行成功。

  • 对账：每天把支付网关的流水和本地订单跑一遍差异。这是兜底，也是唯一能发现"两边都以为自己对了"的手段。

可迁移的原则：跨系统的一致性最终都要靠对账，而不是靠时序设计。 时序设计降低发生概率，对账负责发现和修复剩下的。任何涉及钱的系统，没有对账就是没做完。

Q3为什么"预占"要单独存一列，而不是直接在下单时 stock = stock - 3、超时再加回来？后者少一个字段，逻辑也更简单。

思路提示

只有一个 stock 列时，你无法回答这些问题：现在有多少件是被未付款订单锁着的？这个商品的下单转化率是多少（预占了多少、最终成交多少）？昨天有多少库存因为超时被白白锁了半小时？仓库实际该备多少货（stock 现在既不是实际库存也不是可售库存，它是个混合物）？

更实际的问题是对账：如果某次释放失败了，只有一个数字时你根本发现不了——库存就是少了，没有任何痕迹。有 reserved 列时，你可以定期校验"reserved 是否等于所有 CREATED 订单的明细之和"，不等就说明有 bug，而且能算出差多少。

一般化的原则：把"当前值"和"为什么是这个值"分开存，是可对账系统的基本要求。 同样的道理适用于余额（余额 vs 流水）、积分、优惠券——单独一个数字永远无法自证正确，能被校验的模型才能长期维护。这也是为什么会计系统用复式记账。

第 06 部分的超时关单任务，在三个实例上就会跑三遍。加个锁看起来能解决——这一部分讲为什么它只能解决一部分，以及剩下那部分该靠什么。

先把任务写对

陷阱 · fixedRate 和 fixedDelay 的区别会咬人

fixedDelay = 60_000：上一次执行结束后再等 60 秒。任务本身跑多久都不会重叠。
fixedRate = 60_000：每 60 秒发起一次，不管上一次跑完没有。任务变慢时会积压，同一个 JVM 里就可能并发执行。

默认用 fixedDelay。 只有当"必须按固定节奏触发"（比如指标采样）时才用 fixedRate，并且要确认任务能承受重叠。

另外 cron 表达式默认用服务器时区。跨时区部署或夏令时切换时会出现"某天跑了两次或一次没跑"。永远显式写 @Scheduled(cron = "0 0 3 * * *", zone = "Asia/Shanghai")。

深入 · 锁是性能优化，不是正确性保证

这是这一部分唯一需要记住的结论。锁能把"三个实例都跑一遍"变成"通常只有一个实例跑"，省掉 99.9% 的重复工作——这是实实在在的价值。但它不能保证"绝对只有一个"。

所以正确性必须由别处保证。回头看第 06 部分的超时关单任务，它已经天然具备了：

  • 行锁 + 状态重检：findByIdForUpdate 之后再判断状态，两个实例同时处理同一单时，后者会看到状态已变为 EXPIRED。
  • 状态机幂等：transitionTo 遇到相同状态直接返回，不会重复释放库存。
  • 数据库约束：check (reserved >= 0) 是最后一道，即便前两道都失效，库存也不会变成负数。

换句话说：那个任务即使在没有 ShedLock 的情况下被三个实例同时执行，结果依然是正确的，只是浪费了一些数据库查询。 这才是健壮的设计——锁是加速器，不是承重墙。

反过来说，如果你发现某个任务"没有锁就会出错"，那说明真正缺的不是锁，是幂等性。先让它幂等，再用锁减少重复。顺序反了的话，你就是在用一个不可靠的机制去保障一个必须可靠的结果。

还有两件容易忽略的事

  • 优雅停机。 实例被 kill 时，正在执行的任务应该跑完（或至少能安全中断）。setWaitForTasksToCompleteOnShutdown(true) 加上第一季配的 server.shutdown: graceful，两者要一起用。任务本身也要写成"可中断 + 可重入"，被砍断了下一轮能接上。
  • 可观测。 定时任务是最容易静默失败的东西——它没有用户在等，挂了几周都可能没人发现。至少要有：每次执行的耗时和处理条数打点、连续失败告警、以及"超过 N 分钟没有成功执行过"的心跳告警。第 12 部分会具体讲怎么埋。

动手与思考 · 第 07 部分

Q1ShedLock 的 LockProvider 可以用 Redis 也可以用 JDBC。上面选了 JDBC。既然已经引入 Redis 了，为什么不用它？

思路提示

几个理由，最重要的是故障域。锁存在数据库里，意味着"能拿到锁"和"能执行任务"依赖同一个组件——数据库挂了，任务本来也做不了事，锁失效不会造成额外损害。而锁存在 Redis 里时，会出现一个尴尬状态：Redis 挂了但数据库好着，此时所有实例都拿不到锁，任务全部停摆——尽管它们完全有能力执行。一个用于"提高效率"的组件，变成了阻断业务的单点。

第二个理由是时间源：usingDbTime() 让所有实例参照数据库时钟。Redis 也有 TIME 命令，但 ShedLock 的 Redis provider 依赖各实例的本地时钟。

第三个是可观测性：shedlock 表可以直接 select 查看每个任务上次谁执行的、什么时候。排查"任务为什么没跑"时非常有用，而 Redis 里的一个键不留历史。

可迁移的判断：选存储时不只看"能不能存"，要看"它挂了会怎样"和"它和使用者的故障域是否一致"。 让辅助设施的可用性要求不高于它服务的主体，是避免"为了优化反而降低可用性"的通用做法。

Q2有人提议给 Redis 锁加"看门狗"：持锁期间起一个后台线程每 3 秒续期一次，这样任务跑多久锁都不会过期。这能解决图 8 的问题吗？

思路提示

不能，它只是把窗口挪了个位置。看门狗线程和业务线程在同一个 JVM 里——Full GC 停顿会同时冻结两者，虚拟机被挂起也一样。A 卡住 12 秒时，看门狗也卡了 12 秒，锁照样过期。

网络分区更直接：A 和 Redis 之间断了，续期请求发不出去，锁必然过期；而 A 自己完全正常，会继续执行下去。

看门狗真正解决的是另一个问题：任务执行时间不可预测时，不用把 lockAtMostFor 设得很长。 设得长，进程真崩了要等很久才能释放；设得短，正常任务会被误判。看门狗让你可以设一个短过期时间同时支持长任务——这是有价值的，只是价值不在"消除双持有"。

值得练习的思维：看到一个"加个机制就能解决"的提议，先问它的失效模式和原问题的失效模式是不是同一个。 看门狗的失效模式（进程卡住/网络断）恰恰和原问题完全重合，所以它不可能解决原问题。这个检查能过滤掉很多看起来聪明的方案。

Q3"每天凌晨 3 点生成前一天的销售报表"这个任务，如果因为发布刚好错过了 3 点，或者执行时抛异常挂了，会怎样？怎么设计才不会悄悄漏掉一天？

思路提示

用 @Scheduled(cron = "0 0 3 * * *") 的话，错过了就是错过了——没有补偿机制，那一天的报表永远不会生成，而且不会有任何报错，因为"没有执行"不是一个事件。

健壮的做法是把思路从"在某个时刻执行"换成"确保某个状态达成"：建一张 daily_report 表，任务每小时跑一次，查询"最近 N 天里哪些天还没有报表记录"，然后为每一个缺失的日期生成。这样任何一次错过或失败，下一轮都会自动补上。

这就是第 06 部分那个模式的推广："扫描待处理 → 幂等地处理 → 失败留给下一轮"，比"精确定时触发"健壮得多。 因为前者的正确性只依赖"最终执行过一次"，后者依赖"在正确的时刻恰好执行成功"。

顺带说，这个模式还免费带来了两个好处：想重新生成某天的报表，删掉那条记录即可；系统停机三天后重启，会自动把三天的报表都补出来。把定时任务设计成"收敛到目标状态"而不是"在时间点做动作"，是分布式系统里非常值得养成的习惯。

对外集成：支付网关

第一季的"支付"是从 balance 列里减一个数。真实支付要跨出进程、跨出机房、跨出你的控制范围——这一部分讲的全部是"对方不按预期反应时怎么办"。

声明式 HTTP 客户端

Spring 6 引入了 HTTP 接口客户端：声明一个接口，框架生成实现——和 Spring Data 的 Repository 是同一个思路。

陷阱 · 不设超时 = 把可用性交给对方

多数 HTTP 客户端的默认超时是无限。支付网关那边卡住 60 秒，你这边的线程就占着连接等 60 秒。并发一上来，Tomcat 的工作线程全部堵在那里，整个网站打不开——包括那些根本不涉及支付的页面。

这是最典型的级联故障：一个非核心依赖的慢，通过共享的线程池传染成全站不可用。所以每一个出站调用都必须有超时，没有例外。

超时之后，你不知道发生了什么

这是整个部分最关键的一点，也是最反直觉的一点：超时不是失败，超时是"未知"。

重试：只对安全的操作，且要退避加抖动

深入 · 为什么退避要加随机抖动

固定退避（200ms、600ms、1800ms）有个隐蔽问题：失败的请求会同步化。 支付网关抖动了一下，同一秒内的 500 个请求全部失败，然后它们全部在 200ms 后同时重试、全部在 600ms 后再同时重试——你不是在帮对方恢复，你是在用整齐的脉冲反复打击它。这叫惊群效应，很多故障就是这样从"抖动"升级成"雪崩"的。

random = true 让每次退避在基准值上下随机浮动，把重试请求摊平在时间轴上。这一个布尔值的价值，在故障恢复时比重试次数本身大得多。

同样的道理已经出现过一次：第 04 部分给缓存 TTL 加随机抖动，防的也是"大批键同时过期"。凡是多个独立个体按同一个时间规则行动，就要考虑给它们加随机扰动。

熔断与隔离

重试解决的是"偶发抖动"。如果支付网关是持续不可用，重试只会让情况更糟——每个请求都要等满超时再重试三次，线程被占满，你自己也跟着挂了。

熔断器是个三态机器：CLOSED（正常放行，统计失败率）→ 失败率超阈值 → OPEN（直接快速失败，不再发出请求，给对方喘息时间）→ 等待一段时间 → HALF_OPEN（放少量试探请求）→ 成功则回到 CLOSED，失败则回到 OPEN。

隔离（bulkhead）常被忽略，但它才是防止级联故障的那一层。 限制"最多 20 个并发调用支付网关"，意味着即使支付完全卡死，也只有 20 个线程被困住，剩下的线程照常渲染商品页、处理登录。没有这一层，一个依赖的故障会通过共享线程池扩散到全站。

对照 · 三件工具，三种故障

超时：应对"对方慢"。没有它，其它两个都无从谈起——因为请求永远不会结束，也就永远不会被计入失败率。
重试：应对"偶发抖动"。只对明确没到达的失败重试。
熔断 + 隔离：应对"对方持续故障"。前者保护对方（别再打了），后者保护自己（别被拖死）。

三者的顺序不能乱：先有超时，才谈得上重试；先有隔离，重试才不会放大伤害。只加重试不加超时和隔离，是把小故障变成大故障的经典配方。

Q2熔断配置里把 PaymentDeclinedException（余额不足、卡被拒）放进了 ignore-exceptions。为什么这类失败不该触发熔断？

思路提示

因为熔断器要检测的是"对方系统坏了"，而不是"业务上没通过"。余额不足说明支付网关工作得非常好——它正确地拒绝了一笔不该成功的交易。

如果把业务拒绝计入失败率，会出现荒谬的后果：某天一批用户余额不足（比如月底），失败率超过 50%，熔断器打开，于是那些余额充足的用户也支付不了了。一个正常的业务现象被误判成故障，然后被"保护机制"放大成真实故障。

一般化的原则：区分"技术失败"和"业务失败"，是所有容错机制配置的第一步。 同样的区分适用于告警（不要为业务拒绝告警）、重试（业务拒绝重试多少次都是同样结果）、日志级别（业务拒绝是 INFO，不是 ERROR）。把两者混在一起，会同时造成告警疲劳和真实故障被淹没。

Q3支付网关的响应时间从 200ms 劣化到 3 秒，但没有超时、也没有报错。你的系统会出现什么症状？监控里先看到什么？

思路提示

症状会以一种容易误判的方式出现：先是支付相关接口变慢，然后是全站变慢，最后是全站 503——而错误日志里可能什么都没有。

机制是这样的：每个支付请求占用一个 Tomcat 工作线程 3 秒（原来是 0.2 秒），意味着同样并发下需要 15 倍的线程。线程池打满后，新请求在队列里排队，包括那些只是想看商品列表的请求。数据库连接如果在这些线程手里（比如支付调用被错误地放在了事务里），连接池也会跟着耗尽。

监控上最先动的应该是出站调用的耗时分位数（P99 支付调用延迟），然后是线程池活跃线程数和队列长度，最后才是接口错误率。如果你只监控了错误率，会在最后一刻才发现，而且看到的现象是"全站挂了"，很难定位到支付网关这个真凶。

可迁移的做法：对每一个外部依赖，独立监控它的延迟分位数和并发占用，而不是只监控自己接口的整体成功率。 慢比错更危险，因为错会快速释放资源，慢会持续占用资源直到耗尽。这也是为什么隔离（bulkhead）必须有——它把"这个依赖最多能占用多少资源"变成了一个明确的、有上限的数字。

异步回调与幂等

支付网关不会在你调用时同步告诉你结果，它会在几秒到几分钟后回调你的接口。这个接口是整个系统里最容易写错、写错代价最大的一个。

回调接口的输入完全不受你控制：它会重复到达、会乱序到达、会在你重启时到达、也可能根本不是支付平台发来的。这三行代码写下来只要五分钟，把这四种情况处理对要花的功夫多得多。

回调接口的四件必做事

安全 · 验签要用原始字节，且要常量时间比较

两个细节决定了验签是真防护还是摆设。

必须用原始请求体验签，不能先反序列化再重新序列化。 JSON 的键顺序、空格、数字格式在往返之后可能变化，重新序列化的字节和对方签名时的字节不一样——要么验签总是失败，要么你为了"能用"而放宽比较，等于把防护拆了。

比较签名要用常量时间算法（MessageDigest.isEqual），不能用 String.equals。后者一旦发现不同就立刻返回，攻击者可以通过测量响应时间逐字节猜出正确签名。这类时序侧信道攻击听起来很学术，但在有稳定网络的环境里是可行的。

另外，回调路径需要在 Spring Security 里排除 CSRF 保护并允许匿名访问——支付平台不会带你的 cookie 和 CSRF 令牌。这不是降低安全性，因为这个接口的认证靠的是签名而不是会话。

深入 · 为什么回调里只落库，不做业务处理

支付平台通常有明确的重试规则：没有在 N 秒内收到 200，就重试；重试 M 次后放弃并告警。 这意味着你的回调接口是一个有严格时限的接口。

如果在回调里同步做完所有事（改状态、扣库存、发邮件、更新报表），任何一步慢了或失败了，都会导致对方重试——而重试会带来更多并发，形成恶性循环。更糟的是"处理成功了但响应超时"，对方判定失败继续重试，而你这边已经执行了一遍。

所以正确的形状是：回调接口只做"我收到了"这一件事，用数据库唯一索引保证只记一次，然后立刻返回 200。 真正的处理由后续的异步流程负责，它可以慢、可以失败、可以重试，都不影响对方的判断。

这个模式的名字是接收与处理分离，在所有 webhook、消息消费、事件订阅场景里都成立。一个判断标准：如果你的处理逻辑变慢，会不会导致上游重发？ 会的话，就该拆开。

Q1幂等用的是"插入 payment_callbacks，撞唯一索引就说明重复"。为什么不先 select 查一下有没有？

思路提示

因为"先查再插"是 check-then-act，在并发下有窗口——两个重复回调同时到达（支付平台的重试和首次投递可能并发），都查到"没有"，然后都去处理。这个问题第一季第 10 部分讲幂等键时出现过一次，这里是同一个形状。

值得留意的是这里和第 08 部分的对称性：那边我们希望对方提供幂等键去重，这边我们是被调用方，要自己实现去重。任何提供有副作用接口的系统，都应该主动支持幂等键——这是对调用方最有价值的一个契约。

Q2代码里遇到非法状态转换时只记了一条 warn 日志就返回了。这样处理够吗？会不会掩盖真正的 bug？

思路提示

不够，而且确实会掩盖 bug。问题在于把两种完全不同的情况用同一种方式处理了：

  • 迟到的旧通知（图 10 的 ⑤）——正常现象，忽略是对的。
  • 真正的逻辑错误——比如把退款通知误判成了支付通知、或者订单 ID 对错了。这种情况忽略掉，就是让钱悄悄对不上。

区分的办法是看事件时间戳：如果通知的业务时间早于订单当前状态的变更时间，那是迟到，可以安静忽略；如果它更晚，说明我们的状态和对方的认知产生了分歧，这必须告警并进对账队列。

可迁移的原则："忽略"必须是一个有条件的、被记录的决定，而不是异常处理的兜底分支。 每一处 catch 后不重新抛出的地方，都应该能回答"我凭什么确定这里可以忽略"。答不上来的，就该告警。

Q3如果支付平台把回调发丢了（重试几次都失败，最后放弃），用户的钱扣了但订单永远停在 CREATED，30 分钟后还会被超时任务关掉并释放库存。怎么兜底？

思路提示

这是必然会发生的场景，不能只依赖回调。三层兜底，从快到慢：

  • 主动查询。 用户从支付页跳回来时（returnUrl），前端触发一次"查询订单支付状态"，后端调支付网关的查询接口确认。这条路径最快，覆盖了用户还在线的大多数情况。
  • 轮询补偿。 定时任务扫描"处于 CREATED 且发起过支付、超过 2 分钟仍未收到回调"的订单，逐个调查询接口。这条覆盖用户关了页面的情况，也是第 07 部分那个"扫描 → 幂等处理 → 失败留给下一轮"模式的又一次应用。
  • 每日对账。 拉取支付平台的当日流水，和本地订单逐笔比对，找出"对方有我方无"和"我方有对方无"。这是最后一道，也是唯一能发现前两层都漏掉的问题的手段。

还有一个细节值得注意：超时关单之前应该先查一次支付状态（第 06 部分 Q2 提过）。否则第一层和第二层都还没来得及生效，订单就被关掉了。

更一般的心法：凡是依赖对方主动通知的流程，都必须配一条"我主动去问"的路径。 通知是优化（快），查询是保证（可靠）。只有通知没有查询的集成，迟早会丢单。

事件、Outbox 与通知

还第一季第 10 部分 Q1 的账：下单成功后要发确认邮件，这行代码到底该写在哪。答案比"移到事务提交之后"要长一些。

第一步：把副作用挪到提交之后

第一季已经给出了方向——不要在事务里调用外部服务。Spring 的机制是事务感知的事件监听器：

对照 · 四个 phase 分别在什么时候执行

AFTER_COMMIT（默认）——提交成功后。发通知、清缓存、更新搜索索引都用它。
AFTER_ROLLBACK——回滚后。补偿、告警。
AFTER_COMPLETION——不论提交还是回滚。清理资源。
BEFORE_COMMIT——提交前，仍在事务内。这里抛异常会让整个事务回滚，所以只适合做最后的校验，不适合做副作用。

但这还不够

AFTER_COMMIT 解决了"回滚了却发了邮件"，没有解决另一半：提交成功了，但邮件没发出去。监听器执行时进程被 kill、邮件服务正好挂了、异步线程池队列满了被丢弃——事件就这么消失了，没有任何记录，没有任何重试。

深入 · FOR UPDATE SKIP LOCKED 是把数据库当队列用的关键

没有 SKIP LOCKED 时，第二个实例会阻塞等待第一个实例释放行锁，多实例部署完全没有并行度。加上它之后，每个实例各取各的、互不干扰，一张普通的表就成了一个可靠的工作队列。

这个能力（Postgres 9.5+、MySQL 8.0+ 都支持）让"用数据库做队列"从一个反模式变成了在中小规模下完全合理的选择：你已经有的事务保证、可查询性、备份恢复、监控手段全部免费复用，而且少一个中间件。

什么时候该换成真正的消息中间件？三个信号：吞吐上到每秒几千条以上（数据库的写入和 vacuum 压力会成为瓶颈）；需要多个互不相干的消费者各自订阅同一批事件（数据库表要自己实现消费位点管理）；需要跨团队、跨服务的解耦（让别的团队来读你的表是很糟的耦合）。在这三个信号出现之前，outbox 表就是够用的，而且是更容易运维的。

Q1Outbox 保证"至少一次"，所以用户可能收到两封相同的订单确认邮件。这可以接受吗？如果不能，怎么办？

思路提示

先分场景。订单确认邮件重复发送：轻微尴尬，可以接受——而"用户没收到确认邮件"要严重得多（客服工单、用户以为下单失败又下一单）。所以这个方向的取舍是对的。

但同样的模式用在别处就不一定了：重复发一张优惠券 = 真实损失；重复调用退款接口 = 退两次钱；重复推送一条促销短信 = 用户投诉。

解法一律是把幂等责任下推给消费方：每条 outbox 记录带一个稳定的消息 ID，消费方（或它调用的下游）据此去重。这就是第 09 部分我们对支付平台的要求，反过来在这里由我们对下游提出。"至少一次投递 + 消费方幂等 = 事实上的恰好一次"，这是分布式系统里最常用的组合，因为真正的"恰好一次投递"在跨系统时并不存在。

顺带一提：邮件这个场景还有个便宜办法——邮件服务商大多支持按 Message-ID 去重，把 outbox 记录的 ID 填进去就行。在自己实现幂等之前，先看看下游有没有现成的机制。

Q2轮询器每 2 秒扫一次。有人说这样有最多 2 秒延迟，不如去掉 outbox，直接在 AFTER_COMMIT 里发。怎么回应？

思路提示

可以两者都要，而且这正是好的做法：提交后立即尝试发送一次（快路径），同时把记录留在 outbox 里作为兜底（慢路径）。 正常情况下延迟接近零，异常情况下轮询器会补上。Spring Modulith 的实现就是这个形状。

但要把提问里的隐含假设点破："去掉 outbox 直接发"省下的是一次数据库插入（微秒级），换来的是"事件可能永久丢失且无人知晓"。这个交换在任何时候都不划算。

另外，2 秒延迟这个数字本身也值得质疑——它只在快路径失败时才会发生，也就是本来就要出问题的情况下。用"最坏情况的延迟"去论证"应该去掉兜底机制"，逻辑是反的。

可迁移的思路：当有人用"性能"论证去掉可靠性机制时，先确认那个性能代价在哪条路径上、发生频率多高。 兜底机制的成本通常只在异常路径上产生，而它防的是无法恢复的损失。

Q3outbox 表只增不减，一年后有几千万行。怎么处理？直接 DELETE FROM outbox WHERE sent_at IS NOT NULL 行吗？

思路提示

方向对，但那条 SQL 会出事：一次删除几千万行会产生巨大的事务和 WAL、长时间持锁、Postgres 上还会留下大量死元组等待 vacuum，期间表和索引都会膨胀。

务实的做法，从简到繁：分批删除（每次 delete … where id in (select id … limit 5000)，循环直到删完，每批一个事务）；按时间分区（按月分区，清理变成 drop partition，瞬间完成且不产生死元组）；归档后删除（先导出到冷存储再删，如果合规要求保留）。

但更值得注意的是这个问题该在建表时就想到。任何"只写不读、持续增长"的表——outbox、审计日志、回调记录、状态变更历史——都应该在设计时就确定保留策略。这一季里我们已经建了四张这样的表（order_status_changes、payment_callbacks、outbox、shedlock），前三张都需要。

可迁移的检查项：每建一张表，问一句"它什么时候变小"。 答不上来的，就是一年后的运维事故。

深入 · 令牌桶为什么通常是最好的默认选择

滑动窗口很精确，但它对正常的突发流量不友好：用户打开一个页面同时发出 30 个请求（图片、接口、静态资源），滑动窗口会认为这是异常。而真实的使用模式本来就是"安静很久，然后一小阵密集操作"。

令牌桶天然表达了这个模式：不用的时候攒额度，需要的时候一次花掉。容量决定能突发多大，补充速率决定长期均值。两个参数分别对应两个直观的业务问题——"最多允许一次爆发多少"和"平均每分钟给多少"。

而且它的内存占用是常数（每个键存两个数），滑动窗口日志要存每个请求的时间戳，高频接口下 Redis 内存会很可观。

选择建议：默认令牌桶；需要严格证明"任意 60 秒内不超过 N 次"（比如对外 API 的合同承诺）时用滑动窗口；只是粗略挡一下爬虫时固定窗口足够。

接进 Spring

陷阱 · X-Forwarded-For 是可以伪造的

这个头由客户端发起、由每一层代理追加。攻击者可以直接在请求里塞一个假的 X-Forwarded-For: 1.2.3.4，如果你的代码取的是最左边那个值，限流就形同虚设——每个请求换一个假 IP 即可。

正确做法是从右往左数，跳过你自己已知的可信代理层数，取第一个不可信的值。Spring Boot 的 server.forward-headers-strategy: framework 加上 Tomcat 的 RemoteIpValve 可以配 trustedProxies 正则来做这件事。

更一般的：任何来自客户端的 HTTP 头，在没有明确的信任链之前都是不可信输入。 这条和第一季讲文件上传时的 Content-Type、第 09 部分讲回调时的签名是同一个原则。

应用层还是网关层

网关层（Nginx、云厂商 WAF、API Gateway）：成本最低，能挡住 L7 攻击流量不进入应用，保护范围是整个服务。但它只知道 IP 和路径，不知道"这是哪个用户"或"这个用户的套餐额度是多少"。

应用层：能用业务维度（用户 ID、租户、套餐等级、订单类型），能给出精确的错误提示。代价是流量已经进来了，占用了连接和线程。

两层都要，各管各的。 网关挡住明显的洪水（每 IP 每秒 100 次），应用层做精细的业务规则（每个账号每天 50 单）。只有应用层限流的系统，在被真正的 DDoS 打到时，限流代码本身就是负担。

动手与思考 · 第 11 部分

Q1限流计数存在 Redis 里。如果 Redis 挂了，tryConsume 抛异常，此时应该放行还是拒绝？

思路提示

这题没有普适答案，取决于这个限流器保护的是什么，而且两种选择的失败模式截然不同：

失败时放行（fail-open）：Redis 挂了，所有请求畅通。风险是此时恰好有人在攻击，你完全没有防护。但好处是不会因为一个辅助组件故障而让全站不可用。

失败时拒绝（fail-closed）：Redis 挂了，所有请求 429。安全是安全了，但这等于把 Redis 变成了全站的单点——一个用来防止过载的机制，自己成了制造全站故障的原因。

务实的分法：普通接口的流量限制 fail-open（它保护的是性能，损失可承受）；登录、支付这类安全相关的限流 fail-closed（它保护的是安全，宁可拒绝服务）。并且两类应该用不同的降级策略，而不是一刀切。

还有第三条路，第 13 部分会展开：本地降级——Redis 不可用时退回到每个实例的内存计数。精度下降（三个实例各算各的，实际限额变成三倍），但比完全放开或完全拒绝都好。"降级到一个更差但仍然有用的状态"，通常比在"完全可用"和"完全不可用"之间二选一要好。

Q2限流规则写死在代码里，改一个阈值要重新发布。有什么更好的做法？改成配置中心动态下发，又有什么新问题？

思路提示

动态配置的价值在应急时最明显：正在被刷，需要立刻把某个接口的限额从 100 降到 10，等一次发布流程（构建、测试、灰度）可能要半小时。

但它引入了三个新问题，都不小：

  • 配置成了未经测试的代码路径。 有人把限额误填成 0，全站瞬间 429——而这个改动没有经过 code review、没有 CI、没有灰度。
  • 可审计性。 谁在什么时候改的、为什么改？如果配置中心没有变更记录，事后复盘会很痛苦。
  • 又一个运行时依赖。 配置中心挂了怎么办？必须有本地兜底值。

折中做法：代码里保留一份安全的默认值，动态配置只做覆盖，并且对可接受范围做校验（限额必须在 1 到 100000 之间，否则拒绝加载并告警）。再加上变更记录和一个"一键回滚到默认值"的开关。

可迁移的判断：把配置从代码里移出来，是把"发布的慢"换成"操作的险"。 换得值不值，取决于你有没有为运行时变更配上和代码变更同等的护栏——校验、审计、回滚。没有护栏的动态配置，是把生产环境的方向盘交给了一个文本框。

Q3秒杀活动，1000 件商品，预计 10 万人抢。限流该怎么设？和第 06 部分的库存预扣减是什么关系？

思路提示

关键认识：限流和库存扣减解决的是两个不同层次的问题，不能互相替代。

限流是保护系统——它不关心业务，只保证进入系统的请求量在处理能力之内。库存扣减是保证正确——它决定谁抢到了。10 万请求里有 9.9 万必然失败，但它们失败的方式不同：被限流拒绝的连库存都没查，被库存拒绝的说明它真的参与了竞争。

分层设计通常是这样：网关层按 IP 挡住明显的脚本流量；应用层按账号限制"每人每秒最多 1 次"（防止一个人用脚本刷 1000 次）；Redis 预扣减作为业务闸门，售罄后直接返回，请求到不了数据库；数据库条件更新是最终裁决，保证绝不超卖。

四层里前三层都是"尽力而为"，只有最后一层是保证——这正好是第 07 部分那条结论的又一次体现。而且注意顺序：越便宜的判断放在越外层，让 99% 的请求在最便宜的地方被挡掉。这个"漏斗"结构在任何高并发场景里都成立。

深入 · 告警要基于用户感受，不是基于机器状态

"CPU 超过 80% 告警"是最常见也最没用的告警之一：CPU 高可能完全正常（在做批处理），CPU 低也可能全站挂了（所有线程都堵在等 IO）。这类告警的结果是告警疲劳——半年后没人看告警了，真出事时也就没人知道。

更好的告警对象是这三类：

  • 用户直接感受到的：关键接口的错误率和 P99 延迟。
  • 会累积成灾难的：outbox 积压持续增长、待处理回调堆积、最老未处理记录的年龄。这类的特点是此刻用户还没感觉，但再过一小时就会爆。
  • 本该发生而没发生的：定时任务超过 N 分钟没成功执行过、对账任务今天没跑。这类是最容易被漏掉的，因为"没有发生"不产生任何日志或指标点——必须主动检测。

可迁移的判断：为每一条告警回答"收到它之后我要做什么"。 答不上来的告警应该删掉或降级成看板。一个只有真正需要人介入时才响的告警系统，比一个大而全但被静音的系统有用得多。

Q1追踪采样率设成 10%。用户报了一个问题，你拿他的 traceId 去查，发现没有记录。这是什么原因？怎么改？

思路提示

因为这次请求恰好没被采样——90% 的请求只生成 traceId 但不上报 span 数据。用户看到了 ID，你却查不到链路。

几种改法，可以叠加：基于结果的采样（先缓存 span，请求结束时如果是错误或慢请求就一定上报，正常请求按比例采样）——这是最理想的，但需要采集端支持（OTel Collector 的 tail sampling）；错误请求强制采样；把关键业务路径（下单、支付）设成 100% 采样，浏览类接口低采样。

还有个更便宜的兜底：即使 span 没上报，结构化日志里的 traceId 依然存在。所以只要日志是全量的，你至少能查到这次请求打了哪些日志、报了什么错——虽然拿不到完整的调用链和耗时分解。

一般化的思路：采样是在成本和信息之间做权衡，而权衡不该是均匀的。 正常请求彼此高度相似，采 1% 就够了解分布；异常请求每一条都独一无二，应该全采。用同一个比例对待两者，是在为大量冗余信息付费，同时丢掉稀缺信息。

思路提示

算法很直接：定时跑一条查询，比较 products.reserved 和"所有 CREATED 状态订单里该商品的数量之和"。两者理论上永远相等（第 06 部分 Q3 提到的可对账性），不等就说明某处的预占或释放逻辑漏了。

值得单独埋，是因为这类不一致不会以任何其它形式暴露：不会报错、不会变慢、用户也看不出来——直到某个商品的可售数量莫名其妙变成 0，而仓库里明明还有货。等到那时，已经积累了几个月的漂移，根本无从追溯是哪次 bug 造成的。

这是一类特别值得投资的监控：不变量校验。系统里凡是"两个地方存了同一个事实的不同表示"，就应该有一条定期校验它们是否一致的检查。余额 vs 流水、库存 vs 订单、缓存 vs 数据库、本地订单 vs 支付平台流水，都是这样。

第一季说过"数据库约束是唯一无法绕过的防线"。但有些不变量跨越多张表、无法用约束表达——那就用定期校验补上。能用约束表达的用约束，不能的用对账，两样都没有的地方，数据一定会慢慢坏掉。

Q3业务异常打 INFO 日志。但如果"库存不足"从每天 10 次涨到每分钟 500 次，这显然是个问题。怎么在不把它变成 ERROR 的前提下发现？

思路提示

关键在于区分单个事件和事件的统计特征。单次库存不足永远是正常的，所以日志级别是对的；异常的是速率。

做法是把业务异常也埋成指标（带上原因标签）：business.rejected{reason="insufficient_stock"}，然后对这个指标的变化率而不是绝对值告警。突增 50 倍时告警，即使每一条本身都完全正常。

这类告警能发现很多单点日志发现不了的问题：库存同步任务挂了（所以全都缺货）、某个爆款被脚本刷（所以正常用户抢不到）、价格配错导致大量下单失败、或者上游给的商品数据有问题。它们的共同点是"每一次失败都是合法的，但失败的模式不合法"。

可迁移的原则：凡是"单次正常但批量异常"的事件，都应该同时有 INFO 日志（用于查证）和计数指标（用于发现）。 只有日志，你要靠人去数；只有指标，出事时查不到具体是哪些。两者的分工是：指标负责告诉你出事了，日志负责告诉你出了什么事。

Redis 挂了会怎样

这一季往系统里加了一个新组件，它现在承担着会话、缓存、限流三份职责。收尾的问题是：当它不可用时，这个系统还剩下什么？

序章里说过判断标准——"把 Redis 清空，系统能不能从 PostgreSQL 重建正确状态"。答案是能，数据不会错。但"数据不错"和"服务可用"是两件事：如果每个用途都在 Redis 不可用时直接抛异常，那么加进来的加速层就变成了一个新的单点故障。

让缓存失效不至于变成故障

陷阱 · 降级本身会打垮数据库

把缓存异常降级成回源，听起来很安全。但想一想第 04 部分的图 4：Redis 挂掉等于 100% 的请求同时回源——这就是雪崩，而且是最严重的那种。降级救了缓存这一层，代价可能是数据库跟着挂。

所以降级必须和限流、熔断一起配：回源路径上要有并发上限（bulkhead，比如最多 50 个并发查询打到数据库），超出的请求快速失败或返回降级内容（"商品信息暂时无法加载"）。宁可让 30% 的请求看到降级页面，也不要让数据库连接池耗尽导致 100% 的请求失败——包括下单。

一般化的原则：每一条降级路径都要评估它的容量。 降级的本质是把流量从一条路挪到另一条路，如果没确认那条路承受得住，降级就只是把故障搬了个地方。

动手与思考 · 第 13 部分

Q1图 13 显示会话是唯一的硬依赖。如果业务上不能接受"Redis 挂了全站登出"，有哪些出路？

思路提示

几条路，代价递增：

  • "记住我"令牌：Spring Security 的 persistent token 存在数据库里。Redis 挂了会话丢失，但用户的浏览器带着记住我 cookie，会被自动重新认证——用户几乎无感。这是性价比最高的一条。
  • Redis 高可用：哨兵或集群，降低"完全不可用"的概率。注意它降低的是概率不是影响，而且带来运维复杂度和第 01 部分说过的复制丢失窗口。
  • 会话双写：同时写 Redis 和数据库，Redis 挂了从数据库读。正确但很重——每次会话更新都要写库，失去了外置到 Redis 的主要性能收益。
  • 混合模式：认证状态用无状态签名令牌（图 2 的方案 ③），购物车等可变数据用 Redis。Redis 挂了用户仍然是登录状态，只是购物车暂时不可用。代价是失去即时吊销能力，需要再补一个黑名单。

值得注意的是这些选项的形状：它们都是在"这份数据的第二个副本放在哪"上做文章。 序章那条判断线在这里又出现了一次——没有第二个副本的数据，就是硬依赖，没有例外。

Q2限流降级到"本地内存计数"，三个实例意味着实际限额变成三倍。有没有办法在不依赖 Redis 的前提下更准一些？

思路提示

可以，思路是把全局限额预先分配给各个实例：如果实例数是已知的（Kubernetes 里可以从环境变量或 API 拿到副本数），每个实例的本地限额设成 全局限额 ÷ 实例数。这样降级期间总量大致正确。

缺陷也很明显：负载不均时会误伤——某个实例分到了 60% 的流量，它会在只用掉全局 20% 额度时就开始拒绝。而且扩缩容期间实例数是变化的。

更完整的方案是本地令牌桶 + 周期性向中心协调（每个实例定期上报用量、领取新的配额），但那基本上是在重新实现一个分布式限流器，复杂度陡增。

务实的判断：降级模式下的精度要求应该低于正常模式。 降级是异常状态，持续时间以分钟计，"限额变成三倍"在这段时间里造成的实际损害通常远小于实现和维护一套复杂分配逻辑的成本。为异常路径做过度工程，是把有限的复杂度预算花在了错误的地方。

Q3这一季往系统里加了 Redis、支付网关、通知服务三个外部依赖。整体可用性是提高了还是降低了？

思路提示

先算一笔账：如果三个依赖都是硬依赖，各自可用性 99.9%，加上原本的应用和数据库，整体可用性是它们的乘积——大约 99.5%，也就是每月不可用时间从 43 分钟变成 216 分钟。依赖越多，串联可用性越低，这是数学。

但这一季做的事情正是把串联改成并联：缓存挂了走数据库、锁在数据库里、限流降级到本地、通知走 outbox 异步重试。只有会话和支付是真正的串联环节（支付挂了确实下不了单，但商品浏览不受影响——这就是隔离的价值）。

所以答案是：加依赖必然降低可用性上限，但降级设计决定了实际降低多少。 一个有完整降级路径的五组件系统，可用性可以高于一个没有降级设计的三组件系统。

值得带走的思考方式：评估架构变更时，把"新增了什么能力"和"新增了什么失败模式"分开列。 前者通常在方案文档里写得很详细，后者往往完全缺席——而故障复盘时讨论的全是后者。图 13 那张表就是把后者显式写下来的一个具体动作，它值得成为每次引入新组件时的固定动作。

结语

两季走完，这个在线商店从"一个进程加一个数据库"变成了"多个无状态实例、一个加速层、两个外部系统、若干条异步链路"。功能上没增加多少——还是那些商品、购物车、订单页面。变化全在它现在能承受多少种出错方式。

原书结尾引了一句"批判性地分析你读到和听到的东西"。这两季的重写就是照着做的：原书在事务、并发、上传、会话、测试上的处理不成立，所以换掉了；它的教学结构和节奏很好，所以保留了。这份文档同样应该被这样对待——里面每一条建议都有适用范围，尤其是第二季，因为它引入的每一个组件都有明确的规模门槛。

如果你的商城一天一百单，第 06 部分的 Redis 预扣减、第 10 部分的 outbox、第 11 部分的滑动窗口限流，全都是过度设计。它们的价值不在于现在就用上，而在于当你真的遇到那个问题时，能认出它是什么问题——这一季给的与其说是解法，不如说是一份失败模式的清单。
